## Зачем это нужно

Почти любое реальное приложение хранит данные в реляционной базе: заказы, пользователи, платежи, остатки на складе. Фреймворки приходят и уходят, а **SQL остаётся**: ему больше сорока лет, и он по-прежнему в каждой вакансии Junior .NET.

Зачем изучать SQL руками, если есть EF Core, который «сам пишет запросы»?

- **EF Core — это генератор SQL, а не замена ему.** Когда страница грузится 8 секунд, ты открываешь лог, видишь сгенерированный `SELECT` и должен понять, что он делает. Без знания SQL лог — иероглифы.
- **База — последний рубеж защиты данных.** Ограничения (`NOT NULL`, `UNIQUE`, `CHECK`, внешние ключи) работают даже тогда, когда в C#-коде баг или данные пишет другой сервис.
- **Собеседование.** Практически всегда просят написать запрос «на листочке»: фильтр, JOIN, группировка. А вопрос «чем `= NULL` отличается от `IS NULL`» — классика.
- **Эффективность.** Отфильтровать 10 строк на стороне базы и переслать их по сети — не то же самое, что загрузить миллион и отфильтровать в LINQ.
- **Отчёты и разовые задачи.** Узнать «сколько читателей брали книги в сентябре» быстрее запросом, чем написанием C#-программы.

Эта страница даёт фундамент: установить PostgreSQL, создать учебную схему и уверенно читать данные. Всё остальное в фазе (JOIN, группировки, индексы, транзакции, EF Core) строится на ней.

## Интуиция и аналогия

**Таблица — лист Excel со строгими правилами.** Строки — записи (одна книга), столбцы — поля (название, год). Но в отличие от Excel каждая колонка имеет *тип* и *ограничения*: в `year` нельзя записать «когда-то давно», в `copies` — минус три.

**SELECT — заявка в архив.** Ты не лезешь на стеллажи сам, а пишешь заявку: «дай названия и годы романов старше 1950-го, по возрастанию года». Как архивисты это делают — их дело (план запроса). Ты описываешь **что** хочешь, а не **как** это найти: в этом суть декларативного языка.

**NULL — пустая клетка с вопросом «не знаю».** Не ноль и не пустая строка. Если спросить «сколько лет Вере, если дата рождения неизвестна, и она старше Анны?», ответ — «неизвестно», а не «нет». Отсюда все странности `NULL`.

**Ограничения — вахтёр.** Он не пустит в таблицу запись без названия, дубликат ISBN или книгу 3000-го года издания, неважно, кто стучится: твой C#-код, чужой скрипт или администратор в ночную смену.

### Шаг 2. Учебная схема {#schema}

Выполни этот скрипт целиком — все примеры фазы работают на нём.

~~~sql library.sql
DROP TABLE IF EXISTS loans, book_authors, books, authors, readers CASCADE;

CREATE TABLE authors (
    id    INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name  TEXT NOT NULL
);

CREATE TABLE books (
    id      INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    isbn    TEXT NOT NULL UNIQUE,
    title   TEXT NOT NULL,
    genre   TEXT NOT NULL,
    year    INT  NOT NULL CHECK (year BETWEEN 1450 AND 2100),
    copies  INT  NOT NULL DEFAULT 1 CHECK (copies >= 0)
);

CREATE TABLE book_authors (
    book_id   INT NOT NULL REFERENCES books(id)   ON DELETE CASCADE,
    author_id INT NOT NULL REFERENCES authors(id) ON DELETE RESTRICT,
    PRIMARY KEY (book_id, author_id)
);

CREATE TABLE readers (
    id           INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    full_name    TEXT NOT NULL,
    card_number  TEXT NOT NULL UNIQUE,
    reader_type  TEXT NOT NULL CHECK (reader_type IN ('student', 'teacher', 'external'))
);

CREATE TABLE loans (
    id           INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    book_id      INT  NOT NULL REFERENCES books(id),
    reader_id    INT  NOT NULL REFERENCES readers(id),
    loaned_at    DATE NOT NULL,
    due_at       DATE NOT NULL,
    returned_at  DATE NULL,
    CHECK (due_at >= loaned_at)
);

INSERT INTO authors (name) VALUES
    ('Булгаков'), ('Достоевский'), ('Гоголь'), ('Ильф'), ('Петров'), ('Пушкин');

INSERT INTO books (isbn, title, genre, year, copies) VALUES
    ('978-5-01', 'Мастер и Маргарита',        'Роман',   1967, 3),
    ('978-5-02', 'Собачье сердце',            'Повесть', 1987, 2),
    ('978-5-03', 'Преступление и наказание',  'Роман',   1866, 2),
    ('978-5-04', 'Идиот',                     'Роман',   1869, 1),
    ('978-5-05', 'Мёртвые души',              'Поэма',   1842, 1),
    ('978-5-06', 'Двенадцать стульев',        'Роман',   1928, 2),
    ('978-5-07', 'Справочник по SQL',         'Учебник', 2020, 4);

INSERT INTO book_authors (book_id, author_id) VALUES
    (1, 1), (2, 1), (3, 2), (4, 2), (5, 3), (6, 4), (6, 5);

INSERT INTO readers (full_name, card_number, reader_type) VALUES
    ('Анна Иванова',   'R-001', 'student'),
    ('Борис Петров',   'R-002', 'teacher'),
    ('Вера Смирнова',  'R-003', 'student'),
    ('Глеб Орлов',     'R-004', 'external');

INSERT INTO loans (book_id, reader_id, loaned_at, due_at, returned_at) VALUES
    (1, 1, '2026-09-01', '2026-09-15', '2026-09-14'),
    (3, 1, '2026-09-20', '2026-10-04', NULL),
    (1, 2, '2026-09-05', '2026-10-05', '2026-10-01'),
    (6, 2, '2026-10-01', '2026-10-31', NULL),
    (2, 3, '2026-09-10', '2026-09-24', '2026-09-30'),
    (1, 3, '2026-10-02', '2026-10-16', NULL),
    (6, 1, '2026-08-01', '2026-08-15', '2026-08-15');
~~~

Что здесь стоит заметить:

- `GENERATED ALWAYS AS IDENTITY` — автоинкрементный ключ (современная замена `SERIAL`).
- `NOT NULL`, `UNIQUE`, `CHECK`, `REFERENCES` — **ограничения**. База сама не даст записать мусор: это последний рубеж защиты данных, даже если в C#-коде будет баг.
- `book_authors` — таблица связи многие-ко-многим (у «Двенадцати стульев» два автора).
- `returned_at NULL` — книга ещё на руках.
- `ON DELETE CASCADE` у `book_id`: удалили книгу — исчезли и её связи с авторами. `ON DELETE RESTRICT` у `author_id`: нельзя удалить автора, пока на него ссылаются книги.
- `TEXT` в PostgreSQL — строка без ограничения длины (отдельно `VARCHAR(n)` почти не нужен).

### Шаг 3. SELECT: выборка

~~~sql
SELECT title, year
FROM books
WHERE genre = 'Роман' AND year < 1950
ORDER BY year;
~~~
~~~console
          title           | year 
--------------------------+------
 Преступление и наказание | 1866
 Идиот                    | 1869
 Двенадцать стульев       | 1928
(3 rows)
~~~

`SELECT` перечисляет колонки, `FROM` — таблицу, `WHERE` — условие строк, `ORDER BY` — порядок. Звёздочка `SELECT *` возвращает все колонки: удобно в консоли, но в коде приложения лучше перечислять нужные.

Порядок **выполнения** отличается от порядка написания — это помогает понимать ошибки:

~~~text
FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT/OFFSET
~~~

Поэтому псевдоним из `SELECT` можно использовать в `ORDER BY`, но нельзя в `WHERE`:

~~~sql
SELECT title, copies * 2 AS double_copies FROM books WHERE double_copies > 4;
~~~
~~~console
ERROR:  column "double_copies" does not exist
LINE 1: ...tle, copies * 2 AS double_copies FROM books WHERE double_cop...
                                                             ^
~~~

~~~sql
SELECT title, copies * 2 AS double_copies FROM books WHERE copies * 2 > 4 ORDER BY double_copies DESC, title;
~~~
~~~console
       title        | double_copies 
--------------------+---------------
 Справочник по SQL  |             8
 Мастер и Маргарита |             6
(2 rows)
~~~

Полезные приёмы:

~~~sql
SELECT title FROM books WHERE title ILIKE '%сер%';           -- поиск без учёта регистра (PostgreSQL)
SELECT title FROM books WHERE genre IN ('Роман', 'Повесть') ORDER BY id;
SELECT title FROM books WHERE year BETWEEN 1900 AND 1999 ORDER BY id;     -- включительно
SELECT DISTINCT genre FROM books ORDER BY genre;
SELECT title FROM books ORDER BY year DESC LIMIT 3 OFFSET 0;  -- пагинация: страница 1 по 3
~~~
~~~console

----------------
 Собачье сердце
(1 row)

          title           
--------------------------

 Преступление и наказание

(5 rows)

       title

(3 rows)
~~~

(Когда в одном блоке несколько запросов, выводятся результаты каждого подряд.)

Пагинация через `LIMIT/OFFSET` требует **детерминированного порядка**: добавляй в `ORDER BY` уникальную колонку (`id`) последней, иначе страницы могут пересекаться. На больших смещениях `OFFSET` медленный (БД всё равно пройдёт пропускаемые строки) — для длинных лент используют «keyset»-пагинацию (`WHERE id > :последний`).

### Шаг 4. NULL — «неизвестно», а не «пусто» {#null}

`NULL` означает отсутствие значения. Любое сравнение с `NULL` даёт не `true` и не `false`, а `NULL` (неизвестно), и `WHERE` такие строки отбрасывает.

~~~sql
SELECT count(*) FILTER (WHERE returned_at = NULL)  AS eq_null,   -- ❌ всегда 0
       count(*) FILTER (WHERE returned_at IS NULL) AS is_null    -- ✅ 3
FROM loans;
~~~
~~~console
 eq_null | is_null 
---------+---------
       0 |       3
(1 row)
~~~

- Проверять только через `IS NULL` / `IS NOT NULL`.
- `coalesce(x, 0)` — значение по умолчанию вместо `NULL`.
- `count(*)` считает строки, `count(column)` — только строки, где column не `NULL`. Это пригодится в [JOIN](#p3-joins).

Логика с тремя значениями: `NULL AND false` — `false`, `NULL AND true` — `NULL`, `NOT NULL` — `NULL`. Посмотри сам:

~~~sql
SELECT (NULL = NULL) AS eq, (NULL IS NULL) AS is_null,
       (NULL AND false) AS and_false, (NULL OR true) AS or_true,
       coalesce(NULL, 0) AS dflt, 1 + NULL AS plus_null;
~~~
~~~console
 eq | is_null | and_false | or_true | dflt | plus_null 
----+---------+-----------+---------+------+-----------
    | t       | f         | t       |    0 |          
(1 row)
~~~

Ловушка с `NOT IN`: если во вложенном списке есть хотя бы один `NULL`, `x NOT IN (...)` никогда не станет `true`:

~~~sql
SELECT 5 NOT IN (1, 2, 3)    AS clean_list,
       5 NOT IN (1, 2, NULL) AS list_with_null;
~~~
~~~console
 clean_list | list_with_null 
------------+----------------
 t          | 
(1 row)
~~~

Для сравнения «с учётом `NULL`» есть `IS DISTINCT FROM`. А безопасная замена `NOT IN` — `NOT EXISTS` (разберём в теме про подзапросы).

### Шаг 5. INSERT, UPDATE, DELETE

~~~sql
INSERT INTO readers (full_name, card_number, reader_type)
VALUES ('Дина Ким', 'R-005', 'student')
RETURNING id;                                   -- PostgreSQL сразу вернёт сгенерированный id

UPDATE loans SET returned_at = '2026-10-13'
WHERE id = 2 AND returned_at IS NULL;           -- условие защищает от повторного возврата

DELETE FROM readers WHERE card_number = 'R-005';
~~~
~~~console
 id 
----
  5
(1 row)
~~~

:::danger UPDATE и DELETE без WHERE
`DELETE FROM loans;` удалит всё. Привычка: сначала пиши `SELECT` с тем же `WHERE`, проверь строки, затем меняй `SELECT` на `DELETE`. В учебной базе это не страшно, на работе — увольнительно. Хорошая страховка — выполнять правки внутри транзакции с `BEGIN` ... `ROLLBACK`/`COMMIT` (подробнее в теме про [транзакции](#p3-transactions)).
:::

Нарушение ограничения — не «сбой», а полезная ошибка. Посмотри, как база защищает данные:

~~~sql
INSERT INTO books (isbn, title, genre, year) VALUES ('978-5-01', 'Дубль', 'Роман', 2000);
INSERT INTO books (isbn, title, genre, year) VALUES ('978-5-99', 'Из будущего', 'Роман', 3000);
INSERT INTO loans (book_id, reader_id, loaned_at, due_at) VALUES (999, 1, '2026-10-01', '2026-10-15');
INSERT INTO readers (full_name, card_number) VALUES ('Без типа', 'R-777');
~~~
~~~console
ERROR:  duplicate key value violates unique constraint "books_isbn_key"
DETAIL:  Key (isbn)=(978-5-01) already exists.
ERROR:  new row for relation "books" violates check constraint "books_year_check"
DETAIL:  Failing row contains (9, 978-5-99, Из будущего, Роман, 3000, 1).
ERROR:  insert or update on table "loans" violates foreign key constraint "loans_book_id_fkey"
DETAIL:  Key (book_id)=(999) is not present in table "books".
ERROR:  null value in column "reader_type" of relation "readers" violates not-null constraint
DETAIL:  Failing row contains (6, Без типа, R-777, null).
~~~

Обрати внимание на тексты ошибок: в них названо нарушенное ограничение (`books_isbn_key`, `books_year_check`, `loans_book_id_fkey`) — по ним сразу видно, где проблема. Именно эти имена ты увидишь в исключениях EF Core как `PostgresException`.

### Шаг 6. Типы данных: что выбирать

| Данные | Тип PostgreSQL | Замечание |
|---|---|---|
| Целые | `INT`, `BIGINT`, `SMALLINT` | идентификаторы — `INT` или `BIGINT` |
| Деньги, точные дроби | `NUMERIC(12,2)` | **не** `REAL`/`DOUBLE PRECISION` — они приближённые |
| Текст | `TEXT` (или `VARCHAR(n)`) | в PostgreSQL ограничение длины не ускоряет |
| Дата / дата-время | `DATE`, `TIMESTAMPTZ` | время храни с часовым поясом (UTC) |
| Логическое | `BOOLEAN` | `true`/`false`/`NULL` |
| Идентификатор-GUID | `UUID` | в C# — `Guid` |
| JSON | `JSONB` | для полуструктурных данных, не для всего подряд |

Соответствие с C# вспомнится в EF Core: `INT` ↔ `int`, `NUMERIC` ↔ `decimal`, `TIMESTAMPTZ` ↔ `DateTime`/`DateTimeOffset` (в Npgsql — UTC), `UUID` ↔ `Guid`, `TEXT` ↔ `string`.

~~~sql
SELECT 0.1::double precision + 0.2::double precision AS float_sum,
       0.1::numeric + 0.2::numeric                   AS numeric_sum;
~~~
~~~console
      float_sum      | numeric_sum 
---------------------+-------------
 0.30000000000000004 |         0.3
(1 row)
~~~

Вот почему деньги — только `NUMERIC`: у чисел с плавающей точкой `0.1 + 0.2` не равно `0.3`. Ту же проблему ты уже видел в C# с `double` и `decimal`: выбор типа — не вкусовщина, а вопрос корректности денег. Тип `NUMERIC(12,2)` хранит ровно два знака после запятой и не копит ошибки округления, поэтому суммы в отчётах сходятся до копейки.

## Как это работает под капотом

- **Клиент и сервер.** PostgreSQL — отдельный серверный процесс. `psql`, DBeaver или твоё приложение подключаются по TCP (порт 5432 по умолчанию), отправляют текст запроса и получают строки. Строка подключения — адрес, порт, база, логин, пароль.
- **Путь запроса.** Сервер разбирает текст (parser), строит логическое дерево, **планировщик** выбирает способ выполнения (какой индекс использовать, в каком порядке соединять) на основе статистики, затем исполнитель читает данные. Поэтому один и тот же результат можно получить быстро или медленно (тема про [индексы](#p3-indexes)).
- **Строки на диске.** Данные хранятся страницами по 8 КБ. Строка не «переписывается» на месте: `UPDATE` создаёт новую версию строки, а старая остаётся до очистки (`VACUUM`) — так устроен MVCC, о котором речь в теме про [транзакции](#p3-transactions).
- **Ограничения проверяются сервером.** `UNIQUE` и `PRIMARY KEY` поддерживаются индексами, внешние ключи проверяются при вставке и удалении. Это атомарно: проверка и запись происходят вместе, поэтому гонка «два запроса вставили один ISBN» невозможна.
- **Identity-последовательности.** `GENERATED ALWAYS AS IDENTITY` использует объект-последовательность. Она не откатывается вместе с транзакцией, поэтому в нумерации возможны «дыры» — это нормально.
- **Регистр и кодировка.** Идентификаторы без кавычек приводятся к нижнему регистру (`Books` = `books`); строки сравниваются с учётом коллации. `ILIKE` — расширение PostgreSQL (в стандарте SQL и в SQL Server его нет).
- **Диалекты.** Базовый синтаксис общий, но `LIMIT/OFFSET`, `RETURNING`, `ILIKE`, `||` для конкатенации — PostgreSQL; в SQL Server — `TOP`, `OUTPUT`, `+`. EF Core скрывает различия, когда ты пишешь LINQ.

Справочник по SQL-синтаксису PostgreSQL — официальная документация (postgresql.org/docs); раздел Tutorial читается за вечер.

## Типичные ошибки и ловушки

- **`= NULL` вместо `IS NULL`.** Запрос молча возвращает пустой результат.
- **`NOT IN` со списком, где есть `NULL`.** Вернёт ноль строк; используй `NOT EXISTS`.
- **`UPDATE`/`DELETE` без `WHERE`.** Затрёт всю таблицу. Сначала `SELECT`, потом правка, правки — в транзакции.
- **Двойные кавычки вместо одинарных.** `'Роман'` — строка, `"Роман"` — имя столбца/таблицы; в PostgreSQL ошибка «column не существует».
- **Псевдоним из `SELECT` в `WHERE`.** Не работает, потому что `WHERE` выполняется раньше.
- **`LIMIT` без `ORDER BY`.** Порядок строк не гарантирован — «первые 10» могут быть любыми.
- **`SELECT *` в приложении.** Лишний трафик, ломается при добавлении колонок; перечисляй нужное.
- **Деньги в `REAL`/`double`.** Ошибки округления; используй `NUMERIC`.
- **Сравнение дат со временем.** `WHERE loaned_at = '2026-09-01'` для `TIMESTAMP` найдёт только полночь; используй диапазон `>= дата AND < дата + 1`.
- **Строки с конкатенацией в SQL из C#.** `"... WHERE name = '" + input + "'"` — SQL-инъекция. Всегда параметры (`@name`), EF Core делает это сам.
- **Игнорирование регистра в `LIKE`.** `LIKE` чувствителен к регистру; нужен `ILIKE` или `lower(...)`.
- **Надежда на порядок вставки.** Без `ORDER BY` порядок не определён — даже если «обычно» совпадает.

## Вопросы с собеседований

:::spoiler Почему `WHERE returned_at = NULL` не находит ни одной строки?
Сравнение с `NULL` возвращает `NULL` (неизвестно), а `WHERE` оставляет только строки с результатом `true`. Нужно `IS NULL`.
:::

:::spoiler Почему нельзя использовать псевдоним из SELECT в WHERE?
`WHERE` выполняется раньше `SELECT`: в момент фильтрации псевдоним ещё не вычислен. В `ORDER BY` можно — он выполняется после.
:::

:::spoiler Зачем ограничения CHECK/UNIQUE, если всё проверяется в C#?
Защита в глубину: в базу пишут разные приложения, скрипты, миграции, а в коде бывают баги. Ограничение гарантирует целостность на уровне данных и закрывает гонки (например, два одновременных запроса с одинаковым ISBN).
:::

:::spoiler Чем `count(*)` отличается от `count(column)`? (ловушка: «одно и то же»)
`count(*)` считает все строки, `count(column)` — только те, где значение колонки не `NULL`. Разница видна при `LEFT JOIN` и при колонках, допускающих `NULL`.
:::

:::spoiler Почему деньги нельзя хранить в `REAL`/`double`?
Двоичные числа с плавающей точкой не представляют многие десятичные дроби точно (`0.1 + 0.2 ≠ 0.3`), накапливаются ошибки. Для денег — `NUMERIC(p, s)` (в C# — `decimal`).
:::

:::spoiler Что такое SQL-инъекция и как от неё защититься?
Подстановка пользовательского ввода в текст запроса меняет его смысл. Защита — параметризованные запросы: значения передаются отдельно от текста запроса; ORM (EF Core) делает это по умолчанию.
:::

:::spoiler В каком порядке сервер выполняет части запроса?
`FROM` → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` → `ORDER BY` → `LIMIT/OFFSET`.
:::

:::spoiler Что делает `RETURNING` и чем он удобен?
Возвращает значения вставленных/изменённых строк (например, сгенерированный `id`) тем же запросом — без отдельного `SELECT`. Это расширение PostgreSQL; EF Core использует его для получения ключей.
:::

## Что запомнить

- SQL декларативен: описываешь, *что* нужно; *как* — решает планировщик.
- Порядок выполнения: `FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT`.
- `NULL` — «неизвестно»: `IS NULL`, а не `= NULL`; `NOT IN` с `NULL` ломается; `count(column)` не считает `NULL`.
- Ограничения (`NOT NULL`, `UNIQUE`, `CHECK`, `REFERENCES`) — последний рубеж защиты данных.
- `UPDATE`/`DELETE` — всегда с `WHERE`; сначала `SELECT`, правки в транзакции.
- Деньги — `NUMERIC`, время — `TIMESTAMPTZ`; строки сравнивай осознанно (`ILIKE`).
- Пользовательский ввод — только параметрами, никогда конкатенацией.
- `LIMIT/OFFSET` — с детерминированным `ORDER BY`.

## Зачем это нужно

В хорошо спроектированной базе данные **не дублируются**: имя автора записано один раз в таблице `authors`, а книги ссылаются на него по `id`. Это правильно (нет противоречий, легко менять), но означает, что ответ на вопрос «какие книги написал Булгаков» лежит **в нескольких таблицах сразу**. `JOIN` — операция, которая собирает их обратно в одну строку результата.

Без JOIN нельзя ответить почти ни на один осмысленный вопрос:

- «Кто сейчас держит книгу X и когда её должен вернуть?» — читатели + выдачи + книги;
- «Сколько выдач у каждого автора?» — авторы + связи + книги + выдачи;
- «Какие читатели ничего не брали?» — читатели + выдачи, и нужны именно строки *без* пары.

Для будущего Junior .NET это ключевая тема:

- **Собеседование.** Задача «напиши запрос на три таблицы с группировкой» — стандарт. Критерий этой фазы — написать такой запрос на чистом листе.
- **EF Core.** Каждый `Include(...)` и каждое обращение к навигационному свойству в LINQ превращается в `JOIN`. Чтобы понять, почему запрос медленный или возвращает не то, нужно читать SQL.
- **Ловушки данных.** Неправильный тип JOIN молча теряет строки или умножает суммы. Ошибки такого рода не падают с исключением — они дают неверные числа в отчёте.

## Интуиция и аналогия

Представь три бумажных списка: книги, читатели и «журнал выдач», где написано только «книга №3 → читатель №1». Чтобы узнать, **кто что взял по названиям**, берёшь строку журнала, находишь в списке книг строку с номером 3, в списке читателей — с номером 1 и **склеиваешь** три строки в одну. Это и есть JOIN: склейка по условию `ON` (номера совпали).

А теперь важный вопрос: что делать с книгой, которую **никто не брал**? В журнале её нет, склеивать не с чем. Два варианта:

- **INNER JOIN** — «показывай только то, что нашло пару». Нетронутая книга исчезнет из результата.
- **LEFT JOIN** — «показывай все книги из левого списка; если пары нет, справа оставь пустоту (`NULL`)». Нетронутая книга остаётся — со словом «пусто» в колонках выдачи.

Весь остальной JOIN — вариации этого выбора и способа подсчёта.

## Основная теория по шагам

### Шаг 1. INNER JOIN — только совпадения

~~~sql
SELECT b.title, a.name
FROM books b
JOIN book_authors ba ON ba.book_id = b.id
JOIN authors a       ON a.id = ba.author_id
ORDER BY b.id, a.name;
~~~
~~~console
          title           |    name     
--------------------------+-------------
 Мастер и Маргарита       | Булгаков
 Собачье сердце           | Булгаков
 Преступление и наказание | Достоевский
 Идиот                    | Достоевский
 Мёртвые души             | Гоголь
 Двенадцать стульев       | Ильф
 Двенадцать стульев       | Петров
(7 rows)
~~~

Заметь: «Двенадцать стульев» — две строки (два автора). «Справочник по SQL» (без автора) и Пушкин (без книг) в результат **не попали**: `JOIN` (он же `INNER JOIN`) оставляет только пары, для которых условие `ON` выполнилось.

Составные части: `books b` — псевдоним таблицы `b` (короткие имена удобнее в условиях), `ON ba.book_id = b.id` — правило склейки. Условие почти всегда сравнивает **внешний ключ** с **первичным ключом**. Если забыть `ON`, получится `CROSS JOIN` — каждая строка с каждой:

~~~sql
SELECT count(*) AS cross_rows FROM books, authors;
~~~
~~~console
 cross_rows 
------------
         42
(1 row)
~~~

7 книг × 6 авторов = 42 бессмысленные строки. На больших таблицах такой запрос «кладёт» базу.

### Шаг 2. LEFT JOIN — все строки слева, даже без пары

~~~sql
SELECT b.title
FROM books b
LEFT JOIN loans l ON l.book_id = b.id
WHERE l.id IS NULL
ORDER BY b.title;
~~~
~~~console
       title       
-------------------
 Идиот
 Мёртвые души
 Справочник по SQL
(3 rows)
~~~

`LEFT JOIN` сохраняет каждую книгу; если выдач нет, колонки `l.*` заполняются `NULL`. Условие `WHERE l.id IS NULL` оставляет как раз такие книги. Это классический приём «найти записи без пары» (anti-join). Посмотрим промежуточный результат без фильтра, чтобы увидеть `NULL`:

~~~sql
SELECT b.title, l.id AS loan_id, l.reader_id
FROM books b
LEFT JOIN loans l ON l.book_id = b.id
WHERE b.id IN (4, 5, 2)
ORDER BY b.id;
~~~
~~~console
     title      | loan_id | reader_id 
----------------+---------+-----------
 Собачье сердце |       5 |         3
 Идиот          |         |          
 Мёртвые души   |         |          
(3 rows)
~~~

(Пустые клетки справа — это `NULL`.)

~~~text Типы соединений
 INNER JOIN  — только пары              A ∩ B
 LEFT JOIN   — все из A + пары из B     A (+ B или NULL)
 RIGHT JOIN  — зеркально LEFT; на практике переписывают в LEFT
 FULL JOIN   — все из A и все из B
 CROSS JOIN  — все комбинации (A × B), почти всегда по ошибке
~~~

`FULL JOIN` нужен редко — для сверки двух списков («что есть в одном и нет в другом»). Покажем на маленьком примере:

~~~sql
SELECT a.n AS left_side, b.n AS right_side
FROM (VALUES (1), (2), (3)) AS a(n)
FULL JOIN (VALUES (2), (3), (4)) AS b(n) ON a.n = b.n
ORDER BY coalesce(a.n, b.n);
~~~
~~~console
 left_side | right_side 
-----------+------------
         1 |           
         2 |          2
         3 |          3
           |          4
(4 rows)
~~~

### Шаг 3. JOIN трёх таблиц с агрегацией — формат критерия {#criteria-query}

~~~sql Сколько книг взял каждый читатель и сколько сейчас на руках
SELECT r.full_name,
       count(l.id)                                     AS loans_total,
       count(l.id) FILTER (WHERE l.returned_at IS NULL) AS on_hand
FROM readers r
LEFT JOIN loans l ON l.reader_id = r.id
GROUP BY r.id, r.full_name
ORDER BY loans_total DESC, r.full_name;
~~~
~~~console
   full_name   | loans_total | on_hand 
---------------+-------------+---------
 Анна Иванова  |           3 |       1
 Борис Петров  |           2 |       1
 Вера Смирнова |           2 |       1
 Глеб Орлов    |           0 |       0
(4 rows)
~~~

Строй такие запросы по одному рецепту: (1) определи, что будет **строкой результата** (здесь — читатель); (2) эта таблица — в `FROM`; (3) присоединяй остальные, выбирая `LEFT`, если нужны строки без пары; (4) `GROUP BY` по ключу строки результата; (5) агрегаты считай по колонке **правой** таблицы.

~~~sql Сколько раз брали книги каждого автора (4 таблицы)
SELECT a.name, count(l.id) AS loans
FROM authors a
JOIN book_authors ba ON ba.author_id = a.id
JOIN books b         ON b.id = ba.book_id
LEFT JOIN loans l    ON l.book_id = b.id
GROUP BY a.id, a.name
ORDER BY loans DESC, a.name;
~~~
~~~console
    name     | loans 
-------------+-------
 Булгаков    |     4
 Ильф        |     2
 Петров      |     2
 Достоевский |     1
 Гоголь      |     0
(5 rows)
~~~

Разбери, почему у Гоголя 0, а Пушкина нет вообще: первые два `JOIN` — внутренние, у Пушкина нет книг, и он отсеялся. Последний — `LEFT`, поэтому Гоголь (книги есть, выдач нет) остался с нулём.

~~~sql Должники на 13.10.2026: три таблицы + вычисление
SELECT r.full_name, b.title, l.due_at,
       DATE '2026-10-13' - l.due_at AS days_late
FROM loans l
JOIN readers r ON r.id = l.reader_id
JOIN books b   ON b.id = l.book_id
WHERE l.returned_at IS NULL
  AND l.due_at < DATE '2026-10-13';
~~~
~~~console
  full_name   |          title           |   due_at   | days_late 
--------------+--------------------------+------------+-----------
 Анна Иванова | Преступление и наказание | 2026-10-04 |         9
(1 row)
~~~

В реальном коде вместо литерала даты — `CURRENT_DATE` или параметр. Разность двух значений типа `DATE` в PostgreSQL — число дней.

Ещё один популярный вид: жанр + число выдач, группировка по значению, а не по `id`:

~~~sql
SELECT b.genre, count(l.id) AS loans
FROM books b
LEFT JOIN loans l ON l.book_id = b.id
GROUP BY b.genre
ORDER BY loans DESC, b.genre;
~~~
~~~console
  genre  | loans 
---------+-------
 Роман   |     6
 Повесть |     1
 Поэма   |     0
 Учебник |     0
(4 rows)
~~~

### Шаг 4. Ловушка: `count(*)` в LEFT JOIN

~~~sql
SELECT a.name, count(*) AS wrong, count(ba.book_id) AS right_cnt
FROM authors a
LEFT JOIN book_authors ba ON ba.author_id = a.id
GROUP BY a.id, a.name
ORDER BY a.id;
~~~
~~~console
    name     | wrong | right_cnt 
-------------+-------+-----------
 Булгаков    |     2 |         2
 Достоевский |     2 |         2
 Гоголь      |     1 |         1
 Ильф        |     1 |         1
 Петров      |     1 |         1
 Пушкин      |     1 |         0
(6 rows)
~~~

У Пушкина `LEFT JOIN` дал одну строку с `NULL` справа. `count(*)` посчитал эту строку (`wrong = 1`), `count(ba.book_id)` — нет (`right_cnt = 0`). **В LEFT JOIN считай по колонке правой таблицы.**

### Шаг 5. Ловушка: «размножение» строк

Если соединить книгу и с авторами, и с выдачами одновременно, каждая выдача повторится столько раз, сколько у книги авторов: у «Двенадцати стульев» 2 автора × 2 выдачи = 4 строки. `sum` и `count` по такому результату дадут удвоенные числа.

~~~sql
SELECT b.title,
       count(l.id)          AS loans_wrong,
       count(DISTINCT l.id) AS loans_right
FROM books b
JOIN book_authors ba ON ba.book_id = b.id
JOIN loans l         ON l.book_id = b.id
WHERE b.id = 6
GROUP BY b.id, b.title;
~~~
~~~console
       title        | loans_wrong | loans_right 
--------------------+-------------+-------------
 Двенадцать стульев |           4 |           2
(1 row)
~~~

Решение — агрегировать в подзапросе/CTE до соединения (следующая тема) или `count(DISTINCT l.id)`. `DISTINCT` годится для `count`, но **не для `sum`** (одинаковые суммы схлопнутся) — для сумм агрегируй заранее.

### Шаг 6. Условие в `ON` против условия в `WHERE`

Задача: для каждого читателя посчитать, сколько книг он **уже вернул** (читатели без возвратов должны остаться с нулём).

~~~sql
-- (а) фильтр в WHERE: читатель без возвратов исчезает (LEFT превращается в INNER)
SELECT r.full_name, count(l.id) AS returned
FROM readers r LEFT JOIN loans l ON l.reader_id = r.id
WHERE l.returned_at IS NOT NULL
GROUP BY r.id, r.full_name ORDER BY r.id;

-- (б) фильтр в ON: все читатели остаются, считаются только возвращённые
SELECT r.full_name, count(l.id) AS returned
FROM readers r LEFT JOIN loans l ON l.reader_id = r.id AND l.returned_at IS NOT NULL
GROUP BY r.id, r.full_name ORDER BY r.id;
~~~
~~~console
   full_name   | returned 
---------------+----------
 Анна Иванова  |        2
 Борис Петров  |        1
 Вера Смирнова |        1
(3 rows)

   full_name   | returned 
---------------+----------
 Анна Иванова  |        2
 Борис Петров  |        1
 Вера Смирнова |        1
 Глеб Орлов    |        0
(4 rows)
~~~

В первом варианте Глеб Орлов пропал: для него `LEFT JOIN` создал строку с `NULL` справа, а `WHERE l.returned_at IS NOT NULL` её отбросил. Во втором условие стало частью определения «пары», и читатель без подходящих выдач сохранился с нулём. Это самая частая причина «пропавших» строк в отчётах.

Правило: **условие на правую таблицу при `LEFT JOIN` кладут в `ON`**, иначе левая строка теряется. Условие на левую таблицу — в `WHERE`.

### Шаг 7. Само-соединение и несколько ключей

Таблицу можно соединить саму с собой. Найдём пары читателей одного типа (каждая пара один раз):

~~~sql
SELECT a.full_name AS first, b.full_name AS second, a.reader_type
FROM readers a
JOIN readers b ON a.reader_type = b.reader_type AND a.id < b.id;
~~~
~~~console
    first     |    second     | reader_type 
--------------+---------------+-------------
 Анна Иванова | Вера Смирнова | student
(1 row)
~~~

Условие `a.id < b.id` убирает пары «с самим собой» и зеркальные дубликаты. Подобное применяют для иерархий (сотрудник — начальник) и сравнения соседних записей.

## Как это работает под капотом

- **Логически** JOIN — это декартово произведение с фильтром по `ON`. **Физически** сервер так не делает: планировщик выбирает один из алгоритмов.
- **Nested Loop** — для каждой строки слева ищем пары справа (хорош, когда слева мало строк, а справа есть индекс по ключу соединения).
- **Hash Join** — по одной таблице строится хэш-таблица по ключу соединения, по другой идёт один проход с поиском в ней: O(n + m), как у `Dictionary` из LINQ `Join` (см. [LINQ](#p2-linq)). Хорош для больших несортированных таблиц без индексов.
- **Merge Join** — обе стороны уже отсортированы по ключу (например, по индексу) и «сливаются» за один проход.
- **Порядок соединения.** `A JOIN B JOIN C` можно выполнить в любом порядке — результат тот же, а стоимость разная. Планировщик оценивает варианты по статистике. Для `LEFT JOIN` порядок менять нельзя, поэтому они ограничивают оптимизацию.
- **Индексы на внешних ключах.** PostgreSQL **не создаёт** индекс на внешнем ключе автоматически (на первичном и `UNIQUE` — создаёт). Поэтому колонки вроде `loans.book_id` без индекса соединяются медленно; EF Core при создании связи создаёт индекс по внешнему ключу сам (см. [индексы](#p3-indexes)).
- **`NULL` не соединяется.** `NULL = NULL` — неизвестно, поэтому строки с `NULL` в ключе соединения пары не находят (кроме внешних соединений, где они сохраняются с `NULL`).
- **EF Core и JOIN.** `Include(b => b.Loans)` превращается в `LEFT JOIN`, `Where(b => b.Loans.Any())` — в `EXISTS`, обращение `l.Reader.FullName` в `Select` — во `INNER JOIN` (для обязательной связи). Разные формы LINQ дают разные SQL (см. [загрузку связанных данных](#p3-loading)).

## Типичные ошибки и ловушки

- **`count(*)` вместо `count(правая_колонка)` в LEFT JOIN.** Дубли «ноль» превращаются в «один».
- **Фильтр по правой таблице в `WHERE` при `LEFT JOIN`.** Левая строка теряется, `LEFT` превращается в `INNER`.
- **Размножение строк** при двух «один-ко-многим» соединениях в одном запросе: суммы удваиваются. Считай каждую ветку отдельно (CTE) или `count(DISTINCT ...)`.
- **Забыли условие `ON` (или `WHERE` в старом синтаксисе).** `CROSS JOIN` — миллионы лишних строк.
- **`JOIN` по неподходящим колонкам.** Соединение по `name` вместо `id` даёт «ложные» пары (однофамильцы).
- **`SELECT *` с несколькими таблицами.** Колонки с одинаковыми именами (`id`) путаются; перечисляй с псевдонимами.
- **Отсутствие индекса на внешнем ключе.** Работает на 100 строках, тормозит на миллионе.
- **Двойной учёт через многие-ко-многим.** Книга с двумя авторами «считается» дважды в сумме по книгам; решай, по чему агрегируешь.
- **`NOT IN` вместо `NOT EXISTS`/`LEFT JOIN ... IS NULL`.** Ломается при `NULL`.
- **Использование `RIGHT JOIN`.** Читается тяжелее; перепиши в `LEFT`, поменяв таблицы местами.
- **Группировка не по ключу.** `GROUP BY r.full_name` склеит двух однофамильцев — группируй по `r.id`.

## Вопросы с собеседований

:::spoiler Почему «Справочник по SQL» не попал в результат первого запроса?
У него нет записей в `book_authors`, а `INNER JOIN` оставляет только строки, нашедшие пару.
:::

:::spoiler Как найти читателей, которые ни разу ничего не брали?
`readers LEFT JOIN loans ON ... WHERE loans.id IS NULL` или `WHERE NOT EXISTS (SELECT 1 FROM loans l WHERE l.reader_id = r.id)`. Результат — Глеб Орлов.
:::

:::spoiler Чем отличается условие в ON от условия в WHERE при LEFT JOIN?
Условие в `ON` влияет на то, какие строки справа считаются парой; строка слева сохраняется в любом случае. Условие в `WHERE` фильтрует уже результат соединения: `WHERE l.returned_at IS NULL` после `LEFT JOIN` выбросит читателей, у которых все книги возвращены, — фактически превратив соединение во внутреннее.
:::

:::spoiler Чем INNER JOIN отличается от LEFT JOIN? (ловушка: «LEFT просто медленнее»)
INNER возвращает только пары, нашедшие совпадение; LEFT сохраняет все строки левой таблицы, заполняя недостающие колонки правой `NULL`. Это разные результаты, а не разные скорости.
:::

:::spoiler Почему `count(*)` в `LEFT JOIN` может дать 1 для записи без пары?
Потому что соединение вернуло строку с `NULL` справа, а `count(*)` считает строки, а не значения. `count(правая_колонка)` не считает `NULL`.
:::

:::spoiler Что такое anti-join и как его записать?
Поиск записей без пары: `LEFT JOIN ... WHERE правая.pk IS NULL` или `NOT EXISTS (подзапрос)`. Безопаснее `NOT IN`, который ломается из-за `NULL`.
:::

:::spoiler Какие алгоритмы JOIN знает PostgreSQL?
Nested Loop (хорош для малых внешних наборов и индекса справа), Hash Join (хэш-таблица по одной стороне, O(n+m)), Merge Join (две отсортированные стороны).
:::

:::spoiler Как избежать умножения строк при соединении двух «один-ко-многим»?
Агрегировать каждую ветку отдельно (подзапрос/CTE) и соединять уже итоги по ключу; либо считать `count(DISTINCT ...)` там, где это допустимо.
:::

## Что запомнить

- `JOIN` склеивает таблицы по условию `ON` (обычно внешний ключ = первичный ключ); `INNER` — только пары, `LEFT` — все слева + `NULL` справа.
- Anti-join («записи без пары»): `LEFT JOIN … WHERE правая.id IS NULL` или `NOT EXISTS`.
- В `LEFT JOIN` считай `count(правая_колонка)`, не `count(*)`; условие на правую таблицу кладут в `ON`.
- Два «один-ко-многим» в одном запросе размножают строки; агрегируй до соединения.
- Строй запрос рецептом: что строка результата → `FROM` → `JOIN`-ы → `GROUP BY` по ключу → агрегаты.
- `FULL JOIN` — для сверок, `CROSS JOIN` — почти всегда по ошибке; `RIGHT JOIN` переписывают в `LEFT`.
- Физически JOIN — Nested Loop / Hash / Merge; внешние ключи нужно индексировать самому.
- `Include` в EF Core — это `LEFT JOIN`; смотри сгенерированный SQL.

Отчёты, статистика, дашборды — это агрегаты. Подзапросы и CTE позволяют разбить сложный запрос на понятные шаги, а оконные функции решают задачи вроде «топ-3 в каждой категории», которые без них превращаются в мучение.
:::

## Зачем это нужно

Простой `SELECT` отвечает на вопрос «покажи записи». Но менеджеру нужны не записи, а **ответы**: сколько выдач за месяц, какой автор самый востребованный, у кого просрочки больше двух недель, какие жанры не окупились. Это агрегаты — свёртка многих строк в одно число, — и они лежат в основе любых отчётов.

Темы этой страницы — четыре уровня инструментов:

- **`GROUP BY` / `HAVING`** — свернуть строки в группы и отфильтровать группы;
- **подзапросы** — использовать результат одного запроса внутри другого («книги новее среднего года»);
- **CTE (`WITH`)** — разбить длинный запрос на именованные шаги и избежать размножения строк;
- **оконные функции** — посчитать значение «по группе», не сворачивая строки: ранг, нарастающий итог, сравнение с предыдущей записью.

Зачем это Junior .NET:

- **Собеседование.** «Топ-3 по каждой категории», «вторая по величине зарплата», «пользователи с более чем двумя заказами» — типовые задачи; без `HAVING`, подзапросов и `ROW_NUMBER()` они решаются мучительно.
- **EF Core.** `GroupBy` в LINQ превращается в `GROUP BY`; запросы с `Any()` — в `EXISTS`; понимание SQL помогает не просить у базы невозможного.
- **Производительность.** Агрегировать на стороне базы почти всегда дешевле, чем тянуть строки в C#: по сети идёт десяток итоговых чисел, а не миллион записей.

## Интуиция и аналогия

**GROUP BY — раскладывание карточек по стопкам.** У тебя 7 карточек выдач. Раскладываешь по стопкам «по читателю» и в каждой считаешь: сколько карточек, самая ранняя дата. Из семи карточек получилось четыре строки итога. Исходные карточки на столе больше не видны — они свёрнуты.

**HAVING — проверка стопок.** `WHERE` — выкинуть ненужные карточки *до* раскладки («только 2026 год»). `HAVING` — выкинуть стопки *после* подсчёта («только те, где больше двух карточек»).

**Подзапрос — вопрос внутри вопроса.** «Какие книги новее среднего?» — сначала считаешь среднее (внутренний вопрос), потом используешь число во внешнем.

**Оконная функция — линейка, приложенная к каждой строке.** Ты не сворачиваешь стопку, а к каждой карточке подписываешь: «в своём жанре эта книга — третья по новизне». Карточки остались все, но у каждой появилась дополнительная колонка.

## Основная теория по шагам

### Шаг 1. GROUP BY и HAVING

~~~sql Книги, которые брали хотя бы дважды
SELECT b.title, count(*) AS times
FROM loans l
JOIN books b ON b.id = l.book_id
GROUP BY b.id, b.title
HAVING count(*) >= 2
ORDER BY times DESC;
~~~
~~~console
       title        | times 
--------------------+-------
 Мастер и Маргарита |     3
 Двенадцать стульев |     2
(2 rows)
~~~

- `GROUP BY` сворачивает строки с одинаковыми значениями ключа в одну группу.
- В `SELECT` можно указывать только **ключи группировки и агрегаты** (`count`, `sum`, `avg`, `min`, `max`).
- `WHERE` фильтрует строки **до** группировки, `HAVING` — группы **после**.
- Группировать по `id` и выводить `title` — хорошая привычка: два разных объекта с одинаковым названием не склеятся.

Что будет, если выбрать колонку вне группировки:

~~~sql
SELECT genre, title, count(*) FROM books GROUP BY genre;
~~~
~~~console
ERROR:  column "books.title" must appear in the GROUP BY clause or be used in an aggregate function
LINE 1: SELECT genre, title, count(*) FROM books GROUP BY genre;
                      ^
~~~

База честно говорит: в группе «Роман» четыре названия, какое показать — неизвестно. Выход: добавить `title` в `GROUP BY`, обернуть в агрегат (`min(title)`, `string_agg(title, ', ')`) или иначе переформулировать вопрос.

Полезные агрегаты:

~~~sql
SELECT genre,
       count(*)                          AS books,
       sum(copies)                       AS total_copies,
       round(avg(year), 1)               AS avg_year,
       min(year) || '–' || max(year)     AS years,
       string_agg(title, '; ' ORDER BY title) AS titles
FROM books
GROUP BY genre
ORDER BY books DESC, genre;
~~~
~~~console
  genre  | books | total_copies | avg_year |   years   |                                 titles                                  
---------+-------+--------------+----------+-----------+-------------------------------------------------------------------------
 Роман   |     4 |            8 |   1907.5 | 1866–1967 | Двенадцать стульев; Идиот; Мастер и Маргарита; Преступление и наказание
 Повесть |     1 |            2 |   1987.0 | 1987–1987 | Собачье сердце
 Поэма   |     1 |            1 |   1842.0 | 1842–1842 | Мёртвые души
 Учебник |     1 |            4 |   2020.0 | 2020–2020 | Справочник по SQL
(4 rows)
~~~

Агрегат с условием — `FILTER` (PostgreSQL), в других СУБД пишут `sum(CASE WHEN ... THEN 1 ELSE 0 END)`:

~~~sql
SELECT count(*) AS total,
       count(*) FILTER (WHERE returned_at IS NULL) AS on_hand,
       count(*) FILTER (WHERE returned_at > due_at) AS returned_late,
       round(avg(returned_at - loaned_at), 1) AS avg_days
FROM loans;
~~~
~~~console
 total | on_hand | returned_late | avg_days 
-------+---------+---------------+----------
     7 |       3 |             1 |     18.3
(1 row)
~~~

Важное свойство: агрегаты (кроме `count(*)`) **игнорируют `NULL`**. Среднее считается только по непустым значениям (`avg_days` посчитан по 4 возвращённым выдачам, а не по 7).

### Шаг 2. Подзапросы

Подзапрос — это `SELECT` внутри другого запроса. Бывает трёх видов: скалярный (одно значение), список значений (для `IN`) и таблица (в `FROM`).

~~~sql Книги новее среднего года издания
SELECT title, year
FROM books
WHERE year > (SELECT avg(year) FROM books)
ORDER BY year;
~~~
~~~console
       title        | year 
--------------------+------
 Двенадцать стульев | 1928
 Мастер и Маргарита | 1967
 Собачье сердце     | 1987
 Справочник по SQL  | 2020
(4 rows)
~~~

Подзапрос со списком и коррелированный подзапрос (внутренний запрос ссылается на строку внешнего):

~~~sql
-- читатели, которые брали книги жанра «Роман»
SELECT full_name FROM readers
WHERE id IN (SELECT l.reader_id FROM loans l JOIN books b ON b.id = l.book_id WHERE b.genre = 'Роман')
ORDER BY full_name;

-- у каждой книги: сколько раз её брали (коррелированный: ссылается на b.id)
SELECT b.title, (SELECT count(*) FROM loans l WHERE l.book_id = b.id) AS times
FROM books b ORDER BY times DESC, b.title LIMIT 3;
~~~
~~~console
   full_name   
---------------
 Анна Иванова
 Борис Петров
 Вера Смирнова
(3 rows)

          title           | times 
--------------------------+-------
 Мастер и Маргарита       |     3
 Двенадцать стульев       |     2
 Преступление и наказание |     1
(3 rows)
~~~

`EXISTS` проверяет, что подзапрос вернул **хоть одну строку**; сами значения неважны (принято писать `SELECT 1`):

~~~sql EXISTS: читатели без единой выдачи
SELECT full_name
FROM readers r
WHERE NOT EXISTS (SELECT 1 FROM loans l WHERE l.reader_id = r.id);
~~~
~~~console
 full_name  
------------
 Глеб Орлов
(1 row)
~~~

:::warn `NOT IN` и NULL
`WHERE id NOT IN (SELECT reader_id FROM ...)` вернёт **пустой результат**, если подзапрос содержит хотя бы один `NULL`: сравнение с `NULL` даёт «неизвестно». `NOT EXISTS` такой проблемы не имеет — предпочитай его.
:::

Подзапрос в `FROM` («производная таблица») нужен, когда агрегируешь результат другого агрегата:

~~~sql
-- сколько читателей брали 1, 2, 3 книги
SELECT times, count(*) AS readers
FROM (SELECT reader_id, count(*) AS times FROM loans GROUP BY reader_id) t
GROUP BY times
ORDER BY times;
~~~
~~~console
 times | readers 
-------+---------
     2 |       2
     3 |       1
(2 rows)
~~~

### Шаг 3. CTE (`WITH`) — запрос по шагам

~~~sql Сколько экземпляров каждой книги свободно
WITH on_hand AS (
    SELECT book_id, count(*) AS cnt
    FROM loans
    WHERE returned_at IS NULL
    GROUP BY book_id
)
SELECT b.title, b.copies,
       coalesce(o.cnt, 0)            AS on_hand,
       b.copies - coalesce(o.cnt, 0) AS available
FROM books b
LEFT JOIN on_hand o ON o.book_id = b.id
ORDER BY b.id;
~~~
~~~console
          title           | copies | on_hand | available 
--------------------------+--------+---------+-----------
 Мастер и Маргарита       |      3 |       1 |         2
 Собачье сердце           |      2 |       0 |         2
 Преступление и наказание |      2 |       1 |         1
 Идиот                    |      1 |       0 |         1
 Мёртвые души             |      1 |       0 |         1
 Двенадцать стульев       |      2 |       1 |         1
 Справочник по SQL        |      4 |       0 |         4
(7 rows)
~~~

CTE — именованный промежуточный результат. Он читается сверху вниз как шаги алгоритма и заодно решает проблему «размножения» строк: агрегировали выдачи **до** соединения. Можно объявить несколько CTE через запятую, и следующие могут использовать предыдущие:

~~~sql
WITH per_reader AS (
    SELECT reader_id, count(*) AS cnt FROM loans GROUP BY reader_id
),
avg_cnt AS (
    SELECT avg(cnt) AS a FROM per_reader
)
SELECT r.full_name, p.cnt
FROM per_reader p
JOIN readers r ON r.id = p.reader_id
CROSS JOIN avg_cnt
WHERE p.cnt > avg_cnt.a            -- больше среднего числа выдач
ORDER BY r.full_name;
~~~
~~~console
  full_name   | cnt 
--------------+-----
 Анна Иванова |   3
(1 row)
~~~

Рекурсивный CTE умеет обходить деревья (категории, оргструктура); синтаксис `WITH RECURSIVE` стоит запомнить как факт:

~~~sql
WITH RECURSIVE nums AS (
    SELECT 1 AS n
    UNION ALL
    SELECT n + 1 FROM nums WHERE n < 5
)
SELECT string_agg(n::text, ',') AS list FROM nums;
~~~
~~~console
   list    
-----------
 1,2,3,4,5
(1 row)
~~~

### Шаг 4. Оконные функции — агрегат без сворачивания строк

~~~sql Рейтинг книг по новизне внутри каждого жанра
SELECT genre, title, year,
       rank() OVER (PARTITION BY genre ORDER BY year DESC) AS rnk
FROM books
ORDER BY genre, rnk;
~~~
~~~console
  genre  |          title           | year | rnk 
---------+--------------------------+------+-----
 Повесть | Собачье сердце           | 1987 |   1
 Поэма   | Мёртвые души             | 1842 |   1
 Роман   | Мастер и Маргарита       | 1967 |   1
 Роман   | Двенадцать стульев       | 1928 |   2
 Роман   | Идиот                    | 1869 |   3
 Роман   | Преступление и наказание | 1866 |   4
 Учебник | Справочник по SQL        | 2020 |   1
(7 rows)
~~~

В отличие от `GROUP BY`, оконная функция **сохраняет все строки** и добавляет к каждой вычисленное значение. Конструкция `OVER (PARTITION BY ... ORDER BY ...)` задаёт «окно»: `PARTITION BY` — по каким группам считать, `ORDER BY` — в каком порядке внутри группы.

Различия функций нумерации видны только при **равных** значениях. Возьмём небольшую таблицу результатов с ничьёй:

~~~sql
SELECT name, score,
       row_number() OVER w AS row_num,
       rank()       OVER w AS rnk,
       dense_rank() OVER w AS dense
FROM (VALUES ('Анна', 90), ('Борис', 80), ('Вера', 80), ('Глеб', 70)) AS t(name, score)
WINDOW w AS (ORDER BY score DESC)
ORDER BY score DESC, name;
~~~
~~~console
 name  | score | row_num | rnk | dense 
-------+-------+---------+-----+-------
 Анна  |    90 |       1 |   1 |     1
 Борис |    80 |       2 |   2 |     2
 Вера  |    80 |       3 |   2 |     2
 Глеб  |    70 |       4 |   4 |     3
(4 rows)
~~~

Борис и Вера набрали по 80, поэтому у них один `rank` и один `dense_rank`, но разные `row_number`. У Глеба `rank` равен 4 (место «пропущено»), а `dense_rank` — 3. Именно эту разницу проверяют вопросом «выбери третье место»: при `rank` третьего места в этих данных просто нет.

- `row_number()` — уникальный номер 1, 2, 3 даже при равных значениях;
- `rank()` — равные получают один ранг, следующий номер пропускается (1, 1, 3);
- `dense_rank()` — без пропусков (1, 1, 2).

**«Топ-N в каждой группе»** — обернуть в CTE и отфильтровать (оконные функции нельзя использовать прямо в `WHERE`):

~~~sql
WITH ranked AS (
    SELECT genre, title, year,
           row_number() OVER (PARTITION BY genre ORDER BY year DESC) AS rn
    FROM books
)
SELECT genre, title, year FROM ranked WHERE rn = 1 ORDER BY genre;
~~~
~~~console
  genre  |       title        | year 
---------+--------------------+------
 Повесть | Собачье сердце     | 1987
 Поэма   | Мёртвые души       | 1842
 Роман   | Мастер и Маргарита | 1967
 Учебник | Справочник по SQL  | 2020
(4 rows)
~~~

Нарастающий итог и сравнение с предыдущей строкой:

~~~sql
SELECT date_trunc('month', loaned_at)::date AS month,
       count(*)                              AS loans,
       sum(count(*)) OVER (ORDER BY date_trunc('month', loaned_at)) AS running_total,
       lag(count(*)) OVER (ORDER BY date_trunc('month', loaned_at)) AS prev_month
FROM loans
GROUP BY date_trunc('month', loaned_at)
ORDER BY month;
~~~
~~~console
   month    | loans | running_total | prev_month 
------------+-------+---------------+------------
 2026-08-01 |     1 |             1 |           
 2026-09-01 |     4 |             5 |          1
 2026-10-01 |     2 |             7 |          4
(3 rows)
~~~

Здесь окно применено *поверх* группировки: сначала `GROUP BY` посчитал выдачи по месяцам, затем `sum(...) OVER` собрал нарастающий итог, а `lag` показал значение предыдущего месяца (у первого — `NULL`).

### Шаг 5. Объединение результатов: UNION

Когда нужно склеить строки из двух запросов (не колонки, как JOIN):

~~~sql
SELECT 'книга' AS kind, title AS name FROM books WHERE year < 1870
UNION ALL
SELECT 'автор', name FROM authors WHERE name LIKE 'Г%'
ORDER BY kind, name;
~~~
~~~console
 kind  |           name           
-------+--------------------------
 автор | Гоголь
 книга | Идиот
 книга | Мёртвые души
 книга | Преступление и наказание
(4 rows)
~~~

`UNION ALL` оставляет все строки (быстро), `UNION` ещё и убирает дубликаты (дороже — нужна сортировка/хэш). Количество и типы колонок должны совпадать.

### Шаг 6. Как подойти к отчётному запросу

Сложные запросы не пишут «одним махом». Рабочий порядок, который хорошо ложится на собеседование:

1. **Сформулируй результат словами:** «одна строка — один читатель; колонки: имя, всего выдач, просрочено сейчас». Это определяет, по чему группировать.
2. **Найди таблицы-источники** и выпиши, как они связаны (какой внешний ключ к какому первичному).
3. **Начни с самого простого:** выбери строки без агрегации (`SELECT` с `JOIN`), убедись, что строки правильные и их столько, сколько ждёшь.
4. **Добавь группировку** и агрегаты. Сверь итог с ручным подсчётом на маленьких данных, как у нас: 7 выдач, значит, сумма по читателям тоже обязана быть 7.
5. **Выдели шаги в CTE**, если запрос растёт: каждый CTE можно запускать отдельно и проверять.
6. **Проверь краевые случаи:** читатель без выдач, `NULL` в данных, пустая группа.

Контрольная сумма — простой и мощный приём: после любой переделки запроса проверь, что общее число (выдач, денег) совпадает с исходным. Если после добавления второго `JOIN` сумма выросла, значит, строки размножились.

## Как это работает под капотом

- **Порядок логических шагов:** `FROM/JOIN → WHERE → GROUP BY → агрегаты → HAVING → оконные функции → SELECT → DISTINCT → ORDER BY → LIMIT`. Поэтому оконную функцию нельзя поставить в `WHERE` или `HAVING` (результата ещё нет), а в `ORDER BY` — можно.
- **Агрегация физически.** `HashAggregate` — таблица «ключ группы → накопитель» (как `Dictionary` в LINQ `GroupBy`); `GroupAggregate` — по уже отсортированным данным за один проход. Планировщик выбирает по статистике.
- **Оконные функции** сортируют (или используют индекс), затем идут по партиции скользящим окном. Дорогие на больших данных, но эффективнее самосоединений и коррелированных подзапросов.
- **Коррелированный подзапрос** логически выполняется для каждой внешней строки. Современный планировщик часто превращает его в соединение, но не всегда; при подозрении на тормоза смотри `EXPLAIN`.
- **CTE и материализация.** До PostgreSQL 12 каждый CTE выполнялся отдельно и служил «барьером оптимизации»; начиная с 12 простые CTE подставляются в запрос как подзапросы (если не указано `MATERIALIZED`). Можно думать о CTE как о синтаксическом сахаре читаемости.
- **`NULL` и группировка.** Все `NULL` в ключе группировки попадают в **одну** группу (`GROUP BY` считает их равными), хотя в сравнении `NULL = NULL` — неизвестно. Агрегаты, кроме `count(*)`, пропускают `NULL`.
- **EF Core.** `GroupBy(x => x.Genre).Select(g => new { g.Key, Count = g.Count() })` транслируется в `GROUP BY`; `Any()` — в `EXISTS`; оконные функции в LINQ напрямую не выражаются (нужен сырой SQL или `FromSqlRaw`). Агрегаты по `IQueryable` выполняются в базе (см. [IQueryable](#p2-linq)).
- **`DISTINCT ON` (PostgreSQL).** Нестандартное расширение для «первой строки в группе»: `SELECT DISTINCT ON (genre) ... ORDER BY genre, year DESC`. Короче оконной функции, но привязано к диалекту.

## Типичные ошибки и ловушки

- **Колонка вне `GROUP BY` и вне агрегата.** Ошибка «must appear in the GROUP BY clause»; в MySQL без строгого режима вернёт произвольную строку — молча неверно.
- **Агрегат в `WHERE`.** `WHERE count(*) > 2` невозможно; нужен `HAVING`.
- **`HAVING` вместо `WHERE`.** Фильтр по обычной колонке в `HAVING` работает, но заставляет считать группы, которые потом выбрасываются; фильтруй как можно раньше.
- **Группировка не по ключу.** Группировка по `full_name` склеит однофамильцев.
- **`NOT IN` с `NULL`.** Пустой результат; `NOT EXISTS`.
- **Скалярный подзапрос, вернувший больше одной строки.** Ошибка «more than one row returned by a subquery used as an expression».
- **Оконная функция в `WHERE`.** Нельзя; оберни в CTE и фильтруй снаружи.
- **`rank` вместо `row_number` для «топ-1».** При равенстве вернётся несколько строк; если нужна ровно одна — `row_number` (с детерминированным `ORDER BY`).
- **Отсутствие `ORDER BY` в окне.** Нарастающий итог без порядка бессмыслен.
- **`avg` целых чисел.** В PostgreSQL `avg(int)` даёт `numeric` — ок; а деление `int / int` — целочисленное: `5 / 2 = 2`. Приводи: `5::numeric / 2`.
- **Размножение строк до группировки.** Два `JOIN` «один-ко-многим» умножают суммы; агрегируй до соединения (CTE).
- **Чрезмерные CTE.** Цепочка из десяти CTE нечитаема; иногда проще создать представление (`VIEW`).

## Вопросы с собеседований

:::spoiler Чем WHERE отличается от HAVING?
`WHERE` фильтрует отдельные строки до группировки и не может использовать агрегаты. `HAVING` фильтрует группы после группировки и работает с агрегатами.
:::

:::spoiler Почему `SELECT genre, title, count(*) FROM books GROUP BY genre` — ошибка?
`title` не входит в группировку и не агрегирован: в группе «Роман» четыре разных названия, и база не знает, какое показать.
:::

:::spoiler Когда выбрать оконную функцию, а когда GROUP BY?
`GROUP BY` — когда нужна одна строка на группу (итоги). Оконная функция — когда нужны исходные строки плюс значение, посчитанное по группе (ранг, доля, нарастающий итог, сравнение с соседней строкой).
:::

:::spoiler Найди вторую по величине цену / второго по новизне (классика). Как решить? (ловушка: `LIMIT 1 OFFSET 1` с дубликатами)
`OFFSET 1` с дубликатами вернёт то же значение. Надёжнее: `dense_rank() OVER (ORDER BY price DESC)` в CTE и `WHERE rnk = 2`, либо `SELECT max(price) FROM t WHERE price < (SELECT max(price) FROM t)`.
:::

:::spoiler В чём разница между `row_number`, `rank` и `dense_rank`?
`row_number` — уникальная нумерация; `rank` — равные получают одинаковый ранг, дальше пропуск (1, 1, 3); `dense_rank` — без пропусков (1, 1, 2).
:::

:::spoiler Что такое коррелированный подзапрос и чем он плох?
Подзапрос, ссылающийся на колонку внешнего запроса; логически выполняется для каждой внешней строки, потому может быть медленным на больших таблицах. Часто заменяется `JOIN` или оконной функцией.
:::

:::spoiler Чем `UNION` отличается от `UNION ALL`? Что быстрее?
`UNION` убирает дубликаты (дополнительная сортировка/хэширование), `UNION ALL` — нет, поэтому быстрее. Если дубликатов не бывает или они допустимы, берут `UNION ALL`.
:::

:::spoiler Как найти дубликаты по полю?
`SELECT col, count(*) FROM t GROUP BY col HAVING count(*) > 1`.
:::

:::spoiler Что делает `COALESCE`, и чем отличается от `ISNULL`/`IFNULL`?
Возвращает первое не-`NULL` значение из списка. `COALESCE` — стандарт SQL и работает в PostgreSQL; `ISNULL`/`IFNULL` — диалектные функции с двумя аргументами.
:::

## Что запомнить

- `GROUP BY` сворачивает строки; в `SELECT` — только ключи и агрегаты; `WHERE` — до группировки, `HAVING` — после.
- Агрегаты игнорируют `NULL` (кроме `count(*)`); `FILTER (WHERE …)` — условный агрегат.
- Подзапрос: скалярный, список (`IN`), таблица (`FROM`), коррелированный; `NOT EXISTS` надёжнее `NOT IN`.
- CTE (`WITH`) — запрос по шагам и защита от размножения строк: агрегируй до соединения.
- Оконные функции сохраняют строки: `OVER (PARTITION BY … ORDER BY …)`; ранжирование — `row_number`/`rank`/`dense_rank`; нарастающий итог — `sum() OVER (ORDER BY …)`; `lag/lead` — соседние строки.
- «Топ-N в группе» = оконная функция в CTE + фильтр снаружи.
- `UNION ALL` быстрее `UNION`; число и типы колонок должны совпадать.
- Логический порядок: `FROM → WHERE → GROUP BY → HAVING → окна → SELECT → ORDER BY → LIMIT`.

## Зачем это нужно

Приложения переписывают каждые пять лет, а **схема данных живёт десятилетиями**. Исправить опечатку в коде — коммит; исправить неудачную схему в базе с миллионом записей — это миграция, остановка сервиса и риск потерять данные. Поэтому проектирование таблиц — один из самых «дорогих» навыков: ошибка, сделанная в первый день, платится годами.

Что даёт хорошая схема:

- **Корректность без усилий.** Когда каждый факт (телефон читателя, имя автора) записан один раз, противоречий быть не может.
- **Простые запросы.** Данные разложены по понятным таблицам, и вопросы к ним превращаются в короткие `JOIN`.
- **Защиту от мусора.** Ключи и ограничения не дают записать несуществующую книгу или отрицательное число экземпляров.
- **Лёгкое развитие.** Новая функция («у читателя несколько телефонов») — новая таблица, а не переписывание половины приложения.

Зачем это начинающему .NET-разработчику:

- **Собеседование.** «Спроектируй схему для интернет-магазина / бронирования / блога» — частое задание. Ожидают: сущности, ключи, связи «один-ко-многим» и «многие-ко-многим», понимание нормализации.
- **EF Core Code First.** Ты описываешь схему классами C#; но модель классов должна соответствовать здравому дизайну БД, иначе миграции породят то же самое неудачное устройство.
- **Чтение чужих баз.** В реальной работе ты чаще дорабатываешь существующую схему, чем создаёшь новую. Нужно узнавать типичные проблемы (список в ячейке, дублирование, отсутствие ключей).

## Интуиция и аналогия

**Адресная книга против бардака на стикерах.** Представь, что телефон друга записан на двадцати стикерах: на каждом, где упомянут друг. Он сменил номер — ты обязан найти все двадцать стикеров. Забыл один — теперь у тебя два «правильных» номера. Нормализация — это привычка завести **одну карточку друга** и на стикерах писать только «см. карточку №7».

Отсюда формула: **каждый факт хранится ровно в одном месте, а в остальных — ссылка на него.** Ссылка — это внешний ключ.

**Паспорт и фамилия.** Человека в паспорте идентифицирует номер (суррогатный ключ), а не фамилия: фамилии меняются и повторяются. Так же и в таблицах: идентификатор — число `id`, а такие вещи, как ISBN или e-mail, — обычные поля с ограничением `UNIQUE`.

**Склад и накладная.** Накладная (выдача) ссылается на товар (книгу) и клиента (читателя) по номерам. В накладной не переписывают заново описание товара и адрес клиента — иначе при смене адреса пришлось бы править все прошлые накладные.

## Основная теория по шагам

### Шаг 1. Ненормализованная таблица и её болезни

Возьмём «всё в одной таблице» и воспроизведём её настоящими командами, чтобы увидеть проблемы воочию:

~~~sql
CREATE TABLE loans_flat (
    reader_name  TEXT,
    reader_phone TEXT,
    book_title   TEXT,
    authors      TEXT,        -- список через запятую!
    loaned_at    DATE
);
INSERT INTO loans_flat VALUES
    ('Анна Иванова', '+998 90 111', 'Двенадцать стульев',      'Ильф, Петров', '2026-08-01'),
    ('Анна Иванова', '+998 90 111', 'Преступление и наказание','Достоевский',  '2026-09-20'),
    ('Борис Петров', '+998 91 222', 'Двенадцать стульев',      'Ильф, Петров', '2026-10-01');

-- аномалия обновления: поменяли телефон, но забыли вторую строку Анны
UPDATE loans_flat SET reader_phone = '+998 90 999' WHERE reader_name = 'Анна Иванова' AND loaned_at = '2026-08-01';

SELECT reader_name, reader_phone FROM loans_flat WHERE reader_name = 'Анна Иванова' ORDER BY loaned_at;
~~~
~~~console
 reader_name  | reader_phone 
--------------+--------------
 Анна Иванова | +998 90 999
 Анна Иванова | +998 90 111
(2 rows)
~~~

У Анны теперь два разных телефона — база не видит в этом противоречия. Ещё проблемы:

- **Аномалия обновления:** телефон дублируется в каждой строке выдачи; изменил не везде — данные противоречат друг другу.
- **Аномалия вставки:** нельзя завести читателя, пока он ничего не взял (ведь в таблице должна быть строка выдачи); нельзя записать новую книгу, которую ещё не брали.
- **Аномалия удаления:** удалил последнюю выдачу книги — потерял информацию о самой книге и её авторах.
- **Список в ячейке** (`Ильф, Петров`): невозможно нормально найти все книги Петрова или посчитать их:

~~~sql
SELECT count(*) AS exact_match FROM loans_flat WHERE authors = 'Петров';
SELECT count(*) AS like_match  FROM loans_flat WHERE authors LIKE '%Петров%';
~~~
~~~console
 exact_match 
-------------
           0
(1 row)

 like_match 
------------
          2
(1 row)
~~~

Точное сравнение не находит ни одной строки; `LIKE` находит, но заодно найдёт «Петровский», «Петров-Водкин» и не использует индекс. Решение — разложить таблицу на части.

### Шаг 2. Три нормальные формы на практике

| Форма | Правило простыми словами | Нарушение в примере | Исправление |
|---|---|---|---|
| **1НФ** | В ячейке одно значение, нет повторяющихся групп | `authors = 'Ильф, Петров'` | таблица `book_authors` |
| **2НФ** | Каждый неключевой атрибут зависит от **всего** ключа | при ключе (reader, book, date) телефон зависит только от reader | вынести читателя в `readers` |
| **3НФ** | Неключевые атрибуты не зависят от других неключевых | `reader_type → max_books` в таблице читателей | справочник типов читателей |

Итог — [учебная схема](#p3-select/schema): `readers`, `books`, `authors`, `book_authors`, `loans`. Каждый факт хранится один раз, связи — через внешние ключи.

Запомнить нормальные формы проще через цитату: **«каждый неключевой атрибут зависит от ключа, от всего ключа и ни от чего, кроме ключа»**. «От ключа» — 1НФ, «от всего ключа» — 2НФ, «ни от чего, кроме ключа» — 3НФ.

Пример нарушения 3НФ и его исправления. Допустим, в таблице читателей мы решили хранить ещё и лимит книг, который зависит от типа читателя:

~~~sql
-- ❌ лимит зависит от reader_type, а не от id читателя: транзитивная зависимость
CREATE TABLE readers_bad (
    id INT PRIMARY KEY, full_name TEXT, reader_type TEXT, max_books INT
);
INSERT INTO readers_bad VALUES (1,'Анна','student',3), (2,'Вера','student',3), (3,'Борис','teacher',10);
UPDATE readers_bad SET max_books = 5 WHERE id = 1;    -- у двух студентов теперь разный лимит

-- ✅ справочник типов: лимит хранится один раз
CREATE TABLE reader_types (type TEXT PRIMARY KEY, max_books INT NOT NULL);
INSERT INTO reader_types VALUES ('student', 3), ('teacher', 10), ('external', 1);
CREATE TABLE readers_good (
    id INT PRIMARY KEY, full_name TEXT NOT NULL,
    reader_type TEXT NOT NULL REFERENCES reader_types(type)
);
INSERT INTO readers_good VALUES (1,'Анна','student'), (2,'Вера','student'), (3,'Борис','teacher');

SELECT g.full_name, t.max_books
FROM readers_good g JOIN reader_types t ON t.type = g.reader_type ORDER BY g.id;
~~~
~~~console
 full_name | max_books 
-----------+-----------
 Анна      |         3
 Вера      |         3
 Борис     |        10
(3 rows)
~~~

Теперь лимит студента меняется одной правкой в `reader_types`, и противоречий не возникает.

### Шаг 3. Ключи и связи

- **Первичный ключ** (PK) — уникальный идентификатор строки. Обычно суррогатный `id` (число или GUID), а не «естественный» (ISBN, email): естественные ключи меняются и бывают неуникальны в реальности.
- **Естественная уникальность** всё равно обеспечивается — ограничением `UNIQUE` (ISBN, номер билета).
- **Внешний ключ** (FK) — ссылка на PK другой таблицы, база гарантирует, что ссылка ведёт на существующую строку.
- **Один-ко-многим**: FK на стороне «многих» (`loans.reader_id`).
- **Многие-ко-многим**: таблица связи с двумя FK (`book_authors`), часто с составным PK.
- **Один-к-одному**: FK + `UNIQUE` (например, `reader_profiles.reader_id`).

~~~sql
-- один-к-одному: профиль читателя; UNIQUE на FK запрещает второй профиль
CREATE TABLE reader_profiles (
    reader_id INT PRIMARY KEY REFERENCES readers(id),   -- PK совпадает с FK → ровно один профиль
    birth_date DATE
);
INSERT INTO reader_profiles VALUES (1, '2001-05-17');
INSERT INTO reader_profiles VALUES (1, '1999-01-01');
~~~
~~~console
ERROR:  duplicate key value violates unique constraint "reader_profiles_pkey"
DETAIL:  Key (reader_id)=(1) already exists.
~~~

Составной PK у `book_authors (book_id, author_id)` не даёт добавить одну и ту же пару дважды:

~~~sql
INSERT INTO book_authors VALUES (1, 1);
~~~
~~~console
ERROR:  duplicate key value violates unique constraint "book_authors_pkey"
DETAIL:  Key (book_id, author_id)=(1, 1) already exists.
~~~

### Шаг 4. Поведение при удалении

| `ON DELETE` | Что происходит при удалении родителя | Когда уместно |
|---|---|---|
| `RESTRICT` / `NO ACTION` (по умолчанию) | удаление запрещено, пока есть дети | выдачи не должны пропадать вместе с читателем |
| `CASCADE` | дети удаляются вместе с родителем | строки связи (`book_authors`) — без книги они бессмысленны |
| `SET NULL` | FK у детей становится `NULL` | необязательная связь |

Проверим на нашей базе:

~~~sql
DELETE FROM readers WHERE id = 1;                       -- есть выдачи → запрещено
~~~
~~~console
ERROR:  update or delete on table "readers" violates foreign key constraint "loans_reader_id_fkey" on table "loans"
DETAIL:  Key (id)=(1) is still referenced from table "loans".
~~~

~~~sql
DELETE FROM books WHERE id = 5;                          -- у «Мёртвых душ» нет выдач; связь с автором удалится каскадом
SELECT count(*) AS links_for_book_5 FROM book_authors WHERE book_id = 5;
~~~
~~~console
 links_for_book_5 
------------------
                0
(1 row)
~~~

:::tip Денормализация — осознанно
Иногда данные дублируют ради скорости чтения (например, счётчик выдач в книге). Это допустимо **после** нормализованной схемы и измерений, с понятным механизмом синхронизации. В пет-проектах этой фазы — не нужно.
:::

### Шаг 5. Ограничения как часть дизайна

Хорошая схема кодирует правила предметной области:

~~~sql
CREATE TABLE rooms (id INT PRIMARY KEY, name TEXT NOT NULL UNIQUE, capacity INT NOT NULL CHECK (capacity > 0));
CREATE TABLE bookings (
    id        INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    room_id   INT NOT NULL REFERENCES rooms(id),
    starts_at TIMESTAMPTZ NOT NULL,
    ends_at   TIMESTAMPTZ NOT NULL,
    CHECK (ends_at > starts_at)
);
INSERT INTO rooms VALUES (1, 'Большая', 12);
INSERT INTO bookings (room_id, starts_at, ends_at) VALUES (1, '2026-11-01 10:00+00', '2026-11-01 11:00+00');
INSERT INTO bookings (room_id, starts_at, ends_at) VALUES (1, '2026-11-01 12:00+00', '2026-11-01 11:00+00');
~~~
~~~console
ERROR:  new row for relation "bookings" violates check constraint "bookings_check"
DETAIL:  Failing row contains (2, 1, 2026-11-01 12:00:00+00, 2026-11-01 11:00:00+00).
~~~

Пересечение интервалов бронирования (два человека на одну комнату в одно время) тоже можно запретить на уровне базы — ограничением `EXCLUDE USING gist` с расширением `btree_gist`. Это сильнее проверки в коде: она не допускает гонку двух одновременных запросов. Пока достаточно знать, что такая возможность есть.

### Шаг 6. Как проектировать схему: рабочий порядок

1. **Выпиши существительные предметной области** — это будущие сущности: читатель, книга, автор, выдача.
2. **Для каждой сущности перечисли атрибуты** и определи, что идентифицирует её. Добавь суррогатный `id`, а природную уникальность оформи `UNIQUE`.
3. **Определи связи.** Для каждой пары: один к одному, один ко многим или многие ко многим? Для многие-ко-многим — таблица связи (и у неё могут быть свои атрибуты: дата, роль).
4. **Поставь внешние ключи и поведение при удалении.** Что должно случиться при удалении родителя?
5. **Добавь ограничения** (`NOT NULL`, `CHECK`, `UNIQUE`) для правил предметной области.
6. **Проверь по 1НФ–3НФ.** Нет ли списков в ячейке? Всё ли зависит от ключа? Не дублируется ли что-то?
7. **Проверь запросами.** Напиши 5–10 типовых запросов («что нужно показать на главной странице») — если они выходят сложными, схема, возможно, неудачна.
8. **Продумай индексы** на внешних ключах и полях фильтрации (следующая тема).

## Как это работает под капотом

- **PK и UNIQUE = индекс.** Для первичного ключа и `UNIQUE` PostgreSQL автоматически создаёт уникальный индекс (B-дерево); именно он быстро проверяет уникальность и ускоряет поиск по ключу. Для внешнего ключа индекс **не создаётся** автоматически (на стороне детей) — его добавляют сами; EF Core при описании связи создаёт его по умолчанию.
- **Как проверяется FK.** При вставке в `loans` база ищет `book_id` в PK-индексе `books`; при удалении книги — ищет детей в `loans` (поэтому индекс на `loans.book_id` ускоряет и удаление родителей). Без индекса каждое удаление родителя сканирует таблицу детей.
- **Суррогатный ключ.** `identity` — это скрытая последовательность (sequence), число берётся независимо от транзакции, поэтому после отката в нумерации остаются «дыры» — это нормально. GUID-ключи (`uuid`) удобны для распределённых систем, но крупнее и раскидывают вставки по индексу.
- **Каскады на уровне СУБД против каскадов в EF Core.** `ON DELETE CASCADE` исполняет сама база одной командой. EF Core умеет ещё и каскадно удалять *отслеживаемые* сущности. Поведение задаётся в модели (`OnDelete(...)`) и должно совпадать с тем, что в БД.
- **Типы и нормализация.** Каждая лишняя таблица — это `JOIN` в запросах. Нормализованная схема чуть сложнее читается, но выигрывает в корректности; на отчётных витринах иногда намеренно денормализуют, оставляя нормализованное «ядро» для записи.
- **Схема — это ограничения.** Таблица без PK, без FK и без `NOT NULL` — просто «ящик с данными». Именно ограничения превращают её в проверяемую модель домена.
- **Соответствие C#.** Таблица ↔ класс-сущность, колонка ↔ свойство, FK ↔ навигационное свойство + свойство-ключ, таблица связи многие-ко-многим ↔ коллекции с обеих сторон (EF Core создаёт таблицу связи сам).

## Типичные ошибки и ловушки

- **Список в ячейке** (`'Ильф, Петров'`, теги через запятую). Нарушение 1НФ — выноси в связанную таблицу.
- **Таблица без первичного ключа.** Нельзя однозначно адресовать строку, EF Core не сможет отслеживать сущность.
- **Естественный ключ (email, ISBN) как PK.** Меняется, бывает неуникален, раздувает все внешние ключи.
- **Нет внешних ключей «для скорости».** Целостность перекладывается на код, и в данных заводятся «сироты» — выдачи на несуществующую книгу.
- **`CASCADE` везде.** Удаление читателя молча уничтожит всю историю выдач; для бизнес-данных обычно `RESTRICT` и «мягкое» удаление.
- **Один универсальный столбец `data`/EAV.** «Гибко», но без типов, ограничений и нормальных запросов; используй `JSONB` точечно.
- **Дублирование данных «для удобства».** Имя автора в каждой книге — снова аномалии обновления.
- **Отсутствие `UNIQUE` на естественных уникальных полях.** ISBN, номер билета, e-mail — дубликаты накопятся.
- **Неверный тип.** Дата в `TEXT`, деньги в `REAL`, «да/нет» в `INT` — теряются проверки и сравнения.
- **Многие-ко-многим без таблицы связи.** Попытка хранить `author_id` прямо в `books` не позволит книге иметь двух авторов.
- **Слишком ранняя денормализация.** Усложняет схему, когда проблем со скоростью ещё не измеряли.
- **Игнорирование поведения при удалении.** Решение «по умолчанию» (`NO ACTION`) стоит принимать осознанно.

## Вопросы с собеседований

:::spoiler Почему «список через запятую» в ячейке — плохо?
Нарушает 1НФ: нельзя эффективно искать и соединять по отдельным значениям, нельзя навесить FK и ограничения, обновление одного элемента требует разбора строки.
:::

:::spoiler Где хранится FK в связи один-ко-многим?
На стороне «многих»: у каждой выдачи есть `reader_id`, у читателя нет списка выдач.
:::

:::spoiler Почему не сделать ISBN первичным ключом?
Естественные ключи меняются (опечатки, переиздания), бывают длинными (дорогие FK и индексы) и не всегда реально уникальны. Суррогатный `id` стабилен, а уникальность ISBN обеспечивает `UNIQUE`.
:::

:::spoiler Объясни 1НФ, 2НФ и 3НФ одной фразой. (ловушка: «чем больше таблиц, тем лучше»)
«Каждый неключевой атрибут зависит от ключа (1НФ — атомарные значения), от всего ключа (2НФ) и ни от чего, кроме ключа (3НФ)». Цель — не число таблиц, а отсутствие дублей и аномалий; чрезмерное дробление усложняет запросы.
:::

:::spoiler Как смоделировать связь «многие-ко-многим»?
Таблицей связи с двумя внешними ключами и составным первичным ключом (`book_authors`). В EF Core это две навигационные коллекции; таблицу связи можно скрыть или описать явной сущностью, если у связи есть собственные поля.
:::

:::spoiler Что такое аномалии вставки, обновления и удаления?
Следствия дублирования: нельзя вставить факт без постороннего (читатель без выдачи), обновление нужно делать во многих местах, удаление одного факта уничтожает другой (книга исчезает вместе с последней выдачей).
:::

:::spoiler Когда оправдана денормализация?
Когда измерения показали, что чтение узкое место, а `JOIN`-ы не помогают. Делается осознанно, с механизмом синхронизации (триггер, фоновая задача, материализованное представление) и поверх нормализованного ядра.
:::

:::spoiler Что выбрать для `ON DELETE` у связи «читатель → выдачи»? Почему?
`RESTRICT`: история выдач не должна пропадать при удалении читателя; вместо удаления используют флаг «неактивен». `CASCADE` уместен для строк, которые не имеют смысла без родителя (`book_authors`).
:::

## Что запомнить

- Каждый факт хранится в одном месте; остальные таблицы ссылаются на него внешним ключом.
- 1НФ — атомарные значения (никаких списков в ячейке); 2НФ — зависимость от всего ключа; 3НФ — нет зависимостей между неключевыми атрибутами.
- Ключ — суррогатный `id`; естественная уникальность (ISBN, e-mail) — через `UNIQUE`.
- Один-ко-многим: FK на стороне «многих»; многие-ко-многим: таблица связи; один-к-одному: FK + `UNIQUE`/общий PK.
- Поведение при удалении выбирай осознанно: `RESTRICT` для бизнес-истории, `CASCADE` для зависимых строк-связей.
- Ограничения (`NOT NULL`, `CHECK`, `UNIQUE`, `REFERENCES`) — часть дизайна и защита от багов в коде.
- FK не индексируется автоматически — индексируй сам; PK и `UNIQUE` индексируются.
- Денормализуй только по результатам измерений.

Запрос, который на 100 строках работает мгновенно, на 10 миллионах может идти минуту. Индекс — главное средство это исправить. Джуну нужно понимать идею, уметь прочитать план запроса (`EXPLAIN`) и знать цену индексов.

## Зачем это нужно

Самая частая жалоба на любое приложение — «тормозит». И в большинстве случаев причина одна и та же: база данных на каждый запрос **читает всю таблицу целиком**, потому что для нужного условия нет индекса. На тестовых данных (десятки строк) это незаметно. В проде, когда в таблице `loans` вырастает 10 миллионов строк, страница «мои выдачи» начинает грузиться десятки секунд.

Индекс решает эту проблему так, как оглавление решает проблему поиска в толстой книге. Но у него есть цена, и «индексировать всё» — тоже ошибка.

Что тебе нужно как Junior:

- **Собеседование.** «Что такое индекс? Как он работает? Когда он не помогает? Чем плох?» — один из самых частых вопросов по БД. Ожидают: B-дерево, O(log n) против O(n), цена записи, составной индекс и порядок колонок.
- **Реальная работа.** Тебе будут приходить задачи «страница медленная». Ты откроешь лог EF Core, найдёшь SQL, выполнишь `EXPLAIN` — и увидишь `Seq Scan` на большой таблице. Дальше — решение в одну строку `CREATE INDEX`.
- **EF Core.** Индексы описываются в модели (`HasIndex`, `[Index]`) и попадают в миграции. Понимание того, *какой* индекс нужен, определяет, что ты в них напишешь.
- **Дизайн запросов.** Некоторые формулировки условий «ломают» индекс (функция над колонкой, `LIKE '%…'`). Знание этого — разница между быстрым и медленным запросом.

## Интуиция и аналогия

**Оглавление и предметный указатель книги.** Чтобы найти слово «рекурсия» в книге на 800 страниц без указателя, придётся перелистать всё (это *sequential scan*). С указателем ты открываешь «Р → рекурсия: стр. 214, 389» и идёшь сразу туда (это *index scan*). Указатель — отдельный список, упорядоченный по слову, со ссылками на страницы.

Цена: указатель занимает место и **его нужно обновлять при каждой правке книги**. Добавил главу — перепечатывай указатель. Чем больше указателей (по авторам, по терминам, по датам), тем дороже любая правка.

**Телефонная книга.** Упорядочена по фамилии, потом по имени. Найти «Петров Иван» — быстро. Найти «всех Иванов» — нельзя без полного перебора: порядок начинается с фамилии. Это объясняет правило порядка колонок в составном индексе.

**Двоичный поиск.** Индекс (B-дерево) устроен как многоуровневый «угадай число»: на каждом уровне отбрасывается подавляющая часть данных. Поэтому поиск растёт как O(log n), а не O(n) — идея та же, что в [бинарном поиске](#p2-algorithms).

## Основная теория по шагам

### Шаг 1. Идея: перебор против индекса

Без индекса база **перебирает всю таблицу** (sequential scan) — это O(n). Индекс — отдельная упорядоченная структура (обычно B-дерево): «значение колонки → где лежат строки». Поиск по нему — O(log n).

Создадим таблицу на 500 000 строк и посмотрим план запроса. Чтобы планы были одинаковыми при каждом запуске, отключим параллельное выполнение и вывод стоимостей; на твоей машине можно смотреть и стоимости.

~~~sql Таблица на 500 000 строк
SET max_parallel_workers_per_gather = 0;

CREATE TABLE big_loans AS
SELECT g AS id,
       (g % 5000) + 1            AS reader_id,
       DATE '2020-01-01' + (g % 2000) AS loaned_at
FROM generate_series(1, 500000) g;
ANALYZE big_loans;

EXPLAIN (COSTS OFF) SELECT * FROM big_loans WHERE reader_id = 42;
~~~
~~~console
         QUERY PLAN         
----------------------------
 Seq Scan on big_loans
   Filter: (reader_id = 42)
(2 rows)
~~~

`Seq Scan` — читается вся таблица, и каждая строка проверяется условием. Теперь добавим индекс:

~~~sql Добавляем индекс
SET max_parallel_workers_per_gather = 0;
CREATE INDEX ix_big_loans_reader_id ON big_loans (reader_id);
ANALYZE big_loans;
EXPLAIN (COSTS OFF) SELECT * FROM big_loans WHERE reader_id = 42;
~~~
~~~console
                    QUERY PLAN                     
---------------------------------------------------
 Bitmap Heap Scan on big_loans
   Recheck Cond: (reader_id = 42)
   ->  Bitmap Index Scan on ix_big_loans_reader_id
         Index Cond: (reader_id = 42)
(4 rows)
~~~

`Bitmap Index Scan` по индексу нашёл адреса нужных строк, `Bitmap Heap Scan` прочитал только их. Из 500 000 строк тронуто около 100.

`EXPLAIN` показывает *план*. `EXPLAIN ANALYZE` выполняет запрос и добавляет **реальные** числа: сколько строк прошло, сколько отброшено, сколько времени заняло. Это основной инструмент:

~~~sql
SET max_parallel_workers_per_gather = 0;
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF) SELECT * FROM big_loans WHERE id = 250000;
~~~
~~~console
                  QUERY PLAN                   
-----------------------------------------------
 Seq Scan on big_loans (actual rows=1 loops=1)
   Filter: (id = 250000)
   Rows Removed by Filter: 499999
(3 rows)
~~~

(Поле `id` здесь без индекса, поэтому вместо индекса читается вся таблица: `Rows Removed by Filter: 499999` — почти полмиллиона строк прочитано ради одной.) Добавим уникальный индекс и повторим:

~~~sql
SET max_parallel_workers_per_gather = 0;
CREATE UNIQUE INDEX ux_big_loans_id ON big_loans (id);
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF) SELECT * FROM big_loans WHERE id = 250000;
~~~
~~~console
                              QUERY PLAN                               
-----------------------------------------------------------------------
 Index Scan using ux_big_loans_id on big_loans (actual rows=1 loops=1)
   Index Cond: (id = 250000)
(2 rows)
~~~

Теперь прочитана ровно одна строка. Время на твоей машине будет своим (запусти `EXPLAIN ANALYZE` без `TIMING OFF` и сравни «Execution Time»): полный перебор 500 000 строк занимает заметные миллисекунды, поиск по индексу — доли миллисекунды, а на десятках миллионов строк это секунды против миллисекунд. Поэтому ориентируйся на *количество прочитанных строк* и стоимость в плане, а не на секундомер.

### Шаг 2. Где индексы нужны

- **Первичный ключ и `UNIQUE`** — индекс создаётся автоматически.
- **Внешние ключи** — в PostgreSQL индекс на FK **не создаётся автоматически**. JOIN-ы по `loans.reader_id` и `loans.book_id` без индекса будут медленными. EF Core при миграциях создаёт индексы на FK сам.
- Колонки из частых `WHERE`, `JOIN`, `ORDER BY` на больших таблицах.
- **Составной индекс** `(reader_id, loaned_at)` помогает запросам по `reader_id` и по `reader_id + loaned_at`, но не по одному `loaned_at`: важен порядок колонок.

Проверим правило порядка колонок:

~~~sql
SET max_parallel_workers_per_gather = 0;
CREATE INDEX ix_big_loans_reader_date ON big_loans (reader_id, loaned_at);
ANALYZE big_loans;

-- условие по первой колонке и по обеим — индекс подходит
EXPLAIN (COSTS OFF) SELECT * FROM big_loans WHERE reader_id = 42 AND loaned_at = DATE '2021-06-01';

-- условие только по второй колонке — индекс используется неэффективно (см. ниже)
EXPLAIN (COSTS OFF) SELECT * FROM big_loans WHERE loaned_at = DATE '2021-06-01';
~~~
~~~console
                              QUERY PLAN                               
-----------------------------------------------------------------------
 Index Scan using ix_big_loans_reader_date on big_loans
   Index Cond: ((reader_id = 42) AND (loaned_at = '2021-06-01'::date))
(2 rows)

                      QUERY PLAN                      
------------------------------------------------------
 Bitmap Heap Scan on big_loans
   Recheck Cond: (loaned_at = '2021-06-01'::date)
   ->  Bitmap Index Scan on ix_big_loans_reader_date
         Index Cond: (loaned_at = '2021-06-01'::date)
(4 rows)
~~~

Во втором плане PostgreSQL всё же использовал составной индекс, но он вынужден **просканировать его целиком** (оценка «сколько листьев прочитать» не ограничена первой колонкой) — на большой таблице это заметно дороже, чем поиск по индексу, начинающемуся с `loaned_at`. Индекс «используется» и «используется эффективно» — не одно и то же: смотри на `Index Cond` и на реальное число прочитанных страниц (`EXPLAIN (ANALYZE, BUFFERS)`).

Правило: в составном индексе первыми ставят колонки, по которым **чаще проверяют равенство**, а затем — колонки диапазона и сортировки. Индекс по `(reader_id, loaned_at)` обслуживает и запрос «выдачи читателя, отсортированные по дате» без отдельной сортировки.

### Шаг 3. Что ломает индекс

Функция над колонкой скрывает значение от индекса:

~~~sql
SET max_parallel_workers_per_gather = 0;
CREATE TABLE titles AS
SELECT g AS id, 'Книга номер ' || g AS title FROM generate_series(1, 200000) g;
CREATE INDEX ix_titles_title ON titles (title);
ANALYZE titles;

-- обычный индекс не помогает при lower(...)
EXPLAIN (COSTS OFF) SELECT * FROM titles WHERE lower(title) = 'книга номер 777';

-- индекс по выражению — помогает
CREATE INDEX ix_titles_lower ON titles (lower(title));
ANALYZE titles;
EXPLAIN (COSTS OFF) SELECT * FROM titles WHERE lower(title) = 'книга номер 777';
~~~
~~~console
                     QUERY PLAN                     
----------------------------------------------------
 Seq Scan on titles
   Filter: (lower(title) = 'книга номер 777'::text)
(2 rows)

                       QUERY PLAN                       
--------------------------------------------------------
 Index Scan using ix_titles_lower on titles
   Index Cond: (lower(title) = 'книга номер 777'::text)
(2 rows)
~~~

Другие «убийцы» индекса:

- `LIKE '%слово'` — шаблон с подстановкой в начале нельзя искать по упорядоченному индексу (`LIKE 'слово%'` — можно, при подходящей коллации/классе оператора).
- Неявное приведение типов (`WHERE text_column = 123`).
- Условие `OR` по разным колонкам и отрицания (`<>`, `NOT IN`) — часто приводят к полному перебору.
- `SELECT *` лишает возможности взять данные только из индекса (index-only scan).

### Шаг 4. Частичные, уникальные и покрывающие индексы

Индекс можно построить не по всей таблице, а по части строк. Для библиотеки типичный вопрос — «какие книги сейчас на руках?»; таких выдач немного, а возвращённых — большинство:

~~~sql
SET max_parallel_workers_per_gather = 0;
-- индекс только по «живым» выдачам
CREATE INDEX ix_loans_active ON loans (book_id) WHERE returned_at IS NULL;

SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'loans' ORDER BY indexname;
~~~
~~~console
    indexname    |                                            indexdef                                            
-----------------+------------------------------------------------------------------------------------------------
 ix_loans_active | CREATE INDEX ix_loans_active ON public.loans USING btree (book_id) WHERE (returned_at IS NULL)
 loans_pkey      | CREATE UNIQUE INDEX loans_pkey ON public.loans USING btree (id)
(2 rows)
~~~

Частичный индекс меньше, дешевле в обновлении и точно отвечает частому запросу. `UNIQUE` индекс можно сделать условным: «у книги может быть только одна активная выдача на экземпляр» и т. п. — так выражают бизнес-правила на уровне базы.

Покрывающий индекс хранит дополнительные колонки (`INCLUDE`), чтобы запрос обошёлся одним индексом без чтения таблицы:

~~~sql
SET max_parallel_workers_per_gather = 0;
CREATE INDEX ix_big_loans_cover ON big_loans (reader_id) INCLUDE (loaned_at);
VACUUM ANALYZE big_loans;
EXPLAIN (COSTS OFF) SELECT loaned_at FROM big_loans WHERE reader_id = 42;
~~~
~~~console
                      QUERY PLAN                       
-------------------------------------------------------
 Index Only Scan using ix_big_loans_cover on big_loans
   Index Cond: (reader_id = 42)
(2 rows)
~~~

`Index Only Scan` — таблица не читалась вовсе. Это продвинутый приём; для Junior важно знать, что он существует.

### Шаг 5. Цена индексов

- Каждый `INSERT`/`UPDATE`/`DELETE` обновляет **все** индексы таблицы → запись медленнее.
- Индексы занимают место на диске и в памяти.
- Индекс по колонке с двумя-тремя значениями (`reader_type`) часто бесполезен: база всё равно предпочтёт полный перебор.
- Функция над колонкой ломает индекс: `WHERE lower(title) = 'идиот'` не использует индекс по `title` (нужен индекс по выражению `lower(title)`).

Посмотрим, сколько места занимают данные и индексы нашей таблицы:

~~~sql
SELECT pg_size_pretty(pg_relation_size('big_loans')) AS table_size,
       pg_size_pretty(pg_indexes_size('big_loans'))  AS all_indexes_size;
~~~
~~~console
 table_size | all_indexes_size 
------------+------------------
 22 MB      | 28 MB
(1 row)
~~~

Четыре индекса занимают больше места, чем сама таблица, и каждый из них нужно обновлять при вставке. Поэтому правило такое: **индексируй по запросам, а не «на всякий случай»**, и периодически удаляй неиспользуемые (`pg_stat_user_indexes` показывает, к каким индексам обращались).

:::deep Граница
Внутреннее устройство B-дерева на страницах диска, GIN/GiST/BRIN, покрывающие индексы, статистика планировщика — уровень middle/senior. Для junior достаточно: «индекс — это отсортированная структура для поиска, у него есть цена, проверяю через EXPLAIN».
:::

### Шаг 6. Рабочий алгоритм «запрос медленный»

1. Найди конкретный медленный SQL (лог EF Core, `pg_stat_statements`, профилировщик).
2. Выполни `EXPLAIN (ANALYZE)` на реалистичных данных (не на 10 строках!).
3. Ищи `Seq Scan` на большой таблице с условием, а также большие значения «Rows Removed by Filter».
4. Проверь, нет ли функции над колонкой и неявного приведения типов.
5. Создай индекс под условие `WHERE` и порядок `ORDER BY`; для JOIN — индекс на внешний ключ.
6. Повтори `EXPLAIN ANALYZE`, убедись, что индекс использован и запрос ускорился.
7. Оцени цену: сколько индексов уже есть, как часто таблица пишется.
8. Закрепи индекс миграцией (в EF Core — `HasIndex`), а не ручной командой на проде.

## Как это работает под капотом

- **B-дерево.** Индекс — сбалансированное дерево страниц по 8 КБ. В корне и промежуточных страницах — диапазоны ключей, в листьях — ключи и адреса строк (TID). Глубина обычно 3–4 уровня даже для сотен миллионов строк, отсюда O(log n) и почти постоянная скорость поиска. Листья связаны между собой, поэтому диапазоны (`BETWEEN`, `ORDER BY`) читаются последовательно.
- **Планировщик выбирает сам.** Использовать индекс или нет, решает планировщик по **статистике** (`ANALYZE` собирает распределение значений). Если условию удовлетворяет 40% строк, перебор таблицы дешевле, чем 200 000 прыжков по индексу, — индекс игнорируется, и это правильно.
- **Селективность.** Индекс полезен, когда условие отбирает малую долю строк. Колонка с двумя значениями (`reader_type`) почти бесполезна; уникальный `id` — идеальна.
- **Версии строк и индекс.** При `UPDATE` PostgreSQL создаёт новую версию строки, и индексы нужно обновлять (если не сработала оптимизация HOT). Много индексов на часто обновляемых колонках — дорого.
- **Index-only scan** возможен, если все нужные колонки есть в индексе, а страницы таблицы помечены в карте видимости (`VACUUM`).
- **Типы индексов.** B-дерево (по умолчанию) — равенство и диапазоны; Hash — только равенство; GIN — для массивов, JSONB, полнотекстового поиска; GiST — геоданные, диапазоны; BRIN — огромные упорядоченные таблицы. Для начала нужен только B-дерево.
- **В EF Core.** `modelBuilder.Entity<Loan>().HasIndex(l => new { l.ReaderId, l.LoanedAt })`, `.IsUnique()`, `.HasFilter("returned_at IS NULL")`. Индекс на внешний ключ EF создаёт по соглашению.
- **Блокировки.** Обычный `CREATE INDEX` блокирует запись в таблицу; на проде используют `CREATE INDEX CONCURRENTLY` (дольше, но без блокировки).

## Типичные ошибки и ловушки

- **Отсутствие индекса на внешнем ключе.** JOIN и удаление родителя читают всю таблицу детей.
- **Индекс «на всякий случай» на каждую колонку.** Замедляет запись, занимает место, часто не используется.
- **Индекс по колонке с малым числом значений.** Планировщик его проигнорирует.
- **Функция над индексированной колонкой** (`lower(title)`, `date(created_at)`, `year + 1 = 2027`). Либо индекс по выражению, либо перепиши условие так, чтобы колонка осталась «голой».
- **`LIKE '%текст%'`.** Обычный индекс не поможет; нужен триграммный индекс (`pg_trgm`) или полнотекстовый поиск.
- **Неверный порядок колонок в составном индексе.** `(loaned_at, reader_id)` не поможет запросу по одному `reader_id`.
- **Оптимизация без измерений.** Индекс «наугад» без `EXPLAIN` на реалистичных данных.
- **Тестирование на 10 строках.** Планировщик всегда выберет перебор: на малой таблице он быстрее. Заполни таблицу сотнями тысяч строк.
- **Устаревшая статистика.** После массовой загрузки забыли `ANALYZE`, и планировщик выбирает плохой план.
- **Забыли `CONCURRENTLY` на проде.** Индекс блокирует запись на время построения.
- **Дублирующие индексы.** Индекс `(reader_id)` лишний, если уже есть `(reader_id, loaned_at)`.
- **Индекс вместо исправления запроса.** `SELECT *` с `OFFSET 1000000` индексом не спасти; нужна другая стратегия пагинации.

## Вопросы с собеседований

:::spoiler Почему индекс ускоряет поиск, но замедляет вставку?
Поиск идёт по упорядоченной структуре за O(log n) вместо полного перебора. Но при каждой вставке/изменении эту структуру нужно обновить.
:::

:::spoiler Создаёт ли PostgreSQL индекс на внешний ключ?
Нет. Индекс автоматически создаётся только для PRIMARY KEY и UNIQUE. На FK его нужно создать самому (EF Core делает это в миграциях).
:::

:::spoiler Поможет ли индекс `(reader_id, loaned_at)` запросу `WHERE loaned_at > '2026-01-01'`?
Как правило, нет: B-дерево упорядочено сначала по `reader_id`, и без условия на первую колонку им пользоваться неэффективно.
:::

:::spoiler Что такое B-дерево и какая сложность поиска по нему? (ловушка: «это просто хэш-таблица»)
Сбалансированное дерево страниц с упорядоченными ключами; поиск O(log n), поддерживает равенство и диапазоны, сортировку. Хэш-индекс умеет только равенство.
:::

:::spoiler Почему индекс может не использоваться, даже когда он есть?
Условие не селективно (отбирает большую долю строк), на колонке стоит функция, неявное приведение типов, порядок колонок составного индекса не подходит, статистика устарела, таблица слишком мала.
:::

:::spoiler Как прочитать `EXPLAIN`? На что смотреть в первую очередь?
На тип узла (`Seq Scan` / `Index Scan` / `Bitmap`), оценку и реальное число строк, `Rows Removed by Filter` и время в `EXPLAIN ANALYZE`. `Seq Scan` на большой таблице с селективным условием — кандидат на индекс.
:::

:::spoiler Что такое покрывающий и частичный индекс?
Покрывающий хранит дополнительные колонки (`INCLUDE`), позволяя ответить на запрос без чтения таблицы. Частичный строится по подмножеству строк (`WHERE returned_at IS NULL`) — меньше и быстрее.
:::

:::spoiler Чем кластерный индекс SQL Server отличается от индексов PostgreSQL?
В SQL Server таблица может физически храниться упорядоченной по кластерному индексу (по умолчанию — PK). В PostgreSQL таблица — «куча», все индексы вторичные; команда `CLUSTER` лишь разово переупорядочивает данные.
:::

## Что запомнить

- Индекс — отсортированная структура (B-дерево): поиск O(log n) вместо перебора O(n), но каждая запись обновляет все индексы.
- PK и `UNIQUE` индексируются автоматически; внешние ключи в PostgreSQL — **нет**, индексируй сам.
- Порядок колонок в составном индексе важен: работает «слева направо» (телефонная книга).
- Функция над колонкой, `LIKE '%…'`, неявные приведения ломают индекс; лекарство — индекс по выражению или правка условия.
- Индекс полезен только для селективных условий; планировщик решает по статистике (`ANALYZE`).
- Читай `EXPLAIN (ANALYZE)` на реалистичных объёмах; ищи `Seq Scan` и `Rows Removed by Filter`.
- Индексируй по реальным запросам, не «на всякий случай»; на проде — `CONCURRENTLY`.
- В EF Core индексы описываются в модели и попадают в миграции.

## Зачем это нужно

Большинство бизнес-операций — это **несколько** изменений данных, которые должны пройти вместе. Перевод денег — списать с одного счёта и зачислить на другой. Выдача книги — создать запись выдачи и уменьшить остаток. Оформление заказа — заказ, позиции, резерв товара, платёж. Если между шагами что-то сломается (ошибка, отключение света, падение сервера), без транзакции в базе останется «полуоперация»: деньги списаны и не зачислены, книга выдана, а остаток не уменьшился.

Транзакция даёт гарантию «всё или ничего» и позволяет рассуждать о коде как о едином действии. Вторая половина темы — **параллельность**: в проде одновременно работают сотни запросов, и без понимания изоляции они незаметно портят данные (классика — две покупки одного последнего билета).

Что важно Junior .NET:

- **Собеседование.** «Что такое ACID? Какие уровни изоляции знаешь? Что такое dirty/non-repeatable/phantom read? Как избежать гонки при списании остатка?» — вопросы почти гарантированы.
- **Каждодневный код.** `SaveChanges` в EF Core — это транзакция; ты решаешь, когда нужна явная, как обрабатывать конфликты (`DbUpdateConcurrencyException`), когда повторять.
- **Баги, которые не воспроизвести на ноутбуке.** Гонки проявляются только под нагрузкой и стоят денег. Знание типичных схем (блокировка, атомарный `UPDATE`, оптимистичная конкурентность) отличает того, кто «пишет работающий код», от того, кто «пишет корректный код».

## Интуиция и аналогия

**Банкомат.** Ты снимаешь деньги: банкомат должен списать сумму со счёта *и* выдать купюры. Если пропадёт питание посередине, то после перезагрузки должно быть либо «списано и выдано», либо «ничего не произошло» — но не «списано, а денег нет». Это **атомарность**.

**Бухгалтерская книга и ластик.** Транзакция — страница черновика: пока ты не поставил печать (`COMMIT`), никто чужой не видит правок, и ты можешь вырвать лист (`ROLLBACK`). После печати запись постоянна даже при пожаре в офисе (**долговечность**).

**Очередь в кассу и последний билет.** Две кассирши смотрят на один экран с надписью «осталось 1 билет». Обе видят «1», обе продают. Итог — два проданных билета на одно место. Чтобы так не вышло, нужно либо повесить на билет «занято, подожди» (блокировка), либо проверять и продавать одним неделимым действием (атомарный `UPDATE`), либо обнаруживать конфликт и повторять (оптимистичная конкурентность).

**Изоляция — окно в чужую работу.** Чем строже уровень изоляции, тем меньше ты видишь чужих незавершённых изменений — но тем больше ожиданий и конфликтов. Нет «правильного» уровня, есть компромисс между скоростью и строгостью.

## Основная теория по шагам

### Шаг 1. ACID

- **Atomicity** — всё или ничего.
- **Consistency** — после транзакции соблюдены все ограничения.
- **Isolation** — параллельные транзакции не мешают друг другу (в разной степени).
- **Durability** — после `COMMIT` данные не пропадут даже при сбое.

~~~sql Всё или ничего
BEGIN;
UPDATE books SET copies = copies - 10 WHERE id = 1;
ROLLBACK;

SELECT copies FROM books WHERE id = 1;
~~~
~~~console
ERROR:  new row for relation "books" violates check constraint "books_copies_check"
DETAIL:  Failing row contains (1, 978-5-01, Мастер и Маргарита, Роман, 1967, -7).
 copies 
--------
      3
(1 row)
~~~

Первая команда нарушила `CHECK (copies >= 0)` и вернула ошибку; `ROLLBACK` завершил транзакцию, и в таблице осталось прежнее значение 3 (даже без ошибки `ROLLBACK` отменил бы все изменения). Посмотрим, что происходит при ошибке внутри транзакции: PostgreSQL помечает транзакцию как «сломанную» и отвергает всё дальнейшее до `ROLLBACK`.

~~~sql
BEGIN;
UPDATE books SET copies = copies - 10 WHERE id = 1;
SELECT 1;
ROLLBACK;
~~~
~~~console
ERROR:  new row for relation "books" violates check constraint "books_copies_check"
DETAIL:  Failing row contains (1, 978-5-01, Мастер и Маргарита, Роман, 1967, -7).
ERROR:  current transaction is aborted, commands ignored until end of transaction block
~~~

Каждая одиночная команда в PostgreSQL уже выполняется в своей транзакции. Явный `BEGIN … COMMIT` нужен, когда **несколько** команд должны пройти вместе.

### Шаг 2. Классика: перевод денег

~~~sql
CREATE TABLE accounts (id INT PRIMARY KEY, owner TEXT NOT NULL, balance NUMERIC(12,2) NOT NULL CHECK (balance >= 0));
INSERT INTO accounts VALUES (1, 'Анна', 100), (2, 'Борис', 50);

-- успешный перевод: оба изменения вместе
BEGIN;
UPDATE accounts SET balance = balance - 30 WHERE id = 1;
UPDATE accounts SET balance = balance + 30 WHERE id = 2;
COMMIT;

SELECT owner, balance FROM accounts ORDER BY id;
~~~
~~~console
 owner | balance 
-------+---------
 Анна  |   70.00
 Борис |   80.00
(2 rows)
~~~

Теперь попытка перевести больше, чем есть: первое `UPDATE` нарушит `CHECK`, и вся транзакция откатится, второе списание даже не применится:

~~~sql
BEGIN;
UPDATE accounts SET balance = balance - 500 WHERE id = 1;
UPDATE accounts SET balance = balance + 500 WHERE id = 2;
COMMIT;
SELECT owner, balance FROM accounts ORDER BY id;
~~~
~~~console
ERROR:  new row for relation "accounts" violates check constraint "accounts_balance_check"
DETAIL:  Failing row contains (1, Анна, -430.00).
ERROR:  current transaction is aborted, commands ignored until end of transaction block
 owner | balance 
-------+---------
 Анна  |   70.00
 Борис |   80.00
(2 rows)
~~~

Обрати внимание: `COMMIT` после ошибки выполнился как `ROLLBACK` — в консоли ничего не изменилось. Никакой ручной «компенсации» из проекта Фазы 1 не нужно: за откат отвечает база.

Частичный откат внутри транзакции — **точка сохранения**:

~~~sql
BEGIN;
UPDATE accounts SET balance = balance + 1 WHERE id = 1;
SAVEPOINT before_risky;
UPDATE accounts SET balance = balance - 1000 WHERE id = 1;   -- нарушит CHECK
ROLLBACK TO SAVEPOINT before_risky;                          -- откатили только второй шаг
COMMIT;
SELECT balance FROM accounts WHERE id = 1;
~~~
~~~console
ERROR:  new row for relation "accounts" violates check constraint "accounts_balance_check"
DETAIL:  Failing row contains (1, Анна, -929.00).
 balance 
---------
   71.00
(1 row)
~~~

### Шаг 3. Гонка: последний экземпляр двум читателям

Сценарий «выдать книгу» в приложении: 1) посчитать, сколько экземпляров на руках; 2) если меньше `copies` — вставить выдачу. У книги «Идиот» 1 экземпляр.

~~~text Две параллельные сессии без блокировки
 Сессия A                                   Сессия B
 count(на руках) → 0, свободно 1
                                            count(на руках) → 0, свободно 1
 INSERT loan (Анна)
                                            INSERT loan (Борис)
 COMMIT                                     COMMIT
 Итог: одна книга выдана двоим ❌
~~~

Транзакции сами по себе это не лечат: на уровне Read Committed (по умолчанию в PostgreSQL) обе сессии видят «свободен 1». Нужна **блокировка** строки книги:

~~~sql Выдача с блокировкой @nocheck
BEGIN;
SELECT copies FROM books WHERE id = 4 FOR UPDATE;          -- вторая сессия будет ждать здесь
SELECT count(*) FROM loans WHERE book_id = 4 AND returned_at IS NULL;
-- приложение сравнивает и, если свободно:
INSERT INTO loans (book_id, reader_id, loaned_at, due_at)
VALUES (4, 4, DATE '2026-10-13', DATE '2026-10-27');
COMMIT;                                                    -- блокировка снимается
~~~

`FOR UPDATE` блокирует строку книги до конца транзакции: вторая выдача той же книги дождётся окончания первой и увидит уже вставленную выдачу.

Есть и способ без явных блокировок — **атомарный `UPDATE` с условием**. Идея: проверку и изменение выполняет одна команда, а `RETURNING` сообщает результат:

~~~sql
-- модель: на книге хранится счётчик свободных экземпляров
ALTER TABLE books ADD COLUMN available INT NOT NULL DEFAULT 0 CHECK (available >= 0);
UPDATE books SET available = copies;

-- «взять экземпляр»: уменьшится только если есть что уменьшать
UPDATE books SET available = available - 1 WHERE id = 4 AND available > 0 RETURNING id, available;
-- второй читатель получает пустой результат — книги больше нет
UPDATE books SET available = available - 1 WHERE id = 4 AND available > 0 RETURNING id, available;
~~~
~~~console
 id | available 
----+-----------
  4 |         0
(1 row)

 id | available 
----+-----------
(0 rows)
~~~

Первая команда вернула строку (успех), вторая — пустой результат (0 затронутых строк): приложение понимает, что экземпляров нет. Параллельные сессии сериализуются на блокировке строки автоматически, поэтому двое не «проскочат». Это самый простой и быстрый способ защитить счётчик.

Реальная гонка — не гипотеза. Вот запись настоящего эксперимента (две сессии `psql`, таблица `accounts` с балансом 100): сессия A читает баланс и спит, сессия B прибавляет 20 и фиксирует, затем A записывает «своё» вычисленное значение:

~~~text Потерянное обновление (lost update) на Read Committed
 Сессия A                                   Сессия B
 BEGIN;
 SELECT balance → 100
                                            UPDATE ... SET balance = balance + 20; COMMIT;
 UPDATE ... SET balance = 100 + 10;   ← считали на клиенте
 COMMIT;
 Итог: balance = 110, а должно быть 130 — «+20» потерялось ❌
~~~

Лекарство: не вычислять значение в приложении (`SET balance = balance + 10` — атомарно), или блокировать (`FOR UPDATE`), или использовать версию строки (оптимистичная конкурентность).

### Шаг 4. Уровни изоляции — практическая шпаргалка

| Уровень | Что гарантирует | Когда вспоминать |
|---|---|---|
| Read Committed (**по умолчанию** в PostgreSQL и SQL Server) | видишь только закоммиченные данные; повторный SELECT может увидеть новые изменения | почти всегда достаточно + точечные блокировки `FOR UPDATE` |
| Repeatable Read | в рамках транзакции видишь снимок на момент её начала | отчёты, которые должны быть согласованными |
| Serializable | результат как при последовательном выполнении; база может отменить транзакцию с ошибкой сериализации — её нужно повторить | сложные инварианты, где проще повторить, чем блокировать |

Феномены, которые нужно уметь назвать: **non-repeatable read** (повторное чтение дало другое значение), **phantom read** (повторный запрос вернул новые строки), **lost update** (два «прочитал-изменил-записал» затёрли друг друга). Dirty read (чтение незакоммиченного) PostgreSQL не допускает ни на каком уровне.

~~~sql
SHOW transaction_isolation;
BEGIN ISOLATION LEVEL REPEATABLE READ;
SHOW transaction_isolation;
COMMIT;
~~~
~~~console
 transaction_isolation 
-----------------------
 read committed
(1 row)

 transaction_isolation 
-----------------------
 repeatable read
(1 row)
~~~

Запись эксперимента на `Repeatable Read`: сессия A открыла транзакцию и дважды читает баланс (50 и снова 50, хотя сессия B между чтениями поставила 70 и зафиксировала — снимок не меняется). Когда A пытается изменить строку, уже изменённую другой фиксацией, PostgreSQL отвечает ошибкой, и приложение должно повторить транзакцию целиком:

~~~text Repeatable Read: снимок и конфликт
 A: BEGIN ISOLATION LEVEL REPEATABLE READ; SELECT balance → 50
 B: UPDATE ... SET balance = 70; (коммит)
 A: SELECT balance → 50          ← тот же снимок
 A: UPDATE ... SET balance = balance - 1;
 ERROR:  could not serialize access due to concurrent update
~~~

:::deep Граница
MVCC, снимки, VACUUM, точные различия реализаций уровней в разных СУБД — это та самая «яма на годы». Для junior: транзакция для группы изменений, `FOR UPDATE` или атомарный `UPDATE ... WHERE` для гонок, Read Committed по умолчанию.
:::

### Шаг 5. Транзакции в EF Core (забегая вперёд)

~~~csharp @nocheck
// Один SaveChanges() — уже одна транзакция для всех накопленных изменений.
// Явная транзакция нужна, если между шагами есть логика или несколько SaveChanges:
await using var tx = await db.Database.BeginTransactionAsync();
// ... изменения, SaveChangesAsync() ...
await tx.CommitAsync();       // без Commit при выходе из using будет откат
~~~

Что полезно знать заранее:

- `SaveChanges()` сам открывает транзакцию, если её нет, и откатывает при исключении.
- Для повторяемых сценариев с конфликтами используют **стратегию повторов** (`EnableRetryOnFailure`) — но тогда явные транзакции оборачивают в `strategy.ExecuteAsync(...)`.
- **Оптимистичная конкурентность:** колонка-версия (`[Timestamp]`/`IsRowVersion`, в PostgreSQL — системный столбец `xmin` через `UseXminAsConcurrencyToken`). При `UPDATE ... WHERE id = @id AND version = @old` затронуто 0 строк → `DbUpdateConcurrencyException`, и приложение решает: перечитать и повторить.
- **Пессимистичная блокировка** в EF Core выражается сырым SQL (`FromSqlRaw("... FOR UPDATE")`).

### Шаг 6. Дедлоки и блокировки

Две транзакции могут заблокировать друг друга: A держит строку 1 и ждёт строку 2, B держит строку 2 и ждёт строку 1. PostgreSQL обнаруживает цикл (через секунду-две) и отменяет одну из транзакций ошибкой `deadlock detected`. Защита:

- **Единый порядок блокировок:** всегда берём строки в одном порядке (например, по возрастанию `id`; в переводе денег — сначала счёт с меньшим номером).
- **Короткие транзакции:** никаких сетевых вызовов и ожиданий пользователя внутри.
- **Повтор при ошибке:** deadlock/serialization failure — повод повторить транзакцию, а не показать пользователю 500.

Посмотреть текущие блокировки можно в `pg_locks` / `pg_stat_activity`; но на этом уровне достаточно помнить принципы.

## Как это работает под капотом

- **MVCC (многоверсионность).** PostgreSQL не перезаписывает строку на месте: `UPDATE` создаёт новую версию, старая остаётся для тех, кто начал читать раньше. Каждая транзакция видит «снимок» — набор версий, подходящих ей по номерам транзакций. Поэтому **читатели не блокируют писателей и наоборот**. Устаревшие версии убирает `VACUUM`.
- **WAL (журнал).** Перед изменением данных база записывает намерение в журнал на диск. `COMMIT` возвращает управление после сброса журнала — это и есть durability: после сбоя сервер проигрывает журнал и восстанавливает зафиксированное.
- **Блокировки строк.** `UPDATE`/`DELETE`/`SELECT ... FOR UPDATE` берут блокировку строки; конфликтующая транзакция ждёт, пока владелец завершится. Блокировки снимаются только при `COMMIT`/`ROLLBACK`.
- **Read Committed** делает новый снимок на каждую *команду*, поэтому два `SELECT` подряд могут видеть разное; **Repeatable Read** — один снимок на всю транзакцию; **Serializable** (SSI) отслеживает опасные зависимости чтения/записи и отменяет одну из транзакций.
- **Последовательности не откатываются.** `identity` и `nextval` — вне транзакции, поэтому в нумерации появляются «дыры».
- **Длинные транзакции вредят.** Они держат блокировки, не дают `VACUUM` убирать старые версии (таблицы «пухнут»). Держи транзакции короткими.
- **Разница СУБД.** SQL Server по умолчанию использует блокировочный Read Committed (читатель может ждать писателя), если не включён `READ_COMMITTED_SNAPSHOT`; PostgreSQL — снимочный. Поведение «одного и того же» уровня зависит от СУБД.
- **EF Core.** `SaveChanges` = транзакция вокруг пачки команд; параллельные запросы из разных `DbContext` — разные транзакции; `DbContext` не потокобезопасен.

## Типичные ошибки и ловушки

- **«Прочитал → вычислил в C# → записал».** Классическая потеря обновления. Делай изменения в одной команде (`SET x = x - 1`), под блокировкой или с версией.
- **Проверка остатка отдельным запросом.** Гонка «последний экземпляр двоим»; нужен атомарный `UPDATE ... WHERE available > 0` или `FOR UPDATE`.
- **Длинные транзакции.** Открыл транзакцию, сходил во внешний API, ждёшь пользователя — блокировки висят минутами.
- **Нет транзакции вокруг связанных шагов.** Два `SaveChanges` подряд без общей транзакции — между ними возможен сбой.
- **Проглатывание ошибки внутри транзакции.** В PostgreSQL после ошибки транзакция «сломана»; `catch` без `ROLLBACK` оставляет её висеть.
- **Разный порядок блокировок.** Источник дедлоков; блокируй в едином порядке.
- **Ожидание «чудес» от высокого уровня изоляции.** `Serializable` не отменяет необходимость повторять транзакцию при ошибке сериализации.
- **Ретраи неидемпотентных операций.** Повторив «отправить письмо» вместе с транзакцией, получишь два письма; внешние побочные эффекты выноси за границы транзакции.
- **Отключение ограничений ради «скорости».** Целостность держится на ограничениях и транзакциях вместе.
- **Использование транзакции как «блокировки на время работы пользователя».** Для этого есть оптимистичная конкурентность с версией.
- **Путаница уровней по СУБД.** То, что работает в PostgreSQL, может вести себя иначе в SQL Server.

## Вопросы с собеседований

:::spoiler Почему одна транзакция не спасает от выдачи последнего экземпляра двоим?
На Read Committed обе транзакции читают закоммиченное состояние, где выдачи ещё нет, и обе решают, что книга свободна. Нужна блокировка (`FOR UPDATE`), атомарная проверка в одном `UPDATE ... WHERE`, ограничение в базе или более строгий уровень изоляции с повтором.
:::

:::spoiler Что делает `SaveChanges` в EF Core с точки зрения транзакций?
Отправляет все накопленные изменения в одной транзакции: либо все применятся, либо ни одно.
:::

:::spoiler Расшифруй ACID. (ловушка: «просто атомарность»)
Atomicity — всё или ничего; Consistency — ограничения соблюдены до и после; Isolation — параллельные транзакции не мешают друг другу в заданной степени; Durability — зафиксированное не пропадёт при сбое.
:::

:::spoiler Назови феномены чтения и какой уровень изоляции от каких защищает.
Dirty read (чтение незакоммиченного), non-repeatable read (другое значение при повторе), phantom read (новые строки при повторе), lost update. Read Committed защищает от dirty read; Repeatable Read — ещё и от non-repeatable (в PostgreSQL и от phantom благодаря снимку); Serializable — от всех аномалий. Реализации зависят от СУБД.
:::

:::spoiler Что такое дедлок и как его избежать?
Циклическое ожидание блокировок двумя транзакциями; СУБД отменяет одну. Избегать: единый порядок блокировок, короткие транзакции, повтор при ошибке `deadlock detected`.
:::

:::spoiler Пессимистичная и оптимистичная конкурентность — в чём разница?
Пессимистичная: блокируем данные заранее (`FOR UPDATE`), конкуренты ждут. Оптимистичная: не блокируем, но проверяем версию при записи; при конфликте — исключение и повтор. Оптимистичная лучше при редких конфликтах и длинных пользовательских операциях.
:::

:::spoiler Как безопасно уменьшить остаток товара под нагрузкой?
`UPDATE items SET qty = qty - 1 WHERE id = @id AND qty > 0` и проверить число затронутых строк (или `RETURNING`). Атомарно, без отдельного чтения.
:::

:::spoiler Что такое MVCC и чем хорош?
Многоверсионность: изменение создаёт новую версию строки, читатели видят снимок. Читатели не блокируют писателей, и наоборот. Цена — уборка старых версий (`VACUUM`).
:::

## Что запомнить

- Транзакция = «всё или ничего»: `BEGIN` … `COMMIT`/`ROLLBACK`; одиночная команда уже транзакция; `SaveChanges` в EF Core — тоже.
- ACID: атомарность, согласованность, изоляция, долговечность.
- Гонки «прочитал-вычислил-записал» теряют обновления; лечение — атомарный `UPDATE … SET x = x - 1 WHERE …`, `FOR UPDATE`, версия строки.
- Read Committed (по умолчанию) — каждая команда видит свежий снимок; Repeatable Read — один снимок на транзакцию; Serializable — как будто по очереди, с повтором при конфликте.
- Феномены: non-repeatable read, phantom read, lost update; dirty read в PostgreSQL невозможен.
- Дедлоки: единый порядок блокировок, короткие транзакции, повтор при ошибке.
- Внешние побочные эффекты (письма, платежи) не помещай в повторяемую транзакцию.
- Оптимистичная конкурентность в EF Core: версия строки + `DbUpdateConcurrencyException`.
