Инкапсуляция — это не «поля приватные, а геттеры публичные». Это гарантия того, что **объект невозможно привести в невалидное состояние** извне. В банковском проекте это значит: баланс нельзя поменять в обход операций, а у операции всегда есть след в истории. Здесь же — ответ на вопрос собеседования «зачем свойства, если есть публичные поля».
:::

## Зачем это нужно

Программа из сотен классов живёт долго, и её пишут разные люди (в том числе ты — через полгода, уже забыв, как всё устроено). В такой программе самый дорогой тип багов — **«объект оказался в состоянии, в котором не должен быть»**: отрицательный остаток, заказ без товаров, но «оплаченный», пользователь без e-mail, бронирование, где выезд раньше заезда.

Источник этих багов почти всегда один: правила знает только автор класса, а менять данные может кто угодно. Чем больше мест в коде напрямую трогают поля, тем больше мест нужно проверить при каждом изменении правил. Инкапсуляция решает проблему радикально: **правила живут рядом с данными, а доступ к данным возможен только через методы, которые эти правила соблюдают**.

Что ты получаешь на практике:

- ошибку находит конструктор или метод в момент нарушения, а не бухгалтерия через неделю;
- правило записано в **одном** месте — меняешь его там, и вся программа подчиняется;
- класс можно менять изнутри (хранить баланс иначе, добавить кэш), не ломая тех, кто им пользуется;
- класс легко тестировать: его публичный контракт — это то, что надо проверить.

Эта тема — основа для всего ООП на собеседовании: «что такое инкапсуляция», «зачем свойства», «чем `private set` отличается от `init`», «как защитить коллекцию» — стандартные вопросы.

## Интуиция и аналогия

Банкомат. Внутри — касса с наличными (данные). Снаружи — экран и кнопки (публичный интерфейс): «снять», «пополнить», «показать баланс». Ты не можешь залезть рукой в кассету и вытащить пачку — а даже если бы вставил карту и попросил снять отрицательную сумму, банкомат откажет, потому что **сам знает правила**. Внутреннее устройство банкомата (как он считает купюры, где хранит журнал) можно полностью переделать — ты, как пользователь, этого не заметишь, лишь бы кнопки работали так же.

Если бы вместо этого касса стояла на улице с табличкой «бери сколько хочешь, главное запиши в тетрадку», то правила знали бы все — то есть никто.

**Инвариант** — это правило, которое банкомат никогда не нарушает («баланс не уходит ниже нуля», «каждая операция попадает в журнал»). Инкапсуляция — способ обеспечить его выполнение.

## Основная теория по шагам

### Шаг 1. Класс и объект

**Класс** — чертёж: какие данные хранит объект и что умеет. **Объект** (экземпляр) — конкретная «вещь» по чертежу, живёт в куче; переменная хранит ссылку на него. Класс состоит из *членов*:

- **поля** — переменные внутри объекта (состояние);
- **свойства** — «умные поля» с get/set;
- **конструкторы** — код, который создаёт объект в корректном начальном состоянии;
- **методы** — поведение;
- **события, индексаторы, операторы** — позже.

Порядок инициализации объекта важно знать: сначала выполняются инициализаторы полей (`int _x = 5;`), затем тело конструктора.

~~~csharp
var d = new Demo();
Console.WriteLine("объект создан");

class Demo
{
    private int _x = Log("1. инициализатор поля");

    public Demo() => Log("2. тело конструктора");

    private static int Log(string message)
    {
        Console.WriteLine(message);
        return 0;
    }
}
~~~
~~~console
1. инициализатор поля
2. тело конструктора
объект создан
~~~

Каждый класс неявно наследует от `object` и получает `ToString()`, `Equals()`, `GetHashCode()`. Переопределять `ToString()` полезно для отладки и логов:

~~~csharp
var p = new Person("Анна", 30);
Console.WriteLine(p);                 // вызывается ToString()
Console.WriteLine(new Person("Борис", 25).ToString().Length);

class Person(string name, int age)    // C# 12: первичный конструктор
{
    public string Name { get; } = name;
    public int Age { get; } = age;
    public override string ToString() => $"{Name}, {Age}";
}
~~~
~~~console
Анна, 30
9
~~~

### Шаг 2. Инвариант — главное слово темы

**Инвариант** — условие, которое истинно для объекта всегда, от конструктора до конца жизни. Для банковского счёта:

1. номер и владелец заданы и не пустые;
2. баланс меняется **только** через операции (пополнение, снятие, перевод);
3. каждая операция оставляет запись в истории;
4. сумма операции всегда положительна.

Задача класса — сделать так, чтобы нарушить эти условия было **невозможно**, а не «не принято».

### Шаг 3. Плохой вариант: данные нараспашку

~~~csharp
var acc = new BadAccount();
acc.Balance = -1_000_000m;     // ничто не мешает
acc.History.Clear();           // и следы можно стереть
Console.WriteLine(acc.Balance);

class BadAccount
{
    public string Number = "";
    public decimal Balance;
    public List<string> History = new();
}
~~~
~~~console
-1000000
~~~

Каждое место в программе, которое трогает `Balance`, теперь должно само помнить все правила. Ошибка в любом из них ломает данные.

### Шаг 4. Хороший вариант: класс охраняет свои правила

~~~csharp
var acc = new BankAccount("40817-001", "Анна");
acc.Deposit(1000m);
acc.Withdraw(250m);
Console.WriteLine(acc.Balance);          // 750
Console.WriteLine(acc.History.Count);    // 2
// acc.Balance = 5m;                     // ❌ ошибка компиляции: setter приватный

try { acc.Withdraw(-10m); }
catch (ArgumentOutOfRangeException e) { Console.WriteLine(e.ParamName); }

try { acc.Withdraw(5000m); }
catch (InvalidOperationException e) { Console.WriteLine(e.Message); }

public sealed class BankAccount
{
    private readonly List<Transaction> _history = new();

    public string Number { get; }
    public string Owner { get; }
    public decimal Balance { get; private set; }
    public IReadOnlyList<Transaction> History => _history.AsReadOnly();

    public BankAccount(string number, string owner)
    {
        if (string.IsNullOrWhiteSpace(number))
            throw new ArgumentException("Номер счёта обязателен", nameof(number));
        if (string.IsNullOrWhiteSpace(owner))
            throw new ArgumentException("Владелец обязателен", nameof(owner));

        Number = number;
        Owner = owner.Trim();
    }

    public void Deposit(decimal amount)
    {
        EnsurePositive(amount);
        Balance += amount;
        _history.Add(new Transaction(DateTime.Now, TransactionKind.Deposit, amount));
    }

    public void Withdraw(decimal amount)
    {
        EnsurePositive(amount);
        if (amount > Balance)
            throw new InvalidOperationException($"Недостаточно средств: {Balance}, запрошено {amount}");
        Balance -= amount;
        _history.Add(new Transaction(DateTime.Now, TransactionKind.Withdrawal, amount));
    }

    private static void EnsurePositive(decimal amount)
    {
        if (amount <= 0m)
            throw new ArgumentOutOfRangeException(nameof(amount), "Сумма должна быть положительной");
    }
}

public enum TransactionKind { Deposit, Withdrawal }

public record Transaction(DateTime At, TransactionKind Kind, decimal Amount);
~~~
~~~console
750
2
amount
Недостаточно средств: 750, запрошено 5000
~~~

Что здесь работает на инварианты:

- **Конструктор** не даёт создать счёт без номера и владельца.
- `Number` и `Owner` — свойства только для чтения (`{ get; }`): присвоить можно лишь в конструкторе.
- `Balance { get; private set; }` — читать может кто угодно, менять — только методы класса.
- `History` отдаёт **только для чтения** обёртку `AsReadOnly()`. Если вернуть сам `List<T>` как `IReadOnlyList<T>`, вызывающий код сможет привести его обратно к `List<T>` и изменить.
- Проверка суммы вынесена в один приватный метод — правило записано **в одном месте**.
- `Transaction` — `record`: неизменяемые данные со сравнением по значению.

Утечка внутреннего списка наружу — одна из самых частых ошибок инкапсуляции. Проверим:

~~~csharp
var leaky = new Leaky();
var view = leaky.Items;                                 // тип — IReadOnlyList<int>...
((List<int>)view).Clear();                              // ...но внутри всё равно List<int>
Console.WriteLine(leaky.Items.Count);

var safe = new Safe();
try { ((List<int>)safe.Items).Clear(); }
catch (InvalidCastException) { Console.WriteLine("AsReadOnly: привести к List нельзя"); }
Console.WriteLine(safe.Items.Count);

class Leaky
{
    private readonly List<int> _items = new() { 1, 2, 3 };
    public IReadOnlyList<int> Items => _items;          // ❌ отдали сам список
}

class Safe
{
    private readonly List<int> _items = new() { 1, 2, 3 };
    public IReadOnlyList<int> Items => _items.AsReadOnly();   // ✅ обёртка без изменяющих методов
}
~~~
~~~console
0
AsReadOnly: привести к List нельзя
3
~~~

Один нюанс: `AsReadOnly()` каждый раз создаёт новый объект-обёртку. Если свойство читают в горячем цикле, обёртку можно создать один раз в конструкторе и хранить в поле.

### Шаг 5. Модификаторы доступа

| Модификатор | Кто видит |
|---|---|
| `public` | все |
| `private` | только этот тип (по умолчанию для членов класса) |
| `protected` | этот тип и наследники |
| `internal` | вся сборка (проект); по умолчанию для типов верхнего уровня |
| `protected internal` | сборка **или** наследники из других сборок |
| `private protected` | наследники **внутри** этой же сборки |

:::tip Правило по умолчанию
Начинай с самого закрытого уровня (`private`) и открывай только то, что действительно нужно снаружи. Закрыть то, что уже публично и используется, гораздо труднее, чем открыть.
:::

Модификатор `sealed` на классе запрещает наследование; `readonly` на поле — присваивание только в объявлении или конструкторе; `const` — константа времени компиляции (неявно `static`).

### Шаг 6. Свойства: больше, чем геттеры

~~~csharp
var c = new Customer { FullName = "Анна Иванова", BirthDate = new DateOnly(2000, 5, 17) };
c.Email = "anna@example.com";
Console.WriteLine($"{c.FullName}, {c.Email}, возраст вычисляется: {c.Age >= 25}");
// c.FullName = "Другое";   // ❌ init-свойство после создания менять нельзя

try { c.Email = "без-собаки"; }
catch (ArgumentException) { Console.WriteLine("Некорректный email отклонён"); }

public class Customer
{
    private string _email = "";

    public required string FullName { get; init; }      // init: задаётся только при создании
    public DateOnly BirthDate { get; init; }

    public string Email                                  // свойство с проверкой
    {
        get => _email;
        set
        {
            if (!value.Contains('@'))
                throw new ArgumentException("Некорректный email", nameof(value));
            _email = value.Trim();
        }
    }

    public int Age => CalculateAge(BirthDate, DateOnly.FromDateTime(DateTime.Today)); // вычисляемое

    private static int CalculateAge(DateOnly birth, DateOnly today)
    {
        int age = today.Year - birth.Year;
        if (birth > today.AddYears(-age)) age--;
        return age;
    }
}
~~~
~~~console
Анна Иванова, anna@example.com, возраст вычисляется: True
Некорректный email отклонён
~~~

**Зачем свойства, а не публичные поля?** Свойство — это метод с синтаксисом поля. В него можно добавить проверку, логирование, вычисление, сделать разный доступ на чтение и запись (`private set`) — и всё это **не ломая** вызывающий код. Поле так не умеет. Кроме того, привязка данных, сериализация и ORM (EF Core) работают со свойствами.

Разновидности свойств:

| Запись | Смысл |
|---|---|
| `public int X { get; set; }` | автосвойство: компилятор создаёт скрытое поле |
| `public int X { get; }` | только чтение; присваивается в конструкторе или инициализаторе |
| `public int X { get; private set; }` | снаружи читают, меняет только класс |
| `public int X { get; init; }` | задаётся при создании (в инициализаторе объекта), потом — только чтение |
| `public required int X { get; init; }` | то же, но компилятор **требует** задать при создании |
| `public int Area => W * H;` | вычисляемое, без хранения |

`required` (C# 11) решает старую проблему: объект с обязательными данными можно создавать инициализатором, и при этом компилятор не даст забыть поле.

### Шаг 7. Конструкторы

~~~csharp
var d1 = new Deposit(500m, "USD");
var d2 = new Deposit(300m);
Console.WriteLine($"{d1.Amount} {d1.Currency} / {d2.Amount} {d2.Currency}");

try { new Deposit(-1m); }
catch (ArgumentOutOfRangeException) { Console.WriteLine("конструктор отклонил сумму"); }

public class Deposit
{
    public decimal Amount { get; }
    public string Currency { get; }

    public Deposit(decimal amount, string currency)
    {
        if (amount <= 0m) throw new ArgumentOutOfRangeException(nameof(amount));
        Amount = amount;
        Currency = currency;
    }

    public Deposit(decimal amount) : this(amount, "TJS") { }   // цепочка: проверки — в одном месте
}
~~~
~~~console
500 USD / 300 TJS
конструктор отклонил сумму
~~~

Правило: **конструктор завершается — объект валиден**. Если для создания нужно ещё и вызвать `Init()`, это нарушение инкапсуляции (между `new` и `Init()` объект «полусломан»).

### Шаг 8. `static`: принадлежит типу, а не объекту

~~~csharp
Console.WriteLine(AccountNumberGenerator.Next());
Console.WriteLine(AccountNumberGenerator.Next());

public static class AccountNumberGenerator
{
    private static int _next = 1;                    // одно значение на весь тип
    public static string Next() => $"ACC-{_next++:D4}"; // ACC-0001, ACC-0002, ...
}
~~~
~~~console
ACC-0001
ACC-0002
~~~

`static` удобен для чистых вспомогательных функций и фабрик. Но **статическое изменяемое состояние** — это глобальная переменная: его трудно тестировать, и оно ломается при многопоточности (`_next++` не атомарен). В Фазе 4 ты заменишь такое на сервисы через DI.

### Шаг 9. «Скажи, не спрашивай» и композиция

Принцип *Tell, don't ask*: вместо «достать данные, посчитать снаружи, записать обратно» — «попросить объект сделать». Не `if (acc.Balance >= x) acc.Balance -= x;`, а `acc.Withdraw(x)`. Первый вариант проверяет и меняет в два шага (между ними другой поток может снять деньги), да и правило размазано по вызывающим.

Объекты соединяются двумя способами: **наследование** («является») и **композиция** («содержит»). Счёт *содержит* историю операций, а не *является* списком. Если сомневаешься, выбирай композицию — об этом в следующей теме.

:::deep Граница
Как располагаются поля объекта в памяти, padding и `StructLayout`, как работает `readonly` на уровне IL — не нужно. Достаточно понимать, что поля живут внутри объекта в куче.
:::

## Как это работает под капотом

- **Автосвойство — это поле + два метода.** `public decimal Balance { get; private set; }` компилируется в скрытое поле `<Balance>k__BackingField`, метод `get_Balance()` и метод `set_Balance()` (приватный). JIT почти всегда встраивает такие маленькие методы, поэтому разницы по скорости между полем и автосвойством на практике нет.
- **`private` — проверка компилятора, а не стена в памяти.** Рефлексия может прочитать и приватные поля — это используют сериализаторы и ORM, а во вредных целях — тоже. Инкапсуляция защищает от **ошибок разработчиков**, а не от злонамеренного кода в том же процессе (от него — права доступа ОС, песочницы).

~~~csharp
using System.Reflection;

var fields = typeof(Account).GetFields(BindingFlags.NonPublic | BindingFlags.Instance);
Console.WriteLine(string.Join(", ", fields.Select(f => f.Name)));

var acc = new Account();
fields[0].SetValue(acc, 999m);                    // рефлексия обходит private set
Console.WriteLine(acc.Balance);

class Account { public decimal Balance { get; private set; } }
~~~
~~~console
<Balance>k__BackingField
999
~~~

- **`readonly` поле** помечается в метаданных флагом `initonly`: присвоить можно только в конструкторе. **`const`** подставляется значением прямо в место использования (как и значения параметров по умолчанию).
- **`init`** — это тоже `set`, но с особой пометкой (`modreq(IsExternalInit)`), по которой компилятор разрешает вызов только в инициализаторе при создании.
- **Объект в куче** — это служебная шапка + поля; методы класса хранятся один раз на тип, а не на экземпляр. Поэтому тысяча объектов не копирует тысячу раз код методов.
- **Порядок создания:** `newobj` выделяет память с обнулёнными полями → выполняются инициализаторы полей → вызывается конструктор базового класса → тело конструктора. Если конструктор бросил исключение, объект не создаётся (ссылка не будет присвоена).
- **`record`** компилятор разворачивает в класс с генерируемыми `Equals`, `GetHashCode`, `ToString`, `Deconstruct` и методом клонирования для `with`.

## Типичные ошибки и ловушки

:::danger Публичный setter «на всякий случай»
`public decimal Balance { get; set; }` — то же самое, что публичное поле с точки зрения инвариантов. Если значение должно меняться только через бизнес-операцию, setter приватный.
:::

:::danger Отдавать наружу изменяемую коллекцию
`public List<Transaction> History { get; }` — setter закрыт, но `History.Clear()` работает. Отдавай `IReadOnlyList<T>` или `AsReadOnly()`.
:::

:::danger Анемичная модель
Класс только со свойствами и сервис рядом, который делает `account.Balance -= x`. Правила расползаются по коду. Поведение, защищающее инвариант, должно жить **в самом классе**.
:::

- **Валидация только в UI.** Форма проверила сумму, а другой клиент (API, тест, скрипт) зайдёт в обход. Инвариант проверяет сам класс; UI дополнительно улучшает UX.
- **Конструктор с побочными эффектами** (сетевой запрос, чтение файла) — сложно тестировать, легко получить исключения при создании.
- **Объект с `Init()` после `new`.** Между конструктором и инициализацией объект невалиден.
- **Публичные поля.** Нет контроля, нельзя изменить реализацию без поломки вызывающих.
- **Класс-«свалка» (God object).** Сто полей и пятьдесят методов в одном классе; ответственность размыта. Дели по смыслу.
- **Изменяемые статические поля** — скрытая глобальная переменная.
- **Возвращать `null` для коллекций.** Лучше пустая коллекция.
- **Хранить `DateTime.Now` внутри логики без возможности подменить** — тесты нестабильны; позже научишься подставлять часы через интерфейс.
- **Путать `readonly` поле с неизменяемым объектом.** `readonly List<int>` запрещает *подмену* списка, но не `Add`/`Clear`.

## Вопросы с собеседований

:::spoiler Что такое инвариант? Назови три инварианта для класса «Бронирование номера в гостинице»
Условие, которое всегда истинно для объекта. Например: дата выезда позже даты заезда; число гостей от 1 до вместимости номера; отменённое бронирование нельзя оплатить.
:::

:::spoiler Зачем нужен `AsReadOnly()`, если тип свойства и так `IReadOnlyList<T>`?
`IReadOnlyList<T>` — лишь интерфейс. Если вернуть сам `List<T>`, вызывающий код может написать `((List<Transaction>)acc.History).Clear()`. `AsReadOnly()` возвращает обёртку `ReadOnlyCollection<T>`, у которой изменяющих методов нет в принципе.
:::

:::spoiler Чем `init` отличается от `private set`?
`init` позволяет задать значение **снаружи**, но только при создании объекта (в инициализаторе `new X { P = ... }`). `private set` позволяет менять значение в любой момент, но только **изнутри** класса.
:::

:::spoiler Зачем свойства, если можно сделать поля публичными? (ловушка: «свойства — просто синтаксис»)
Свойство — метод: можно добавить проверку, вычисление, разный доступ на чтение/запись, поменять реализацию без поломки клиентов, а ещё свойства поддерживают интерфейсы, привязку данных, сериализацию и ORM. Поле — прямой доступ к памяти без этих возможностей.
:::

:::spoiler Что такое инкапсуляция — это «просто private»? (ловушка)
Нет. `private` — инструмент. Инкапсуляция — гарантия инвариантов: данные и правила их изменения живут вместе, а снаружи объект нельзя привести в недопустимое состояние. Публичный `get; set;` с приватным полем внутри — не инкапсуляция.
:::

:::spoiler Что делает `required` и чем он лучше конструктора?
Обязывает задать свойство при создании объекта инициализатором. Полезно для DTO и объектов с большим числом полей, где конструктор на 8 параметров нечитаем; для сущностей с важными инвариантами конструктор остаётся надёжнее.
:::

:::spoiler Можно ли обойти `private`? Значит ли это, что инкапсуляция бесполезна?
Рефлексией — можно. Но инкапсуляция защищает от ошибок разработчиков и поддерживает целостность через публичный API, а не от кода с полным доступом к процессу.
:::

:::spoiler Что выполняется раньше: инициализатор поля или конструктор?
Инициализаторы полей, затем конструктор базового класса, затем тело конструктора.
:::

## Что запомнить

- **Инвариант** — условие, истинное для объекта всегда; класс обязан не допускать его нарушения (конструктор + методы + закрытое состояние).
- Данные закрыты (`private`), доступ — через свойства и методы с проверками; начинай с самого узкого модификатора.
- `get; private set;` — менять только внутри; `init`/`required` — задать при создании; `readonly` поле — только в конструкторе.
- Наружу не отдавай изменяемые внутренности: `IReadOnlyList<T>` + `AsReadOnly()`, неизменяемые `record`.
- Конструктор завершён — объект валиден; никаких `Init()`.
- Поведение — внутри класса (Tell, don't ask), а не в сервисе, который правит поля.
- `static`-состояние = глобальные переменные; `private` не защищает от рефлексии, только от ошибок.

@@page id="p1-inheritance" phase="1" kind="topic" title="ООП: наследование и полиморфизм" nav="ООП: наследование, полиморфизм" est="~1 неделя"
:::why
Полиморфизм позволяет писать код, который работает с **семейством** типов, не зная конкретного: «для каждого счёта начисли конец месяца». Наследование — один из способов его получить, и самый легко ломаемый. Здесь важно научиться и пользоваться, и вовремя остановиться. Вместо абстрактного «Animal → Dog» берём реальную задачу: виды банковских счетов.
:::

## Зачем это нужно

В любой нетривиальной программе есть «семейства» похожих вещей: виды счетов, способы оплаты, форматы отчётов, типы уведомлений, стратегии скидок. У них много общего (номер, сумма, отправка) и немного различий (правила снятия, формат вывода). Без наследования и полиморфизма такой код превращается в длинные цепочки `if (type == …) … else if …`, которые приходится править в десяти местах при каждом новом виде.

Полиморфизм решает эту проблему: вызывающий код работает с общим типом (`Account`, `IPayment`), а конкретное поведение выбирается автоматически по реальному типу объекта. Новый вид — новый класс; старый код не меняется.

Но наследование — одновременно **самый часто злоупотребляемый** механизм ООП. Глубокие иерархии, «наследуем, чтобы переиспользовать код», классы-наследники, ломающие обещания базового — частые причины жёсткого, хрупкого кода. Поэтому цель темы двойная: научиться применять наследование там, где оно уместно, и распознавать, когда нужна композиция.

На собеседованиях эту тему спрашивают всегда: «что такое полиморфизм», «чем `virtual` отличается от `abstract`», «`override` против `new`», «порядок вызова конструкторов», «принцип подстановки Лисков», «наследование или композиция».

## Интуиция и аналогия

Представь должность «**кассир**» в магазине. Есть общие обязанности: принять товары, назвать сумму, выдать чек. А есть различия: кассир самообслуживания просит отсканировать товары самому, кассир в бутике предлагает упаковку. Менеджеру магазина безразлично, какой именно кассир на смене: он говорит «**закрой смену**» — и каждый делает это по-своему. Это полиморфизм: один вызов, разные реализации, выбор — по реальному «исполнителю».

Наследование — это правило «**является**»: кассир самообслуживания *является* кассиром. Если проверить фразу вслух звучит нелепо («логгер является списком»), наследование выбрано неверно.

А принцип Лисков звучит так: везде, где ожидается кассир, должен работать любой кассир. Если «кассир-стажёр» не умеет закрывать смену и бросает исключение, значит, это не кассир, и менеджер получит сюрприз.

## Основная теория по шагам

### Шаг 1. Основы наследования

~~~csharp
var d = new Dog("Рекс");
d.Eat();                       // унаследованный метод базы
Console.WriteLine(d.Speak());  // метод, переопределённый в Dog
Console.WriteLine(d.Name);

class Animal
{
    public string Name { get; }
    public Animal(string name) => Name = name;
    public void Eat() => Console.WriteLine($"{Name} ест");
    public virtual string Speak() => "...";
}

class Dog : Animal
{
    public Dog(string name) : base(name) { }            // обязательно вызвать конструктор базы
    public override string Speak() => "Гав";
}
~~~
~~~console
Рекс ест
Гав
Рекс
~~~

- Наследник получает все члены базового класса (кроме `private` — они есть в объекте, но недоступны по имени) и может добавлять свои.
- C# допускает **одиночное наследование** классов (у класса один родитель), но много интерфейсов.
- Все классы наследуют от `object`.
- `base.Метод()` вызывает реализацию родителя — типичный приём для расширения, а не замены поведения.
- `protected` — доступ для наследников, `private` — только для самого класса.

**Приведение типов.** Переменная базового типа может ссылаться на объект-наследник (*upcast*, неявно). Обратное (*downcast*) требует явного приведения и может не получиться:

~~~csharp
Animal a = new Dog("Рекс");                  // upcast: неявный, всегда безопасен
Console.WriteLine(a.GetType().Name);         // реальный тип объекта — Dog
Console.WriteLine(a is Dog);                 // True

Dog? dog = a as Dog;                         // as: вернёт null, если не подходит
Console.WriteLine(dog is not null);

if (a is Dog d2) Console.WriteLine($"это собака {d2.Name}");   // проверка + приведение в одном

Animal plain = new Animal("Зверь");
try { Dog bad = (Dog)plain; }                // явное приведение: исключение, если тип не подходит
catch (InvalidCastException) { Console.WriteLine("InvalidCastException"); }
Console.WriteLine(plain as Dog is null);

class Animal { public string Name { get; } public Animal(string n) => Name = n; }
class Dog : Animal { public Dog(string n) : base(n) { } }
~~~
~~~console
Dog
True
True
это собака Рекс
InvalidCastException
True
~~~

Статический тип — то, что написано в объявлении переменной (`Animal`); динамический — реальный тип объекта (`Dog`). Виртуальный вызов выбирает метод по **динамическому** типу, обычный — по статическому.

### Шаг 2. Порядок вызова конструкторов

~~~csharp
var c = new C();

class A
{
    public A() => Console.WriteLine("конструктор A");
}

class B : A
{
    private readonly int _f = Log("поле B");
    public B() => Console.WriteLine("конструктор B");
    protected static int Log(string s) { Console.WriteLine(s); return 0; }
}

class C : B
{
    private readonly int _g = Log("поле C");
    public C() => Console.WriteLine("конструктор C");
}
~~~
~~~console
поле C
поле B
конструктор A
конструктор B
конструктор C
~~~

Сначала выполняются инициализаторы полей — от самого производного класса к базовому (`C`, затем `B`), потом управление уходит вверх по цепочке конструкторов, и **тела** конструкторов отрабатывают в порядке от базового к производному: A → B → C. Это важно для понимания ловушки с виртуальными вызовами в конструкторе (она ниже).

### Шаг 3. Задача: виды счетов

Есть два вида счетов:

- **Расчётный** (`CheckingAccount`): можно уйти в минус до лимита овердрафта; в конце месяца, если баланс отрицательный, списывается комиссия.
- **Накопительный** (`SavingsAccount`): в минус нельзя; не больше 3 снятий в месяц; в конце месяца начисляются проценты.

Общее: номер, баланс, пополнение, снятие с проверками. Различается: **разрешено ли снятие** и **что происходит в конце месяца**.

### Шаг 4. Решение: абстрактный базовый класс + переопределение

~~~csharp
var accounts = new List<Account>
{
    new CheckingAccount("40817-001", overdraftLimit: 500m),
    new SavingsAccount("42301-002", monthlyRate: 0.01m),
};

foreach (Account a in accounts) a.Deposit(1000m);

accounts[0].Withdraw(1200m);      // расчётный: уходим в минус в пределах овердрафта

foreach (Account a in accounts)   // полиморфизм: один цикл — разное поведение
{
    a.ApplyMonthEnd();
    Console.WriteLine(a);
}

public abstract class Account
{
    public string Number { get; }
    public decimal Balance { get; protected set; }

    protected Account(string number)
    {
        if (string.IsNullOrWhiteSpace(number)) throw new ArgumentException("Номер обязателен", nameof(number));
        Number = number;
    }

    public void Deposit(decimal amount)
    {
        if (amount <= 0m) throw new ArgumentOutOfRangeException(nameof(amount));
        Balance += amount;
    }

    // Шаблонный метод: общий алгоритм в базе, отличающийся шаг — в наследниках
    public void Withdraw(decimal amount)
    {
        if (amount <= 0m) throw new ArgumentOutOfRangeException(nameof(amount));
        if (!CanWithdraw(amount))
            throw new InvalidOperationException($"Счёт {Number}: снятие {amount} отклонено");
        Balance -= amount;
        OnWithdrawn(amount);
    }

    protected abstract bool CanWithdraw(decimal amount);   // обязан реализовать каждый наследник
    protected virtual void OnWithdrawn(decimal amount) { } // можно переопределить, а можно нет
    public abstract void ApplyMonthEnd();

    public override string ToString() => $"{GetType().Name} {Number}: {Balance:N2}";
}

public sealed class CheckingAccount : Account
{
    private const decimal OverdraftFee = 5m;
    public decimal OverdraftLimit { get; }

    public CheckingAccount(string number, decimal overdraftLimit) : base(number)
    {
        if (overdraftLimit < 0m) throw new ArgumentOutOfRangeException(nameof(overdraftLimit));
        OverdraftLimit = overdraftLimit;
    }

    protected override bool CanWithdraw(decimal amount) => Balance - amount >= -OverdraftLimit;

    public override void ApplyMonthEnd()
    {
        if (Balance < 0m) Balance -= OverdraftFee;
    }
}

public sealed class SavingsAccount : Account
{
    private const int MaxWithdrawalsPerMonth = 3;
    private int _withdrawalsThisMonth;
    public decimal MonthlyRate { get; }

    public SavingsAccount(string number, decimal monthlyRate) : base(number) => MonthlyRate = monthlyRate;

    protected override bool CanWithdraw(decimal amount) =>
        amount <= Balance && _withdrawalsThisMonth < MaxWithdrawalsPerMonth;

    protected override void OnWithdrawn(decimal amount) => _withdrawalsThisMonth++;

    public override void ApplyMonthEnd()
    {
        Balance += Math.Round(Balance * MonthlyRate, 2, MidpointRounding.AwayFromZero);
        _withdrawalsThisMonth = 0;
    }
}
~~~
~~~console
CheckingAccount 40817-001: -205.00
SavingsAccount 42301-002: 1,010.00
~~~

(Формат чисел `N2` зависит от культуры системы: в русской локали вывод будет `-205,00` и `1 010,00`.)

#### Что здесь важно

- `abstract class Account` — нельзя создать «просто счёт», только конкретный вид.
- `abstract` метод — **обязан** быть реализован в наследнике. `virtual` — **может** быть переопределён, есть реализация по умолчанию.
- `override` — переопределение; вызов идёт через **таблицу виртуальных методов**: какой метод вызвать, решается во время выполнения по реальному типу объекта, а не по типу переменной.
- `sealed class` — от этого класса наследоваться нельзя. Хорошее значение по умолчанию для конечных классов. `sealed override` запечатывает отдельный метод.
- `: base(number)` — конструктор базового класса вызывается **до** тела конструктора наследника.
- `protected set` у `Balance` — наследники могут менять баланс, внешний код — нет.
- **Шаблонный метод**: `Withdraw` не виртуален, он гарантирует общие правила, а наследники меняют только точки расширения (`CanWithdraw`, `OnWithdrawn`). Это защищает инварианты базы (см. [инкапсуляцию](#p1-encapsulation)).

:::warn Округление денег
`Math.Round(x, 2)` по умолчанию использует **банковское округление** (`MidpointRounding.ToEven`): 2.345 → 2.34, а 2.355 → 2.36. Для денег обычно явно указывают `MidpointRounding.AwayFromZero`. Это частый «баг на копейку».
:::

### Шаг 5. Полиморфизм — без него код выглядел бы так

~~~csharp @nocheck
// ❌ Каждый новый вид счёта = правка этого кода и всех похожих мест
foreach (object a in accounts)
{
    if (a is CheckingAccount ch) { /* комиссия */ }
    else if (a is SavingsAccount sv) { /* проценты */ }
    // а сюда забудут добавить DepositAccount...
}
~~~

С полиморфизмом новый вид счёта — это **новый класс**, а существующий код не меняется. Это и есть принцип открытости/закрытости (O в SOLID), к которому ты вернёшься в Фазе 2.

### Шаг 6. `override` против `new`

~~~csharp
Base b = new Derived();
Console.WriteLine(b.Who());    // Derived    — виртуальный вызов, решает реальный тип объекта
Console.WriteLine(b.Name());   // Base.Name  — new только СКРЫВАЕТ метод, решает тип переменной

Derived d = (Derived)b;
Console.WriteLine(d.Name());   // Derived.Name

class Base
{
    public virtual string Who() => "Base";
    public string Name() => "Base.Name";
}

class Derived : Base
{
    public override string Who() => "Derived";
    public new string Name() => "Derived.Name";
}
~~~
~~~console
Derived
Base.Name
Derived.Name
~~~

`new` почти всегда признак проблемы в дизайне. Если компилятор предупреждает «member hides inherited member», реши осознанно: тебе нужно `override` (и `virtual` в базе) или другое имя.

Сводка по ключевым словам:

| Слово | Где | Смысл |
|---|---|---|
| `virtual` | метод/свойство базы | можно переопределить; есть реализация |
| `abstract` | метод/свойство абстрактного класса | реализации нет, наследник обязан переопределить |
| `override` | наследник | переопределяет виртуальный/абстрактный член |
| `sealed override` | наследник | переопределяет и запрещает дальнейшее переопределение |
| `new` | наследник | скрывает член базы (не полиморфизм) |
| `sealed class` | класс | наследоваться нельзя |
| `abstract class` | класс | нельзя создать экземпляр |

### Шаг 7. Ловушка: виртуальный вызов в конструкторе

~~~csharp
var r = new Report();   // выведет «Заголовок: » — пустую строку!

class Document
{
    public Document() => Console.WriteLine("Заголовок: " + GetTitle());
    protected virtual string GetTitle() => "Документ";
}

class Report : Document
{
    private readonly string _title;
    public Report() { _title = "Отчёт за месяц"; }   // тело выполнится ПОСЛЕ конструктора Document
    protected override string GetTitle() => _title ?? "";
}
~~~
~~~console
Заголовок:
~~~

Конструктор базы вызывает переопределённый метод наследника, когда тело конструктора наследника ещё **не выполнилось**. **Не вызывай виртуальные методы из конструктора.**

### Шаг 8. Когда наследование ломается

- **Глубокие иерархии** (больше 2–3 уровней): изменение в базе неожиданно влияет на всех потомков («хрупкий базовый класс»).
- **Наследование ради повторного использования кода**, а не ради «является»: `class Logger : List<string>` — логгер не является списком.
- **Нарушение обещаний базы** (принцип подстановки Лисков): если `SavingsAccount.Deposit` вдруг бросает `NotSupportedException`, любой код, работающий с `Account`, сломается.

Классический пример нарушения — «квадрат является прямоугольником»:

~~~csharp
static int Resize(Rectangle r)
{
    r.Width = 5;
    r.Height = 4;
    return r.Width * r.Height;       // клиент уверен: ширина и высота независимы → 20
}

Console.WriteLine(Resize(new Rectangle()));
Console.WriteLine(Resize(new Square()));   // 16, а не 20 — подстановка сломала ожидания

class Rectangle
{
    public virtual int Width { get; set; }
    public virtual int Height { get; set; }
}

class Square : Rectangle
{
    public override int Width { get => base.Width; set { base.Width = value; base.Height = value; } }
    public override int Height { get => base.Height; set { base.Width = value; base.Height = value; } }
}
~~~
~~~console
20
16
~~~

В математике квадрат — прямоугольник, но в коде **изменяемый** `Square` не выполняет контракт `Rectangle` (независимость сторон). Решение — не наследовать, а выделить общий интерфейс (`IShape` с `Area`) либо сделать типы неизменяемыми.

:::key Композиция вместо наследования
Если хочется унаследоваться, чтобы получить кусок поведения, — чаще лучше **содержать** объект с этим поведением: у счёта есть `IFeePolicy`, а не «счёт наследуется от `FeeCalculator`». Подробнее — в [интерфейсах vs абстрактных классах](#p1-interfaces).
:::

Эмпирическая проверка перед тем как наследоваться: (1) фраза «X является Y» звучит естественно; (2) X можно **везде** подставить вместо Y; (3) иерархия неглубокая; (4) базовый класс спроектирован для наследования (понятные точки расширения, `protected`-контракт), а не взят «потому что там есть нужный метод».

## Как это работает под капотом

- **Виртуальные методы и таблица методов.** У каждого типа в памяти есть *таблица методов* со слотами для виртуальных методов. Объект хранит указатель на таблицу своего **реального** типа. Вызов `a.ApplyMonthEnd()` — это «взять из объекта указатель на таблицу, взять из слота адрес метода и вызвать». Это IL-инструкция `callvirt`; накладные расходы — несколько наносекунд. У наследника таблица начинается с копии таблицы родителя, а `override` просто заменяет адрес в слоте.
- **`new`-метод** занимает *новый* слот (или вообще невиртуален): поэтому вызов через переменную базового типа попадает в старый слот и вызывает базовую версию.
- **Невиртуальные методы** вызываются напрямую (адрес известен при компиляции), поэтому они быстрее и могут быть встроены JIT. `sealed`-классы и `sealed override` позволяют JIT *девиртуализировать* вызовы и встраивать их — ещё одна причина делать конечные классы `sealed`.
- **Раскладка объекта.** В памяти поля базового класса идут первыми, затем поля наследника. Поэтому объект-наследник можно трактовать как объект базового типа (приведение вверх ничего не копирует и не преобразует — это та же ссылка). Приведение вниз (`(Dog)animal`) — проверка типа в рантайме (`castclass`).
- **`as` и `is`** сравнивают реальный тип объекта (из его таблицы методов) с целевым и учитывают наследование: `dog is Animal` — `true`.
- **Конструкторы не наследуются.** Каждый класс объявляет свои и обязан вызвать конструктор базы (явно через `base(…)` или неявно — безпараметрический).
- **Статические члены не полиморфны:** виртуальной диспетчеризации у них нет.

Больше деталей и схем — в справочнике: [виртуальные методы и vtable](#/ref/c/cl-vtable), [наследование](#/ref/c/cl-inheritance), [абстрактный класс против интерфейса](#/ref/c/cl-abstract-vs-interface).

## Типичные ошибки и ловушки

- **Наследование ради повторного использования кода.** `class Report : List<Row>` — отчёт не является списком; наружу «протекают» все методы `List<T>` и нарушаются инварианты. Используй композицию: поле `List<Row>`.
- **Глубокие иерархии.** `Entity → Person → Employee → Manager → SeniorManager`: каждый новый уровень усложняет понимание. Предпочитай 1–2 уровня.
- **Нарушение принципа Лисков.** Наследник бросает `NotSupportedException`, ужесточает предусловия или не выполняет обещания базового класса.
- **Виртуальный вызов в конструкторе.** Наследник ещё не инициализирован — получаешь `null`/нули.
- **Забыть `override`** (или написать `new`): метод «скрывает», а не переопределяет; вызовы через базовый тип идут в старую версию.
- **Делать всё `virtual` «на всякий случай».** Каждый виртуальный метод — обещание поддерживать переопределение; закрывай по умолчанию (`sealed`, не `virtual`).
- **Публичные поля и `protected`-поля.** Наследник получает доступ к внутренностям и может сломать инварианты; лучше `protected`-методы и свойства с проверками.
- **Проверки типа вместо полиморфизма.** Цепочка `if (x is A) … else if (x is B) …` — признак того, что поведение надо вынести в виртуальный метод.
- **Приведение вниз без проверки.** `(Dog)animal` без `is`/`as` — `InvalidCastException`.
- **Наследование от конкретных классов фреймворка** (`List<T>`, `Dictionary`) — они не рассчитаны на переопределение (методы не виртуальны).

## Вопросы с собеседований

:::spoiler Разница между `abstract` и `virtual`
`abstract` метод не имеет реализации и обязан быть переопределён в каждом неабстрактном наследнике; сам класс тоже должен быть `abstract`. `virtual` имеет реализацию по умолчанию, переопределение необязательно.
:::

:::spoiler Что выведет `b.Name()`, если `Name` в наследнике объявлен через `new`, а `b` имеет тип базы?
Метод базы. `new` не участвует в виртуальной диспетчеризации: метод выбирается по статическому типу переменной.
:::

:::spoiler В каком порядке выполняются конструкторы `Account` и `CheckingAccount`?
Сначала инициализаторы полей `CheckingAccount`, затем конструктор `Account` (включая его инициализаторы полей и тело), затем тело конструктора `CheckingAccount`. Поэтому из базового конструктора нельзя рассчитывать на состояние, которое задаёт тело конструктора наследника.
:::

:::spoiler Почему метод `Withdraw` в базе не `virtual`?
Это шаблонный метод: он гарантирует общие правила (сумма > 0, проверка, списание, хук) для всех видов счетов. Если бы его можно было переопределить целиком, наследник мог бы обойти проверки. Наследники меняют только **точки расширения** — `CanWithdraw` и `OnWithdrawn`.
:::

:::spoiler Что такое полиморфизм простыми словами? (ловушка: «это перегрузка методов»)
Один и тот же вызов через общий тип приводит к разному поведению в зависимости от реального типа объекта (подтиповой полиморфизм, `virtual`/`override`). Перегрузка — выбор метода по типам аргументов **при компиляции**, это другое.
:::

:::spoiler Когда выбирать композицию вместо наследования?
Когда связь не «является», а «имеет/использует»; когда нужно менять поведение во время выполнения (подставить другую стратегию); когда хочется избежать глубоких иерархий и хрупкости базового класса. Правило: «предпочитай композицию наследованию».
:::

:::spoiler Что такое принцип подстановки Лисков? Приведи пример нарушения
Объект наследника можно подставить вместо объекта базового класса без нарушения корректности программы. Пример нарушения: изменяемый `Square : Rectangle`, где установка одной стороны меняет другую — клиент базы получает не то, что ожидал.
:::

:::spoiler Можно ли в C# наследоваться от нескольких классов? Как получить «множественное» поведение?
Нет, только от одного класса. Поведение комбинируют через реализацию нескольких интерфейсов и композицию.
:::

:::spoiler Зачем нужен `sealed`?
Запретить наследование (или дальнейшее переопределение) — защита инвариантов и возможность оптимизации (девиртуализация вызовов JIT-ом). Хорошее значение по умолчанию для классов, не рассчитанных на наследование.
:::

## Что запомнить

- Наследование = «является»; используй, когда подстановка потомка вместо предка безопасна (Лисков), иначе — композиция.
- `virtual` (можно переопределить) → `override` (переопределили); `abstract` (обязан реализовать); `sealed` (закрыть); `new` (скрыть, **не** полиморфизм).
- Вызов виртуального метода выбирается по **реальному типу** объекта в рантайме (таблица методов); невиртуального и `new` — по типу переменной.
- Порядок: инициализаторы полей наследника → конструктор базы → тело конструктора наследника.
- Не вызывай виртуальные методы из конструктора.
- Шаблонный метод: общий алгоритм в базе (не виртуальный), точки расширения — `protected abstract/virtual`.
- Приведение вверх неявное и безопасное; вниз — через `is`/`as` (иначе `InvalidCastException`).
- Иерархии неглубокие (1–2 уровня), по умолчанию — `sealed`.

## Зачем это нужно

Программа — это набор частей, которые общаются друг с другом: бизнес-логика вызывает хранилище, хранилище — базу или файл, сервис уведомлений — почту или SMS, расчёт процентов — часы. Если каждая часть напрямую знает конкретные классы остальных, программу невозможно менять частями: замена файла на базу означает правку по всему коду, а автоматически проверить логику без реальной базы и реальной почты нельзя.

Интерфейс — способ сказать: «**мне не важно, кто ты, мне важно, что ты умеешь**». Он описывает контракт (набор членов), не привязываясь к реализации. Именно поэтому:

- в тестах настоящую базу заменяют заглушкой в памяти;
- в ASP.NET Core весь Dependency Injection — это «запроси `IMyService`, получи подходящую реализацию»;
- стандартная библиотека работает через интерфейсы: `foreach` работает с любым `IEnumerable<T>`, `using` — с любым `IDisposable`, `Sort` — с любым `IComparable<T>`;
- один класс может сочетать несколько ролей (читаемый, сравнимый, освобождаемый), чего нельзя при единственном базовом классе.

Абстрактный класс решает другую задачу: общее состояние и общий алгоритм семейства. Умение выбрать между ними — не «знание таблицы», а понимание, где проходят границы системы. Это один из самых частых вопросов на собеседованиях: «интерфейс или абстрактный класс — что и когда?».

## Интуиция и аналогия

**Интерфейс — розетка.** Прибору всё равно, какая электростанция за стеной: угольная, солнечная или генератор. Ему важно, что в розетке 220 В и подходящие штыри. Розетка — контракт; станции — реализации. Благодаря этому ты меняешь поставщика, не переделывая все приборы.

**Абстрактный класс — полуфабрикат.** Базовое тесто, из которого пекари делают разные пироги: часть шагов готова (замешено), часть оставлена на выбор (начинка). Полуфабрикат хранит «внутренности» (состояние, готовые шаги), и все пироги из него — действительно пироги одного семейства.

Если твоя задача — «подключить что угодно, что умеет X», нужна розетка. Если «сделать несколько пирогов по одному рецепту с вариациями» — полуфабрикат.

## Основная теория по шагам

### Шаг 1. Что такое интерфейс

Интерфейс объявляет члены (методы, свойства, события, индексаторы) без реализации. Класс или структура, которые **реализуют** интерфейс, обязаны предоставить все его члены.

~~~csharp
IShape[] shapes = { new Circle(1), new Rectangle(2, 3) };
foreach (IShape s in shapes)
    Console.WriteLine($"{s.Name}: {s.Area():F2}");

object o = shapes[0];
if (o is IShape shape) Console.WriteLine($"объект умеет быть фигурой: {shape.Name}");
Console.WriteLine(o is IDisposable);

interface IShape
{
    string Name { get; }
    double Area();
}

class Circle(double r) : IShape
{
    public string Name => "Круг";
    public double Area() => Math.PI * r * r;
}

class Rectangle(double w, double h) : IShape
{
    public string Name => "Прямоугольник";
    public double Area() => w * h;
}
~~~
~~~console
Круг: 3.14
Прямоугольник: 6.00
объект умеет быть фигурой: Круг
False
~~~

Принятые соглашения: имя интерфейса начинается с `I` (`IShape`, `IAccountStore`), члены неявно `public`, реализации — обычные публичные члены. Переменную можно объявить типом интерфейса (`IShape s`) и присвоить ей любую реализацию; вызовы будут полиморфными. Проверка «умеет ли объект X» — `is IShape`, `as IShape`.

Класс может реализовывать **несколько** интерфейсов и при этом наследоваться от одного класса: `class Report : Document, IPrintable, IExportable`. Интерфейс может расширять другие интерфейсы: `interface IReadWriteStore : IReader, IWriter`.

Стандартные интерфейсы, которые ты встретишь в первые же недели:

| Интерфейс | Что обещает | Где применяется |
|---|---|---|
| `IEnumerable<T>` | можно обойти в `foreach` | все коллекции, LINQ |
| `IDisposable` | можно освободить ресурсы | `using`, файлы, соединения |
| `IComparable<T>` | можно упорядочить | `Sort`, `SortedSet` |
| `IEquatable<T>` | можно сравнить по значению | словари, `Contains` |
| `IList<T>` / `IReadOnlyList<T>` | доступ по индексу | параметры и возвращаемые значения методов |
| `IFormattable` | форматируется строкой формата | `ToString("N2")`, интерполяция |

~~~csharp
using var res = new Resource("файл");
Console.WriteLine("работаем с ресурсом");
// при выходе из области видимости using вызовет Dispose автоматически

var people = new List<Person> { new("Борис", 30), new("Анна", 25) };
people.Sort();                                         // List<T>.Sort использует IComparable<T>
Console.WriteLine(string.Join(", ", people.Select(p => p.Name)));

class Resource(string name) : IDisposable
{
    public void Dispose() => Console.WriteLine($"{name}: освобождён");
}

record Person(string Name, int Age) : IComparable<Person>
{
    public int CompareTo(Person? other) => Age.CompareTo(other?.Age);
}
~~~
~~~console
работаем с ресурсом
Анна, Борис
файл: освобождён
~~~

### Шаг 2. Короткая таблица (чтобы не возвращаться)

| | Интерфейс | Абстрактный класс |
|---|---|---|
| Сколько можно унаследовать/реализовать | Сколько угодно | Только один базовый класс |
| Состояние (поля экземпляра) | Нет | Да |
| Конструкторы | Нет | Да |
| Реализация методов | Только default interface methods (C# 8+) — с осторожностью | Да, полноценно |
| Могут реализовать структуры и record-ы | Да | Структуры — нет; `record` может наследовать только другой `record` |
| Смысл | **Что объект умеет** (контракт, возможность) | **Чем объект является** + общий код семейства |

### Шаг 3. Где выбор ломает архитектуру

#### Сценарий 1: абстрактный класс как граница модуля

Ты сохраняешь счета в файл и делаешь базу «для хранилищ»:

~~~csharp @nocheck
public abstract class FileStorageBase
{
    protected readonly string FilePath;
    protected FileStorageBase(string filePath) => FilePath = filePath;

    public abstract void Save(IEnumerable<BankAccount> accounts);
    public abstract IReadOnlyList<BankAccount> Load();
}
~~~

Через три месяца (Фаза 3) нужно хранить в PostgreSQL. У базы данных нет `FilePath`, но наследник **обязан** его получить. Для тестов нужно хранилище в памяти — тоже без файла. А если новому хранилищу нужно наследоваться от библиотечного класса, второй базовый класс в C# недоступен. Абстракция «протекла»: деталь реализации (файл) стала частью контракта.

#### Как правильно: интерфейс на границе, детали — в реализациях

~~~csharp
IAccountStore memory = new InMemoryAccountStore();
memory.SaveAll(new[] { new BankAccount("A-1"), new BankAccount("A-2") });

var service = new BankService(memory);              // сервис не знает, что внутри — память
Console.WriteLine(service.CountAccounts());

var fileService = new BankService(new TextFileAccountStore("accounts.txt"));   // другая реализация
Console.WriteLine(fileService.CountAccounts());

public record BankAccount(string Number);

public interface IAccountStore
{
    IReadOnlyList<BankAccount> LoadAll();
    void SaveAll(IEnumerable<BankAccount> accounts);
}

public sealed class TextFileAccountStore : IAccountStore
{
    private readonly string _path;
    public TextFileAccountStore(string path) => _path = path;

    public IReadOnlyList<BankAccount> LoadAll() { /* чтение файла */ return new List<BankAccount>(); }
    public void SaveAll(IEnumerable<BankAccount> accounts) { /* запись файла */ }
}

public sealed class InMemoryAccountStore : IAccountStore   // для тестов и экспериментов
{
    private List<BankAccount> _accounts = new();
    public IReadOnlyList<BankAccount> LoadAll() => _accounts.ToList();
    public void SaveAll(IEnumerable<BankAccount> accounts) => _accounts = accounts.ToList();
}

public sealed class BankService
{
    private readonly IAccountStore _store;               // зависит от КОНТРАКТА, а не от файла
    public BankService(IAccountStore store) => _store = store;

    public int CountAccounts() => _store.LoadAll().Count;
}
~~~
~~~console
2
0
~~~

`BankService` не знает, файл это, база или память. В Фазе 3 появится `PostgresAccountStore : IAccountStore`, и `BankService` не изменится ни на строчку. Ровно так же в Фазе 4 ASP.NET Core будет подставлять реализации через DI. Идея «зависеть от абстракции, а не от конкретики» называется принципом инверсии зависимостей (D в SOLID); а передача зависимости снаружи через конструктор — *внедрением зависимостей*.

#### Сценарий 2: «невидимые» зависимости — время и случайность

~~~csharp
IClock clock = new FixedClock(new DateTime(2026, 1, 31));
var job = new MonthEndJob(clock);
Console.WriteLine(job.ShouldRun());                    // 31 января — последний день месяца

job = new MonthEndJob(new FixedClock(new DateTime(2026, 1, 15)));
Console.WriteLine(job.ShouldRun());

public interface IClock
{
    DateTime Now { get; }
}

public sealed class SystemClock : IClock
{
    public DateTime Now => DateTime.Now;
}

public sealed class FixedClock : IClock      // для проверки «конца месяца» без ожидания месяца
{
    public FixedClock(DateTime now) => Now = now;
    public DateTime Now { get; }
}

public sealed class MonthEndJob
{
    private readonly IClock _clock;
    public MonthEndJob(IClock clock) => _clock = clock;

    public bool ShouldRun() => _clock.Now.Day == DateTime.DaysInMonth(_clock.Now.Year, _clock.Now.Month);
}
~~~
~~~console
True
False
~~~

Если `MonthEndJob` вызывает `DateTime.Now` напрямую, проверить логику «в конце месяца начисляются проценты» можно, только дождавшись конца месяца. С `IClock` — подставив `FixedClock`. (В современном .NET есть и готовая абстракция `TimeProvider`.) То же относится ко всему, что «недетерминированно»: время, случайные числа, сеть, файловая система.

#### Сценарий 3: абстрактный класс там, где он уместен

Абстрактный класс хорош, когда у **семейства, которое ты контролируешь**, есть общее **состояние и алгоритм**: как `Account` с шаблонным методом `Withdraw` в [теме про наследование](#p1-inheritance). Все счета — действительно счета, у всех есть номер и баланс, и общие правила снятия должны быть в одном месте.

:::key Практическое правило
- **Граница между частями системы** (хранилище, отправка уведомлений, часы, внешние API) → **интерфейс**.
- **Семейство похожих сущностей с общим состоянием и алгоритмом** внутри одного модуля → **абстрактный класс**.
- Часто — **оба**: интерфейс как контракт + абстрактный класс, который реализует его общую часть для удобства.
:::

### Шаг 4. Маленькие интерфейсы

~~~csharp @nocheck
// ❌ «Жирный» интерфейс: отчёту, который только читает, придётся тянуть и запись
public interface IAccountRepository
{
    BankAccount? Find(string number);
    IReadOnlyList<BankAccount> All();
    void Add(BankAccount account);
    void Remove(string number);
    void SaveChanges();
}

// ✅ Разделить по потребностям клиентов
public interface IAccountReader
{
    BankAccount? Find(string number);
    IReadOnlyList<BankAccount> All();
}

public interface IAccountWriter
{
    void Add(BankAccount account);
    void Remove(string number);
    void SaveChanges();
}
~~~

Это принцип разделения интерфейсов (I в SOLID). Отчёт принимает `IAccountReader` и просто не имеет возможности ничего испортить — это тоже форма инкапсуляции. Реализация может поддерживать оба: `class Repo : IAccountReader, IAccountWriter`. В Фазе 1 запомни идею, подробно — в Фазе 2.

### Шаг 5. Версионирование: что ломается при изменении

| Изменение | Интерфейс | Абстрактный класс |
|---|---|---|
| Добавить новый метод с реализацией | Через default interface method — возможно, но спорно | **Не ломает** наследников |
| Добавить новый абстрактный метод / метод без реализации | **Ломает** все реализации | **Ломает** всех наследников |
| Добавить поле | Нельзя | Не ломает |

Поэтому интерфейсы держат маленькими и стабильными, а не добавляют в них методы каждую неделю.

**Default interface methods** (C# 8) позволяют дать реализацию по умолчанию прямо в интерфейсе. Это сделано в первую очередь для эволюции библиотек. Нюанс: такой метод виден только через переменную типа интерфейса.

~~~csharp
IGreeter g = new Polite();
Console.WriteLine(g.Greet());          // есть реализация по умолчанию
Console.WriteLine(g.Farewell());       // класс её переопределил

var p = new Polite();
// p.Greet();                          // ❌ не скомпилируется: через класс метод не виден
Console.WriteLine(((IGreeter)p).Greet());

interface IGreeter
{
    string Greet() => "Здравствуйте";            // default interface method
    string Farewell();
}

class Polite : IGreeter
{
    public string Farewell() => "До свидания";
}
~~~
~~~console
Здравствуйте
До свидания
Здравствуйте
~~~

### Шаг 6. Явная реализация интерфейса

~~~csharp
IExportable e = new Statement();
Console.WriteLine(e.Export());
// new Statement().Export();                 // ❌ не видно

var s = new Statement();
Console.WriteLine(((IExportable)s).Export());     // ✅ через интерфейс

IJson j = new Report();
IXml x = new Report();
Console.WriteLine(j.Export());                    // два интерфейса с одноимённым методом — разные реализации
Console.WriteLine(x.Export());

public interface IExportable { string Export(); }
public interface IJson { string Export(); }
public interface IXml { string Export(); }

public sealed class Statement : IExportable
{
    string IExportable.Export() => "CSV...";   // доступен только через переменную типа IExportable
}

public sealed class Report : IJson, IXml
{
    string IJson.Export() => "{...}";
    string IXml.Export() => "<report/>";
}
~~~
~~~console
CSV...
CSV...
{...}
<report/>
~~~

Явная реализация нужна, когда у двух интерфейсов совпадают имена членов (но реализации должны различаться) или когда не хочется выставлять член в публичном API типа.

### Шаг 7. Статические абстрактные члены (знать, что существует)

С C# 11 интерфейс может требовать **статические** члены — на этом построена «математика на generic-типах» (`INumber<T>`):

~~~csharp
Console.WriteLine(SumAll<int>(new[] { 1, 2, 3 }));
Console.WriteLine(SumAll<decimal>(new[] { 0.5m, 0.25m }));

static T SumAll<T>(IEnumerable<T> items) where T : System.Numerics.INumber<T>
{
    T sum = T.Zero;                 // T.Zero — статический член интерфейса
    foreach (T x in items) sum += x;
    return sum;
}
~~~
~~~console
6
0.75
~~~

Для Junior это «интересно, но редко нужно»; главное — понимать, что `where T : INumber<T>` — это ограничение через интерфейс.

## Как это работает под капотом

- **Вызов через интерфейс — тоже виртуальный.** Но у класса может быть много интерфейсов, и одной таблицы методов, как у наследования, недостаточно. Поэтому рантайм использует *карту интерфейсов* и механизм «virtual stub dispatch» с кэшированием: первый вызов находит нужную реализацию, следующие идут по готовому адресу. Накладные расходы чуть выше, чем у `virtual`-вызова, но в большинстве программ незаметны. Если JIT видит, что конкретный тип известен (например, `sealed`), он может вызвать метод напрямую.
- **Структура за интерфейсом = боксинг.** Приведение `IShape s = new CircleStruct()` упаковывает структуру ([боксинг](#p1-boxing)), а вызов метода меняет копию. Generic-метод с ограничением `where T : IShape` вызывает метод без упаковки (constrained call) — поэтому `INumber<T>` работает для `int` быстро.
- **Интерфейс не хранит состояние.** В экземпляре его нет — есть только «карта»: какие члены интерфейса реализованы какими методами класса. Default interface methods хранятся в самом интерфейсе и вызываются через переменную интерфейсного типа.
- **Явная реализация** компилируется в приватный метод с особой пометкой, привязанный к слоту интерфейса; поэтому он не виден через имя класса.
- **Приведение к интерфейсу** (`is IShape`, `(IShape)o`) — проверка в рантайме: реализует ли реальный тип этот интерфейс (результат кэшируется).
- **Интерфейс — ссылочный тип** с точки зрения переменной (хранит ссылку), даже если реализует его `struct` (в этом случае внутри — коробка).
- **Ковариантность** `IEnumerable<out T>`: `IEnumerable<string>` можно присвоить `IEnumerable<object>`. Об этом подробнее в теме про generics.

В справочнике: [абстрактный класс против интерфейса](#/ref/c/cl-abstract-vs-interface), [явная реализация](#/ref/c/cl-explicit-interface).

## Типичные ошибки и ловушки

:::danger Интерфейс «на каждый класс» без причины
`IBankAccount` для доменной сущности, у которой никогда не будет второй реализации, — лишняя церемония. Интерфейс нужен на **границах**, где реально нужна подмена: хранилище, внешние сервисы, время.
:::

:::danger Абстрактный класс с деталями реализации в контракте
Пути к файлам, строки подключения, HTTP-клиенты в базовом классе превращают абстракцию в привязку к конкретной технологии.
:::

:::danger Структура за интерфейсом
`IShape s = new Circle()`, где `Circle` — struct, означает [боксинг](#p1-boxing) и работу с копией. Если тип живёт за интерфейсом, пусть это будет класс.
:::

- **«Жирные» интерфейсы.** Двадцать членов в одном интерфейсе: каждая реализация вынуждена заполнять неиспользуемые заглушки (`throw new NotImplementedException()`). Дели по ролям.
- **Интерфейс как «папка для методов».** `IHelper`, `IManager`, `IUtils` — неопределённые роли. Хороший интерфейс называется по возможности: `IPriceCalculator`, `IClock`.
- **Менять опубликованный интерфейс.** Добавление члена ломает всех реализующих. Для публичных библиотек — новые интерфейсы (`IStoreV2`) или default-методы.
- **Утечки конкретных типов.** Метод интерфейса возвращает `List<T>` или принимает `SqlConnection` — детали реализации снова в контракте. Возвращай `IReadOnlyList<T>`, принимай абстракции.
- **Выбор реализации внутри потребителя.** `new TextFileAccountStore()` прямо в `BankService` убивает смысл интерфейса. Реализацию передают снаружи (конструктор), выбирают в одном месте — точке входа.
- **`NotImplementedException` в реализации** — сигнал, что интерфейс слишком широкий или класс не должен его реализовывать (нарушение принципа Лисков).
- **Использование `is`-проверок вместо полиморфизма.** `if (store is TextFileAccountStore)` внутри сервиса возвращает зависимость от конкретики.
- **Путаница `IEnumerable<T>` и `List<T>` в сигнатурах.** Принимай самый общий тип, который нужен; возвращай достаточно конкретный (но не изменяемый наружу).

## Вопросы с собеседований

:::spoiler Почему `IAccountStore` лучше `FileStorageBase` для банковского проекта?
Интерфейс описывает только то, что нужно потребителю (загрузить и сохранить счета), не навязывая деталей вроде пути к файлу. Его могут реализовать файл, база, память — без общего состояния и без занятого единственного базового класса. Потребитель не меняется при смене хранилища.
:::

:::spoiler Когда абстрактный класс — правильный выбор?
Когда есть семейство типов, которые ты контролируешь, с общим состоянием и общим алгоритмом, и наследники «являются» базовым типом. Пример — `Account` с шаблонным методом `Withdraw`.
:::

:::spoiler Зачем `IClock`, если есть `DateTime.Now`?
Чтобы логику, зависящую от времени (конец месяца, просрочка, срок вклада), можно было проверить детерминированно, подставив фиксированное время, — без ожидания и без изменения системных часов.
:::

:::spoiler Что сломается, если добавить метод в опубликованный интерфейс?
Все существующие реализации перестанут компилироваться, пока не реализуют новый метод (если только не использовать default interface method). У абстрактного класса добавление невиртуального или виртуального метода с реализацией наследников не ломает.
:::

:::spoiler Может ли интерфейс содержать реализацию методов? Поля? (ловушка: «нет, никогда»)
Реализацию — да, начиная с C# 8 (default interface methods) и статические члены; поля экземпляра — нет (состояния у интерфейса нет). Default-методы видны только через тип интерфейса.
:::

:::spoiler Класс реализует два интерфейса с одинаковым методом — что делать?
Либо одна общая публичная реализация (если поведение должно быть одним), либо явная реализация каждого интерфейса (`void IA.M()`, `void IB.M()`), когда поведение должно различаться.
:::

:::spoiler Можно ли создать экземпляр интерфейса или абстрактного класса?
Нет. Создают экземпляры конкретных классов; переменная при этом может быть интерфейсного/базового типа.
:::

:::spoiler Что такое внедрение зависимостей и как оно связано с интерфейсами?
Зависимости класса передаются ему снаружи (обычно через конструктор), а не создаются внутри. Класс объявляет их интерфейсами, поэтому реализацию можно подменять (в тестах, при смене технологии). В ASP.NET Core этим занимается встроенный DI-контейнер.
:::

:::spoiler Почему структуру за интерфейсом считают проблемой?
Приведение структуры к интерфейсу упаковывает её (аллокация), а вызовы методов через интерфейс работают с копией в коробке — изменения не видны оригиналу.
:::

## Что запомнить

- **Интерфейс** — контракт «что умеет»: нет состояния и конструкторов, можно реализовать много, подходит для структур. **Абстрактный класс** — «чем является» + общее состояние/алгоритм, наследуется один.
- На **границах системы** (хранилище, часы, внешние сервисы) — интерфейс; внутри одного семейства с общим кодом — абстрактный класс; часто комбинируют.
- Потребитель зависит от интерфейса и получает реализацию снаружи (конструктор) — это основа DI и тестирования.
- Интерфейсы маленькие и стабильные (ISP); добавление члена ломает все реализации.
- Default interface methods и статические абстрактные члены существуют, но используются осторожно.
- Явная реализация разрешает конфликты имён и скрывает член из публичного API типа.
- Структура за интерфейсом → боксинг и копия.
- Интерфейс — не «на каждый класс», а там, где нужна подмена.
