## Зачем это нужно

Вопрос по системному дизайну проверяет не знание модных технологий, а **способ думать**: задаёшь ли ты уточняющие вопросы, умеешь ли прикинуть масштаб, видишь ли цену каждого решения. Junior, который говорит «поставим Redis, Kafka и Kubernetes», выглядит хуже, чем тот, кто сказал: «Сначала уточню: сколько запросов в секунду и что важнее, скорость или точность? Читают намного чаще, чем пишут, поэтому кэш здесь оправдан; вот чем я за него плачу».

Системный дизайн нужен и в обычной работе: любое решение «добавить кэш», «вынести в очередь», «поднять второй экземпляр» опирается на одни и те же понятия. Эта тема связывает всё, что ты прошёл: [кэш](#p6-cache), [базу данных и индексы](#p3-indexes), [контейнеры и деплой](#p6-deploy), [фоновые службы](#p5-background).

Чего эта страница не делает: она не учит проектировать распределённые системы уровня senior (консенсус, шардирование, согласованность в конце концов). Она даёт каркас ответа на 20 минут, словарь из десяти понятий и разбор одной задачи (сервис коротких ссылок). Особенность формата: примеры ниже **считают и запускают** то, о чём обычно только говорят. Оценка нагрузки посчитана кодом, балансировщик с тремя экземплярами работает на живых серверах, планы запросов получены из настоящего PostgreSQL, а эффект кэша на неравномерной нагрузке измерен моделью. Только то, что требует облачной инфраструктуры (CDN, реплики, настоящие очереди), описано словами.

## Интуиция и аналогия

**Система — это ресторан в час пик.** Один повар (сервер) рано или поздно не справится: можно купить ему плиту побольше (вертикальное масштабирование) или нанять ещё поваров (горизонтальное), но тогда нужен администратор зала (балансировщик), и поварам нельзя помнить заказ гостя «в голове» (stateless): заказ должен лежать на общем листке, иначе следующий повар его не найдёт.

**Кэш — готовые заготовки.** Самые популярные блюда лежат наготове. Они быстрее, но к вечеру черствеют (устаревание).

**Очередь — приёмное окно на кухню.** Официанты не стоят у плиты, а кладут заказы в окно; повара берут их по очереди. Пик заказов не ломает кухню, а лишь удлиняет очередь.

**Индекс — оглавление книги.** Найти главу по оглавлению быстро; но каждую новую главу нужно вписать и в оглавление (запись дороже).

**Оценка «на салфетке» — не точность, а порядок величин.** Три запроса в секунду и тридцать тысяч — разные архитектуры. Различить их можно за минуту простым делением.

## Основная теория по шагам

### Шаг 1. Словарь, который нужно уметь объяснить

| Понятие | Одним предложением |
|---|---|
| Вертикальное масштабирование | больше CPU/памяти одному серверу; просто, но есть потолок |
| Горизонтальное масштабирование | больше одинаковых экземпляров за балансировщиком; требует stateless-приложения |
| Stateless API | экземпляр не хранит состояние между запросами (сессии — в токене/Redis, файлы — в хранилище), поэтому любой экземпляр обслужит любой запрос |
| Балансировщик нагрузки | распределяет запросы между экземплярами и убирает больные (по health check) |
| Кэш | быстрая копия часто читаемых данных; цена — устаревание |
| Индекс БД | ускоряет поиск, замедляет запись |
| Реплика для чтения | копия БД для чтений; данные могут отставать |
| Очередь сообщений | отложенная и сглаженная обработка, развязка сервисов |
| CDN | раздача статики и файлов ближе к пользователю |
| Идемпотентность | повтор операции не меняет результат — основа безопасных ретраев |

Проверь себя: если можешь объяснить каждое понятие вслух за 20 секунд и привести пример, где оно *вредно*, словарь освоен. Три из них (stateless и балансировщик, индекс, очередь) мы сейчас потрогаем руками.

### Шаг 2. Схема ответа из 5 шагов

1. **Требования.** Что система делает (функциональные), сколько пользователей и запросов, что важнее — скорость, согласованность, доступность (нефункциональные). Задай уточняющие вопросы — это часть оценки.
2. **API.** Основные эндпоинты.
3. **Данные.** Сущности, таблицы, ключи, индексы.
4. **Схема.** Клиент → балансировщик → API → БД / кэш / очередь. Путь основного запроса.
5. **Узкие места и масштабирование.** Что сломается первым при росте в 10 раз и что делать.

Распределяй время: примерно 20% на требования и оценку, 30% на API и данные, 30% на схему, 20% на узкие места. Если дошёл до схемы за 15 минут из 20, ты пересказывал требования слишком долго.

### Шаг 3. Оценка нагрузки «на салфетке»

Первое, что делает хороший ответ: переводит «много пользователей» в числа. Принцип прост: называешь допущения вслух, считаешь порядок величин, не гонишься за точностью. Посчитаем для сервиса коротких ссылок (допущения мои, на собеседовании ты называешь свои): 10 миллионов новых ссылок в месяц, чтений в сто раз больше, пик в пять раз выше средней нагрузки, одна запись занимает 500 байт:

~~~csharp
using System.Globalization;

string F(double v, string fmt = "F1") => v.ToString(fmt, CultureInfo.InvariantCulture);

// Допущения — их проговаривают вслух и сразу уточняют у интервьюера
double newLinksPerMonth = 10_000_000;
double readWriteRatio = 100;                    // переходов в 100 раз больше, чем созданий
double peakFactor = 5;                          // пик выше среднего в 5 раз
double bytesPerLink = 500;
double secondsPerMonth = 30 * 24 * 3600;

var writesPerSec = newLinksPerMonth / secondsPerMonth;
var readsPerSec = writesPerSec * readWriteRatio;
var peakReads = readsPerSec * peakFactor;
Console.WriteLine($"записей в секунду (среднее): {F(writesPerSec)}");
Console.WriteLine($"чтений в секунду (среднее):  {F(readsPerSec, "F0")}");
Console.WriteLine($"чтений в секунду (пик):      {F(peakReads, "F0")}");

var links5Years = newLinksPerMonth * 12 * 5;
var storageGb = links5Years * bytesPerLink / 1e9;
Console.WriteLine($"ссылок за 5 лет: {F(links5Years / 1e6, "F0")} млн, места на диске: {F(storageGb, "F0")} ГБ");

var hotShare = 0.01;                            // допущение: горячим окажется 1% ссылок
var cacheGb = links5Years * hotShare * bytesPerLink / 1e9;
Console.WriteLine($"кэш под 1% ссылок: {F(cacheGb, "F0")} ГБ памяти");

// Вывод для ответа
Console.WriteLine(peakReads < 5000
    ? "вывод: пик в пределах возможностей одного-двух экземпляров API; кэш нужен ради скорости и разгрузки БД, а не из-за невозможности справиться"
    : "вывод: нужно несколько экземпляров и кэш");
~~~
~~~console
записей в секунду (среднее): 3.9
чтений в секунду (среднее):  386
чтений в секунду (пик):      1929
ссылок за 5 лет: 600 млн, места на диске: 300 ГБ
кэш под 1% ссылок: 3 ГБ памяти
вывод: пик в пределах возможностей одного-двух экземпляров API; кэш нужен ради скорости и разгрузки БД, а не из-за невозможности справиться
~~~

Главный вывод оценки: при таких допущениях нагрузка скромная (около двух тысяч чтений в секунду в пик), и честный ответ звучит так: «один экземпляр API справится, но я держу два ради отказоустойчивости, а кэш поставлю для скорости редиректа». Это лучше, чем сразу рисовать десять серверов. Меняя допущения, ты видишь, где архитектура меняется качественно. Цифры не должны быть «из головы»: полезно помнить порядки (диск на сервере измеряется терабайтами, одна машина с кэшем в памяти обслуживает десятки тысяч запросов в секунду), но называй их допущениями, а не фактами.

### Шаг 4. Разбор: сервис коротких ссылок

**Требования:** создать короткую ссылку для длинного URL; переход по короткой ссылке → редирект; статистика переходов. Чтений (переходов) намного больше, чем записей (создания).

**API:**

~~~text
POST /api/links          { "url": "https://..." }  → 201 { "code": "aZ3k9", "shortUrl": "https://sh.rt/aZ3k9" }
GET  /{code}                                         → 302 Location: https://...
GET  /api/links/{code}/stats                         → 200 { "clicks": 1234, ... }
~~~

Код ответа редиректа важен: `301` браузеры кэшируют навсегда (переход перестанет попадать в статистику), `302` не кэшируют (каждый переход виден серверу). Для сервиса со статистикой берут `302`.

**Данные.** Вот схема, и сразу проверим её на настоящем PostgreSQL с реальными объёмами (100 тысяч ссылок, 60 тысяч переходов). Главный запрос системы — найти ссылку по коду; убедимся, что его обслуживает индекс (его создаёт ограничение `UNIQUE`), и сравним с поиском по неиндексированной колонке. Команда `EXPLAIN` показывает план запроса без выполнения; `COSTS OFF` убирает числовые оценки, чтобы вывод был стабильным:

~~~sql
CREATE TABLE links (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    code        TEXT NOT NULL UNIQUE,          -- индекс: поиск по коду на каждый переход
    target_url  TEXT NOT NULL,
    owner_id    INT  NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE clicks (
    link_id     BIGINT NOT NULL REFERENCES links(id),
    clicked_at  TIMESTAMPTZ NOT NULL,
    referrer    TEXT NULL
);

INSERT INTO links(code, target_url) SELECT 'c' || g, 'https://example.com/page/' || g FROM generate_series(1, 100000) g;
INSERT INTO clicks(link_id, clicked_at, referrer)
SELECT (g % 1000) + 1, TIMESTAMPTZ '2026-01-01 00:00:00+00' + g * interval '1 minute', CASE WHEN g % 3 = 0 THEN 'https://news.example' END
FROM generate_series(1, 60000) g;
ANALYZE links;
ANALYZE clicks;
SET max_parallel_workers_per_gather = 0;

-- редирект: поиск по коду (индекс от UNIQUE)
EXPLAIN (COSTS OFF) SELECT target_url FROM links WHERE code = 'c777';
-- поиск по колонке без индекса
EXPLAIN (COSTS OFF) SELECT target_url FROM links WHERE owner_id = 5;
-- статистика по ссылке без индекса на clicks
EXPLAIN (COSTS OFF) SELECT count(*) FROM clicks WHERE link_id = 7;

CREATE INDEX clicks_link_time ON clicks (link_id, clicked_at);
ANALYZE clicks;
EXPLAIN (COSTS OFF) SELECT count(*) FROM clicks WHERE link_id = 7;
SELECT count(*) AS clicks, min(clicked_at)::date AS first_day FROM clicks WHERE link_id = 7;
~~~

Три урока из планов. Поиск по коду идёт через индекс (`Index Scan`) без просмотра ста тысяч строк; на колонке без индекса база вынуждена читать всю таблицу (`Seq Scan`); для статистики индекс по `(link_id, clicked_at)` превращает полный просмотр в точечное чтение. Но индекс не бесплатен: каждая вставка в `clicks` теперь обновляет и его, поэтому запись клика становится дороже. На схеме ниже это одна из причин вынести запись клика из горячего пути редиректа. Подробнее про индексы и планы читай в [разделе про индексы](#p3-indexes).

**Схема:**

~~~text
                 ┌────────────────┐
 браузер ──────▶ │ балансировщик  │
                 └───────┬────────┘
             ┌───────────┼───────────┐
             ▼           ▼           ▼
          API #1      API #2      API #3        (stateless, одинаковые)
             │  GET /{code}: сначала Redis ──▶ промах → PostgreSQL → положить в Redis
             │
             └─ событие «переход» ──▶ очередь ──▶ воркер пишет clicks пачками
~~~

### Шаг 5. Как кодировать ссылку

Короткий код можно получить двумя способами: закодировать числовой `id` в систему счисления с 62 символами (цифры и латинские буквы двух регистров) или выдавать случайную строку и проверять уникальность. Посчитаем оба варианта:

~~~csharp
using System.Text;

const string Alphabet = "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz";

string Encode(long id)
{
    if (id == 0) return "0";
    var sb = new StringBuilder();
    for (; id > 0; id /= 62) sb.Insert(0, Alphabet[(int)(id % 62)]);
    return sb.ToString();
}
long Decode(string code) => code.Aggregate(0L, (acc, c) => acc * 62 + Alphabet.IndexOf(c));

Console.WriteLine("числовой id → код → обратно:");
foreach (var id in new long[] { 1, 61, 62, 125, 1_000_000, 56_800_235_583 })
{
    var code = Encode(id);
    Console.WriteLine($"  {id,14} → {code,-7} → {Decode(code)}");
}
var space6 = Math.Pow(62, 6);
Console.WriteLine($"шестизначных кодов: {space6:N0}");

// случайные коды: сколько будет коллизий (парных совпадений)?
double ExpectedCollisions(double n, double space) => n * n / (2 * space);                                // приближение задачи о днях рождения
Console.WriteLine($"ожидаемых коллизий при 1 млн случайных 6-значных кодов: {ExpectedCollisions(1e6, space6):F1}");
Console.WriteLine($"ожидаемых коллизий при 10 млн случайных 6-значных кодов: {ExpectedCollisions(1e7, space6):F0}");

// проверим моделью: 1 млн случайных кодов, собственный детерминированный генератор
ulong state = 88172645463325252UL;
ulong Next() { state ^= state << 13; state ^= state >> 7; state ^= state << 17; return state; }
var seen = new HashSet<ulong>();
var collisions = 0;
for (int i = 0; i < 1_000_000; i++)
    if (!seen.Add(Next() % (ulong)space6)) collisions++;
Console.WriteLine($"в модели получилось коллизий: {collisions} — порядок совпадает с оценкой, значит повтор при коллизии нужен, но он редок");

Console.WriteLine($"последовательные id угадываются: коды {Encode(1000)}, {Encode(1001)}, {Encode(1002)} идут подряд");
~~~

Вывод для ответа. Кодирование `id` не даёт коллизий и даёт короткие коды (шесть символов вмещают около 57 миллиардов ссылок), но коды идут подряд: любой перебирает чужие ссылки (враждебное «перечисление»). Случайные коды скрывают порядок, но требуют `UNIQUE` и повтора при коллизии (при десятках миллионов ссылок коллизии появляются регулярно). Обе схемы приемлемы; важно назвать цену и выбрать осознанно. Если сервис не должен раскрывать темп роста, бери случайные коды.

### Шаг 6. Stateless и балансировщик на живых серверах

Фраза «API должен быть stateless» кажется абстрактной, пока не увидишь, как ломается жизнь без неё. Поднимем настоящие три экземпляра «API» (A, B, C) и простой балансировщик, который раздаёт запросы по кругу и перед каждым запросом проверяет `/health` (экземпляры, не отвечающие на проверку, пропускаются). Сначала сессии хранятся в памяти каждого экземпляра, потом в общем хранилище (в проекте это был бы Redis; здесь общий словарь на всех), в конце один экземпляр падает:

~~~csharp
using System.Collections.Concurrent;

async Task<(List<Node>, Balancer)> Start(bool shared)
{
    var store = new ConcurrentDictionary<string, string>();
    var nodes = new[] { "A", "B", "C" }.Select(n => new Node(n, shared, store)).ToList();
    foreach (var n in nodes) await n.StartAsync();
    return (nodes, new Balancer(nodes));
}

async Task Scenario(string title, bool shared, bool killOne)
{
    var (nodes, lb) = await Start(shared);
    Console.WriteLine(title);
    Console.WriteLine($"  вход:        {await lb.SendAsync(HttpMethod.Post, "/login/valera", null)}");
    for (int i = 1; i <= 3; i++)
        Console.WriteLine($"  запрос /me {i}: {await lb.SendAsync(HttpMethod.Get, "/me", "tok-valera")}");
    if (killOne)
    {
        await nodes[1].StopAsync();
        Console.WriteLine("  --- узел B остановлен ---");
        for (int i = 4; i <= 7; i++)
            Console.WriteLine($"  запрос /me {i}: {await lb.SendAsync(HttpMethod.Get, "/me", "tok-valera")}");
    }
    foreach (var n in nodes) await n.StopAsync();
}

await Scenario("1. сессия хранится в памяти экземпляра:", shared: false, killOne: false);
await Scenario("2. сессия в общем хранилище, затем падает узел B:", shared: true, killOne: true);

public sealed class Node
{
    private readonly WebApplication _app;
    public string Name { get; }
    public string Url { get; private set; } = "";

    public Node(string name, bool shared, ConcurrentDictionary<string, string> store)
    {
        Name = name;
        var sessions = shared ? store : new ConcurrentDictionary<string, string>();                     // свой словарь у каждого, если не общий
        var builder = WebApplication.CreateBuilder();
        builder.WebHost.UseUrls("http://127.0.0.1:0");
        builder.Logging.ClearProviders();
        _app = builder.Build();
        _app.MapPost("/login/{user}", (string user) => { var token = "tok-" + user; sessions[token] = user; return Results.Ok(token); });
        _app.MapGet("/me", (HttpContext c) => sessions.TryGetValue(c.Request.Headers["X-Token"].ToString(), out var user)
            ? Results.Ok($"привет, {user}") : Results.Unauthorized());
        _app.MapGet("/health", () => Results.Ok());
    }

    public async Task StartAsync() { await _app.StartAsync(); Url = _app.Urls.First(); }
    public Task StopAsync() => _app.StopAsync();
}

public sealed class Balancer(List<Node> nodes)
{
    private int _next;
    private readonly HttpClient _http = new() { Timeout = TimeSpan.FromSeconds(1) };

    public async Task<string> SendAsync(HttpMethod method, string path, string? token)
    {
        for (int i = 0; i < nodes.Count; i++)
        {
            var node = nodes[_next++ % nodes.Count];
            try { if (!(await _http.GetAsync(node.Url + "/health")).IsSuccessStatusCode) continue; }    // проверка здоровья перед выбором
            catch (HttpRequestException) { continue; }
            var req = new HttpRequestMessage(method, node.Url + path);
            if (token is not null) req.Headers.Add("X-Token", token);
            var response = await _http.SendAsync(req);
            return $"узел {node.Name}: {(int)response.StatusCode}";
        }
        return "нет живых узлов: 503";
    }
}
~~~
~~~console
1. сессия хранится в памяти экземпляра:
  вход:        узел A: 200
  запрос /me 1: узел B: 401
  запрос /me 2: узел C: 401
  запрос /me 3: узел A: 200
2. сессия в общем хранилище, затем падает узел B:
  вход:        узел A: 200
  запрос /me 1: узел B: 200
  запрос /me 2: узел C: 200
  запрос /me 3: узел A: 200
  --- узел B остановлен ---
  запрос /me 4: узел C: 200
  запрос /me 5: узел A: 200
  запрос /me 6: узел C: 200
  запрос /me 7: узел A: 200
~~~

Первый сценарий воспроизводит классическую ошибку: пользователь вошёл на узле A, а следующий запрос по кругу попал на B, где сессии нет, и получил `401`. Для пользователя это «меня случайно разлогинивает». Во втором сценарии состояние вынесено в общее хранилище, и любой узел обслужит любой запрос; когда B упал, балансировщик по проверке здоровья перестал отправлять ему запросы, и пользователи ничего не заметили. Альтернатива общему хранилищу, о которой стоит знать, — «липкие сессии» (балансировщик всегда отправляет пользователя на один узел): они работают, но при падении узла сессия пропадает, а нагрузка распределяется неровно.

### Шаг 7. Очередь для статистики

Запись клика в базу не должна замедлять редирект. Обработчик кладёт событие в очередь и сразу отвечает, а воркер забирает события пачками. Покажем механику встроенной очередью `Channel<T>`, а границу очереди (что делать, когда она заполнена) стоит обсуждать отдельно:

~~~csharp
using System.Threading.Channels;

// 1. Горячий путь: событие кладём в очередь, на запись в базу не ждём
var queue = Channel.CreateUnbounded<int>();
for (int click = 1; click <= 25; click++) queue.Writer.TryWrite(click);
queue.Writer.Complete();
Console.WriteLine("редиректов обслужено без обращения к базе: 25");

// 2. Воркер забирает пачками по 10 и пишет одним запросом
var batches = new List<int>();
var batch = new List<int>();
await foreach (var click in queue.Reader.ReadAllAsync())
{
    batch.Add(click);
    if (batch.Count == 10) { batches.Add(batch.Count); batch.Clear(); }                                  // «INSERT … VALUES (…10 строк…)»
}
if (batch.Count > 0) batches.Add(batch.Count);
Console.WriteLine($"обращений к базе вместо 25: {batches.Count} (размеры пачек: {string.Join(", ", batches)})");

// 3. Граница очереди: ограниченная очередь защищает память
var bounded = Channel.CreateBounded<int>(new BoundedChannelOptions(5) { FullMode = BoundedChannelFullMode.Wait });
int accepted = 0, rejected = 0;
for (int click = 1; click <= 8; click++)
    if (bounded.Writer.TryWrite(click)) accepted++; else rejected++;
Console.WriteLine($"очередь на 5 мест, пришло 8: принято {accepted}, отклонено {rejected} (решаем заранее: отбросить клик, ответить ошибкой или ждать)");
~~~
~~~console
редиректов обслужено без обращения к базе: 25
обращений к базе вместо 25: 3 (размеры пачек: 10, 10, 5)
очередь на 5 мест, пришло 8: принято 5, отклонено 3 (решаем заранее: отбросить клик, ответить ошибкой или ждать)
~~~

`Channel<T>` живёт внутри процесса: при падении приложения содержимое очереди пропадёт. Для статистики кликов это допустимо (потеря нескольких событий не критична), для заказов нет: тогда нужна внешняя очередь с подтверждением обработки (брокер сообщений), а обработчик событий должен быть **идемпотентным**, потому что брокеры обычно доставляют сообщение «как минимум один раз», то есть возможны дубли ([идемпотентность](#p6-cache)).

### Шаг 8. Эффект кэша: почему он работает, когда нагрузка неравномерна

Кэш помогает, если популярных данных мало, а запросов к ним много. Проверим моделью: 10 тысяч ссылок, популярность падает по закону Ципфа (вторая по популярности вдвое реже первой, третья втрое и так далее; так обычно ведут себя ссылки, статьи, товары), кэш вмещает только 1% ссылок (100 штук) и вытесняет давно не использованные:

~~~csharp
const int links = 10_000;
// накопленные веса по закону Ципфа: ранг r имеет вес 1/r
var cumulative = new double[links];
double sum = 0;
for (int r = 0; r < links; r++) { sum += 1.0 / (r + 1); cumulative[r] = sum; }

ulong state = 1234567890123456789UL;                                                                    // собственный генератор: результат воспроизводим
double NextDouble() { state ^= state << 13; state ^= state >> 7; state ^= state << 17; return (state >> 11) / (double)(1UL << 53); }
int NextRank()
{
    var x = NextDouble() * sum;
    int lo = 0, hi = links - 1;
    while (lo < hi) { var mid = (lo + hi) / 2; if (cumulative[mid] < x) lo = mid + 1; else hi = mid; }
    return lo;
}

double HitRate(int capacity, int requests)
{
    var order = new LinkedList<int>();                                                                  // от свежих к давним
    var index = new Dictionary<int, LinkedListNode<int>>();
    int hits = 0;
    for (int i = 0; i < requests; i++)
    {
        var rank = NextRank();
        if (index.TryGetValue(rank, out var node)) { hits++; order.Remove(node); order.AddFirst(node); }   // попадание: освежаем
        else
        {
            if (index.Count >= capacity) { index.Remove(order.Last!.Value); order.RemoveLast(); }          // вытесняем самого давнего
            index[rank] = order.AddFirst(rank);
        }
    }
    return 100.0 * hits / requests;
}

foreach (var capacity in new[] { 10, 100, 1000 })
    Console.WriteLine($"кэш на {capacity,4} ссылок ({100.0 * capacity / links,4:F1}% всех): доля попаданий {HitRate(capacity, 200_000):F0}%");
~~~
~~~console
кэш на   10 ссылок ( 0.1% всех): доля попаданий 13%
кэш на  100 ссылок ( 1.0% всех): доля попаданий 39%
кэш на 1000 ссылок (10.0% всех): доля попаданий 68%
~~~

Даже кэш на 1% ссылок снимает с базы около 40% запросов, а на 10% — около 70%; чем дальше, тем медленнее растёт выигрыш на каждый дополнительный процент памяти. Это и есть ответ на вопрос «почему кэш помогает»: нагрузка неравномерна. Но модель предупреждает и о границах: если бы запросы шли к ссылкам равновероятно, тот же кэш давал бы около 1% попаданий. Прежде чем добавлять кэш, выясни, есть ли такая «голова» в реальной нагрузке (логи, метрики), и измерь результат.

### Шаг 9. Решения и почему

- **Код ссылки:** base62 от `id` (короткий, без коллизий) или случайная строка + `UNIQUE` и повтор при коллизии (не раскрывает количество ссылок).
- **Кэш на чтение:** переходов намного больше, чем созданий, ссылка почти никогда не меняется → идеальный кандидат для кэша с долгим TTL.
- **Статистика через очередь:** запись клика не должна замедлять редирект; воркер пишет пачками.
- **Масштабирование:** API stateless → добавляем экземпляры; БД — индексы, затем реплики для чтения статистики.
- **Защита:** rate limiting на создание, проверка URL (не давать делать редиректы на вредоносные сайты — хотя бы чёрный список доменов).

## Как это работает под капотом

- **Балансировщик работает на разных уровнях.** Уровень соединений (L4) просто пересылает TCP-поток, уровень приложения (L7, как nginx или Caddy) понимает HTTP и может выбирать узел по пути и заголовкам. Алгоритмы: по кругу (мы использовали), по наименьшему числу соединений, по хэшу клиента (липкость). Проверки здоровья исключают больные узлы и возвращают их, когда они восстановились.
- **Почему stateless масштабируется.** Если запрос не зависит от того, какой узел его обслуживает, узлов можно добавлять и убирать без потерь. Состояние при этом не исчезает, а переезжает в специализированное хранилище (база, Redis, объектное хранилище), и оно становится узким местом, которое масштабируется отдельно.
- **Индекс в базе — дерево.** B-дерево по колонке хранит значения отсортированными с указателями на строки, поэтому поиск по значению — это логарифмическое число шагов, а не просмотр всей таблицы (мы видели `Index Scan` против `Seq Scan`). Каждая запись обновляет дерево, отсюда цена записи. Планировщик сам выбирает между индексом и полным просмотром по статистике (`ANALYZE`), поэтому на крошечной таблице индекс может быть проигнорирован.
- **Реплика для чтения.** Запись идёт на основной сервер, изменения асинхронно копируются на реплики. Читая с реплики, можно увидеть данные, которых ещё нет «последних изменений» (отставание репликации). Поэтому «создал и сразу открыл» может не найти запись, если читать с реплики.
- **CAP и компромиссы.** При разделении сети нельзя одновременно сохранить согласованность и доступность; на практике выбирают, что важнее для конкретной операции: баланс счёта должен быть согласованным, счётчик просмотров может отставать.
- **Очередь и гарантии доставки.** «Не более одного раза» теряет сообщения, «как минимум один раз» дублирует, «ровно один раз» на практике достигается идемпотентной обработкой поверх «как минимум одного». Поэтому идемпотентность появляется снова и снова.
- **Кэш и согласованность.** Данные в кэше — копия. Любое решение «читаем из кэша» означает, что ты согласен на окно устаревания; в этом окне пользователь может видеть старое.
- **Узкое место сдвигается.** Усилив одно звено (больше экземпляров API), нагрузка перекладывается на следующее (база). Поэтому ответ о масштабировании всегда идёт по цепочке: что упрётся первым, потом что следом.
- **Чего здесь нет.** Мы не запускали реальные реплики, CDN и брокер сообщений: описаны их свойства и последствия, а примеры показывают соседние механизмы (индексы, балансировщик, очередь в процессе, кэш).

## Типичные ошибки и ловушки

- **Начать с технологий вместо требований.** «Поставим Kafka» до вопроса, сколько запросов.
- **Не оценить масштаб.** Проектирование на тысячу запросов в секунду, когда их три; или наоборот.
- **Состояние в памяти экземпляра** (сессии, загруженные файлы, локальный кэш, который должен быть общим): «меня случайно разлогинивает».
- **Один экземпляр и «надёжно».** Единая точка отказа: балансировщик, база, кэш. Назови, что будет, если упадёт каждое звено.
- **Кэш без ответа на вопрос о свежести.** Какой TTL, кто инвалидирует, что при недоступном кэше.
- **Индекс «на всё».** Каждый индекс замедляет запись и занимает память; индексируй по реальным запросам.
- **Запись в базу на горячем пути, когда она не нужна пользователю сразу** (статистика, логи): вынеси в очередь.
- **Очередь без плана на переполнение и дубли.** Бесконечная очередь съедает память; необработанные дубли ломают данные.
- **Чтение с реплики сразу после записи.** Отставание репликации даёт «не найдено».
- **Предсказуемые идентификаторы в публичных адресах.** Последовательные коды перебираются.
- **Не называть слабые места своего решения.** Интервьюер хочет услышать компромиссы, а не «идеальную» схему.
- **Усложнять ради красоты.** Для капстоуна микросервисы и шардирование не нужны: их преждевременное внедрение — минус, а не плюс.

## Вопросы с собеседований

:::spoiler Почему для горизонтального масштабирования API должен быть stateless?
Балансировщик отправляет запросы одного пользователя на разные экземпляры. Если состояние хранится в памяти экземпляра (сессия, кэш, загруженный файл), другой экземпляр его не увидит.
:::

:::spoiler Когда кэш — плохая идея?
Когда данные часто меняются и устаревание недопустимо (баланс счёта при списании), когда данные редко читаются повторно, или когда кэш добавляет сложности больше, чем экономит.
:::

:::spoiler Зачем очередь для статистики переходов?
Чтобы основная операция (редирект) не ждала записи в БД, а нагрузка от пиков переходов сглаживалась: воркер пишет с постоянной скоростью и пачками.
:::

:::spoiler С чего ты начнёшь проектировать систему? (ловушка: «выберу технологии»)
С требований и оценки нагрузки: что система делает, сколько запросов и данных, что важнее (скорость, согласованность, доступность). Технологии выбираются потом и обосновываются этими числами.
:::

:::spoiler Чем вертикальное масштабирование отличается от горизонтального?
Вертикальное: усилить один сервер (просто, но есть потолок и единая точка отказа). Горизонтальное: добавить одинаковые экземпляры за балансировщиком (сложнее, требует stateless, зато растёт почти линейно и отказоустойчиво).
:::

:::spoiler Что такое реплика для чтения и какие у неё риски?
Копия базы, на которую направляют чтения. Риск: отставание репликации — свежая запись может быть не видна. Подходит для отчётов и статистики, не для «прочитай только что записанное».
:::

:::spoiler Как кодировать короткие ссылки: id в base62 или случайные коды?
Base62 от `id`: короткий и без коллизий, но последовательный и угадываемый. Случайные коды: непредсказуемы, но нужны `UNIQUE` и повтор при коллизии. Выбор зависит от требований к приватности и росту.
:::

:::spoiler Что произойдёт при падении одного экземпляра API? А базы? А кэша?
Экземпляр: балансировщик по health check перестанет слать на него запросы. База: единая точка отказа, нужны резервные копии и реплика/переключение. Кэш: приложение должно работать медленнее, обращаясь к базе. Умение пройтись по каждому звену — часть ответа.
:::

:::spoiler Почему 301 плохо подходит для сервиса коротких ссылок со статистикой?
Браузеры кэшируют постоянный редирект, поэтому повторные переходы не доходят до сервера и не попадают в статистику. Используют 302/307.
:::

- Схема ответа: требования и оценка → API → данные → схема → узкие места. Задавай уточняющие вопросы и называй допущения.
- Оценка нагрузки «на салфетке» определяет архитектуру: часто один-два экземпляра справляются, а кэш нужен ради скорости.
- Stateless-API масштабируется горизонтально; состояние живёт в общем хранилище; балансировщик исключает больные узлы по health check.
- Индекс ускоряет поиск и замедляет запись; проверяй план запроса (`EXPLAIN`).

## Зачем это нужно

Алгоритмические задачи — спорная, но реальная часть найма. Компании используют их как быстрый фильтр: за 30–40 минут видно, как человек разбирает условие, ищет решение, пишет код и проверяет его. Можно спорить, насколько это справедливо; полезнее принять правила игры и подготовиться системно. Подготовка к собеседованиям при этом даёт и побочную пользу: ты начинаешь замечать, что цикл внутри цикла по большому списку — это O(n²), что словарь превращает поиск в O(1), а что-то «слишком медленное» можно ускорить сменой структуры данных. Это ежедневная инженерная гигиена.

Главная мысль страницы: **не зубри решения, а запоминай приёмы и признаки**. Одиннадцати паттернов хватает для большинства задач уровня easy–medium. Для каждого ниже есть: по каким словам в условии его узнать, решение «в лоб» и оптимизированное, подсчёт того, сколько работы действительно делает код, и типичные грабли. Все примеры запускаются: решения проверены на крайних случаях и **стресс-тестами против перебора**: ты увидишь приём, который позволяет находить собственные ошибки, не дожидаясь, пока их найдёт интервьюер.

Чего здесь нет: сложных тем (сегментные деревья, потоки в сетях, продвинутое динамическое программирование). Для junior на .NET это почти не встречается; если встретится, приём разбора останется тем же.

## Интуиция и аналогия

**Паттерн — это приём из набора столяра.** Новичок пытается каждую деталь придумать с нуля; опытный смотрит на деталь и понимает, что здесь нужен шип-паз. Задачи на собеседовании — типовые детали. Задача «подстрока без повторов» — это окно, «следующий большой» — монотонный стек, «минимальная скорость, при которой успеешь» — бинарный поиск по ответу.

**Сложность — это счёт работы, а не секундомер.** Если у тебя тысяча человек и надо проверить каждую пару, пар почти полмиллиона; для десяти тысяч уже пятьдесят миллионов. Алгоритм, который смотрит каждого один раз, делает ровно столько же «шагов», сколько людей. Рост числа шагов с ростом входа и есть сложность.

**Стресс-тест — сверка с калькулятором.** Умное быстрое решение сверяют с тупым медленным, но заведомо правильным, на тысячах маленьких случайных входов. Если они расходятся, ошибка найдена вместе с примером, на котором она проявляется.

## Основная теория по шагам

### Шаг 1. Как решать задачу на собеседовании

1. Переформулируй условие и уточни ограничения (размеры, отрицательные числа, пустой вход, дубликаты).
2. Разбери 1–2 примера руками.
3. Предложи решение в лоб и его сложность.
4. Найди узкое место и паттерн, который его снимает.
5. Пиши код, **проговаривая** мысли.
6. Прогони код на примере и граничных случаях, назови сложность по времени и памяти.

Правило, которое стоит больше всех остальных: **решение в лоб надо назвать вслух**, даже если оно неэффективно. Оно показывает, что ты понял задачу, и даёт точку отсчёта («здесь O(n²), узкое место — повторный поиск пары; заменю на словарь»). Молчание на десять минут и внезапно идеальное решение выглядит хуже, чем честное улучшение шаг за шагом.

### Шаг 2. Сложность по времени и памяти

| Запись | Растёт как | Пример |
|---|---|---|
| O(1) | не растёт | чтение элемента массива, `Dictionary` в среднем |
| O(log n) | очень медленно | бинарный поиск |
| O(n) | пропорционально | один проход по массиву |
| O(n log n) | чуть быстрее квадрата | сортировка |
| O(n²) | в квадрате | два вложенных цикла по входу |
| O(2ⁿ) | взрывной | перебор всех подмножеств, наивная рекурсия Фибоначчи |

Оценка ограничений подсказывает, какая сложность допустима: при n до 1 000 хватит O(n²); при n до 100 000 нужен O(n log n) или O(n); при n до 20–25 допустим перебор подмножеств. Если в условии 10⁵ элементов, а ты предлагаешь два вложенных цикла, ты уже знаешь, что решение не пройдёт.

### Шаг 3. Паттерн «два указателя»

**Узнаётся по:** отсортированный массив, пары, палиндромы, «на месте». Идея: два индекса идут навстречу (или оба вперёд), и на каждом шаге один из них сдвигается, потому что отсортированность доказывает, что другой вариант не подойдёт.

Покажем, насколько это дешевле перебора, подсчитав сравнения, и проверим решение стресс-тестом:

~~~csharp
foreach (var n in new[] { 1000, 10000 })
{
    var a = Enumerable.Range(0, n).Select(i => i * 2).ToArray();                   // чётные числа: нечётная цель недостижима → худший случай
    var brute = new Counter(); var fast = new Counter();
    BruteTwoSum(a, 1, brute);
    TwoSumSorted(a, 1, fast);
    Console.WriteLine($"n = {n,5}: перебор сделал {brute.Value,10:N0} сравнений, два указателя — {fast.Value,6:N0}");
}

Console.WriteLine(TwoSumSorted(new[] { 1, 3, 4, 6, 8, 11 }, 10, new Counter()));      // (2, 3): 4 + 6

// стресс-тест: 5000 случайных массивов, сравниваем «есть ли пара» с перебором
ulong state = 42;
int Rand(int bound) { state ^= state << 13; state ^= state >> 7; state ^= state << 17; return (int)(state % (ulong)bound); }
int mismatches = 0;
for (int t = 0; t < 5000; t++)
{
    var a = Enumerable.Range(0, Rand(10)).Select(_ => Rand(25) - 5).OrderBy(x => x).ToArray();
    var target = Rand(30) - 5;
    var (l, r) = TwoSumSorted(a, target, new Counter());
    var expected = BruteTwoSum(a, target, new Counter());
    bool foundFast = l >= 0 && l < r && a[l] + a[r] == target;
    if (foundFast != (expected.Item1 >= 0)) mismatches++;
}
Console.WriteLine($"расхождений с перебором на 5000 случайных входов: {mismatches}");

static (int, int) TwoSumSorted(int[] a, int target, Counter ops)
{
    int l = 0, r = a.Length - 1;
    while (l < r)
    {
        ops.Value++;
        int sum = a[l] + a[r];
        if (sum == target) return (l, r);
        if (sum < target) l++; else r--;      // сумма мала — двигаем левый, велика — правый
    }
    return (-1, -1);
}
// O(n) по времени, O(1) по памяти

static (int, int) BruteTwoSum(int[] a, int target, Counter ops)
{
    for (int i = 0; i < a.Length; i++)
        for (int j = i + 1; j < a.Length; j++) { ops.Value++; if (a[i] + a[j] == target) return (i, j); }
    return (-1, -1);
}

public sealed class Counter { public long Value; }
~~~

~~~console
n = 10000: перебор сделал 49,995,000 сравнений, два указателя —  9,999
(2, 3)
расхождений с перебором на 5000 случайных входов: 0
~~~

Перебор делает n²/2 сравнений, два указателя не больше n. На тысяче элементов разница уже 500 раз, на десяти тысячах — 5 000 раз. Принцип корректности: если сумма меньше цели, то левый элемент в паре с *любым* правым из оставшихся даст сумму не больше, значит, его можно отбросить. Запомни это рассуждение: на собеседовании просят объяснить, *почему* можно двигать указатель.

### Шаг 4. Паттерн «скользящее окно»

**Узнаётся по:** «самая длинная/короткая подстрока/подмассив, удовлетворяющий условию». Окно `[start, end]` расширяется правым краем, а при нарушении условия сжимается левым. Каждый край проходит массив один раз, поэтому O(n).

~~~csharp
Console.WriteLine(LongestUniqueSubstring("abcabcbb"));   // 3 ("abc")
Console.WriteLine(LongestUniqueSubstring("pwwkew"));     // 3 ("wke")
Console.WriteLine(LongestUniqueSubstring(""));           // 0 — пустая строка
Console.WriteLine($"классическая ошибка: abba → {LongestUniqueSubstringBuggy("abba")}, верно: {LongestUniqueSubstring("abba")}");

// стресс-тест против перебора всех подстрок
ulong state = 7;
int Rand(int bound) { state ^= state << 13; state ^= state >> 7; state ^= state << 17; return (int)(state % (ulong)bound); }
int mismatches = 0;
for (int t = 0; t < 5000; t++)
{
    var s = new string(Enumerable.Range(0, Rand(13)).Select(_ => "abc"[Rand(3)]).ToArray());
    if (LongestUniqueSubstring(s) != Brute(s)) mismatches++;
}
Console.WriteLine($"расхождений с перебором на 5000 случайных строк: {mismatches}");

static int LongestUniqueSubstring(string s)
{
    var lastSeen = new Dictionary<char, int>();
    int best = 0, start = 0;
    for (int end = 0; end < s.Length; end++)
    {
        if (lastSeen.TryGetValue(s[end], out int prev) && prev >= start)
            start = prev + 1;                 // сдвигаем левую границу окна за повтор
        lastSeen[s[end]] = end;
        best = Math.Max(best, end - start + 1);
    }
    return best;
}
// O(n): каждая граница окна проходит строку один раз

static int LongestUniqueSubstringBuggy(string s)           // забыли условие prev >= start: левая граница «прыгает» назад
{
    var lastSeen = new Dictionary<char, int>();
    int best = 0, start = 0;
    for (int end = 0; end < s.Length; end++)
    {
        if (lastSeen.TryGetValue(s[end], out int prev)) start = prev + 1;
        lastSeen[s[end]] = end;
        best = Math.Max(best, end - start + 1);
    }
    return best;
}

static int Brute(string s)
{
    int best = 0;
    for (int i = 0; i < s.Length; i++)
        for (int j = i; j < s.Length; j++)
            if (s.Substring(i, j - i + 1).Distinct().Count() == j - i + 1) best = Math.Max(best, j - i + 1);
    return best;
}
~~~
~~~console
3
3
0
классическая ошибка: abba → 3, верно: 2
расхождений с перебором на 5000 случайных строк: 0
~~~

Строка `abba` — любимая ловушка: на втором `a` запись о её предыдущей позиции (0) уже вне окна, и без проверки `prev >= start` левая граница откатится назад и окно «воскресит» повтор. Стресс-тест ловит такие ошибки автоматически; на собеседовании похожий эффект даёт проверка на пограничных строках (`abba`, пустая, из одного символа).

### Шаг 5. Паттерн «хэш-таблица и префиксные суммы»

**Узнаётся по:** «найти пару/подмассив с суммой k», подсчёт частот, «встречалось ли раньше». Хэш-таблица заменяет внутренний цикл поиска на O(1)-обращение. Префиксная сумма `P[i]` — сумма первых `i` элементов; сумма отрезка `(j, i]` равна `P[i] − P[j]`, поэтому условие «сумма отрезка равна k» превращается в «встречалась ли раньше префиксная сумма `P[i] − k`».

~~~csharp
Console.WriteLine(SubarraySum(new[] { 1, 2, 3, -2, 2 }, 3));   // 4: [1,2] [3] [2,3,-2] [3,-2,2]
Console.WriteLine($"метод окна на тех же данных (работает только без отрицательных): {WindowWrong(new[] { 1, 2, 3, -2, 2 }, 3)}");

ulong state = 99;
int Rand(int bound) { state ^= state << 13; state ^= state >> 7; state ^= state << 17; return (int)(state % (ulong)bound); }
int mismatches = 0;
for (int t = 0; t < 5000; t++)
{
    var nums = Enumerable.Range(0, Rand(10)).Select(_ => Rand(9) - 4).ToArray();
    var k = Rand(9) - 4;
    if (SubarraySum(nums, k) != Brute(nums, k)) mismatches++;
}
Console.WriteLine($"расхождений с перебором на 5000 случайных входов (с отрицательными числами): {mismatches}");

static int SubarraySum(int[] nums, int k)
{
    var seen = new Dictionary<int, int> { [0] = 1 };   // сколько раз встречалась каждая префиксная сумма
    int prefix = 0, count = 0;
    foreach (int x in nums)
    {
        prefix += x;
        count += seen.GetValueOrDefault(prefix - k);   // подмассивы, заканчивающиеся здесь, с суммой k
        seen[prefix] = seen.GetValueOrDefault(prefix) + 1;
    }
    return count;
}

static int WindowWrong(int[] nums, int k)               // скользящее окно рассчитывает, что сумма растёт при расширении
{
    int count = 0, left = 0, sum = 0;
    for (int right = 0; right < nums.Length; right++)
    {
        sum += nums[right];
        while (sum > k && left <= right) sum -= nums[left++];
        if (sum == k) count++;
    }
    return count;
}

static int Brute(int[] nums, int k)
{
    int count = 0;
    for (int i = 0; i < nums.Length; i++)
    {
        int sum = 0;
        for (int j = i; j < nums.Length; j++) { sum += nums[j]; if (sum == k) count++; }
    }
    return count;
}
~~~
~~~console
4
метод окна на тех же данных (работает только без отрицательных): 3
расхождений с перебором на 5000 случайных входов (с отрицательными числами): 0
~~~

Начальное значение `[0] = 1` — подмассив с самого начала; без него теряются отрезки от первого элемента. Выбор между окном и префиксными суммами определяется одним вопросом: **монотонно ли растёт сумма при расширении окна**. Для положительных чисел да, и подойдёт окно; при отрицательных нет, и нужны префиксные суммы со словарём. Это частый вопрос «почему здесь не работает окно?».

### Шаг 6. Паттерн «монотонный стек»

**Узнаётся по:** «следующий больший/меньший элемент», «сколько дней до потепления». Стек хранит индексы, ожидающие ответа; новый элемент «разрешает» всех, кто меньше него. Каждый индекс кладётся и снимается не более одного раза, поэтому O(n), несмотря на цикл внутри цикла.

~~~csharp
Console.WriteLine(string.Join(",", DailyTemperatures(new[] { 73, 74, 75, 71, 69, 72, 76, 73 }, new Counter())));
// 1,1,4,2,1,1,0,0

var ops = new Counter();
var big = Enumerable.Range(0, 100_000).Select(i => (i * 37) % 1000).ToArray();
DailyTemperatures(big, ops);
Console.WriteLine($"n = 100 000: снятий со стека {ops.Value:N0} — не больше n, хотя внутри цикла есть while");

ulong state = 5;
int Rand(int bound) { state ^= state << 13; state ^= state >> 7; state ^= state << 17; return (int)(state % (ulong)bound); }
int mismatches = 0;
for (int t = 0; t < 3000; t++)
{
    var temps = Enumerable.Range(0, Rand(12)).Select(_ => 60 + Rand(8)).ToArray();
    if (!DailyTemperatures(temps, new Counter()).SequenceEqual(Brute(temps))) mismatches++;
}
Console.WriteLine($"расхождений с перебором на 3000 случайных входов (с повторяющимися значениями): {mismatches}");

static int[] DailyTemperatures(int[] t, Counter ops)
{
    var answer = new int[t.Length];
    var stack = new Stack<int>();                      // индексы дней, ожидающих потепления
    for (int i = 0; i < t.Length; i++)
    {
        while (stack.Count > 0 && t[stack.Peek()] < t[i])
        {
            int j = stack.Pop();
            ops.Value++;
            answer[j] = i - j;
        }
        stack.Push(i);
    }
    return answer;
}

static int[] Brute(int[] t)
{
    var answer = new int[t.Length];
    for (int i = 0; i < t.Length; i++)
        for (int j = i + 1; j < t.Length; j++)
            if (t[j] > t[i]) { answer[i] = j - i; break; }
    return answer;
}

public sealed class Counter { public long Value; }
~~~
~~~console
1,1,4,2,1,1,0,0
n = 100 000: снятий со стека 99,864 — не больше n, хотя внутри цикла есть while
расхождений с перебором на 3000 случайных входов (с повторяющимися значениями): 0
~~~

Обрати внимание на строгое неравенство `<`: при равных температурах потепления нет, поэтому равные значения остаются на стеке. Замена на `<=` была бы тихой ошибкой, которую поймал бы стресс-тест с повторами (мы специально брали значения из узкого диапазона).

### Шаг 7. Паттерн «бинарный поиск по границе и по ответу»

**Узнаётся по:** отсортированные данные, «первая позиция, где условие становится истинным», а также «минимальное значение, при котором условие выполняется» (когда условие монотонно: если подходит `x`, то подходит и любое большее). Второй вид — бинарный поиск **по ответу**: ты ищешь не элемент в массиве, а число, проверяя гипотезу функцией.

~~~csharp
Console.WriteLine(LowerBound(new[] { 1, 3, 3, 5, 8 }, 3));   // 1 — первый индекс, где a[i] >= 3
Console.WriteLine(LowerBound(new[] { 1, 3, 3, 5, 8 }, 4));   // 3 — сюда вставили бы 4
Console.WriteLine($"пустой массив: {LowerBound(Array.Empty<int>(), 7)}, все меньше цели: {LowerBound(new[] { 1, 2 }, 9)}, все больше: {LowerBound(new[] { 5, 6 }, 1)}");

// переполнение при вычислении середины
int lo = 2_000_000_000, hi = 2_100_000_000;
Console.WriteLine($"(lo + hi) / 2 = {unchecked((lo + hi) / 2)} — отрицательное, ошибка; lo + (hi - lo) / 2 = {lo + (hi - lo) / 2}");

// бинарный поиск по ответу: Koko Eating Bananas
// piles — кучи бананов, h часов; за час можно съесть k бананов из одной кучи. Минимальное k, чтобы успеть?
Console.WriteLine($"Koko: {MinSpeed(new[] { 3, 6, 7, 11 }, 8)}");          // 4
Console.WriteLine($"Koko: {MinSpeed(new[] { 30, 11, 23, 4, 20 }, 5)}");    // 30
Console.WriteLine($"Koko: {MinSpeed(new[] { 30, 11, 23, 4, 20 }, 6)}");    // 23

ulong state = 11;
int Rand(int bound) { state ^= state << 13; state ^= state >> 7; state ^= state << 17; return (int)(state % (ulong)bound); }
int mismatches = 0;
for (int t = 0; t < 3000; t++)
{
    var a = Enumerable.Range(0, Rand(10)).Select(_ => Rand(8)).OrderBy(x => x).ToArray();
    var target = Rand(10) - 1;
    int expected = a.Length; for (int i = 0; i < a.Length; i++) if (a[i] >= target) { expected = i; break; }
    if (LowerBound(a, target) != expected) mismatches++;
    var piles = Enumerable.Range(0, 1 + Rand(5)).Select(_ => 1 + Rand(20)).ToArray();
    var h = piles.Length + Rand(10);
    int k = 1; while (Hours(piles, k) > h) k++;                                        // перебор скоростей
    if (MinSpeed(piles, h) != k) mismatches++;
}
Console.WriteLine($"расхождений с перебором на 3000 случайных входов: {mismatches}");

static int LowerBound(int[] a, int target)
{
    int lo = 0, hi = a.Length;                         // полуинтервал [lo, hi)
    while (lo < hi)
    {
        int mid = lo + (hi - lo) / 2;
        if (a[mid] < target) lo = mid + 1; else hi = mid;
    }
    return lo;
}

static long Hours(int[] piles, int k) => piles.Sum(p => (long)((p + k - 1) / k));         // потолок деления

static int MinSpeed(int[] piles, int h)
{
    int lo = 1, hi = piles.Max();                      // ответ всегда в [1, max]
    while (lo < hi)
    {
        int mid = lo + (hi - lo) / 2;
        if (Hours(piles, mid) <= h) hi = mid; else lo = mid + 1;                          // условие монотонно по скорости
    }
    return lo;
}
~~~

~~~console
пустой массив: 0, все меньше цели: 2, все больше: 0
(lo + hi) / 2 = -97483648 — отрицательное, ошибка; lo + (hi - lo) / 2 = 2050000000
Koko: 4
Koko: 30
Koko: 23
расхождений с перебором на 3000 случайных входов: 0
~~~

Две вещи для запоминания. Первая: полуинтервал `[lo, hi)` и условие `a[mid] < target` дают шаблон «первая позиция, где `a[i] >= target`», он же вставляет элемент и ищет границу повторов. Вторая: бинарный поиск по ответу требует, чтобы условие было *монотонным*; сформулируй его вслух («если успеваю при скорости k, то успеваю и при больших»). Ошибка `(lo + hi) / 2` приводит к отрицательному индексу на больших границах; в .NET массив не может быть настолько большим, но границы ответа (например, суммы) вполне могут.

### Шаг 8. Паттерн «деревья: DFS и BFS»

Дерево обходят **вглубь (DFS)** рекурсией или стеком и **вширь (BFS)** очередью по уровням. Выбор: глубина, пути и проверки «поддерева» естественны для DFS; уровни и кратчайшие пути в невзвешенных структурах для BFS.

~~~csharp
using System.Runtime.CompilerServices;

var tree = new TreeNode(3, new TreeNode(9), new TreeNode(20, new TreeNode(15), new TreeNode(7)));
Console.WriteLine(MaxDepth(tree));                                                        // 3

static int MaxDepth(TreeNode? node) =>                 // DFS рекурсией
    node is null ? 0 : 1 + Math.Max(MaxDepth(node.Left), MaxDepth(node.Right));

static int RecursiveDepth(TreeNode? node)
{
    if (node is null) return 0;
    RuntimeHelpers.EnsureSufficientExecutionStack();   // бросает исключение, а не убивает процесс
    return 1 + Math.Max(RecursiveDepth(node.Left), RecursiveDepth(node.Right));
}

static int DepthIterative(TreeNode? root)              // DFS с явным стеком
{
    if (root is null) return 0;
    int best = 0;
    var stack = new Stack<(TreeNode, int)>();
    stack.Push((root, 1));
    while (stack.Count > 0)
    {
        var (n, d) = stack.Pop();
        best = Math.Max(best, d);
        if (n.Left is not null) stack.Push((n.Left, d + 1));
        if (n.Right is not null) stack.Push((n.Right, d + 1));
    }
    return best;
}

static bool IsBstNaive(TreeNode? n) =>
    n is null || ((n.Left is null || n.Left.Val < n.Val) && (n.Right is null || n.Right.Val > n.Val) && IsBstNaive(n.Left) && IsBstNaive(n.Right));

static bool IsBst(TreeNode? n, long min, long max) =>   // каждый узел обязан лежать в допустимом диапазоне, унаследованном сверху
    n is null || (n.Val > min && n.Val < max && IsBst(n.Left, min, n.Val) && IsBst(n.Right, n.Val, max));

static List<List<int>> LevelOrder(TreeNode? root)      // BFS очередью — по уровням
{
    var result = new List<List<int>>();
    if (root is null) return result;
    var queue = new Queue<TreeNode>();
    queue.Enqueue(root);
    while (queue.Count > 0)
    {
        int levelSize = queue.Count;
        var level = new List<int>(levelSize);
        for (int i = 0; i < levelSize; i++)
        {
            var n = queue.Dequeue();
            level.Add(n.Val);
            if (n.Left is not null) queue.Enqueue(n.Left);
            if (n.Right is not null) queue.Enqueue(n.Right);
        }
        result.Add(level);
    }
    return result;
}

public sealed class TreeNode(int val, TreeNode? left = null, TreeNode? right = null)
{
    public int Val { get; } = val;
    public TreeNode? Left { get; } = left;
    public TreeNode? Right { get; } = right;
}
~~~

### Шаг 9. Паттерн «графы и сетки»

Сетка и граф обходятся одинаково: соседи клетки — это рёбра. **BFS** находит кратчайший путь по числу шагов, **DFS** подходит для связных компонент, **топологическая сортировка** — для зависимостей (порядок прохождения курсов, порядок сборки). Обязательный элемент — множество посещённых вершин, иначе цикл в графе даст бесконечный обход.

~~~csharp
static int NumIslands(char[][] grid)                   // не портим вход: отдельный массив посещённых
{
    int rows = grid.Length, cols = grid[0].Length, islands = 0;
    var visited = new bool[rows, cols];
    var dirs = new (int dr, int dc)[] { (1, 0), (-1, 0), (0, 1), (0, -1) };
    for (int r = 0; r < rows; r++)
    for (int c = 0; c < cols; c++)
    {
        if (grid[r][c] != '1' || visited[r, c]) continue;
        islands++;
        var queue = new Queue<(int, int)>();
        queue.Enqueue((r, c));
        visited[r, c] = true;                          // помечаем сразу при постановке в очередь, иначе клетка попадёт в очередь дважды
        while (queue.Count > 0)
        {
            var (cr, cc) = queue.Dequeue();
            foreach (var (dr, dc) in dirs)
            {
                int nr = cr + dr, nc = cc + dc;
                if (nr < 0 || nc < 0 || nr >= rows || nc >= cols || grid[nr][nc] != '1' || visited[nr, nc]) continue;
                visited[nr, nc] = true;
                queue.Enqueue((nr, nc));
            }
        }
    }
    return islands;
}

static int NumIslandsDestructive(char[][] grid)        // пометка прямо в сетке: короче, но входные данные испорчены
{
    int rows = grid.Length, cols = grid[0].Length, islands = 0;
    for (int r = 0; r < rows; r++)
    for (int c = 0; c < cols; c++)
    {
        if (grid[r][c] != '1') continue;
        islands++;
        var stack = new Stack<(int, int)>();
        stack.Push((r, c)); grid[r][c] = '0';
        while (stack.Count > 0)
        {
            var (cr, cc) = stack.Pop();
            foreach (var (dr, dc) in new[] { (1, 0), (-1, 0), (0, 1), (0, -1) })
            {
                int nr = cr + dr, nc = cc + dc;
                if (nr < 0 || nc < 0 || nr >= rows || nc >= cols || grid[nr][nc] != '1') continue;
                grid[nr][nc] = '0'; stack.Push((nr, nc));
            }
        }
    }
    return islands;
}

static int ShortestPath(string[] maze)
{
    int rows = maze.Length, cols = maze[0].Length;
    (int, int) start = (0, 0), end = (0, 0);
    for (int r = 0; r < rows; r++) for (int c = 0; c < cols; c++) { if (maze[r][c] == 'S') start = (r, c); if (maze[r][c] == 'E') end = (r, c); }
    var dist = new Dictionary<(int, int), int> { [start] = 0 };
    var queue = new Queue<(int, int)>(); queue.Enqueue(start);
    while (queue.Count > 0)
    {
        var (r, c) = queue.Dequeue();
        if ((r, c) == end) return dist[(r, c)];
        foreach (var (dr, dc) in new[] { (1, 0), (-1, 0), (0, 1), (0, -1) })
        {
            int nr = r + dr, nc = c + dc;
            if (nr < 0 || nc < 0 || nr >= rows || nc >= cols || maze[nr][nc] == '#' || dist.ContainsKey((nr, nc))) continue;
            dist[(nr, nc)] = dist[(r, c)] + 1;
            queue.Enqueue((nr, nc));
        }
    }
    return -1;
}

static string Order(int n, (int course, int prereq)[] edges)
{
    var next = new List<int>[n]; for (int i = 0; i < n; i++) next[i] = new List<int>();
    var indegree = new int[n];
    foreach (var (course, prereq) in edges) { next[prereq].Add(course); indegree[course]++; }
    var queue = new Queue<int>(Enumerable.Range(0, n).Where(i => indegree[i] == 0));
    var order = new List<int>();
    while (queue.Count > 0)
    {
        var v = queue.Dequeue(); order.Add(v);
        foreach (var w in next[v]) if (--indegree[w] == 0) queue.Enqueue(w);
    }
    return order.Count == n ? "можно, порядок " + string.Join("→", order) : "нельзя: есть цикл";
}
~~~

### Шаг 10. Паттерн «динамическое программирование»

**Узнаётся по:** «сколько способов», «максимальная/минимальная сумма при ограничениях», решение строится из решений меньших подзадач, а наивная рекурсия пересчитывает одно и то же. Схема: 1) определи состояние («лучший результат для первых i домов»), 2) переход (взять/не взять), 3) база, 4) порядок вычисления, 5) часто можно оставить только последние значения вместо массива.

~~~csharp
// 1. зачем нужна «память»: наивная рекурсия пересчитывает одно и то же
long calls = 0;
long FibNaive(int n) { calls++; return n < 2 ? n : FibNaive(n - 1) + FibNaive(n - 2); }
var memo = new Dictionary<int, long>(); long memoCalls = 0;
long FibMemo(int n) { memoCalls++; if (n < 2) return n; if (memo.TryGetValue(n, out var v)) return v; return memo[n] = FibMemo(n - 1) + FibMemo(n - 2); }
Console.WriteLine($"fib(30) = {FibNaive(30)}: наивных вызовов {calls:N0}; с запоминанием {FibMemo(30)}: вызовов {memoCalls}");

// 2. House Robber
Console.WriteLine($"Rob = {Rob(new[] { 2, 7, 9, 3, 1 })}");                    // 12 = 2 + 9 + 1

// 3. Coin Change: жадность ошибается, ДП нет

Console.WriteLine($"сумма 6, монеты 1,3,4: жадный алгоритм {Greedy(coins, 6)} монет, динамическое программирование {CoinChange(coins, 6)}");
Console.WriteLine($"сумма 7, монеты 2:    {CoinChange(new[] { 2 }, 7)} (невозможно)");

// 4. стресс-тест Rob против перебора всех подмножеств без соседей
ulong state = 3;
int Rand(int bound) { state ^= state << 13; state ^= state >> 7; state ^= state << 17; return (int)(state % (ulong)bound); }
int mismatches = 0;
for (int t = 0; t < 2000; t++)
{
    var h = Enumerable.Range(0, Rand(11)).Select(_ => Rand(20)).ToArray();
    int best = 0;
    for (int mask = 0; mask < (1 << h.Length); mask++)
    {
        if ((mask & (mask >> 1)) != 0) continue;                                    // соседние дома выбраны — недопустимо
        int sum = 0; for (int i = 0; i < h.Length; i++) if ((mask >> i & 1) == 1) sum += h[i];

static int Rob(int[] houses)                         // нельзя грабить два соседних дома
{
    int prev = 0, best = 0;                          // лучший результат до i-2 и до i-1
    foreach (int h in houses)
    {
        int next = Math.Max(best, prev + h);         // пропустить дом или взять его
        prev = best;
        best = next;
    }
    return best;
}

static int Greedy(int[] coins, int amount)
{
    int count = 0;
    foreach (var c in coins.OrderByDescending(c => c)) { count += amount / c; amount %= c; }
    return amount == 0 ? count : -1;
}

static int CoinChange(int[] coins, int amount)
{
    var dp = new int[amount + 1];                    // dp[x] — минимум монет на сумму x
    Array.Fill(dp, int.MaxValue); dp[0] = 0;
    for (int x = 1; x <= amount; x++)
        foreach (var c in coins)
            if (c <= x && dp[x - c] != int.MaxValue) dp[x] = Math.Min(dp[x], dp[x - c] + 1);
    return dp[amount] == int.MaxValue ? -1 : dp[amount];
}
~~~

### Шаг 11. Паттерн «куча и интервалы»

**Куча** (в .NET это `PriorityQueue<TElement, TPriority>`, минимальная куча) нужна, когда надо постоянно доставать наименьший (или наибольший) элемент: «k-й по величине», «k ближайших», «расписание задач». Ключевой трюк: чтобы найти k-й **наибольший**, держат минимальную кучу размера k: в корне лежит k-й по величине. **Интервалы** решают сортировкой по началу и одним проходом.

~~~csharp
static int KthLargest(int[] a, int k)
{
    var heap = new PriorityQueue<int, int>();                      // минимальная куча: приоритет = значение
    foreach (var x in a)
    {
        heap.Enqueue(x, x);
        if (heap.Count > k) heap.Dequeue();                         // выбрасываем наименьший, остаётся k наибольших
    }
    return heap.Peek();                                             // наименьший из k наибольших = k-й по величине
}
// O(n log k) по времени, O(k) по памяти

static List<(int, int)> Merge((int start, int end)[] intervals)
{
    var sorted = intervals.OrderBy(i => i.start).ToList();
    var result = new List<(int, int)>();
    foreach (var (s, e) in sorted)
    {
        if (result.Count > 0 && s <= result[^1].Item2) result[^1] = (result[^1].Item1, Math.Max(result[^1].Item2, e));   // пересекается — расширяем последний
        else result.Add((s, e));
    }
    return result;
}

static int MinRooms((int start, int end)[] meetings)
{
    var starts = meetings.Select(m => m.start).OrderBy(x => x).ToArray();
    var ends = meetings.Select(m => m.end).OrderBy(x => x).ToArray();
    int rooms = 0, best = 0, j = 0;
    for (int i = 0; i < starts.Length; i++)
    {
        while (ends[j] <= starts[i]) { j++; rooms--; }               // встреча закончилась до начала этой — комната освободилась
        rooms++;
        best = Math.Max(best, rooms);
    }
    return best;
}
~~~

### Шаг 12. Паттерн «связные списки»

Списки проверяют аккуратность работы со ссылками. Три приёма закрывают большинство задач: **быстрый и медленный указатель** (середина списка, цикл), **разворот** ссылок на месте и **фиктивная голова** (dummy node), которая убирает особые случаи для первого узла.

~~~csharp
var list = Build(1, 2, 3, 4, 5);

Console.WriteLine($"середина: {Middle(list)!.Val}; у списка из 4 элементов: {Middle(Build(1, 2, 3, 4))!.Val} (второй из двух средних)");
Console.WriteLine($"разворот: {Show(Reverse(Build(1, 2, 3)))}");
Console.WriteLine($"удалить 2-й с конца: {Show(RemoveNthFromEnd(Build(1, 2, 3, 4, 5), 2))}");
Console.WriteLine($"удалить голову (n = длина): {Show(RemoveNthFromEnd(Build(1, 2), 2))}");        // особый случай, который решает dummy

var cyclic = Build(1, 2, 3, 4);
cyclic!.Next!.Next!.Next!.Next = cyclic.Next;                                                    // 4 → 2: цикл
Console.WriteLine($"цикл в списке с замкнутым хвостом: {HasCycle(cyclic)}; без цикла: {HasCycle(Build(1, 2, 3))}");

static ListNode? Build(params int[] values)
{
    ListNode? head = null;
    for (int i = values.Length - 1; i >= 0; i--) head = new ListNode(values[i], head);
    return head;
}

static string Show(ListNode? head)
{
    var parts = new List<int>();
    for (var n = head; n is not null; n = n.Next) parts.Add(n.Val);
    return parts.Count == 0 ? "пусто" : string.Join("→", parts);
}

static ListNode? Middle(ListNode? head)
{
    ListNode? slow = head, fast = head;
    while (fast?.Next is not null) { slow = slow!.Next; fast = fast.Next.Next; }         // быстрый идёт вдвое быстрее
    return slow;
}

static ListNode? Reverse(ListNode? head)
{
    ListNode? prev = null;
    while (head is not null) { var next = head.Next; head.Next = prev; prev = head; head = next; }   // порядок присваиваний важен
    return prev;
}

static ListNode? RemoveNthFromEnd(ListNode? head, int n)
{
    var dummy = new ListNode(0, head);                                                    // фиктивная голова
    ListNode? lead = dummy, follow = dummy;
    for (int i = 0; i < n; i++) lead = lead!.Next;                                        // лидер уходит на n шагов вперёд
    while (lead!.Next is not null) { lead = lead.Next; follow = follow!.Next; }          // двигаем оба, пока лидер не дойдёт до конца
    follow!.Next = follow.Next!.Next;
    return dummy.Next;
}

static bool HasCycle(ListNode? head)                                                      // алгоритм Флойда: быстрый догонит медленного, если есть цикл
{
    ListNode? slow = head, fast = head;
    while (fast?.Next is not null)
    {
        slow = slow!.Next; fast = fast.Next.Next;
        if (ReferenceEquals(slow, fast)) return true;
    }
    return false;
}

public sealed class ListNode(int val, ListNode? next = null)
{
    public int Val { get; } = val;
    public ListNode? Next { get; set; } = next;
}
~~~

~~~console
середина: 3; у списка из 4 элементов: 3 (второй из двух средних)
разворот: 3→2→1
удалить 2-й с конца: 1→2→3→5
удалить голову (n = длина): 2
цикл в списке с замкнутым хвостом: True; без цикла: False
~~~

Самое частое место ошибок списка — порядок присваиваний при развороте: сначала сохрани `next`, потом перенаправь ссылку. Второе — работа с `null`: пустой список, список из одного элемента, удаление головы. Привычка прогонять эти три случая перед сдачей решения экономит больше всего баллов.

## Как это работает под капотом

- **Почему O(n) у цикла в цикле (стек, окно).** Считают не вложенность, а суммарное число действий: каждый элемент кладётся и снимается со стека не больше одного раза, каждая граница окна проходит массив один раз. Такой подсчёт называется амортизированным.
- **Словарь `Dictionary`.** Хэш-таблица: по хэшу ключа вычисляется «корзина», поиск в среднем O(1). В худшем случае (много коллизий) деградирует, но с хорошей хэш-функцией это редкость; для ключей-структур (кортежи, `ValueTuple`) .NET даёт готовые хэши. Порядок перечисления формально не гарантирован; не полагайся на него.
- **`SortedDictionary` и `SortedSet`** — деревья: операции за O(log n), но ключи упорядочены. Если порядок не нужен, обычный словарь быстрее.
- **`List<T>` — массив.** Вставка и удаление в середине O(n), добавление в конец амортизированно O(1). `Queue<T>` и `Stack<T>` — O(1) на операции. `LinkedList<T>` почти всегда проигрывает `List<T>` по скорости из-за расхода памяти и промахов кэша процессора.
- **`PriorityQueue<TElement, TPriority>`** — двоичная куча в массиве: вставка и извлечение O(log n), просмотр минимума O(1). Порядок равных приоритетов не определён.
- **Рекурсия и стек.** Каждый вызов занимает кадр на стеке потока (по умолчанию порядка мегабайта, на главном потоке Linux больше). Глубокая рекурсия приводит к `StackOverflowException`, который невозможно перехватить: процесс завершается. Поэтому глубокие обходы переписывают на явный стек.
- **Переполнение `int`.** Арифметика `int` по умолчанию молча переходит через границу (в контексте `checked` бросает исключение). Суммы, произведения и середины на больших границах считай в `long` или безопасной формулой.
- **LINQ и производительность.** `OrderBy`, `Distinct`, `Sum` удобны, но выделяют память и замыкания; в задачах на сложность держи в голове, что `Distinct().Count()` внутри цикла делает решение квадратичным или хуже. Для собеседования читаемость важнее, но называй стоимость.
- **Как проверяют решения платформы.** Прогоняют на скрытых тестах с жёсткими ограничениями по времени. Крайние случаи (пустой вход, один элемент, все одинаковые, максимальный размер) там всегда есть; в своих стресс-тестах генерируй именно такие.

## Типичные ошибки и ловушки

- **Сразу писать код.** Без разбора примеров и уточнения ограничений теряются пограничные случаи.
- **Молчать.** Интервьюер оценивает ход мысли; решение в лоб, названное вслух, лучше долгой паузы.
- **Решение, не проходящее по размерам входа.** Квадратичный перебор при 10⁵ элементов. Оценивай сложность до кода.
- **Ошибки на единицу (off-by-one).** Границы `<` против `<=`, полуинтервал против закрытого отрезка. Определи инвариант и придерживайся его.
- **Забытые крайние случаи.** Пустой массив, один элемент, все одинаковые, отрицательные числа, дубликаты, переполнение.
- **Применение окна при отрицательных числах** и вообще немонотонных условиях: нужен словарь префиксных сумм.
- **Жадность без доказательства.** Работает «на примерах» и ломается на контрпримере (монеты 1, 3, 4). Если не можешь обосновать, ищи динамику.
- **Проверка BST только с детьми.** Нужны границы, унаследованные от предков.
- **Пометка посещённых при извлечении из очереди.** Клетка попадает в очередь несколько раз.
- **Порча входных данных.** Если массив нужен потом, не помечай посещённое прямо в нём (или предупреди).
- **Глубокая рекурсия на длинной цепочке.** Исчерпание стека; нужен итеративный обход.
- **Порядок присваиваний при развороте списка** и забытая фиктивная голова при удалении первого узла.
- **Решил и забыл.** Без повторения через неделю навык не закрепляется; ведёт таблицу задач.
- **Зубрёжка решений вместо паттернов.** Меняется условие, и заученное не работает.

## Вопросы с собеседований

:::spoiler Как ты подходишь к новой алгоритмической задаче?
Переформулирую и уточняю ограничения, разбираю примеры, называю решение в лоб и его сложность, ищу узкое место и подходящий паттерн, пишу код с пояснениями, проверяю на крайних случаях и называю сложность по времени и памяти.
:::

:::spoiler Какая сложность у решения со скользящим окном или монотонным стеком, хотя внутри цикла есть ещё цикл? (ловушка: «O(n²)»)
O(n): внутренний цикл не перезапускается заново, суммарно каждый элемент добавляется и удаляется не более одного раза (амортизированный анализ).
:::

:::spoiler Когда подходит скользящее окно, а когда нужны префиксные суммы со словарём?
Окно требует монотонности: расширение окна не уменьшает сумму (положительные числа). При отрицательных числах окно ломается, и нужен словарь префиксных сумм.
:::

:::spoiler Как найти k-й по величине элемент и какая сложность? (ловушка: «отсортировать»)
Сортировка даёт O(n log n). Минимальная куча размера k даёт O(n log k): держим k наибольших, в корне k-й по величине. Есть и быстрый выбор (quickselect) со средним O(n).
:::

:::spoiler Чем BFS отличается от DFS и когда что брать?
BFS обходит по уровням (очередь) и находит кратчайший путь в невзвешенном графе. DFS идёт вглубь (стек или рекурсия) и удобен для компонент связности, проверок поддеревьев и перебора. Обоим нужно множество посещённых вершин в графах с циклами.
:::

:::spoiler Почему жадный алгоритм не решает задачу о размене монет?
Выбор самой большой монеты не всегда ведёт к минимуму: для монет 1, 3, 4 и суммы 6 жадность даёт 4+1+1 (три монеты), а оптимум 3+3 (две). Нужна динамика, перебирающая варианты для подзадач.
:::

:::spoiler Как проверить, что дерево является BST? (ловушка: «сравнить узел с детьми»)
Передавать вниз допустимый диапазон (min, max): каждый узел должен лежать строго внутри диапазона, унаследованного от предков. Альтернатива: симметричный обход должен дать строго возрастающую последовательность.
:::

:::spoiler Как найти цикл в связном списке и его середину?
Быстрый и медленный указатели: если есть цикл, быстрый догонит медленного (алгоритм Флойда). Середина: когда быстрый дошёл до конца, медленный в середине.
:::

:::spoiler Что такое динамическое программирование и как отличить задачу на него?
Решение строится из решений меньших подзадач, которые повторяются (перекрывающиеся подзадачи) и из которых складывается оптимум (оптимальная подструктура). Реализуется мемоизацией сверху вниз или таблицей снизу вверх.
:::

:::spoiler Как ты проверяешь своё решение, если нет готовых тестов?
Прогоняю примеры из условия, крайние случаи (пустой вход, один элемент, дубликаты, отрицательные числа, максимальный размер) и, если время позволяет, сверяю с простым перебором на случайных маленьких входах (стресс-тест).
:::

## Что запомнить

- Цель: узнавать паттерн по признакам условия, а не заучивать решения; решение в лоб называй вслух.
- Сложность — это счёт операций; ограничения входа подсказывают допустимую сложность (10⁵ — не O(n²)).
- Два указателя — отсортированные данные и пары; окно — самая длинная/короткая подстрока при монотонном условии; хэш + префиксные суммы — суммы на отрезках, в том числе с отрицательными числами.
- Монотонный стек — следующий больший/меньший; строгость неравенства важна при равных значениях.
- Бинарный поиск — по границе и по ответу; полуинтервал `[lo, hi)`, середина `lo + (hi - lo) / 2`, условие монотонно.
- Дерево и граф — DFS/BFS с множеством посещённых; BST проверяется диапазонами; зависимости — топологическая сортировка.
- ДП — перекрывающиеся подзадачи и оптимальная подструктура; жадность требует доказательства.
- Куча (`PriorityQueue`) для k наибольших/наименьших; интервалы — сортировка и один проход; границы касания уточняй.
- Списки: быстрый/медленный указатель, разворот, фиктивная голова; проверяй `null`, один элемент, удаление головы.
- Проверяй себя стресс-тестом против перебора; повторяй задачи через неделю.

| Маркетплейс услуг (мастера и клиенты) | расписание, отзывы, рейтинг, модерация |
| Личные финансы с бюджетами | категории, лимиты, периодические операции, аналитика |

:::tip Своя предметная область — преимущество
Если тема связана с реальной задачей (кафедра, знакомый бизнес, проблема, которую ты видел), её легко объяснить и интересно обсуждать на собеседовании. Пет-проект «как у всех» (ещё один TODO-лист) запоминается хуже.
:::
