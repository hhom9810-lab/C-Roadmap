## Зачем это нужно

Пока программа маленькая, можно жить без знания о том, что происходит между «нажал Run» и «увидел текст в консоли». Но уже через пару недель начнутся вопросы, на которые без этой картины не ответить:

- Почему первый запрос к только что запущенному сервису медленнее остальных?
- Почему `.dll`, собранная на ноутбуке с Windows, спокойно запускается на Linux-сервере?
- Почему в статьях пишут «лишняя аллокация — лишняя работа для GC», и что вообще такое аллокация?
- Почему утекает память в языке, где «есть сборщик мусора»?
- Что означает ответ «managed-код» на собеседовании, и что стоит за словом «рантайм»?

В работе ты встретишь эти термины ежедневно: в логах («JIT-compiling», «Gen2 collection»), в настройках деплоя (`DOTNET_gcServer`, `PublishReadyToRun`, `PublishAot`), в ревью («тут лишние аллокации»), в диагностике (`dotnet-counters`, `dotnet-trace`). Задача этой темы — не научить настраивать, а дать **единый словарь и правильную картинку в голове**. На собеседовании на позицию Junior вопрос «что происходит, когда ты запускаешь C#-программу?» задают очень часто: он быстро показывает, понимает ли кандидат платформу или только синтаксис.

## Интуиция и аналогия

Представь книгу на английском, которую нужно прочитать в разных странах.

- **Исходный код C#** — рукопись автора. Читаемая тобой, но не машиной.
- **IL** — перевод книги на условный «международный» язык, который понимают переводчики во всех странах. Один перевод годится везде.
- **CLR + JIT** — синхронный переводчик в каждой стране. Он переводит с международного на местный язык (машинный код процессора) **по ходу чтения**, и только те главы, до которых дошли. Одну и ту же главу второй раз переводить не нужно — запись перевода сохраняется.
- **GC** — уборщик в читальном зале. Он убирает со столов то, чем больше никто не пользуется. Он сам решает, когда прийти, и ему нужно, чтобы читатели на время замерли — поэтому лишний мусор на столах (ненужные аллокации) замедляет всех.

Аналогия не идеальна (JIT не «переводит по ходу чтения» в буквальном смысле — компилирует метод целиком при первом вызове), но она хорошо удерживает порядок: **код → промежуточный язык → машинный код по требованию → уборка за программой**.

## Основная теория по шагам

### Шаг 1. Из чего состоит .NET

Слово «.NET» обозначает сразу несколько вещей, и путаница в них — типичная причина мутных ответов:

- **C#** — язык программирования. Правила записи, ключевые слова, синтаксис.
- **Компилятор Roslyn** — программа, которая читает C# и выдаёт сборку. Входит в .NET SDK.
- **CLR** (Common Language Runtime) — среда выполнения: загружает сборки, проверяет типы, компилирует IL в машинный код, управляет памятью и потоками.
- **BCL** (Base Class Library) — стандартная библиотека: `string`, `List<T>`, `File`, `Task` и тысячи других типов.
- **.NET SDK** — набор для разработчика: компилятор, команда `dotnet`, шаблоны проектов, NuGet. Нужен тебе на компьютере.
- **.NET Runtime** — то, что нужно для запуска готовой программы (CLR + BCL). Нужен на сервере.

Одно и то же слово «.NET» сегодня — это современный кроссплатформенный .NET (версии 5, 6, 7, 8, 9, 10…). Старый .NET Framework, который работает только на Windows, поддерживается как наследие, но новые проекты на нём не начинают. Языки C#, F# и VB.NET компилируются в один и тот же IL, поэтому могут использовать библиотеки друг друга (это называется *CLS-совместимость* — детали в [справочнике](#/ref/g/rt-clr-jit)).

### Шаг 2. Путь от `.cs` до работающей программы

~~~text Конвейер
 Program.cs ──▶ компилятор C# (Roslyn) ──▶ App.dll  (IL + метаданные)
                    dotnet build                 │
                                                 ▼
                                    dotnet run / dotnet App.dll
                                                 │
                                   CLR загружает сборку
                                                 │
                         первый вызов метода ──▶ JIT: IL → машинный код
                                                 │
                                   машинный код выполняется на CPU
                                   GC следит за объектами в куче
~~~

- **Компиляция (build).** Roslyn проверяет синтаксис и типы. Если ошибка — сборка не появится. Результат — **сборка** (`.dll` или `.exe`): файл, где лежат **IL** (Intermediate Language, промежуточный байткод) и **метаданные** (описания всех типов, методов, полей, ссылок на другие сборки). Машинного кода для процессора в обычной сборке **нет**.
- **Запуск.** Команда `dotnet App.dll` стартует процесс, в котором живёт CLR. Она находит точку входа (`Main`) и начинает исполнение.
- **JIT-компиляция.** Перед первым вызовом метода JIT берёт его IL и порождает машинный код под *текущий* процессор (x64, ARM64…). Код кэшируется в памяти процесса — при следующем вызове этого метода компиляция не повторяется. Методы, которые ни разу не вызвали, не компилируются вообще.
- **Исполнение.** Теперь метод — обычный машинный код, процессор выполняет его на полной скорости.

Почему не компилировать сразу в машинный код, как делают C и C++? Тогда пришлось бы собирать программу отдельно под каждую ОС и архитектуру. IL позволяет собрать **один раз** и запускать везде, где есть CLR. Бонус: JIT знает точную модель процессора и может использовать его особенности (векторные инструкции, например).

Цена — время «прогрева»: первые вызовы медленнее. Современный .NET смягчает это **многоуровневой компиляцией** (tiered compilation): метод сначала компилируется быстро и без глубоких оптимизаций, а если вызывается часто — перекомпилируется оптимально. Для приложений, где важен старт (консольные утилиты, serverless), существуют заранее скомпилированные режимы (**ReadyToRun**, **NativeAOT**). Их настройка — не ваш уровень Фазы 1; нужно знать, что они есть и зачем.

### Шаг 3. Первая программа

~~~bash
dotnet new console -n Hello
cd Hello
dotnet build          # компиляция в IL
dotnet run            # build + запуск
ls bin/Debug/         # внутри папка с версией .NET, а в ней Hello.dll
~~~

~~~csharp Program.cs — top-level statements
// Это вся программа: компилятор сам обернёт её в класс Program и метод Main.
Console.WriteLine("Привет, .NET!");
Console.WriteLine($"Аргументов командной строки: {args.Length}");

int total = 0;
foreach (string a in args)
{
    if (int.TryParse(a, out int n)) total += n;
}
Console.WriteLine($"Сумма числовых аргументов: {total}");
~~~

~~~bash
dotnet run -- 10 20 abc 5
# Привет, .NET!
# Аргументов командной строки: 4
# Сумма числовых аргументов: 35
~~~

Ключи после `--` передаются самой программе, а не команде `dotnet`.

:::info Классический Main
До C# 9 точка входа выглядела так: `static void Main(string[] args)` внутри класса. Top-level statements — это синтаксический сахар: в IL всё равно появляется метод `Main`. Ты встретишь оба стиля, читать нужно уметь оба.
:::

~~~csharp Эквивалент без top-level statements
namespace Hello;

internal class Program
{
    private static void Main(string[] args)
    {
        Console.WriteLine("Привет, .NET!");
    }
}
~~~

Убедиться, что «магия» top-level statements — просто сгенерированный метод, можно прямо из кода:

~~~csharp
using System.Diagnostics;

// Компилятор упаковал эти строки в метод со странным именем:
var method = new StackTrace().GetFrame(0)!.GetMethod()!;
Console.WriteLine(method.Name);
~~~

<Main>$
~~~

### Шаг 4. Что внутри сборки: IL своими глазами

IL выглядит как ассемблер для виртуальной стековой машины. Метод

~~~csharp
int Add(int a, int b) => a + b;
~~~

превращается примерно в такие инструкции:

~~~text
ldarg.0     // положить на стек первый аргумент
ldarg.1     // положить второй
add         // снять два, сложить, положить результат
ret         // вернуть то, что на вершине стека
~~~

Читать IL в работе нужно редко, но знать, что он существует, полезно: именно в нём видны `box`/`unbox` (тема про боксинг), вызовы виртуальных методов, генерируемый компилятором код для `foreach`, `async` и лямбд. Увидеть его можно в `ildasm`, ILSpy, dotPeek или на сайте sharplab.io.

Метаданные позволяют рантайму и инструментам узнавать о типах, не запуская код — именно на них работает *рефлексия* (`typeof(X).GetMethods()`), сериализация и внедрение зависимостей (Фаза 4).

### Шаг 5. Managed-код и безопасность типов

**Managed-код** — это код, исполняемый под управлением CLR. Что это даёт на практике:

- память под объекты выделяет и освобождает рантайм (ты не пишешь `free`/`delete`);
- обращение за границы массива даёт исключение `IndexOutOfRangeException`, а не тихую порчу чужой памяти;
- приведение типов проверяется (`InvalidCastException`);
- обращение по `null` даёт `NullReferenceException`, а не обращение по случайному адресу.

Иначе говоря: многие классы ошибок, которые в C и C++ приводят к уязвимостям и необъяснимым падениям, в managed-коде превращаются в понятные исключения со стеком вызовов. Существует и **unmanaged-код** (нативные библиотеки, системные вызовы), и в C# есть способы с ним общаться (`P/Invoke`, `unsafe`) — на этой фазе они не нужны.

### Шаг 6. Сборка мусора на уровне Junior

- Объекты reference-типов (`new SomeClass()`, массивы, строки) живут в **управляемой куче** (managed heap).
- Память под новый объект в куче выделяется очень быстро: рантайм просто сдвигает указатель «конца занятой памяти». Это называется *bump allocation* — аллокация почти бесплатна.
- Плата приходит позже: GC периодически находит объекты, **недостижимые из «корней»** (локальные переменные, статические поля, регистры), и освобождает их память, уплотняя кучу.
- Куча разделена на **поколения** 0, 1, 2: большинство объектов умирают молодыми, поэтому поколение 0 собирается часто и быстро. Выжившие повышаются в старшее поколение, которое собирается реже и дороже. Очень большие объекты (от ~85 000 байт) попадают в отдельную **кучу больших объектов** (LOH).
- Во время сборки приложение может ненадолго приостанавливаться. Чем меньше лишних аллокаций, тем меньше работы у GC и меньше пауз. Отсюда весь интерес к боксингу и `StringBuilder` в следующих темах.
- Режимы: **Workstation** (по умолчанию для консольных и настольных приложений) и **Server** (включён по умолчанию в проектах ASP.NET Core): Server GC использует несколько потоков и отдельную кучу на ядро и ориентирован на пропускную способность.
- GC освобождает **память**, но не закрывает файлы и соединения. Для этого есть `IDisposable` и `using` (будет в теме про исключения).

Увидеть работу поколений можно прямо в коде:

~~~csharp
var obj = new object();
Console.WriteLine($"сразу после создания: поколение {GC.GetGeneration(obj)}");
GC.Collect();                               // принудительная сборка — только в учебных целях!
Console.WriteLine($"пережил 1 сборку:      поколение {GC.GetGeneration(obj)}");
GC.Collect();
Console.WriteLine($"пережил 2 сборки:      поколение {GC.GetGeneration(obj)}");
GC.KeepAlive(obj);                          // не даём JIT счесть obj мёртвым раньше времени
~~~
~~~console
сразу после создания: поколение 0
пережил 1 сборку:      поколение 1
пережил 2 сборки:      поколение 2
~~~

И почувствовать «стоимость мусора»: чем больше создаём, тем чаще GC вынужден работать.

~~~csharp
int before = GC.CollectionCount(0);
var ring = new byte[16][];                  // держим ссылки, чтобы JIT не выбросил аллокации
for (int i = 0; i < 200_000; i++)
    ring[i % 16] = new byte[1000];          // короткоживущий мусор
int after = GC.CollectionCount(0);
Console.WriteLine($"сборок поколения 0 было: {(after > before ? "несколько" : "ни одной")}");
~~~
~~~console
сборок поколения 0 было: несколько
~~~

## Как это работает под капотом

Это уровень «знать, чтобы не бояться», не уровень «настраивать». Границу из Обзора фазы мы держим: достаточно понять, что изнутри происходит несколько событий.

**Загрузка и проверка.** Когда в коде первый раз встречается обращение к типу (например, `new List<int>()`), CLR находит сборку, читает метаданные, строит внутреннее описание типа — таблицу методов, раскладку полей — и только затем создаёт объект. Поэтому первое обращение к типу чуть дороже последующих.

**Заглушки и JIT.** Для ещё не скомпилированного метода в таблице методов лежит *заглушка* (stub). Первый вызов попадает в неё, запускается JIT, затем адрес в таблице подменяется на готовый машинный код, и дальнейшие вызовы идут напрямую. Это и есть «компиляция при первом вызове».

**Многоуровневая компиляция.** На первом уровне (Tier-0) метод компилируется быстро, но неоптимально. Рантайм считает вызовы; «горячий» метод (вызван 30 раз и более) в фоне перекомпилируется оптимально (Tier-1), в том числе с учётом наблюдённого профиля выполнения. Поэтому микробенчмарки «на глаз» через `Stopwatch` врут: нужен прогрев и специализированный инструмент (BenchmarkDotNet).

**Куча и корни.** GC не ходит по всем объектам подряд. Он стартует от *корней* — локальных переменных в стеках потоков, статических полей, регистров, дескрипторов — и обходит граф ссылок, помечая достижимое. Всё непомеченное — мусор. Выжившие объекты сдвигаются (compaction), и ссылки на них обновляются. Это ещё одна причина, почему нельзя «держать адрес объекта»: объект может переехать.

**Точка остановки.** Чтобы безопасно обойти граф, GC должен на время остановить потоки приложения в безопасных точках (*suspension*). Современный GC делает значительную часть работы для старших поколений **параллельно** с приложением (фоновая сборка), но паузы не исчезают полностью.

Подробности с картинками и таблицами — в справочнике: [стек и куча](#/ref/g/rt-stack-heap), [GC и поколения](#/ref/g/rt-gc), [CLR и JIT](#/ref/g/rt-clr-jit), [сборки](#/ref/g/rt-assemblies).

:::deep Граница: сюда не копаем
Tiered PGO, ReadyToRun, NativeAOT, устройство поколений и card tables, инлайнинг и распределение регистров — всё это интересно, но **не нужно для Фазы 1**. Всплыл вопрос — запиши в [rabbit-holes](#rabbit-holes) и вернись к теме.
:::

## Типичные ошибки и ловушки

:::danger «C# компилируется в машинный код»
Нет: компилятор C# генерирует IL, а машинный код создаёт JIT во время выполнения (или AOT-компиляция заранее, но это отдельный режим публикации). Отсюда «первый вызов чуть медленнее» и переносимость одной `.dll` между ОС.
:::

:::danger «Раз есть GC, утечек памяти не бывает»
Бывают. Если объект достижим (например, лежит в статическом списке, который никто не чистит, или подписан на событие долгоживущего объекта), GC его не тронет. GC освобождает только то, что **недостижимо**.
:::

Ещё несколько ловушек, которые стоят отдельного внимания:

- **«GC освобождает всё: и файлы, и соединения».** Нет. Сборщик знает только про управляемую память. Файл, сокет, соединение с базой — ресурсы ОС, их закрывают явно: `Dispose()` или `using`. Финализатор существует как страховка, но срабатывает в неопределённый момент.
- **«Вызову `GC.Collect()`, чтобы стало быстрее».** Почти всегда наоборот: принудительная сборка провоцирует паузу и продвигает живые объекты в старшие поколения, где они потом дороже убираются. GC знает про память больше, чем ты. В приведённом выше примере вызов нужен только чтобы *показать* поколения.
- **«Debug и Release — одно и то же».** Нет: в Release JIT оптимизирует агрессивно (инлайнинг, выкидывание неиспользуемых переменных), поэтому и поведение GC (например, момент, когда объект считается мёртвым), и скорость отличаются. Замеры производительности в Debug бессмысленны.
- **«Время жизни локальной переменной = до конца блока».** Для GC важна не область видимости, а *последнее использование*: в оптимизированном коде объект может стать недостижимым раньше, чем закончится метод.
- **«Раз код переносимый, то поведение одинаково везде».** В целом да, но существуют платформенные различия: пути к файлам (`/` и `\`), регистр в именах файлов, часовые пояса, кодировки, наличие нативных библиотек. Переносим IL, а не окружение.
- **Путаница `dotnet build` и `dotnet run`.** `build` только компилирует (и порождает `bin/`/`obj/`), `run` собирает при необходимости и запускает. Папки `bin` и `obj` не коммитятся в git.

## Вопросы с собеседований

:::spoiler Что лежит внутри .dll после `dotnet build`?
IL-код методов и метаданные: описания типов, их полей, методов, ссылки на другие сборки. Машинного кода для CPU там (в обычном режиме) нет.
:::

:::spoiler Когда JIT компилирует метод?
При первом вызове этого метода. Последующие вызовы идут в уже скомпилированный машинный код. Методы, которые ни разу не вызывались, вообще не компилируются JIT-ом.
:::

:::spoiler Кто освобождает память под объект `new List<int>()` и когда?
Сборщик мусора — в какой-то момент после того, как на объект не останется ссылок из корней. Точный момент не определён: ты не управляешь им вручную.
:::

:::spoiler Почему закрывать файл нужно явно, если есть GC?
GC управляет только управляемой памятью и срабатывает в неопределённый момент. Файловый дескриптор — неуправляемый ресурс операционной системы; его нужно освободить детерминированно через `Dispose()` / `using`.
:::

:::spoiler Что такое managed-код? (ловушка: «это код без указателей»)
Код, исполняемый под управлением CLR: рантайм выделяет и освобождает память, проверяет типы и границы, превращает ошибки в исключения. Указатели в C# есть (`unsafe`), но это осознанное исключение, а не определение managed-кода.
:::

:::spoiler Чем IL отличается от машинного кода? Зачем нужен промежуточный шаг?
IL не привязан к процессору и ОС; машинный код привязан. Промежуточный шаг позволяет собрать программу один раз, а под конкретное железо превратить её в машинный код уже на целевой машине (JIT) — с учётом её возможностей.
:::

:::spoiler «Если в C# есть GC, то `using` не нужен» — согласен?
Нет. GC освобождает память, а `using` вызывает `Dispose()` и детерминированно освобождает неуправляемые ресурсы (файлы, сокеты, соединения), не дожидаясь неопределённой сборки.
:::

:::spoiler Почему первый вызов метода может быть медленнее последующих?
Нужно скомпилировать IL в машинный код (JIT), загрузить типы, прогреть кэши. Для критичных к старту сценариев применяют ReadyToRun или NativeAOT.
:::

## Что запомнить

- Компилятор C# (Roslyn) выпускает **IL + метаданные** в `.dll`; машинный код делает **JIT** при первом вызове метода (или AOT заранее).
- **CLR** — рантайм: загрузка типов, JIT, память, потоки. **BCL** — стандартная библиотека. **SDK** — инструменты разработчика.
- **Managed-код** = код под управлением CLR: память, типобезопасность и исключения контролирует рантайм.
- **GC** освобождает *недостижимые* объекты по достижимости из корней, а не по областям видимости; поколения 0/1/2, большие объекты — в LOH.
- GC не закрывает файлы и соединения — для этого `Dispose`/`using`. Лишние аллокации = лишняя работа GC.
- Top-level statements — сахар: в IL есть обычный метод `Main`.
- Замеры производительности — только в Release и с прогревом.

## Зачем это нужно

Синтаксис — это азбука: без неё не прочитать ни один чужой код, ни одно задание на собеседовании. Но в C# за привычными `if` и `for` прячется несколько особенностей, на которых ломаются именно новички и даже опытные люди из других языков:

- целые числа делятся «неправильно» (`7 / 2` даёт `3`), а переполнение `int` ничего не сообщает;
- `double` для денег приводит к копейкам, которые куда-то деваются;
- `switch` в современном C# — это не просто цепочка `if`, а мощное выражение с шаблонами (pattern matching), и в реальных проектах его встречаешь постоянно;
- ввод пользователя нельзя обрабатывать через `Parse` без проверки: программа «падает» от одного лишнего символа.

В работе всё это превращается в конкретные баги: неверная сумма в счёте, «странные» значения после арифметики, исключение на валидный (с точки зрения пользователя) ввод. Ревьюер с первого взгляда замечает `double price` или `int.Parse(Console.ReadLine())` — и это сразу формирует мнение о кандидате.

## Интуиция и аналогия

Программа — это рецепт. **Переменные** — банки на полках с этикетками («тут только мука», «тут только соль»): C# строго типизирован, в банку с этикеткой `int` нельзя положить строку. **Операторы** — действия над содержимым банок. **Ветвления** — развилки рецепта («если тесто липнет — добавь муки»). **Циклы** — «месить, пока не станет эластичным».

Особенность C# — этикетки обязательны и проверяются **до запуска**, на этапе компиляции. Это похоже на кухню, где повар-контролёр читает рецепт заранее и кричит: «здесь написано положить соль в банку с сахаром!» — до того как ты включил плиту. В JavaScript такого контролёра нет: ошибку обнаружишь, когда попробуешь блюдо.

Для денег нужны не «примерные весы» (`double`), а аптекарские (`decimal`): они медленнее, зато не врут в копейках.

## Основная теория по шагам

### Шаг 1. Переменные и встроенные типы

~~~csharp @nocheck
int count = 10;              // 32-битное целое
long big = 3_000_000_000L;   // 64-битное целое; _ — разделитель для читаемости
double ratio = 0.75;         // двоичное число с плавающей точкой
decimal price = 199.99m;     // десятичное число — для денег; суффикс m обязателен
bool isActive = true;
char letter = 'Я';           // один UTF-16 символ, одинарные кавычки
string name = "Тимур";       // строка — reference type (подробно в теме про строки)

var total = price * count;   // var: тип выводит компилятор (здесь decimal), типизация остаётся строгой
const int MaxAttempts = 3;   // константа времени компиляции
~~~

Основные встроенные типы и их диапазоны, которые стоит знать наизусть:

| Тип | Размер | Что хранит | Диапазон / точность |
|---|---|---|---|
| `byte` / `sbyte` | 1 байт | целое | 0…255 / −128…127 |
| `short` / `ushort` | 2 байта | целое | −32 768…32 767 / 0…65 535 |
| `int` | 4 байта | целое | ≈ ±2,1 млрд (`int.MaxValue` = 2 147 483 647) |
| `long` | 8 байт | целое | ≈ ±9,2·10¹⁸ |
| `float` | 4 байта | дробное, двоичное | ≈ 7 значащих цифр |
| `double` | 8 байт | дробное, двоичное | ≈ 15–17 значащих цифр |
| `decimal` | 16 байт | дробное, десятичное | 28–29 значащих цифр, точное для десятичных дробей |
| `bool` | 1 байт | `true`/`false` | — |
| `char` | 2 байта | символ UTF-16 | `'\u0000'`…`'￿'` |

По умолчанию бери `int` для целых, `double` для «научных» дробей (физика, графика, статистика), `decimal` — для денег и всего, где важна десятичная точность, `string` — для текста.

Несколько правил именования, чтобы код читался как C#: переменные и параметры — `camelCase`, типы, методы, свойства — `PascalCase`, константы — `PascalCase` (не `UPPER_CASE`), приватные поля — `_camelCase`. Имена на английском, осмысленные: `totalPrice`, а не `tp`.

**`var` — это не `dynamic`.** `var total = ...` по-прежнему имеет **один конкретный тип**, определённый при компиляции. Присвоить потом строку в `total` нельзя. `var` уместен, когда тип очевиден из правой части (`var list = new List<int>()`); если из правой части тип непонятен (`var x = Calculate();`), лучше написать тип явно.

**`const` и `readonly`.** `const` — значение подставляется компилятором на этапе сборки, допустимо только для простых типов и строк (`const int Max = 3;`). Поле с `readonly` присваивается один раз — в объявлении или в конструкторе, и может содержать любой объект.

**Область видимости.** Переменная живёт в пределах блока `{ }`, где объявлена. Нельзя объявить в вложенном блоке переменную с именем, которое уже занято во внешнем (в отличие от JavaScript, это ошибка компиляции — «теневое» объявление запрещено для локальных переменных). Переменная должна быть **определённо присвоена** до чтения — компилятор следит за этим (ошибка CS0165).

**Nullable reference types.** Запись `string?` означает «здесь может быть `null`», `string` — «`null` не ожидается». Компилятор предупреждает, если ты обращаешься к потенциально пустому значению без проверки. Включено в современных шаблонах проектов; подробнее — в теме про типы.

### Шаг 2. Преобразования типов

Неявное преобразование разрешено, когда ничего не теряется (`int` → `long`, `int` → `double`, `int` → `decimal`). Явное нужно, когда возможна потеря данных:

~~~csharp
double d = 3.99;
int truncated = (int)d;               // отбрасывается дробная часть, НЕ округление
Console.WriteLine(truncated);         // 3
Console.WriteLine((int)-3.99);        // -3

Console.WriteLine(Math.Round(2.5));   // 2 — «банковское» округление к чётному
Console.WriteLine(Math.Round(3.5));   // 4
Console.WriteLine(Math.Round(2.5, MidpointRounding.AwayFromZero));  // 3 — как в школе

int big = 300;
byte b = (byte)big;                   // не помещается в 0..255 — старшие биты потеряны
Console.WriteLine(b);                 // 44
~~~
~~~console
3
-3
2
4
3
44
~~~

Для конвертации строки в число используют `int.Parse` / `int.TryParse`, для объектов — `Convert.ToInt32`. Метод `Convert` округляет при преобразовании из `double`, а приведение `(int)` — отбрасывает дробь; не путай.

### Шаг 3. Деньги: `double` против `decimal`

~~~csharp
double a = 0.1 + 0.2;
Console.WriteLine(a == 0.3);   // False
Console.WriteLine(a);          // 0.30000000000000004

decimal b = 0.1m + 0.2m;
Console.WriteLine(b == 0.3m);  // True
Console.WriteLine(1m / 3m);    // 0.3333333333333333333333333333
~~~
~~~console
False
0.30000000000000004
True
0.3333333333333333333333333333
~~~

`double` хранит число в двоичной дроби, и 0.1 в ней представляется только приближённо (как 1/3 в десятичной системе — бесконечная дробь). `decimal` хранит десятичные цифры точно (в пределах 28–29 значащих цифр). **Для денег в проекте используй только `decimal`**, а суффикс `m` не забывай: `decimal x = 0.1;` — ошибка компиляции, потому что `0.1` без суффикса — `double`.

Сравнивать `double` на равенство через `==` нельзя; сравнивают с допуском: `Math.Abs(a - b) < 1e-9`. Для `decimal` можно, но округляй осознанно (`Math.Round(x, 2)`).

Особые значения `double`: `double.NaN` (не число; `NaN == NaN` даёт `false`), `double.PositiveInfinity` (результат `1.0 / 0`). Деление **целых** на ноль, наоборот, бросает `DivideByZeroException`.

### Шаг 4. Операторы

Арифметика: `+ - * / %`. Составное присваивание: `+= -= *= /= %=`. Инкремент и декремент: `++`, `--` — в префиксной форме значение меняется до использования, в постфиксной — после.

~~~csharp
int count = 10;

Console.WriteLine(7 / 2);      // 3   — оба операнда int → целочисленное деление
Console.WriteLine(7 / 2.0);    // 3.5 — один операнд double → обычное деление
Console.WriteLine(-7 / 2);     // -3  — округление к нулю
Console.WriteLine(-7 % 2);     // -1  — знак остатка совпадает со знаком делимого

int max = int.MaxValue;
Console.WriteLine(max + 1);    // -2147483648 — тихое переполнение (unchecked по умолчанию)
Console.WriteLine(unchecked(max + 1));

try { Console.WriteLine(checked(max + 1)); }
catch (OverflowException) { Console.WriteLine("OverflowException"); }

int i = 5;
int post = i++;                // post = 5, потом i = 6
int pre = ++i;                 // i = 7, потом pre = 7
Console.WriteLine($"{post} {pre} {i}");
~~~
~~~console
3
3.5
-3
-1
-2147483648
-2147483648
OverflowException
5 7 7
~~~

Сравнение: `== != < > <= >=`. Логика: `&&` (И), `||` (ИЛИ), `!` (НЕ). Операторы `&&` и `||` **вычисляют правый операнд только если нужно** (короткое замыкание). Это не оптимизация, а правило, на которое опираются: `if (user != null && user.Age > 18)`.

Побитовые операции `& | ^ ~ << >>` нужны для флагов и низкоуровневого кода; на этой фазе достаточно знать, что они существуют:

~~~csharp
Console.WriteLine(5 & 3);      // 1  (0101 & 0011 = 0001)
Console.WriteLine(5 | 3);      // 7  (0101 | 0011 = 0111)
Console.WriteLine(5 ^ 3);      // 6  (0101 ^ 0011 = 0110)
Console.WriteLine(1 << 4);     // 16
~~~
~~~console
1
7
6
16
~~~

**Приоритет** операторов: умножение выше сложения, `&&` выше `||`. Если сомневаешься — ставь скобки: читаемость важнее.

**Операторы для `null`.**

~~~csharp
string? input = null;
string shown = input ?? "(пусто)";   // ?? — значение по умолчанию для null
int len = input?.Length ?? 0;        // ?. — безопасный доступ: null вместо исключения
input ??= "по умолчанию";            // ??= — присвоить, только если сейчас null
Console.WriteLine($"{shown} | {len} | {input}");

int count = 10;
bool ok = count > 0 && 100 / count > 5; // && не вычисляет правую часть, если левая false
Console.WriteLine(ok);
~~~
~~~console
(пусто) | 0 | по умолчанию
True
~~~

Условный оператор (тернарный) `условие ? значение1 : значение2` годится для коротких выражений. Вкладывать его друг в друга не стоит — используй `switch`-выражение.

### Шаг 5. Строки и форматирование вывода

Интерполяция `$"..."` — основной способ собирать строки. Внутри фигурных скобок можно указать **ширину** и **формат**:

~~~csharp
decimal price = 1234.5m;
int n = 42;
Console.WriteLine($"[{n,6}]");        // выравнивание вправо в 6 символов
Console.WriteLine($"[{n,-6}]");       // влево
Console.WriteLine($"{price:F2}");     // два знака после запятой
Console.WriteLine($"{n:D5}");         // 00042
Console.WriteLine($"{255:X}");        // FF — шестнадцатеричное
Console.WriteLine($"{1.5}");          // разделитель берётся из текущей культуры
~~~
~~~console
[    42]
[42    ]
1234.50
00042
FF
1.5
~~~

Формат зависит от **культуры** (текущей локали): в русской культуре `1.5` выведется как `1,5`. Для файлов и обмена между системами используй `CultureInfo.InvariantCulture`. Подробно про строки — в отдельной теме.

### Шаг 6. Ветвления: `if`, `switch`, `switch`-выражения

~~~csharp @nocheck
decimal amount = 250m;

if (amount <= 0m)
    Console.WriteLine("Сумма должна быть положительной");
else if (amount > 10_000m)
    Console.WriteLine("Нужна дополнительная проверка");
else
    Console.WriteLine("Ок");
~~~

Фигурные скобки у однострочного `if` можно опустить, но в команде их обычно требуют всегда — это защищает от ошибок при добавлении второй строки в ветку.

**`switch`-выражение + pattern matching: возвращает значение.**

~~~csharp
decimal amount = 250m;

string category = amount switch
{
    < 0m => "отрицательная",
    0m => "ноль",
    > 0m and <= 1_000m => "мелкий платёж",
    _ => "крупный платёж"            // _ — «всё остальное», обязательно для полноты
};
Console.WriteLine(category);          // мелкий платёж
~~~
~~~console
мелкий платёж
~~~

Шаблоны (patterns) — это условия, встроенные в `switch` и `is`:

~~~csharp
static string Describe(object o) => o switch
{
    null => "ничего",
    int n when n < 0 => "отрицательное число",
    int n => $"число {n}",
    string { Length: 0 } => "пустая строка",
    string s => $"строка '{s}'",
    _ => "что-то другое"
};

Console.WriteLine(Describe(-5));
Console.WriteLine(Describe(7));
Console.WriteLine(Describe(""));
Console.WriteLine(Describe("мир"));
Console.WriteLine(Describe(null!));
Console.WriteLine(Describe(3.5));

static string Light(bool red, bool yellow) => (red, yellow) switch
{
    (true, false) => "стоп",
    (true, true) => "приготовься",
    (false, true) => "внимание",
    (false, false) => "езжай"
};
Console.WriteLine(Light(true, true));
~~~
~~~console
отрицательное число
число 7
пустая строка
строка 'мир'
ничего
что-то другое
приготовься
~~~

Здесь: `when` — дополнительное условие; `string { Length: 0 }` — *property pattern* (проверка свойств); `(red, yellow)` — *tuple pattern*, удобный способ ветвиться по нескольким значениям сразу.

**Классический `switch`-оператор** по строке команды меню:

~~~csharp @nocheck
string command = "deposit";
switch (command)
{
    case "deposit":
    case "d":
        Console.WriteLine("Пополнение");
        break;                        // break обязателен: «проваливания» в C# нет
    case "exit":
        return;
    default:
        Console.WriteLine("Неизвестная команда");
        break;
}
~~~

Метки `case "deposit": case "d":` подряд — это объединение вариантов, а не проваливание. Если ветка непустая, она обязана завершаться `break`, `return`, `throw` или `continue`.

Проверка типа и значения в условиях: `if (x is int n && n > 0)`, `if (obj is not null)`, `if (c is >= 'a' and <= 'z')` — те же шаблоны работают и в `if`.

### Шаг 7. Циклы

~~~csharp
for (int i = 0; i < 3; i++)
    Console.Write(i + " ");              // 0 1 2
Console.WriteLine();

int attempts = 0;
while (attempts < 3)
{
    attempts++;
}
Console.WriteLine(attempts);

var amounts = new List<decimal> { 100m, 250m, -5m, 40m };
decimal sum = 0m;
foreach (decimal x in amounts)
{
    if (x < 0m) continue;                // пропустить итерацию
    if (sum > 300m) break;               // выйти из цикла
    sum += x;
}
Console.WriteLine(sum);                  // 350
~~~
~~~console
0 1 2 
3
350
~~~

- **`for`** — когда нужен индекс или известное число повторений.
- **`foreach`** — когда нужно обойти все элементы коллекции без индекса; переменная цикла доступна только для чтения.
- **`while`** — повторять, пока условие истинно (проверка **до** тела).
- **`do … while`** — тело выполнится хотя бы раз (проверка **после**).
- `break` выходит из ближайшего цикла, `continue` переходит к следующей итерации. Для выхода из вложенных циклов лучше вынести их в метод и использовать `return`, чем пользоваться `goto`.

~~~csharp @nocheck
string? line;
do
{
    Console.Write("Введите 'q' для выхода: ");
    line = Console.ReadLine();
} while (line is not null && line != "q");   // null — конец ввода (Ctrl+Z / Ctrl+D)
~~~

**Бесконечный цикл** (`while (true)`) допустим, если внутри есть выход (`break`/`return`) — например, главный цикл меню.

### Шаг 8. Ввод пользователя без падений

~~~csharp @nocheck
Console.Write("Сумма: ");
string? raw = Console.ReadLine();

if (decimal.TryParse(raw, out decimal value) && value > 0m)
    Console.WriteLine($"Принято: {value}");
else
    Console.WriteLine("Это не положительное число, попробуйте ещё раз");
~~~

Шаблон «спросить → проверить → повторить» оформляют циклом:

~~~csharp @nocheck
decimal ReadPositive(string prompt)
{
    while (true)
    {
        Console.Write(prompt);
        if (decimal.TryParse(Console.ReadLine(), out decimal v) && v > 0m) return v;
        Console.WriteLine("Нужно положительное число.");
    }
}
~~~

:::warn Культура и десятичный разделитель
`decimal.TryParse` по умолчанию использует **текущую культуру** системы. В русской культуре разделитель — запятая, поэтому `"10.5"` может не распознаться, а `"10,5"` — распознается. В проекте реши явно: либо принимаешь ввод в текущей культуре, либо используешь `CultureInfo.InvariantCulture` (точка). Для **файлов** всегда используй `InvariantCulture`.
:::

`TryParse` не бросает исключений: возвращает `bool`, а результат кладёт в `out`-параметр. Это правильный инструмент для ожидаемо неверного ввода — подробнее про `out` в теме про методы.

## Как это работает под капотом

- **`int`, `double`, `bool` — псевдонимы типов .NET.** `int` — это `System.Int32`, `double` — `System.Double`, `string` — `System.String`. Ключевое слово и полное имя — одно и то же; у `int` есть методы (`5.ToString()`, `int.Parse`) именно поэтому. Все они — `struct` (кроме `string`), живут по правилам value types (следующая тема).
- **Арифметика и переполнение.** В IL обычное сложение — инструкция `add`, она «обёртывается» при переполнении. В контексте `checked` компилятор использует `add.ovf`, которая бросает `OverflowException`. Включить проверку для всего проекта можно настройкой `<CheckForOverflowUnderflow>true</CheckForOverflowUnderflow>`. Константные выражения, переполняющие тип, не компилируются вовсе.
- **Плавающая точка** хранится по стандарту IEEE 754: знак, порядок и мантисса в двоичном виде. Поэтому 0.1 — бесконечная двоичная дробь, обрезанная до 53 бит мантиссы. **`decimal`** хранится иначе: 96-битное целое и масштаб (степень десяти), поэтому `0.1m` — это «1, сдвинутое на один знак». Цена — скорость: операции с `decimal` в разы медленнее `double`, потому что процессор не умеет их аппаратно.
- **`switch` и циклы.** `switch` по числам и перечислениям компилируется в таблицу переходов (jump table) или в цепочку сравнений — выбирает компилятор; по строкам — через вычисление хеша. `foreach` по массиву превращается в обычный цикл с индексом; по другим коллекциям — в вызовы перечислителя ([что именно](#/ref/d/fl-foreach)).
- **Интерполяция строк** в современных версиях компилируется в вызовы специальной структуры-обработчика (`DefaultInterpolatedStringHandler`), которая собирает результат без лишних промежуточных строк.
- **`var` не влияет на IL**: получается тот же код, что и с явным типом — тип просто выводится компилятором. Это и есть причина, по которой `var` безопасен.

## Типичные ошибки и ловушки

:::danger Изменение коллекции внутри `foreach`
`foreach (var x in list) if (x < 0) list.Remove(x);` бросит `InvalidOperationException`: коллекцию нельзя менять во время перечисления. Решения: цикл `for` с конца, `list.RemoveAll(x => x < 0)` или новая коллекция.
:::

Проверим на практике:

~~~csharp
var list = new List<int> { 1, 2, 3, 4 };
try
{
    foreach (var x in list)
        if (x == 2) list.Remove(x);
}
catch (InvalidOperationException e)
{
    Console.WriteLine(e.GetType().Name);
}

list.RemoveAll(x => x % 2 == 0);       // правильный способ
Console.WriteLine(string.Join(",", list));
~~~
~~~console
InvalidOperationException
1,3
~~~

:::danger `int.Parse` на пользовательском вводе
`int.Parse("abc")` бросает `FormatException`. Для ввода, который **ожидаемо** может быть неверным, используй `TryParse` — это не исключительная ситуация.
:::

- **Целочисленное деление там, где ждали дробь.** `double avg = sum / count;` при `int sum, count` сначала делит как `int`, потом превращает в `double` — дробная часть уже потеряна. Решение: `(double)sum / count`.
- **`double` для денег.** Накапливает ошибки, разные округления в разных местах. Только `decimal`.
- **Забытый `break`** в классическом `switch` — не ошибка проваливания (как в C), а ошибка компиляции «control cannot fall through»; полезно знать для собеседования.
- **Сравнение `==` для `double`.** Результаты вычислений сравнивай с допуском.
- **Смешивание `=` и `==`.** В `if (x = 5)` для `int` компилятор выдаст ошибку (в отличие от C); для `bool` — только предупреждение.
- **Бесконечный цикл** из-за забытого изменения счётчика в `while`. Проверяй, что условие когда-то станет ложным.
- **Off-by-one.** Индексы идут с 0: `for (i = 0; i <= arr.Length; i++)` выйдет за границы; правильно `i < arr.Length`.
- **Теневые имена.** Одноимённая переменная во вложенном блоке — ошибка компиляции; не пытайся «переиспользовать» имя.
- **Магические числа.** `if (x > 18)` — что за 18? Вынеси в `const int AdultAge = 18;`.

## Вопросы с собеседований

:::spoiler Чему равно `5 / 2 * 2.0` и почему?
`4`. Сначала `5 / 2` — оба `int`, целочисленное деление даёт `2`. Потом `2 * 2.0` = `4.0` (double). Порядок вычисления слева направо при одинаковом приоритете.
:::

:::spoiler Почему `switch`-выражение требует ветку `_`?
Выражение обязано вернуть значение для любого входа. Если компилятор видит, что не все случаи покрыты, он выдаёт предупреждение, а при непокрытом значении во время выполнения будет `SwitchExpressionException`. `_` закрывает «все остальные» случаи.
:::

:::spoiler Почему для денег `decimal`, а не `double`?
`double` — двоичная плавающая точка: многие десятичные дроби (0.1, 0.2) в ней непредставимы точно, ошибки накапливаются. `decimal` хранит десятичные цифры точно, а финансовые суммы — десятичные.
:::

:::spoiler В чём разница между `int.Parse` и `int.TryParse`? (ловушка: «TryParse быстрее»)
`Parse` бросает исключение при неверном формате, `TryParse` возвращает `false`. Для ожидаемо неверного ввода (пользователь, файл) — `TryParse`: исключения дороги и не должны управлять потоком. Для данных, которые обязаны быть корректными и иначе — баг, `Parse` уместен.
:::

:::spoiler Что делает `max + 1` для `int max = int.MaxValue`? Как это поймать?
Результат «оборачивается» в `-2147483648` — молчаливо, это поведение `unchecked` по умолчанию. Поймать: `checked(max + 1)` или `checked { … }` — тогда `OverflowException`; либо включить `CheckForOverflowUnderflow` в проекте. Для денег и счётчиков в критичных местах используйте `checked` или тип побольше (`long`).
:::

:::spoiler Чем `foreach` отличается от `for`? Можно ли менять коллекцию в `foreach`?
`foreach` не даёт индекса и не позволяет присваивать переменную цикла; обход идёт через перечислитель. Изменение коллекции во время обхода (добавление/удаление) приводит к `InvalidOperationException`. Менять *элементы* изменяемых типов можно, но саму коллекцию — нет.
:::

:::spoiler Чем `var` отличается от `dynamic`? (ловушка: «var — это динамический тип»)
`var` — вывод типа на этапе компиляции, тип фиксирован навсегда. `dynamic` — проверка типов отложена до выполнения, ошибки видны только в рантайме. `var` — просто сокращение записи, `dynamic` — отдельный механизм (почти не нужен джуну).
:::

:::spoiler Почему `Math.Round(2.5)` даёт `2`?
По умолчанию используется «банковское» округление: половинка округляется к ближайшему чётному (`MidpointRounding.ToEven`) — оно не смещает суммы при массовых округлениях. Школьное поведение — `MidpointRounding.AwayFromZero`.
:::

## Что запомнить

- `int / int` — целочисленное деление; `-7 / 2 = -3`, `-7 % 2 = -1`. Для дроби нужен `double`/`decimal` хотя бы у одного операнда.
- Деньги — только `decimal` (литерал с `m`); `double` не сравнивают через `==`.
- Переполнение `int` молчаливо (`unchecked`); `checked` бросает `OverflowException`.
- `??`, `?.`, `??=` — рабочие инструменты против `null`; `&&` и `||` — с коротким замыканием.
- `switch`-выражение возвращает значение и требует полноты (`_`); шаблоны работают и в `if`/`is`.
- Классический `switch` не проваливается: нужен `break`/`return`/`throw`.
- Ввод пользователя — только через `TryParse` и с учётом культуры; файлы — `InvariantCulture`.
- Нельзя менять коллекцию в `foreach`; `var` — вывод типа при компиляции, не `dynamic`.

## Зачем это нужно

Эта тема отвечает на вопрос, который рано или поздно задаёт себе каждый, кто пишет на C#: «**почему я поменял переменную в одном месте, а изменилось в другом?**» — или наоборот: «почему я поменял, а ничего не изменилось?».

Типичные ситуации из реальной работы:

- метод принимает заказ, правит его и… вызывающий код видит изменения (или нет — зависит от типа);
- в списке лежат DTO, и «копия» списка на самом деле ссылается на те же объекты;
- кто-то сделал `struct` «для производительности», а код стал медленнее и запутаннее;
- из кэша вернулся объект, его изменили в одном запросе — и другой запрос получил чужие данные;
- на собеседовании просят «нарисовать, где что лежит в памяти» для пятнадцати строк кода.

Если понимаешь модель «переменная хранит либо значение, либо ссылку», все эти случаи перестают быть загадкой. Это один из тех фундаментов, которые не устаревают за десятилетия: модель одинакова в C# 1.0 и в C# 14.

## Интуиция и аналогия

Представь два способа поделиться документом.

- **Value type — ксерокопия.** Ты отдаёшь коллеге копию листа. Что бы он ни зачеркнул, твой оригинал не изменится. Каждая переменная — владелец своего листа.
- **Reference type — ссылка на общий документ.** Ты отправляешь коллеге ссылку на Google Doc. Теперь у вас **один документ на двоих**: любая правка видна обоим. А «отправить коллеге ссылку» — это тоже копирование, только копируется не документ, а адрес.

Теперь тонкость, на которой ловят на собеседованиях. Если коллега, получив ссылку, **пошлёт её в корзину** и заведёт себе новый документ — твоя ссылка по-прежнему ведёт на старый. Он сменил *свою копию ссылки*, а не сам документ. Это в точности `p = new PointC()` внутри метода.

Про «стек и кучу» можно думать так: **стек — это стол прямо перед тобой** (быстро, но места мало, и всё со стола убирают, когда работа закончена), **куча — склад** (места много, но чтобы что-то взять, нужен адрес, а уборкой занимается GC).

## Основная теория по шагам

### Шаг 1. Две семьи типов

| | Value types | Reference types |
|---|---|---|
| Что хранит переменная | **Само значение** | **Ссылку** на объект в куче |
| Примеры | `int`, `double`, `decimal`, `bool`, `char`, `DateTime`, `enum`, любой `struct`, `record struct` | `class`, `string`, массивы, `record` (class), делегаты, `object` |
| Присваивание `b = a` | Копирует **данные** | Копирует **ссылку**: две переменные — один объект |
| Может быть `null` | Нет (только `int?` = `Nullable<int>`) | Да |
| Наследование | Не наследуется от других типов (неявно производен от `System.ValueType`), но может реализовывать интерфейсы | Можно (если класс не `sealed`) |
| Значение по умолчанию | Все поля обнулены (`0`, `false`) | `null` |

Все value-типы неявно наследуют `System.ValueType`, а тот — `System.Object`. Поэтому у любого `int` есть `ToString()` и `GetHashCode()`.

Как отличить в коде: если тип объявлен словом `struct` (или `enum`, или `record struct`) — это value type. Если `class`, `record`, `interface`, `delegate` — reference. Все числовые типы, `bool`, `char`, `DateTime`, `Guid`, `TimeSpan` — value types. `string`, массивы (даже `int[]`) и `object` — reference.

### Шаг 2. Где физически лежат данные

Популярная фраза «value types живут на стеке, reference types — в куче» **упрощение, и на собеседовании за него могут поймать**. Точная версия:

- **Объект reference-типа** семантически создаётся в управляемой куче. Переменная хранит только ссылку (адрес).
- **Значение value-типа** хранится **там, где объявлена переменная или поле**:
  - локальная переменная метода → в кадре стека этого метода (или в регистре процессора);
  - поле внутри класса → внутри объекта этого класса, то есть **в куче**;
  - элемент массива `int[]` → внутри массива, то есть **в куче**;
  - локальная переменная, захваченная лямбдой, или переменная в `async`-методе → компилятор переносит её в объект в куче.
- Сама **ссылка** — тоже значение (адрес), и она лежит там же, где переменная: на стеке, в поле объекта или в элементе массива.

~~~csharp @nocheck
int n = 42;
var s = new PointS { X = 1, Y = 2 };
var list = new List<int> { 1, 2, 3 };
var c = new PointC { X = 1, Y = 2 };

struct PointS { public int X; public int Y; }
class PointC { public int X; public int Y; }
~~~

~~~text Память после выполнения
 СТЕК (кадр метода Main)            КУЧА (managed heap)
┌─────────────────────────┐        ┌─────────────────────────────┐
│ int n       = 42        │        │ List<int>                   │
│ PointS s  { X=1, Y=2 }  │   ┌──▶ │   _items ──────────┐        │
│ List<int> list  ────────┼───┘    │   _size = 3        │        │
│ PointC c  ──────────────┼───┐    └────────────────────┼────────┘
└─────────────────────────┘   │    ┌────────────────────▼────────┐
                              │    │ int[4] { 1, 2, 3, 0 }       │
                              │    │ int-ы лежат прямо в массиве │
                              │    │ (без «коробок»)             │
                              │    └─────────────────────────────┘
                              │    ┌─────────────────────────────┐
                              └──▶ │ PointC { X=1, Y=2 }         │
                                   └─────────────────────────────┘
~~~

Обрати внимание: `List<int>` — это **два** объекта в куче: сам список (с полями `_items`, `_size`) и внутренний массив. Сами `int` лежат в массиве **непосредственно**, без упаковки — это главное преимущество generic-коллекций (подробнее в [боксинге](#p1-boxing)). Ёмкость массива 4, а не 3: при первом добавлении `List<T>` выделяет 4 ячейки и потом удваивает — это тема Фазы 2.

Ещё два уточнения «как на самом деле»:

- Локальная переменная value-типа не обязана быть на стеке: JIT вправе держать её в регистре процессора, а то и вовсе выбросить. «Стек» — модель для рассуждений, не гарантия реализации.
- Аналогично, в последних версиях .NET JIT умеет размещать в стеке некоторые короткоживущие объекты reference-типа, если докажет, что ссылка на них никуда не «убегает». Для тебя это ничего не меняет: **поведение** (копируется ссылка, объект общий) определяется языком, а место хранения — оптимизация рантайма.

### Шаг 3. Присваивание: копия данных или копия ссылки

~~~csharp
var s1 = new PointS { X = 1, Y = 2 };
var s2 = s1;          // копия всех полей
s2.X = 100;
Console.WriteLine(s1.X);   // 1   — s1 не изменился

var c1 = new PointC { X = 1, Y = 2 };
var c2 = c1;          // копия ССЫЛКИ: оба указывают на один объект
c2.X = 100;
Console.WriteLine(c1.X);   // 100 — это один и тот же объект
Console.WriteLine(ReferenceEquals(c1, c2));

struct PointS { public int X; public int Y; }
class PointC { public int X; public int Y; }
~~~
~~~console
1
100
True
~~~

`ReferenceEquals(a, b)` отвечает на вопрос «это один и тот же объект?» — независимо от того, как класс переопределил `Equals`.

**Поведение по умолчанию** тоже различается. Массив структур сразу содержит «нулевые» структуры, массив ссылок — `null`:

~~~csharp
var structs = new PointS[2];
var classes = new PointC[2];
Console.WriteLine(structs[0].X);          // 0 — готовая структура с обнулёнными полями
Console.WriteLine(classes[0] is null);    // True — объектов ещё нет
PointS zero = default;                    // «значение по умолчанию» для любого типа
Console.WriteLine(zero.Y);

struct PointS { public int X; public int Y; }
class PointC { public int X; public int Y; }
~~~
~~~console
0
True
0
~~~

**Строки — особый случай.** `string` — reference type, но он **неизменяемый**, поэтому ведёт себя «как значение»: любая «правка» создаёт новую строку, и общий оригинал никто не испортит.

~~~csharp
string a = "кот";
string b = a;          // копия ссылки на одну и ту же строку
b += "ик";             // создаётся НОВАЯ строка, a не меняется
Console.WriteLine(a);  // кот
Console.WriteLine(b);  // котик
~~~
~~~console
кот
котик
~~~

**Мелкое копирование.** Копия структуры копирует поля, но если поле — ссылка, копируется *ссылка*, а не объект, на который она указывает:

~~~csharp
var a = new Holder { Items = new[] { 1, 2, 3 } };
var b = a;                  // копия структуры...
b.Items[0] = 99;            // ...но массив внутри один на двоих
Console.WriteLine(a.Items[0]);

struct Holder { public int[] Items; }
~~~
~~~console
99
~~~

Это называется *shallow copy* (поверхностная копия). Чтобы получить независимую копию вложенного объекта, нужно скопировать и его (*deep copy*) — явно, руками или через неизменяемые структуры данных.

### Шаг 4. Передача в метод — тот самый вопрос из критерия {#pass}

**В C# по умолчанию всё передаётся по значению.** Разница в том, *что является значением*:

- для `struct` значение — это **все данные**, метод получает копию;
- для `class` значение — это **ссылка**, метод получает копию ссылки на **тот же** объект.

~~~csharp
var s = new PointS { X = 1, Y = 2 };
var c = new PointC { X = 1, Y = 2 };

MoveStruct(s);
MoveClass(c);
Console.WriteLine(s.X);   // 1  — метод менял свою копию структуры
Console.WriteLine(c.X);   // 11 — метод менял общий объект через копию ссылки

ReplaceClass(c);
Console.WriteLine(c.X);   // 11 — подменить объект вызывающего метод не может

static void MoveStruct(PointS p) { p.X += 10; }
static void MoveClass(PointC p) { p.X += 10; }
static void ReplaceClass(PointC p)
{
    p = new PointC { X = 99 };   // меняется только локальная копия ссылки
}

struct PointS { public int X; public int Y; }
class PointC { public int X; public int Y; }
~~~
~~~console
1
11
11
~~~

:::key Формулировка для собеседования
«Аргументы по умолчанию передаются по значению. У структуры значение — это сами данные, поэтому метод работает с копией, и изменения не видны снаружи. У класса значение — это ссылка; метод получает копию ссылки на тот же объект, поэтому изменения **полей** видны вызывающему коду. Но если метод присвоит параметру новый объект, вызывающий код этого не увидит — для этого нужен `ref`.»
:::

~~~text Что происходит при вызове MoveClass(c)
 кадр Main          кадр MoveClass             КУЧА
┌─────────────┐    ┌─────────────┐       ┌───────────────────┐
│ c  ─────────┼──┐ │ p  ─────────┼──┐    │ PointC { X: 1→11 }│
└─────────────┘  │ └─────────────┘  │    └───────────────────┘
                 │                  │              ▲
                 └──────────────────┴──────────────┘
          две ссылки (c и p) → один и тот же объект
~~~

Модификатор `ref` (и `out`, `in`) меняет правило: метод получает не копию, а **саму переменную вызывающего** — подробности в теме про [методы](#p1-methods). Для ссылки на класс с `ref` метод может подменить объект целиком; для структуры с `ref` — изменить оригинал без копирования.

### Шаг 5. Равенство

~~~csharp
var a = new PointC { X = 1, Y = 2 };
var b = new PointC { X = 1, Y = 2 };
Console.WriteLine(a == b);          // False — для классов == сравнивает ссылки
Console.WriteLine(a.Equals(b));     // False — Equals по умолчанию тоже по ссылке

var r1 = new PointR(1, 2);
var r2 = new PointR(1, 2);
Console.WriteLine(r1 == r2);        // True — record сравнивается по значениям полей

var s1 = new PointS { X = 1, Y = 2 };
var s2 = new PointS { X = 1, Y = 2 };
Console.WriteLine(s1.Equals(s2));   // True — ValueType.Equals сравнивает поля
// Console.WriteLine(s1 == s2);     // ошибка компиляции: для struct оператор == не определён

class PointC { public int X; public int Y; }
struct PointS { public int X; public int Y; }
record PointR(int X, int Y);
~~~
~~~console
False
False
True
True
~~~

Исключение из правила «`==` по ссылке» — `string`: оператор `==` для строк переопределён и сравнивает **содержимое**. Для собственных классов равенство по значению нужно писать самому (`Equals`, `GetHashCode`) либо брать `record` — подробнее в [справочнике по равенству](#/ref/e/co-equality).

### Шаг 6. Ловушки изменяемых структур

~~~csharp
var arr = new PointS[2];
arr[0].X = 5;                  // ✅ работает: элемент массива — это переменная
Console.WriteLine(arr[0].X);   // 5

struct PointS { public int X; public int Y; }
~~~
~~~console
5
~~~

~~~csharp @nocheck
var list = new List<PointS> { new PointS() };
// list[0].X = 5;              // ❌ ошибка CS1612: индексатор вернул КОПИЮ, менять её бессмысленно
var tmp = list[0];
tmp.X = 5;
list[0] = tmp;                 // правильный способ: достать, изменить, положить обратно
~~~

Есть и **тихая** версия этой ловушки, где компилятор ничего не скажет: вызов *метода*, меняющего структуру, на копии.

~~~csharp
var list = new List<Counter> { new Counter() };
list[0].Inc();                              // компилируется! но работает с копией из индексатора
Console.WriteLine(list[0].N);               // 0 — ничего не изменилось

foreach (var c in list) c.Inc();            // и здесь — копия переменной цикла
Console.WriteLine(list[0].N);               // 0

var arr = new[] { new Counter() };
arr[0].Inc();                               // у массива элемент — настоящая «ячейка»
Console.WriteLine(arr[0].N);                // 1

struct Counter { public int N; public void Inc() => N++; }
~~~
~~~console
0
0
1
~~~

Отсюда правило: **делай структуры неизменяемыми** (`readonly struct`, свойства только для чтения). Тогда таких ловушек не бывает в принципе: «изменить» значит создать новое.

~~~csharp
var a = new Money(10m, "RUB");
var b = a.Add(new Money(5m, "RUB"));
Console.WriteLine($"{a.Amount} {b.Amount}");

public readonly struct Money
{
    public decimal Amount { get; }
    public string Currency { get; }

    public Money(decimal amount, string currency)
    {
        Amount = amount;
        Currency = currency;
    }

    public Money Add(Money other) =>
        other.Currency == Currency
            ? new Money(Amount + other.Amount, Currency)   // возвращаем НОВОЕ значение
            : throw new InvalidOperationException("Разные валюты");
}
~~~
~~~console
10 15
~~~

### Шаг 7. Когда выбирать `struct`

Рекомендация из Framework Design Guidelines: избегай `struct`, если тип не обладает **всеми** признаками:

- логически представляет **одно значение** (как `int`, `DateTime`, координата);
- размер экземпляра **меньше 16 байт**;
- **неизменяемый**;
- его **не придётся часто упаковывать** (боксить).

В остальных случаях — `class`. В backend-коде 95% твоих типов будут классами и record-ами.

Почему такие строгие требования? Передача большой структуры в метод — это копирование всех её байт при каждом вызове; одна ссылка (8 байт) копируется дешевле. А изменяемые структуры порождают ловушки из предыдущего шага. Типичные удачные структуры: `DateTime`, `Guid`, `TimeSpan`, `Point`, `Money`, идентификаторы (`readonly record struct OrderId(Guid Value)`).

Есть и среднее — `record struct` (C# 10): структура с генерируемым равенством, `ToString()` и удобным синтаксисом.

~~~csharp
var p1 = new Point2(1, 2);
var p2 = p1 with { X = 10 };       // «изменённая копия»
Console.WriteLine(p1);
Console.WriteLine(p2);
Console.WriteLine(p1 == new Point2(1, 2));

readonly record struct Point2(int X, int Y);
~~~
~~~console
Point2 { X = 1, Y = 2 }
Point2 { X = 10, Y = 2 }
True
~~~

### Шаг 8. `null` и nullable

~~~csharp
int? maybe = null;                // Nullable<int>: value type, который умеет быть null
Console.WriteLine(maybe.HasValue);          // False
Console.WriteLine(maybe.GetValueOrDefault()); // 0
maybe = 5;
Console.WriteLine(maybe + 1);               // 6
Console.WriteLine(maybe ?? -1);             // 5

string? owner = null;             // nullable reference type: подсказка компилятору
// Console.WriteLine(owner.Length);  // компилятор предупредит: возможна NullReferenceException
Console.WriteLine(owner?.Length ?? 0);
~~~
~~~console
False
0
6
5
0
~~~

`int?` — это настоящий другой тип (`Nullable<int>`, структура с флагом «значение есть» и самим значением). А `string?` при включённых nullable reference types — только **аннотация для компилятора**: в рантайме это всё тот же `string`, просто компилятор помогает не забыть проверку на `null`.

### Шаг 9. Время жизни

- Кадр стека исчезает, когда метод возвращает управление. Значения локальных value-переменных пропадают вместе с ним — это бесплатно.
- Объект в куче живёт, пока на него есть ссылки из корней; потом его когда-нибудь соберёт GC.
- Поэтому «вернуть ссылку на объект из метода» — нормально: объект в куче переживёт кадр стека.
- Переменную, которую «захватила» лямбда, компилятор выносит в специальный объект в куче — она живёт, пока жива лямбда:

~~~csharp
int n = 0;
Action inc = () => n++;     // n «захвачена»: теперь живёт в объекте-замыкании
inc(); inc(); inc();
Console.WriteLine(n);       // 3 — лямбда и внешний код видят ОДНУ переменную
~~~
~~~console
3
~~~

:::deep Граница
Как именно JIT решает, держать ли переменную в регистре, что такое escape analysis и `stackalloc`, как устроены `Span<T>` и `ref struct` — **не сейчас**. Для Фазы 1 тебе нужна модель «переменная хранит значение или ссылку» и умение нарисовать память. Остальное — в [rabbit-holes](#rabbit-holes).
:::

## Как это работает под капотом

**Раскладка объекта в куче.** У каждого объекта reference-типа есть небольшая служебная «шапка»: заголовок объекта (используется для блокировок, хеш-кода) и указатель на *таблицу методов* (описание типа: какой он, какие виртуальные методы). На 64-битной платформе это порядка 16 байт сверху на поля. Поэтому `new PointC { X = 1, Y = 2 }` занимает в куче заметно больше 8 байт полезных данных, а структура `PointS` — ровно 8 и без шапки. Это одна из причин, по которой миллион маленьких объектов дороже миллиона структур в массиве.

**Размеры можно увидеть.** Структура занимает суммарный размер полей (с выравниванием), ссылка — размер указателя (8 байт на 64-битной платформе):

~~~csharp
using System.Runtime.CompilerServices;

Console.WriteLine(Unsafe.SizeOf<int>());
Console.WriteLine(Unsafe.SizeOf<decimal>());
Console.WriteLine(Unsafe.SizeOf<PointS>());
Console.WriteLine(Unsafe.SizeOf<PointC>());   // размер ССЫЛКИ, а не объекта (64-бит: 8)

struct PointS { public int X; public int Y; }
class PointC { public int X; public int Y; }
~~~
~~~console
4
16
8
8
~~~

**Массив структур против массива объектов.** `PointS[1000]` — один объект в куче, где 1000 пар `int` лежат подряд (процессор читает их быстро, кэш работает хорошо). `PointC[1000]` — массив из 1000 ссылок, а сами объекты разбросаны по куче; на каждый — своя шапка, и каждый — работа для GC. Поэтому структуры выигрывают на больших массивах мелких данных (координаты, пиксели, цены).

**Стек потока.** Каждому потоку выделяется стек фиксированного размера (для главного потока обычно 1–8 МБ в зависимости от ОС). В нём лежат кадры вызовов: аргументы, локальные переменные, адрес возврата. Бесконечная рекурсия исчерпывает стек и приводит к `StackOverflowException`, которое **перехватить нельзя** — процесс аварийно завершается. Из-за этого глубокие рекурсивные алгоритмы заменяют итерацией со своим стеком (`Stack<T>`).

**Копирование структуры** — это копирование блока памяти (`memcpy`-подобная операция); при вызове метода с большой структурой копия делается каждый раз. Поэтому для больших value-типов применяют передачу по `in`/`ref`, а лучше — класс. **Равенство структур** по умолчанию (`ValueType.Equals`) в общем случае использует рефлексию, если в структуре есть ссылочные поля, и потому медленное — для структур в качестве ключей словаря реализуют `IEquatable<T>` или берут `record struct`.

Больше деталей и картинок — в справочнике: [стек и куча](#/ref/g/rt-stack-heap), [GC и поколения](#/ref/g/rt-gc).

## Типичные ошибки и ловушки

:::danger «Структуры всегда на стеке»
Поле-структура внутри класса лежит в куче вместе с объектом. Массив структур — в куче. Правильнее говорить: value type хранится **там, где объявлен**.
:::

:::danger «Объекты передаются по ссылке»
Нет: передаётся **ссылка по значению**. Разница видна, когда метод присваивает параметру новый объект — вызывающий код этого не увидит. Настоящая передача по ссылке — это `ref`.
:::

:::danger Изменяемая структура в свойстве или списке
`account.Position.X = 5` не скомпилируется или изменит копию. Если ловишь себя на таком — сделай тип классом или неизменяемым.
:::

- **«`string` — value type, потому что копируется».** Нет, это reference type; «копируется» кажется, потому что строка неизменяема.
- **«`List<int>` содержит ссылки на `int`».** Нет: `int` лежат в массиве внутри списка непосредственно.
- **Поверхностная копия.** `var b = a;` для класса — не копия объекта. Хочешь независимую копию — создай новый объект и скопируй поля (для вложенных — тоже).
- **Возврат ссылки на внутреннюю коллекцию.** Метод `GetItems()` возвращает `_items` — снаружи кто угодно может её изменить. Отдавай копию или `IReadOnlyList<T>` (тема про инкапсуляцию).
- **Структура «для скорости» без измерений.** Выигрыш бывает только в узких случаях, а ловушки — всегда.
- **Mutable-структура в `readonly`-контексте.** Вызов метода на таком поле выполняется на скрытой копии: изменения теряются без предупреждения.
- **Ожидание, что `==` для класса сравнит поля.** Не сравнит — только если тип это явно реализует (`record`, перегрузка).
- **Бесконечная рекурсия** — единственное, что в .NET нельзя перехватить `try/catch`.

## Вопросы с собеседований

:::spoiler Где лежит `int` в поле `class Account { int _count; }`?
В куче, внутри объекта `Account`. Value type хранится там, где объявлено поле, а поле — часть объекта в куче.
:::

:::spoiler Сколько объектов в куче создаёт `var list = new List<int> { 1, 2, 3 };`?
Минимум два: сам объект `List<int>` и его внутренний массив `int[]`. Числа хранятся в массиве напрямую, отдельных объектов для них нет.
:::

:::spoiler Что выведет код?
~~~csharp
var a = new[] { 1, 2, 3 };
var b = a;
b[0] = 100;
Console.WriteLine(a[0]);
~~~

`100`. Массив — reference type, даже если его элементы `int`. `b = a` копирует ссылку, оба имени указывают на один массив.
:::

:::spoiler Почему `list[0].X = 5` не компилируется для `List<PointS>`?
Индексатор `List<T>` — это метод, который возвращает **копию** структуры. Изменение поля временной копии было бы потеряно, поэтому компилятор запрещает это (CS1612). С массивом работает, потому что `arr[0]` — это сама ячейка массива, а не результат метода.
:::

:::spoiler Объясни разницу `class` и `struct` при передаче в метод за 30 секунд
Смотри [формулировку для собеседования](#p1-types/pass) выше. Запиши себя на голосовую заметку и сравни.
:::

:::spoiler «Структуры лежат на стеке, классы — в куче». Верно? (ловушка)
Нет, это упрощение. Value type лежит там, где объявлен: локальная — на стеке (или в регистре), поле класса и элемент массива — в куче. Reference-объект семантически в куче, на стеке — только ссылка.
:::

:::spoiler Строка — значимый или ссылочный тип? Почему тогда `==` сравнивает содержимое?
Ссылочный. Оператор `==` для `string` переопределён и сравнивает символы. А «ведёт себя как значение» из-за неизменяемости: любое изменение создаёт новую строку.
:::

:::spoiler Почему структура не может быть унаследована? Может ли она реализовывать интерфейс?
Структура неявно наследуется от `ValueType` и запечатана; наследование потребовало бы хранить виртуальную таблицу и ломало бы размер/копирование. Интерфейсы реализовывать может (но при приведении к интерфейсу произойдёт боксинг).
:::

:::spoiler Что такое поверхностное копирование структуры с полем-массивом?
Копируется ссылка на массив, а не его содержимое: исходная и скопированная структуры разделяют один массив, и изменения элементов видны обеим.
:::

:::spoiler Что делает `ref` при передаче параметра-класса?
Передаёт саму переменную вызывающего, а не копию ссылки. Метод может присвоить параметру новый объект — и вызывающий код увидит подмену.
:::

## Что запомнить

- Value type: переменная хранит **значение**, присваивание копирует **данные**. Reference type: переменная хранит **ссылку**, присваивание копирует **ссылку**.
- Value type лежит **там, где объявлен** (стек, поле объекта, массив) — «структуры на стеке» неточно.
- Всё передаётся **по значению**: для struct — копия данных, для class — копия ссылки; подмена объекта внутри метода снаружи не видна, нужен `ref`.
- `==`/`Equals` для классов по умолчанию — по ссылке; `record` и `string` сравниваются по содержимому.
- Структуры делай `readonly`/неизменяемыми, маленькими (≤16 байт); по умолчанию — `class`/`record`.
- `int?` — настоящий тип `Nullable<int>`, `string?` — аннотация компилятора.
- Копия структуры с ссылочным полем — поверхностная.
- `StackOverflowException` не перехватывается; `GC` управляет только кучей.
