@@ref id="pf-terms" cat="G" title="Словарь терминов: O(1), O(log n), O(n), амортизированная сложность" cs="1.0" cx="словарь" mem="словарь" tags="Big-O O(1) O(n) O(log n) O(n log n) O(n²) амортизированная сложность лучший худший средний случай асимптотика рост функции Theta Omega" topic="p2-bigo" related="pf-op-costs,pf-bigo-lies,co-complexity" learn="?dotnet/standard/collections/::Коллекции .NET"
Сложность описывает, как растёт время или память с ростом размера входа `n`. Она отвечает на вопрос «что будет, если данных станет в 1000 раз больше», а не «сколько миллисекунд это займёт».

## Синтаксис {#syntax}

~~~csharp @nocheck
O(1)        // константа: индекс массива, доступ к полю
O(log n)    // логарифм: двоичный поиск, операции со сбалансированным деревом
O(n)        // линейная: проход по списку, Contains в List<T>
O(n log n)  // линеарифметическая: эффективная сортировка
O(n²)       // квадратичная: два вложенных цикла по тем же данным
O(2ⁿ), O(n!) // экспонента, факториал: перебор подмножеств, перестановок
~~~

## Семантика {#semantics}

- **O-нотация** — верхняя оценка роста: отбрасываются константы и младшие слагаемые (`3n² + 10n + 7` → `O(n²)`). Она сравнивает алгоритмы при большом `n`, но не говорит о скорости при малом.
- **Лучший, средний, худший случай** — разные входы для одного алгоритма. Быстрая сортировка: в среднем `O(n log n)`, в худшем `O(n²)`; поиск в хеш-таблице: в среднем `O(1)`, в худшем `O(n)` при массовых коллизиях.
- **Амортизированная сложность** усредняет редкие дорогие операции по серии: `List<T>.Add` обычно `O(1)`, раз в удвоение — `O(n)` копирование, в среднем на операцию `O(1)`. Это не среднее по входам, а гарантия на последовательность операций.
- **Память** оценивается так же: `O(1)` дополнительной памяти — только несколько переменных; `O(n)` — копия данных. Рекурсия занимает `O(глубина)` стека.
- **Порядок роста:** `1 < log n < n < n log n < n² < 2ⁿ < n!`. При `n = 1 000 000` линейный алгоритм выполняет порядка миллиона шагов, квадратичный — триллион (практически недостижимо).
- `Θ(f)` — точная оценка (и сверху, и снизу), `Ω(f)` — нижняя; в разговоре про код обычно имеют в виду `O` как «примерно».
- Для нескольких входов сложность записывают через несколько переменных: `O(n + m)`, `O(n · m)`.
- Логарифм без указания основания: основание влияет лишь на константу.
- Практическое правило: `O(n)` и `O(n log n)` для миллионов элементов нормальны, `O(n²)` — только для небольших `n`.

## Под капотом {#internals}

Big-O считает «элементарные шаги» абстрактной машины. Реальное время зависит от того, какой шаг: чтение из кэша процессора — доли наносекунды, промах кэша — сотни тактов, аллокация, системный вызов, сеть — на порядки больше ([когда Big-O обманывает](#/ref/g/pf-bigo-lies)).

## Сложность {#complexity}

Сами термины стоимости не имеют; они нужны, чтобы оценивать код: вложенные циклы перемножают сложность, последовательные — складывают (берётся максимум), рекурсия с делением пополам даёт логарифм.

## Версии {#versions}

Понятия не зависят от версии C#. Документация BCL указывает сложность основных операций коллекций в разделе «Remarks» методов.

## Ловушки {#pitfalls}

**Скрытая квадратичность.**

~~~csharp
int[] data = Enumerable.Range(0, 2000).ToArray();

long steps1 = 0;                                       // два вложенных цикла: n² шагов
for (int i = 0; i < data.Length; i++)
    for (int j = 0; j < data.Length; j++) steps1++;

long steps2 = 0;                                       // два последовательных: 2n шагов
for (int i = 0; i < data.Length; i++) steps2++;
for (int j = 0; j < data.Length; j++) steps2++;

Console.WriteLine($"{steps1} {steps2}");
var list = data.ToList();
int hits = 0;
foreach (var x in data) if (list.Contains(x)) hits++;   // Contains скрывает внутренний цикл: итого O(n²)
Console.WriteLine(hits);
~~~
~~~console
4000000 4000
2000
~~~

**Путаница «амортизированная» и «средняя»:** первая — по серии операций, вторая — по входам.

**Игнорирование памяти:** быстрый алгоритм с `O(n)` дополнительной памяти может не поместиться.

**Оценка по малым данным:** «на тестах быстро» не доказывает, что на миллионе строк так же.

## Примеры {#examples}

~~~csharp
static int Binary(int[] a, int x)
{
    int lo = 0, hi = a.Length - 1, steps = 0;
    while (lo <= hi) { steps++; int mid = (lo + hi) / 2; if (a[mid] == x) break; if (a[mid] < x) lo = mid + 1; else hi = mid - 1; }
    return steps;
}
var sorted = Enumerable.Range(0, 1_000_000).ToArray();
Console.WriteLine(Binary(sorted, 999_999) <= 21);        // log₂(10⁶) ≈ 20
Console.WriteLine(Binary(sorted, -1));
~~~
~~~console
True
19
~~~

## Семантика {#semantics}

- Основная идея: операции различаются на порядки. Арифметика и доступ к кэшированной памяти — доли наносекунды; вызов виртуального метода — единицы; аллокация короткоживущего объекта — десятки; захват `lock` без конкуренции — десятки; выброс исключения — десятки микросекунд; обращение к диску — сотни микросекунд; к сети — миллисекунды.
- **Оптимизировать нужно то, что дороже и чаще.** Заменить `x * 2` на `x << 1` бессмысленно, а убрать запрос к базе из цикла — выигрыш в тысячи раз.
- Стоимость зависит от данных: промах кэша процессора превращает «бесплатный» доступ к массиву в сотни тактов.
- Аллокация сама быстра, но её цена проявляется при сборке мусора ([аллокации](#/ref/g/rt-allocations)).
- Колонка «класс» показывает, где искать узкие места.
- Для точных измерений используйте BenchmarkDotNet; `Stopwatch` без прогрева даёт шум ([диагностика](#/ref/g/rt-diagnostics)).
- Асимптотику и константы нужно рассматривать вместе: см. [когда Big-O обманывает](#/ref/g/pf-bigo-lies).

## Под капотом {#internals}

Цифры складываются из аппаратных латентностей (регистры, три уровня кэша, ОЗУ), работы JIT (встраивание, девиртуализация) и среды выполнения (сборщик мусора, пул потоков). На одном и том же коде они меняются между версиями .NET.

## Сложность {#complexity}

Таблица — не Big-O, а «константы»: для одного и того же `O(n)` цикла стоимость шага может отличаться в сто раз в зависимости от того, что в нём — арифметика или аллокация.

## Версии {#versions}

Значения ориентировочные для .NET 8–10; динамический PGO и новые оптимизации JIT сдвигают цифры вниз. Точные числа требуют проверки на вашем железе.

## Ловушки {#pitfalls}

**Оптимизация дешёвого вместо дорогого.**

~~~csharp
static long Bytes(Action a) { long b = GC.GetAllocatedBytesForCurrentThread(); a(); return GC.GetAllocatedBytesForCurrentThread() - b; }

long exc = 0;
var sw = System.Diagnostics.Stopwatch.StartNew();
for (int i = 0; i < 300; i++) { try { throw new InvalidOperationException(); } catch (InvalidOperationException) { exc++; } }
long tExc = sw.ElapsedTicks;

sw.Restart();
long sum = 0;
for (int i = 0; i < 300; i++) sum += i * 2;
long tArith = sw.ElapsedTicks;

Console.WriteLine($"{exc} исключений дороже арифметики: {tExc > tArith * 100}");
Console.WriteLine(Bytes(() => { object o = 5; _ = o; }) >= 0);
~~~
~~~console
300 исключений дороже арифметики: True
True
~~~

**Сравнение цифр между машинами:** важны отношения, а не абсолюты.

**Игнорирование ввода-вывода:** один запрос к базе в цикле стоит как миллионы арифметических операций.

**Микрооптимизация в холодном коде:** выигрыш незаметен, читаемость страдает.

## Примеры {#examples}

~~~csharp
// сколько арифметических операций «стоит» один сетевой запрос
double arithNs = 0.3, netNs = 500_000;
Console.WriteLine((long)(netNs / arithNs));
// порядок: исключение против вызова метода
double exceptionNs = 20_000, callNs = 1;
Console.WriteLine(exceptionNs / callNs);
~~~
~~~console
1666666
20000
~~~

@@ref id="pf-bigo-lies" cat="G" title="Когда Big-O обманывает: константы, кэш, аллокации" cs="1.0" cx="константы и кэш" mem="O(n)" danger="1" tags="Big-O константы кэш процессора локальность данных row-major column-major связный список массив аллокации малый n измерение амортизированная" topic="p2-bigo" related="pf-terms,pf-op-costs,co-complexity,rt-allocations" learn="?dotnet/core/diagnostics/::Диагностика в .NET"
Асимптотика описывает рост, но не саму скорость. Для небольших данных, из-за кэша процессора и аллокаций алгоритм «хуже по Big-O» нередко оказывается быстрее.

## Синтаксис {#syntax}

~~~csharp @nocheck
// O(n) по массиву       может быстрее, чем    O(1) по хеш-таблице   при n ≈ 10
// O(n) по List<T>       может быстрее, чем    O(1) по LinkedList     при вставках в середину
// обход матрицы по строкам и по столбцам — одна сложность O(n·m), но разное время
~~~

## Семантика {#semantics}

- **Константы.** `O(1)` хеш-таблицы включает вычисление хеша, поиск корзины, сравнение: десятки нс. Линейный поиск в массиве из 8 элементов — менее 10 нс. Для малых `n` простая структура выигрывает.
- **Кэш и локальность.** Процессор читает память строками (64 байта). Массив лежит подряд, и обход почти бесплатен; связный список раскидан по куче, каждый переход — потенциальный промах (сотни тактов). Поэтому вставка в середину `List<T>` с копированием часто быстрее `LinkedList<T>`.
- **Порядок обхода многомерных данных.** Двумерный массив `int[n, m]` хранится по строкам: внутренний цикл должен идти по последнему индексу. Обход по столбцам делает ту же работу, но в разы медленнее.
- **Аллокации.** Алгоритм с меньшим числом шагов, но создающий много объектов, может проиграть из-за сборщика мусора.
- **Амортизация.** `O(1)` амортизированно может иметь редкие дорогие пики (копирование при росте); для систем реального времени важна и худшая задержка.
- **Параллелизм и блокировки.** Асимптотика не учитывает конкуренцию за общую память и блокировки.
- **Ввод-вывод.** Один запрос к базе дороже миллиона арифметических операций: сокращение запросов важнее выбора структуры данных.
- **Практика:** начните с простого решения, измерьте, затем оптимизируйте узкое место. «Лучшая по Big-O» структура без измерений — преждевременная оптимизация.
- Big-O остаётся главным инструментом против катастрофических случаев (`O(n²)` на миллионе записей); обманывает он в диапазоне «разумных» размеров.

## Под капотом {#internals}

Современный процессор выполняет предсказание переходов и предзагрузку (prefetch) для последовательного доступа. Массивы и `Span<T>` используют эти механизмы; связные структуры — нет. Поэтому плоские структуры данных обычно выигрывают на практике.

## Сложность {#complexity}

Один и тот же код обхода матрицы `n × n` — `O(n²)` в обоих порядках, но время различается в 3–10 раз из-за кэша; различие растёт с размером.

## Версии {#versions}

Эффекты аппаратные, от версии C# не зависят; .NET 8+ дополнительно сильнее оптимизирует циклы по массивам (векторизация, PGO), что усиливает преимущество плоских структур.

## Ловушки {#pitfalls}

**Один и тот же `O(n²)` в разном порядке обхода.**

~~~csharp
const int N = 3000;
var m = new int[N, N];
var sw = System.Diagnostics.Stopwatch.StartNew();
long a = 0;
for (int i = 0; i < N; i++) for (int j = 0; j < N; j++) a += m[i, j];      // по строкам (последовательно)
long byRows = sw.ElapsedTicks;

sw.Restart();
long b = 0;
for (int j = 0; j < N; j++) for (int i = 0; i < N; i++) b += m[i, j];      // по столбцам (прыжки по памяти)
long byCols = sw.ElapsedTicks;

Console.WriteLine(a == b);
Console.WriteLine("по столбцам медленнее: " + (byCols > byRows));

int steps = 0, copies = 0;
var list = new List<int>();
for (int i = 0; i < 1000; i++) { int cap = list.Capacity; list.Add(i); steps++; if (list.Capacity != cap) copies += cap; }
Console.WriteLine(copies < 2 * steps);
~~~
~~~console
True
по столбцам медленнее: True
True
~~~

**Выбор `LinkedList` ради «O(1) вставки»** без учёта кэша и аллокаций узлов.

**Оптимизация малых коллекций** хеш-таблицей вместо массива.

**Игнорирование задержек худшего случая** при амортизированной оценке.

## Примеры {#examples}

~~~csharp
var small = new[] { 3, 1, 4, 1, 5, 9, 2, 6 };
Console.WriteLine(Array.IndexOf(small, 9));             // линейный поиск по 8 элементам
Console.WriteLine(small.Contains(7));

var jagged = new int[3][];
for (int i = 0; i < 3; i++) jagged[i] = new int[] { i, i + 1, i + 2 };
Console.WriteLine(jagged.Sum(r => r.Sum()));
~~~
~~~console
5
False
18
~~~

@@ref id="rt-memory-model" cat="F" title="Модель памяти, volatile и false sharing" cs="1.0" cx="O(1)" mem="O(1)" danger="1" tags="модель памяти volatile Volatile.Read Volatile.Write барьер памяти acquire release видимость переупорядочивание false sharing кэш-линия MemoryBarrier гонка данных Interlocked" topic="p5-concurrency" related="as-sync-primitives,fl-lock,as-threads,rt-gc" learn="?dotnet/standard/threading/::Потоки и многопоточность"
Модель памяти определяет, какие значения поток может увидеть при чтении данных, записанных другим потоком. Без синхронизации компилятор и процессор вправе переставлять операции и кэшировать значения.

## Синтаксис {#syntax}

~~~csharp @nocheck
private volatile bool _ready;
Volatile.Write(ref _data, value);   var v = Volatile.Read(ref _data);
Thread.MemoryBarrier();
Interlocked.Exchange(ref _flag, 1);
[StructLayout(LayoutKind.Explicit, Size = 128)] struct Padded { [FieldOffset(64)] public long Value; }
~~~

## Семантика {#semantics}

- Одиночный поток видит свои операции так, будто они выполнены по порядку. Другой поток может увидеть их **в другом порядке** или не увидеть изменение вовсе из-за кэшей и оптимизаций.
- Типичный пример: поток-писатель делает `data = 42; ready = true;`, читатель — `if (ready) Use(data)`. Без барьеров читатель теоретически увидит `ready == true` и устаревшее `data`.
- **Release-запись и acquire-чтение:** `Volatile.Write` не позволяет предыдущим операциям «просочиться» после себя; `Volatile.Read` — последующим «просочиться» до себя. Вместе они безопасно публикуют данные.
- Ключевое слово `volatile` на поле даёт acquire при чтении и release при записи, а также запрещает JIT кэшировать значение в регистре. Оно **не** делает составные операции (`x++`) атомарными.
- `lock`, `Interlocked`, `Task`/`await`, запуск и `Join` потока включают нужные барьеры — при их использовании думать о модели памяти обычно не надо.
- **Гонка данных** (data race) — одновременный доступ к одной переменной, когда хотя бы один поток пишет, без синхронизации. Результат непредсказуем.
- **False sharing:** две независимые переменные лежат в одной кэш-линии (64 байта), и разные ядра постоянно инвалидируют линию друг у друга. Лечится выравниванием/паддингом либо локальными накопителями.
- Атомарны чтение и запись переменных размером до размера слова (`int`, ссылки); `long` на 32-битных платформах — нет.
- .NET на ARM имеет более слабую модель, чем на x86: код, «случайно работавший» на x86, может сломаться на ARM.
- Предпочитайте высокоуровневые средства: `lock`, `Channel<T>`, `Interlocked`, неизменяемые данные.

## Под капотом {#internals}

JIT вставляет аппаратные барьеры (на x86 — преимущественно для `StoreLoad`, на ARM — `dmb`) по семантике `volatile`/`Volatile`. Кэш-когерентность (MESI) гарантирует согласованность линии, но стоит межъядерного трафика.

## Сложность {#complexity}

`Volatile.Read/Write` на x86 почти бесплатны; на ARM — десятки тактов. False sharing может замедлить параллельный код в разы без единой ошибки в логике.

## Версии {#versions}

- .NET 1.0 — `volatile`, `Thread.MemoryBarrier`; .NET 4.5 — `Volatile.Read/Write`.
- .NET Core — формальные гарантии модели памяти задокументированы для ARM64 и x64.

## Ловушки {#pitfalls}

**Публикация данных через флаг без барьеров и счётчик без атомарности.**

~~~csharp
var box = new Box();
var reader = Task.Run(() =>
{
    while (!Volatile.Read(ref box.Ready)) Thread.SpinWait(50);       // ждём флаг
    return box.Data;                                                  // после acquire данные видны
});
box.Data = 42;
Volatile.Write(ref box.Ready, true);                                  // release: данные опубликованы
Console.WriteLine(await reader);

int plain = 0, safe = 0;
Parallel.For(0, 100_000, _ => { plain++; Interlocked.Increment(ref safe); });
Console.WriteLine(safe);
Console.WriteLine(plain <= 100_000);

class Box { public int Data; public bool Ready; }
~~~
~~~console
42
100000
True
~~~

**`volatile` вместо `lock`** для составных операций.

**Бесконечный цикл ожидания флага** без `volatile`: JIT может вынести чтение из цикла.

**Массив счётчиков по потокам рядом в памяти** — false sharing.

## Примеры {#examples}

~~~csharp
int counter = 0;
var tasks = Enumerable.Range(0, 4).Select(_ => Task.Run(() => { for (int i = 0; i < 10_000; i++) Interlocked.Increment(ref counter); }));
await Task.WhenAll(tasks);
Console.WriteLine(Volatile.Read(ref counter));

long value = 0;
Volatile.Write(ref value, 7);
Console.WriteLine(Volatile.Read(ref value));
Console.WriteLine(Interlocked.Read(ref value));
~~~
~~~console
40000
7
7
~~~

Сериализация превращает объект в поток байтов или строку (JSON), десериализация — обратно. В современном .NET стандарт для JSON — `System.Text.Json`; `BinaryFormatter` удалён из-за небезопасности.

## Синтаксис {#syntax}

~~~csharp @nocheck
string json = JsonSerializer.Serialize(order, new JsonSerializerOptions { WriteIndented = true });
Order? o = JsonSerializer.Deserialize<Order>(json);
class Order { [JsonPropertyName("id")] public int Id { get; set; } [JsonIgnore] public string? Secret { get; set; } }
[JsonSerializable(typeof(Order))] partial class AppJson : JsonSerializerContext { }
await JsonSerializer.SerializeAsync(stream, value);
~~~

## Семантика {#semantics}

- По умолчанию сериализуются **публичные свойства** (не поля); имена сохраняются как в коде (`Name`), если не задан `PropertyNamingPolicy = JsonNamingPolicy.CamelCase`. В ASP.NET Core по умолчанию используется camelCase и нечувствительное к регистру чтение.
- Атрибуты: `[JsonPropertyName]` — имя; `[JsonIgnore]` — исключить; `[JsonConstructor]` — выбрать конструктор для десериализации; `[JsonInclude]` — включить непубличный `get`.
- Записи (`record`) и классы с первичными конструкторами десериализуются через конструктор: имена параметров сопоставляются со свойствами.
- `null` и отсутствующие поля: свойство получает значение по умолчанию; с `required` (C# 11) отсутствие поля — ошибка десериализации.
- Даты `DateTime`/`DateTimeOffset` пишутся в ISO 8601; перечисления — числами, если не подключить `JsonStringEnumConverter`.
- Циклические ссылки приводят к исключению; решение — `ReferenceHandler.IgnoreCycles` или изменение модели (DTO).
- **Полиморфизм** поддерживается атрибутами `[JsonPolymorphic]` и `[JsonDerivedType]` (.NET 7); без них сериализуется только объявленный тип свойства.
- **Генератор исходного кода** (`JsonSerializerContext`) убирает рефлексию во время выполнения: быстрее старт, меньше памяти, совместимость с обрезкой и NativeAOT.
- Не десериализуйте непроверенные данные в произвольные типы и не используйте устаревшие бинарные сериализаторы (уязвимости десериализации).
- Для больших потоков используйте асинхронные потоковые перегрузки и `Utf8JsonReader`/`Utf8JsonWriter` (низкоуровневый API без аллокаций).

## Под капотом {#internals}

`JsonSerializer` строит и кэширует метаданные типа (через рефлексию или сгенерированный код) и записывает UTF-8 байты напрямую, без промежуточных строк. Первый вызов для типа дороже последующих (создание метаданных).

## Сложность {#complexity}

`O(размер данных)`; первый вызов для нового типа дорог (рефлексия, построение делегатов), последующие — быстрые. Генератор исходного кода переносит эту стоимость на этап компиляции.

## Версии {#versions}

- .NET Core 3.0 — `System.Text.Json`; .NET 5 — поддержка записей и `[JsonConstructor]`.
- .NET 6 — генератор исходного кода, `IAsyncEnumerable`; .NET 7 — полиморфизм, `required`; .NET 9 — `BinaryFormatter` всегда бросает исключение.

## Ловушки {#pitfalls}

**Поля не сериализуются, имена и регистр.**

~~~csharp
using System.Text.Json;

var d = new Dto { Name = "Анна", Age = 30, Hidden = "x" };
Console.WriteLine(JsonSerializer.Serialize(d));                              // поле Age не попадёт
var opts = new JsonSerializerOptions { PropertyNamingPolicy = JsonNamingPolicy.CamelCase };
Console.WriteLine(JsonSerializer.Serialize(d, opts));

var back = JsonSerializer.Deserialize<Dto>("""{"name":"Борис"}""", new JsonSerializerOptions { PropertyNameCaseInsensitive = true });
Console.WriteLine(back!.Name);
var rec = JsonSerializer.Deserialize<Point>("""{"X":1,"Y":2}""");
Console.WriteLine(rec);

class Dto { public string Name { get; set; } = ""; public int Age; [System.Text.Json.Serialization.JsonIgnore] public string? Hidden { get; set; } }
record Point(int X, int Y);
~~~
~~~console
{"Name":"\u0410\u043D\u043D\u0430"}
{"name":"\u0410\u043D\u043D\u0430"}
Борис
Point { X = 1, Y = 2 }
~~~

**Десериализация неверного JSON** бросает `JsonException`; ловите и возвращайте 400.

**Циклические ссылки** падают без `ReferenceHandler`.

**Серверная десериализация полей-перечислений** числами без конвертера.
