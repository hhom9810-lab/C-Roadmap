Нужен ограничитель частоты запросов `RateLimiter`: не более `limit` запросов за скользящее окно в `windowSeconds` секунд **на каждый ключ** (например, IP клиента).

- `Allow(key)` → `true`, если запрос разрешён (и учитывается), иначе `false` (не учитывается);
- время берётся из переданной функции `now` — иначе его не протестировать.
@code
~~~csharp

using System.Collections.Generic;

public class RateLimiter
{
    public RateLimiter(int limit, int windowSeconds, Func<DateTime> now)
    {
    }

    public bool Allow(string key)
    {
        throw new NotImplementedException();
    }
}
~~~
@tests
~~~csharp
class T
{
    public static void Run()
    {
        var t = new DateTime(2024, 1, 1, 12, 0, 0);
        var rl = new RateLimiter(3, 10, () => t);

        Assert.True(rl.Allow("ip1"), "1-й");
        Assert.True(rl.Allow("ip1"), "2-й");
        t = t.AddSeconds(1);
        Assert.True(rl.Allow("ip1"), "3-й");
        Assert.False(rl.Allow("ip1"), "4-й — лимит");
        Assert.True(rl.Allow("ip2"), "другой ключ независим");

        t = t.AddSeconds(9);
        Assert.True(rl.Allow("ip1"), "первые два запроса вышли из окна");
        Assert.True(rl.Allow("ip1"), "ещё один слот освободился");
        Assert.False(rl.Allow("ip1"), "снова лимит");
    }
}
~~~
@hint
Для каждого ключа храни `Queue<DateTime>` меток времени разрешённых запросов. Перед проверкой выкинь из начала очереди метки старше окна (`(now - q.Peek()).TotalSeconds >= windowSeconds`). Если в очереди меньше `limit` — добавь текущую метку и верни `true`.
@solution
~~~csharp
using System;
using System.Collections.Generic;

public class RateLimiter
{
    private readonly int _limit;
    private readonly int _window;
    private readonly Func<DateTime> _now;
    private readonly Dictionary<string, Queue<DateTime>> _hits = new Dictionary<string, Queue<DateTime>>();

    public RateLimiter(int limit, int windowSeconds, Func<DateTime> now)
    {
        _limit = limit;
        _window = windowSeconds;
        _now = now;
    }

    public bool Allow(string key)
    {
        var now = _now();
        if (!_hits.TryGetValue(key, out var q))
        {
            q = new Queue<DateTime>();
            _hits[key] = q;
        }
        while (q.Count > 0 && (now - q.Peek()).TotalSeconds >= _window)
            q.Dequeue();
        if (q.Count >= _limit) return false;
        q.Enqueue(now);
        return true;
    }
}
~~~
@why
Скользящее окно точнее фиксированного: у фиксированного на границе можно сделать 2×limit запросов за секунду. Это решение хранит O(limit) меток на ключ. В продакшене состояние лежит в Redis (иначе при нескольких экземплярах лимит «размножается»), а в ASP.NET Core уже есть `AddRateLimiter`.
:::

@context Цены на сайте иногда устаревшие, а под нагрузкой в логах появляются `KeyNotFoundException` и пики на БД.
@code
~~~csharp

    public decimal Get(int id)
    {

        {
            _prices[id] = LoadFromDb(id);
        }

    }

~~~
@bug 3 | [bug] Статический `Dictionary` без потокобезопасности | Параллельные запросы портят внутреннюю структуру словаря (зацикливания, потеря записей). Нужен `ConcurrentDictionary` или `IMemoryCache`.
@bug 7-10 | [bug] «Проверил — потом записал» без синхронизации | Между `ContainsKey` и записью другой поток может изменить словарь; множество потоков одновременно идут в БД за одним и тем же id (cache stampede).
@bug 11 | [bug] Повторный поиск по ключу после проверки | Если `Clear()` сработает между проверкой и чтением — `KeyNotFoundException`. Используй `TryGetValue` и работай с одним снимком.
@bug 3-12 | [design] У записей нет срока жизни | Изменилась цена в БД — кэш показывает старую вечно (до `Clear()`). Нужны TTL и инвалидация при изменении.
@fixed
~~~csharp
public class PriceCache
{
    private readonly IMemoryCache _cache;
    private readonly IPriceRepository _repo;
    public PriceCache(IMemoryCache cache, IPriceRepository repo) { _cache = cache; _repo = repo; }

    public Task<decimal> GetAsync(int id) =>
        _cache.GetOrCreateAsync(id, e =>
        {
            e.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5);
            return _repo.LoadAsync(id);
        });
}
~~~
:::

TTL :: Срок жизни записи; защита от вечно устаревших данных.
Rate limiting :: Ограничение частоты запросов; 429 + Retry-After.
Circuit Breaker :: Быстрый отказ при сбоях зависимости, чтобы не получить каскад.

        Assert.Equal(3, Solver.LongestUnique("pwwkew"), "pwwkew");
        Assert.Equal(0, Solver.LongestUnique(""), "пустая строка");

@hint
`left = 0`; идём `right` по строке. Если символ уже встречался на позиции `>= left` — `left = last[c] + 1`. Запомни `last[c] = right`, обнови максимум `right - left + 1`.
@solution
~~~csharp
using System;
using System.Collections.Generic;

public static class Solver
{
    public static int LongestUnique(string s)
    {
        var last = new Dictionary<char, int>();
        int left = 0, best = 0;
        for (int right = 0; right < s.Length; right++)
        {
            char c = s[right];
            if (last.TryGetValue(c, out var prev) && prev >= left)
                left = prev + 1;
            last[c] = right;
            best = Math.Max(best, right - left + 1);
        }
        return best;
    }
}
~~~
@why
Ловушка на «abba»: левая граница никогда не двигается назад — поэтому проверка `prev >= left`. Скользящее окно превращает O(N²) в O(N): каждый символ посещается указателями не более двух раз.

@solution
~~~csharp
using System;
using System.Collections.Generic;
using System.Linq;

public static class Solver
{
    public static string Merge(int[][] intervals)
    {
        var sorted = intervals.OrderBy(x => x[0]).ToList();
        var res = new List<int[]>();
        foreach (var iv in sorted)
        {
            if (res.Count > 0 && iv[0] <= res[res.Count - 1][1])
                res[res.Count - 1][1] = Math.Max(res[res.Count - 1][1], iv[1]);
            else
                res.Add(new[] { iv[0], iv[1] });
        }
        return string.Join(",", res.Select(r => "[" + r[0] + "," + r[1] + "]"));
    }
}
~~~
@why
Сортировка превращает задачу о пересечениях в линейный проход: нужно сравнивать только с последним результатом. Шаблон «отсортируй, затем сканируй» решает десятки интервальных задач (расписания, бронирования).

@q Расскажите о проекте из вашего портфолио: что он делает, какие решения вы приняли и что бы сделали иначе?
@trap Понимает ли кандидат свой код: может ли обосновать выбор, назвать компромиссы и честно признать недостатки.
@answer
Структура ответа: (1) проблема и пользователь — одним предложением; (2) архитектура — слои, БД, внешние зависимости; (3) 2–3 осознанных решения с причинами («использовал проекцию в DTO, потому что N+1 съедал 40 запросов на страницу — замерил логом»); (4) что пошло не так и чему научился (например, deadlock в синхронном `.Result` или миграция, сломавшая тестовую БД); (5) что улучшил бы — тесты на интеграционные сценарии, кэш, наблюдаемость. Цифры и факты убеждают сильнее, чем списки технологий.
@fail Перечислить технологии без объяснения решений: «Там ASP.NET, EF, Docker, Redis…». Это выдаёт, что проект не осмыслен.
@follow Как масштабировать проект на 100 000 пользователей? Что сломается первым?
:::

:::cards Капстоун
Проект как аргумент :: Для каждого решения должен быть ответ «почему так» и «какая альтернатива».
Чек-лист проекта :: README, запуск одной командой, тесты в CI, миграции, обработка ошибок, логирование.
:::

## Итоговый тест фазы 6 {#lab}

:::quiz Итог фазы 6: инфраструктура и подготовка
? Приложение работает локально, но в Docker не подключается к БД по `localhost:5432`. Причина? #web
+ `localhost` в контейнере — сам контейнер; надо обращаться по имени сервиса compose (`db:5432`)
- Docker блокирует порт 5432
- БД не поддерживает контейнеры
- Нужен другой драйвер
= Классическая ошибка новичка с Docker.

? Какой подход лучше защищает от падения всего сервиса при отказе внешнего API? #web
+ Таймауты + повторы с задержкой (retry) + Circuit Breaker + осмысленный fallback
- Бесконечные повторы без пауз
- Игнорировать ошибки
- Увеличить размер пула потоков
= Без таймаутов один медленный сервис заблокирует все потоки.

? Что произойдёт при деплое новой версии с необратимой миграцией («удалили столбец») и ошибкой в приложении? #web
+ Откат приложения не восстановит данные из удалённого столбца — миграции должны быть совместимы со старой версией
- Откат всё починит
- Ничего
- Столбец вернётся автоматически
= Принцип expand/contract: сначала добавляем, потом переходим, затем удаляем.

? Кто виноват, если секрет попал в git и репозиторий публичный? #web
+ Секрет скомпрометирован навсегда: нужно немедленно отозвать/сменить его, а не просто удалить из кода
- Никто, достаточно удалить файл
- Только GitHub
- Никто, история сотрётся
= Боты находят секреты за минуты.

? Алгоритм «найти пересекающиеся интервалы» за O(N log N) — какой шаг важен? #algo
+ Сортировка по началу и один линейный проход
- Хэш-таблица
- Рекурсия
- Двоичный поиск
= O(N log N) — цена сортировки, дальше O(N).

? Что лучше для кэша справочника, редко меняющегося и общего для всех пользователей? #web
+ Кэш в памяти приложения / распределённый кэш с TTL, инвалидация при изменении
- Читать из БД на каждый запрос
- Хранить на клиенте без проверки
- Писать в файл на сервере
= Сначала замерь: кэш усложняет систему.
:::

:::interview Что делает хороший CI/CD pipeline
@q Из каких шагов состоит ваш CI/CD для проекта и зачем каждый шаг?
@trap Видит ли кандидат pipeline как систему страховок, а не как «кнопку деплоя».
@answer
CI на pull request: restore → build → unit-тесты → интеграционные тесты (в контейнерах с БД) → статический анализ/линтер → сборка Docker-образа. CD после merge в main: публикация образа с версией (sha коммита) в registry → применение миграций → выкладка (rolling/blue-green) → health-check → автоматический откат при провале. Секреты — из хранилища окружения. Каждый шаг ловит свой класс проблем; чем раньше — тем дешевле.
@fail «Собираем и копируем на сервер по SSH» — нет тестов, версий, отката.
:::

:::cards Фаза 6: минимум
Контейнер и localhost :: Обращайся к соседним сервисам по имени из compose.
Устойчивость :: Таймаут + retry + circuit breaker + fallback.
Миграции и откат :: Expand/contract; необратимые изменения — отдельным релизом.
Кэш :: TTL + стратегия инвалидации + защита от stampede.
Алгоритмы :: Hash map, скользящее окно, два указателя, сортировка+скан, стек.
:::
