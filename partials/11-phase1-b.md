:::why
Боксинг — это **скрытая аллокация в куче**, которую не видно в коде. На собеседовании спрашивают «что такое boxing и почему `List<int>` лучше `ArrayList`». В реальной работе это объясняет, почему горячий цикл вдруг нагружает GC. Тема прямо продолжает [value vs reference](#p1-types).
:::

## Зачем это нужно

После темы про value и reference types понятно, что `int` — это просто четыре байта, а `object` — ссылка на что-то в куче. Но в C# `int` можно положить в `object`, передать в метод, принимающий интерфейс, добавить в старую коллекцию. Как это работает, если у `int` нет «шапки» объекта, нет таблицы методов, нет адреса в куче? Ответ — **боксинг**: компилятор и рантайм молча заворачивают значение в настоящий объект.

Почему это важно на практике:

- это **незаметные аллокации**: код выглядит невинно (`list.Add(i)`), а в куче появляется миллион маленьких объектов, и GC начинает работать больше;
- это источник тонких багов: изменения «пропадают», потому что менялась копия в коробке; сравнение `==` двух `object` с одинаковыми числами даёт `false`;
- это любимый вопрос собеседований, потому что он быстро показывает, понимает ли кандидат разницу между value и reference types «по-настоящему»;
- с ним связаны generics (зачем они вообще появились) и многие советы по производительности.

Важная калибровка: в обычной бизнес-логике один боксинг на запрос ничего не стоит. Цель темы — **видеть** боксинг и не допускать его там, где он умножается на миллион.

## Интуиция и аналогия

Reference-тип — это склад с адресной системой: каждая вещь лежит в пронумерованной ячейке, на руках у людей только номера. Value-тип — это деньги в кармане: купюры у тебя самого, никаких ячеек.

Теперь вдруг нужна универсальная служба, которая принимает *только* номерки на склад (`object`). Чтобы отдать ей 42 рубля, ты кладёшь купюру в **коробку**, оформляешь коробку на складе, получаешь номерок и отдаёшь его. Это **боксинг**. Купюра в коробке — уже *копия*: потратишь свою — коробочная не изменится. Чтобы вернуть деньги, нужно прийти на склад, открыть коробку и достать купюру — **анбоксинг**; и открывать надо именно ту коробку, где лежит нужная валюта (рубли в доллары «не распаковываются»).

Каждая коробка — это упаковка, место на складе и работа для уборщика (GC). Пара коробок — не проблема; миллион в цикле — уже склад, который приходится часто чистить.

## Основная теория по шагам

### Шаг 1. Что происходит

**Боксинг (упаковка)** — преобразование value-типа в `object` или в интерфейс, который он реализует. CLR:

1. выделяет в куче новый объект («коробку»);
2. копирует в него значение;
3. возвращает ссылку на коробку.

**Анбоксинг (распаковка)** — явное приведение обратно: CLR проверяет, что в коробке лежит **ровно этот** тип, и копирует значение наружу.

~~~csharp
int n = 42;
object o = n;          // боксинг: аллокация в куче + копия значения
n = 100;
Console.WriteLine(o);  // 42 — в коробке своя, независимая копия

int m = (int)o;        // анбоксинг: проверка типа + копия
Console.WriteLine(m);

try { long l = (long)o; }          // ❌ распаковывать можно только в исходный тип
catch (InvalidCastException) { Console.WriteLine("InvalidCastException"); }

long ok = (int)o;      // ✅ сначала распаковка в int, потом обычное расширение до long
Console.WriteLine(ok);
~~~
~~~console
42
42
InvalidCastException
42
~~~

~~~text Память после object o = n
 СТЕК                         КУЧА
┌──────────────────┐        ┌───────────────────────────┐
│ int n = 100      │        │ коробка System.Int32      │
│ object o ────────┼──────▶ │ [заголовок][тип] 42       │
└──────────────────┘        └───────────────────────────┘
~~~

В 64-битном процессе коробка с `int` занимает около 24 байт (заголовок объекта, указатель на тип и сами 4 байта с выравниванием) вместо 4 байт. Плюс работа для GC, когда коробка станет мусором.

### Шаг 2. Где боксинг прячется

| Код | Боксинг? | Почему |
|---|---|---|
| `ArrayList list; list.Add(5);` | **Да** | `Add(object)` — каждый `int` упаковывается |
| `List<int> list; list.Add(5);` | Нет | generic-коллекция хранит `int` напрямую |
| `object o = 5;` | **Да** | явное приведение к `object` |
| `IComparable c = 5;` | **Да** | приведение структуры к интерфейсу |
| `Console.WriteLine(5);` | Нет | есть перегрузка `WriteLine(int)` |
| `Console.WriteLine("{0}", 5);` | **Да** | перегрузка с `object` |
| `$"Баланс: {5}"` (C# 10+) | Нет | интерполяция через специальный обработчик форматирует значение без упаковки |
| `string.Format("{0}", 5)` | **Да** | параметр `object` |
| `5.GetType()` | **Да** | `GetType` — невиртуальный метод `object`, вызов на структуре требует коробки |
| `Equals(object)` на своей структуре | **Да** | аргумент приводится к `object` |
| `Dictionary<object, X>` с ключом `int` | **Да** | ключ приводится к `object` |
| `params object[] args` | **Да** | каждый value-аргумент упаковывается в массив |
| `where T : struct` и вызов метода интерфейса через `T` | Нет | вызов «constrained», без упаковки |

:::info Как увидеть боксинг своими глазами
В IL боксинг — это инструкция `box`. Вставь код в SharpLab (нужен интернет) и посмотри вкладку IL: каждая `box` — аллокация. Это хороший **10-минутный эксперимент**. Изучать весь IL — уже кроличья нора.
:::

Проверим тоже самое руками: сравним число байт, выделенных при передаче значения «в интерфейс» (боксинг) и через generic с ограничением (без боксинга). Метод помечен `NoInlining`, чтобы JIT не убрал коробку оптимизацией:

~~~csharp
using System.Runtime.CompilerServices;

const int N = 1000;
long Measure(Action a)
{
    a();                                         // прогрев (JIT-компиляция не должна попасть в замер)
    long before = GC.GetAllocatedBytesForCurrentThread();
    a();
    return GC.GetAllocatedBytesForCurrentThread() - before;
}

long viaInterface = Measure(() => { for (int i = 0; i < N; i++) Boxed.Compare(i, 5); });
long viaGeneric   = Measure(() => { for (int i = 0; i < N; i++) Boxed.Generic(i, 5); });
Console.WriteLine($"через интерфейс: ≥ 24 байт на вызов — {viaInterface >= 24L * N}");
Console.WriteLine($"через generic: аллокаций нет — {viaGeneric == 0}");

static class Boxed
{
    [MethodImpl(MethodImplOptions.NoInlining)]
    public static int Compare(IComparable<int> a, int b) => a.CompareTo(b);       // int → IComparable<int>: БОКСИНГ

    [MethodImpl(MethodImplOptions.NoInlining)]
    public static int Generic<T>(T a, T b) where T : IComparable<T> => a.CompareTo(b);  // без упаковки
}
~~~
~~~console
через интерфейс: ≥ 24 байт на вызов — True
через generic: аллокаций нет — True
~~~

Вывод: интерфейс как *тип параметра* упаковывает; интерфейс как *ограничение generic* — нет. Это ключевая причина, почему в современном коде `where T : IComparable<T>` предпочтительнее принятия `IComparable`.

### Шаг 3. Эксперимент: `ArrayList` против `List<int>`

~~~csharp
using System.Collections;

const int N = 100_000;

long before = GC.GetAllocatedBytesForCurrentThread();
var arrayList = new ArrayList();
for (int i = 0; i < N; i++) arrayList.Add(i);          // боксинг на каждой итерации
long arrayListBytes = GC.GetAllocatedBytesForCurrentThread() - before;

before = GC.GetAllocatedBytesForCurrentThread();
var list = new List<int>();
for (int i = 0; i < N; i++) list.Add(i);               // без боксинга
long listBytes = GC.GetAllocatedBytesForCurrentThread() - before;

Console.WriteLine($"ArrayList: больше 30 байт на элемент — {arrayListBytes / N >= 30}");
Console.WriteLine($"List<int>: меньше 16 байт на элемент — {listBytes / N < 16}");
Console.WriteLine($"ArrayList расходует минимум втрое больше — {arrayListBytes > 3 * listBytes}");
~~~
~~~console
ArrayList: больше 30 байт на элемент — True
List<int>: меньше 16 байт на элемент — True
ArrayList расходует минимум втрое больше — True
~~~

Точные числа зависят от версии .NET и платформы (выведи их сам: `Console.WriteLine($"{arrayListBytes:N0}")`). Важно увидеть **порядок**: у `ArrayList` на каждый элемент приходится коробка (~24 байта) плюс ссылка в массиве (8 байт), у `List<int>` — 4 байта в массиве. Обе коллекции дополнительно аллоцируют при росте внутреннего массива.

### Шаг 4. Опасная ловушка: изменение копии в коробке

~~~csharp
var c = new Counter();
ICounter boxed = c;          // боксинг: в коробке КОПИЯ структуры
boxed.Increment();
boxed.Increment();
Console.WriteLine(c.Value);      // 0 — оригинал не менялся
Console.WriteLine(boxed.Value);  // 2 — менялась копия в коробке

interface ICounter
{
    int Value { get; }
    void Increment();
}

struct Counter : ICounter
{
    public int Value { get; private set; }
    public void Increment() => Value++;
}
~~~
~~~console
0
2
~~~

Это ещё один довод в пользу **неизменяемых структур**: с ними не возникает вопроса, какую копию ты изменил.

### Шаг 5. Равенство и коробки

Две коробки — это два разных объекта, даже если внутри одно и то же число. Оператор `==` для `object` сравнивает *ссылки*:

~~~csharp
object a = 5;
object b = 5;
Console.WriteLine(a == b);              // False — разные коробки (сравнение ссылок)
Console.WriteLine(a.Equals(b));         // True  — Int32.Equals сравнивает значения
Console.WriteLine((int)a == (int)b);    // True  — распаковали и сравнили числа
Console.WriteLine(ReferenceEquals(a, b));
~~~
~~~console
False
True
True
False
~~~

Правило: если значения лежат в `object`, сравнивай через `Equals` или распаковывай. То же верно для ключей, которыми ты индексируешь словарь `Dictionary<object, …>`: поиск работает через `Equals`/`GetHashCode`, и это корректно, но каждая операция упаковывает аргумент.

### Шаг 6. Особые случаи

**`Nullable<T>` при упаковке.** Структура `int?` упаковывается особым образом: если значения нет — результат `null` (не коробка!), если есть — коробка с обычным `int`, а не с `Nullable<int>`.

~~~csharp
int? with = 5;
int? none = null;
object o1 = with;
object o2 = none;
Console.WriteLine(o1!.GetType());
Console.WriteLine(o2 is null);
~~~
~~~console
System.Int32
True
~~~

**Анбоксинг `null`.** Попытка распаковать `null` в `int` — `NullReferenceException`. Безопасная проверка — шаблон `is`:

~~~csharp
object? o = null;
try { int x = (int)o!; }
catch (NullReferenceException) { Console.WriteLine("нельзя распаковать null"); }

object? p = 42;
if (p is int n) Console.WriteLine($"это int: {n}");        // проверка и распаковка в одном выражении
if (p is long l) Console.WriteLine("long");                   // не сработает: в коробке именно int
~~~
~~~console
нельзя распаковать null
это int: 42
~~~

**Строки и массивы — не боксинг.** `string` и `int[]` уже reference-типы: присваивание в `object` просто копирует ссылку.

### Шаг 7. Как находить и убирать боксинг

Искать боксинг «глазами» по всему проекту бессмысленно — смотри там, где он умножается на большие числа. Практичный порядок действий:

1. **Сначала измерь, что вообще тормозит.** Профилировщик (dotnet-trace, встроенный профилировщик IDE) и счётчики (`dotnet-counters`: число сборок мусора, размер выделенной памяти) покажут реальные горячие места. Если аллокаций там нет — боксинг не твоя проблема.
2. **Найди источник аллокаций.** Профилировщик памяти показывает, какие типы создаются чаще всего. Много объектов `System.Int32`, `System.Double` или `System.Boolean` в куче — почти наверняка боксинг.
3. **Посмотри IL** подозрительного метода (SharpLab, ILSpy): строки `box` — это и есть упаковка.
4. **Исправь по шаблону:**
   - `ArrayList`/`Hashtable`/необобщённый `IEnumerable` → generic-версии (`List<T>`, `Dictionary<K,V>`, `IEnumerable<T>`);
   - параметр `object` → generic-метод `Method<T>(T value)`;
   - параметр-интерфейс для структуры → generic с ограничением `where T : IInterface`;
   - `string.Format`/`params object[]` → интерполяция или generic-перегрузки;
   - свои структуры в словарях → реализуй `IEquatable<T>` и `GetHashCode`, иначе стандартное сравнение может упаковывать.
5. **Проверь результат измерением**, а не интуицией: `GC.GetAllocatedBytesForCurrentThread()` до и после, либо BenchmarkDotNet с `[MemoryDiagnoser]` (показывает выделенные байты на операцию).

Часть инструментов подсвечивает неявные аллокации (включая боксинг) прямо в редакторе — например, плагин Heap Allocations Viewer в Rider/ReSharper. Это удобно для обучения, но исправлять стоит только то, что реально попадает в горячий путь.

## Как это работает под капотом

**IL-инструкции.** Приведение `object o = n;` компилируется в `box System.Int32`, обратное `(int)o` — в `unbox.any System.Int32`. Инструкция `unbox.any` сравнивает указатель на тип в коробке с ожидаемым — отсюда точная проверка и `InvalidCastException` для «совместимых» типов.

**Constrained calls.** Когда ты вызываешь метод интерфейса на значении типа-параметра (`T a; a.CompareTo(b)` при `where T : IComparable<T>`), компилятор эмитит префикс `constrained.`: если `T` — структура, JIT вызовет метод **напрямую**, без упаковки. Если `T` — класс, будет обычный виртуальный вызов. Именно поэтому generic-код с ограничениями не боксит.

**Generics и value-типы.** Для каждого value-типа в качестве аргумента (`List<int>`, `List<double>`) JIT создаёт **отдельный** машинный код, оптимизированный под конкретный тип; для всех reference-типов (`List<string>`, `List<Order>`) код общий. Поэтому `List<int>` хранит `int` в массиве `int[]` напрямую (ни коробок, ни приведений типов), а старый `ArrayList` — массив `object[]`.

**Оптимизации JIT.** Современный JIT способен убрать коробку, если докажет, что она не «убегает» из метода (в последних версиях — и разместить её на стеке). Поэтому «боксинг в коде» не всегда означает «аллокацию в куче»; но рассчитывать на это нельзя, а измерять — можно (`GC.GetAllocatedBytesForCurrentThread`, BenchmarkDotNet с `MemoryDiagnoser`).

**Стоимость.** Аллокация маленького объекта в .NET очень быстрая (сдвиг указателя), поэтому один боксинг стоит десятки наносекунд. Реальная цена — нагрузка на GC при миллионах коробок и ухудшение локальности данных (числа разбросаны по куче вместо плотного массива). Порядки цен — в [таблице стоимости операций](#/ref/g/pf-op-costs) и в записи про [аллокации](#/ref/g/rt-allocations).

## Типичные ошибки и ловушки

:::danger Распаковка в «совместимый» тип
`(long)o`, где в `o` лежит `int`, — это `InvalidCastException`, хотя `int` неявно расширяется до `long`. Распаковка проверяет **точный** тип. Нужно `(long)(int)o`.
:::

:::danger `ArrayList`/`Hashtable` в новом коде
Это наследие .NET 1.0, до появления generics. Помимо боксинга они теряют типобезопасность: в один `ArrayList` можно положить `int` и `string`, и ошибка вылезет только при приведении.
:::

- **Сравнение коробок через `==`.** `object a = 1000, b = 1000; a == b` — `false`. Сравнивай через `Equals` или распаковывай.
- **Структура за интерфейсом.** Присвоение структуры переменной интерфейсного типа боксит и создаёт *копию*; вызовы через интерфейс меняют копию.
- **Боксинг в логах.** `logger.Log("x = {0}", x)` с `params object[]` упаковывает аргументы даже если уровень логирования выключен. Современные API логирования используют generic- или source-generated перегрузки.
- **`foreach` по `IEnumerable` (необобщённому).** Каждый элемент `int` приходит как `object` — боксинг при обходе; используй `IEnumerable<int>`.
- **«Лечение» боксинга везде.** Не превращай код в нечитаемый ради экономии 24 байт на запрос: оптимизируй после измерений в горячих местах.
- **Анбоксинг `null`** — `NullReferenceException`.
- **Предположение, что `string` боксится.** Нет: `string` — ссылочный тип.

## Вопросы с собеседований

:::spoiler Почему после `object o = n; n = 100;` в `o` осталось 42?
Боксинг копирует значение в новый объект в куче. Дальше `n` и коробка независимы: изменение переменной на стеке не трогает копию в куче.
:::

:::spoiler Будет ли боксинг в `List<int> list; list.Contains(5)`?
Нет. `List<T>` использует `EqualityComparer<T>.Default`, который для `int` сравнивает значения напрямую, без приведения к `object`.
:::

:::spoiler Почему `$"{x}"` в C# 10+ не боксит, а `string.Format("{0}", x)` боксит?
Интерполированная строка компилируется в обращения к `DefaultInterpolatedStringHandler` с generic-методом `AppendFormatted<T>(T value)`, который принимает значение без приведения к `object`. У `string.Format` параметры типа `object`, поэтому value-тип упаковывается.
:::

:::spoiler Что выведет `Console.WriteLine(boxed.Value)` в примере со счётчиком и почему?
`2`. `Increment()` через интерфейс вызывается на копии структуры внутри коробки, и эта копия меняется. Оригинальная переменная `c` остаётся с `Value == 0`.
:::

:::spoiler Что такое боксинг и чем он плох? (ловушка: «боксинг всегда плох»)
Упаковка value-типа в объект в куче с копированием значения. Минус — аллокация, нагрузка на GC, потеря локальности данных. Но в обычном коде один-два боксинга несущественны; важен он в горячих участках и при больших объёмах.
:::

:::spoiler `object a = 5; object b = 5;` — чему равно `a == b`?
`false`: оператор `==` для `object` сравнивает ссылки, а коробки две. `a.Equals(b)` вернёт `true`.
:::

:::spoiler Как избежать боксинга? Назови три способа
Использовать generic-коллекции и методы вместо `object`/`ArrayList`; применять generic-ограничения (`where T : IComparable<T>`) вместо параметров-интерфейсов; выбирать перегрузки, принимающие конкретные типы (`WriteLine(int)`, `AppendFormatted<T>`), а не `object`; не приводить структуры к интерфейсам без необходимости.
:::

:::spoiler Что получится при упаковке `int?` со значением `null`?
Результат — `null` (не коробка). При наличии значения упаковывается обычный `int`, а не `Nullable<int>`.
:::

## Что запомнить

- Боксинг = `value type → object/интерфейс`: аллокация в куче + **копия** значения; анбоксинг = проверка **точного** типа + копия наружу.
- Типичные места: `ArrayList`, `object`/`params object[]`, `string.Format`, приведение структуры к интерфейсу, `GetType()` на значении.
- Не боксят: generic-коллекции, интерполяция (C# 10+), generic-ограничения, перегрузки под конкретный тип.
- Изменения через интерфейс меняют копию в коробке, не оригинал: делай структуры неизменяемыми.
- Две коробки с одним числом: `==` → `false`, `Equals` → `true`.
- `(long)o` для `int` в `o` — `InvalidCastException`; `null` не распаковывается.
- Один боксинг — копейки; миллион в цикле — нагрузка на GC. Сначала измерь, потом оптимизируй.

## Зачем это нужно

Любая программа больше сотни строк без методов превращается в стену текста. Метод — это именованный кусок логики, который можно вызвать, проверить и заменить. Хорошие методы — основа читаемости, тестируемости и повторного использования; плохие (длинные, с побочными эффектами и пятью флагами в параметрах) — главный источник боли в реальных проектах.

Но у методов в C# есть набор особенностей, о которых надо знать, чтобы не споткнуться:

- параметры передаются **по значению**, но «значением» бывает и копия данных, и копия ссылки (продолжение темы про value/reference);
- есть три модификатора (`ref`, `out`, `in`), которые это меняют, и вопрос про них задают на каждом втором собеседовании;
- перегрузка выбирается **компилятором** по набору строгих правил, и иногда выбор неожиданный;
- параметры по умолчанию и `params` удобны, но имеют подводные камни, о которых редко рассказывают в туториалах;
- Try-паттерн (`int.TryParse(…, out var n)`) встречается в стандартной библиотеке повсюду; его нужно уметь писать и читать.

В работе это превращается в ежедневные решения: что вернуть — кортеж, `out` или результат-объект; как назвать параметры; что выбросить, а что вернуть как «не удалось»; как не сломать вызывающий код при изменении сигнатуры.

## Интуиция и аналогия

Метод — это **кухонный комбайн**: ты кладёшь ингредиенты (параметры), нажимаешь кнопку (вызов) и получаешь результат (возврат).

- Обычный параметр — ты кладёшь *копию* ингредиента (если ингредиент — это «адрес овощной лавки», комбайн получит копию адреса и сможет сходить в ту же лавку и что-то там поменять, но *твою* бумажку с адресом перечеркнуть не сможет).
- `ref` — ты не кладёшь ингредиент, а **отдаёшь ключ от своего холодильника**: комбайн может достать оттуда, заменить содержимое, и ты увидишь изменения. Холодильник должен быть уже заполнен.
- `out` — ты отдаёшь **пустую тарелку**: комбайн обязан положить в неё результат. Пустая тарелка допустима, но возвращать её пустой нельзя.
- `in` — ты отдаёшь ключ, но с условием «**только смотреть**»: большую коробку не нужно копировать, и портить её нельзя.

Перегрузка — это набор кнопок «Сок», «Смузи», «Пюре» на одном и том же комбайне: название общее («Приготовить»), а режим выбирается по тому, что ты положил.

## Основная теория по шагам

### Шаг 1. Объявление метода

~~~csharp
Console.WriteLine(Fees.ApplyFee(1000m, 0.05m));
Console.WriteLine(Fees.IsPositive(-5m));

static class Fees
{
    public static decimal ApplyFee(decimal amount, decimal rate)
    {
        if (rate < 0m) throw new ArgumentOutOfRangeException(nameof(rate));
        return amount + amount * rate;
    }

    // expression-bodied: тело — одно выражение
    public static bool IsPositive(decimal amount) => amount > 0m;
}
~~~
~~~console
1050.00
False
~~~

Из чего состоит объявление: модификатор доступа (`public`, `private`…), `static` или нет, возвращаемый тип (`void`, если ничего не возвращает), имя в `PascalCase`, список параметров, тело. Имя метода обычно — **глагол**: `CalculateTotal`, `IsPositive`, `TryParse`.

Сигнатура метода — это **имя + типы и модификаторы параметров**. Возвращаемый тип в сигнатуру для перегрузки не входит. Названия параметров тоже не входят: `M(int a)` и `M(int b)` — один и тот же метод.

Правила хорошего метода:

- делает **одну вещь** и называется по тому, что делает;
- умещается на экран (грубо — до 20–30 строк);
- проверяет входные данные в начале (*guard clauses*) и рано выходит из метода, вместо вложенных `if`;
- не принимает больше 3–4 параметров (иначе — объект с параметрами);
- не использует булевы флаги для переключения режимов (`Process(order, true, false)` читать невозможно).

~~~csharp @nocheck
public static void Ship(Order order)
{
    ArgumentNullException.ThrowIfNull(order);          // guard clause: проверка контракта
    if (order.Items.Count == 0) throw new InvalidOperationException("Пустой заказ");
    // ... основная логика без вложенности
}
~~~

**Статические и экземплярные методы.** `static`-метод принадлежит типу и вызывается как `Math.Max(…)`; экземплярный — объекту (`list.Add(…)`), имеет доступ к его полям через неявный параметр `this`. Чистая функция без состояния — естественный кандидат на `static`.

**Область видимости локальных функций.** Внутри метода можно объявлять *локальные функции* — вспомогательные методы, видимые только здесь; `static` перед ними запрещает захват внешних переменных.

~~~csharp
Console.WriteLine(Factorial(5));
Console.WriteLine(Factorial(0));

static long Factorial(int n)
{
    if (n < 0) throw new ArgumentOutOfRangeException(nameof(n));
    return Loop(n);

    static long Loop(int k) => k <= 1 ? 1 : k * Loop(k - 1);   // рекурсия: базовый случай + шаг
}
~~~
~~~console
120
1
~~~

У рекурсии всегда должен быть **базовый случай**, иначе стек переполнится (`StackOverflowException`, перехватить нельзя).

### Шаг 2. Перегрузка

~~~csharp
Console.WriteLine(Pricing.Fee(1000m));          // 10.00
Console.WriteLine(Pricing.Fee(1000m, 0.02m));   // 20.00
Console.WriteLine(Pricing.Fee(1000));           // 10.00 — int неявно приводится к decimal

static class Pricing
{
    public static decimal Fee(decimal amount) => amount * 0.01m;
    public static decimal Fee(decimal amount, decimal rate) => amount * rate;
    // public static int Fee(decimal amount) => 0;   // ❌ отличается только возвращаемым типом — ошибка
}
~~~
~~~console
10.00
20.00
10.00
~~~

:::info Почему 10.00, а не 10
`decimal` помнит **масштаб** (количество знаков после запятой). При умножении масштабы складываются: `1000m` (0 знаков) × `0.01m` (2 знака) = `10.00`. Это не баг, а свойство типа. Для вывода используй формат: `{fee:N2}` или `{fee:0.##}`.
:::

Компилятор выбирает перегрузку **во время компиляции** по типам аргументов: сначала точное совпадение, потом варианты с неявными преобразованиями, при равенстве — более специфичный. Посмотрим, как это работает на «лестнице» числовых типов:

~~~csharp
P.Show((byte)1);
P.Show((short)2);
P.Show(3);
P.Show(4L);
P.Show(5.5f);
P.Show('a');
P.Show("строка");
P.Show(null);

static class P
{
    public static void Show(int x) => Console.WriteLine($"int: {x}");
    public static void Show(long x) => Console.WriteLine($"long: {x}");
    public static void Show(double x) => Console.WriteLine($"double: {x}");
    public static void Show(string s) => Console.WriteLine($"string: {s}");
    public static void Show(object o) => Console.WriteLine($"object: {o}");
}
~~~
~~~console
int: 1
int: 2
int: 3
long: 4
double: 5.5
int: 97
string: строка
string:
~~~

Правило «лучшего преобразования»: выбирается перегрузка, к типу параметра которой преобразование аргумента ближайшее и наиболее специфичное (`byte → int` лучше, чем `byte → long`); `null` выбирает `string` (специфичнее `object`). Если подходящих несколько и ни одна не лучше — ошибка «неоднозначный вызов» (CS0121).

:::warn Перегрузка + параметры по умолчанию
~~~csharp
Log.Write("старт");   // какая перегрузка вызовется?

static class Log
{
    public static void Write(string message) => Console.WriteLine("1: " + message);
    public static void Write(string message, int level = 0) => Console.WriteLine("2: " + message);
}
~~~
~~~console
1: старт
~~~

Вызовется первая: при прочих равных выигрывает кандидат, которому не нужно подставлять значения по умолчанию. Код компилируется, но читателю непонятно, что происходит. **Не смешивай перегрузки и параметры по умолчанию с пересекающимися сигнатурами.**
:::

### Шаг 3. Способы передачи параметров

| Модификатор | Что передаётся | Должен ли быть инициализирован до вызова | Может ли метод изменить переменную вызывающего |
|---|---|---|---|
| (нет) | копия значения (для class — копия ссылки) | да | нет (но может менять поля объекта класса) |
| `ref` | ссылка на **переменную** | **да** | **да** |
| `out` | ссылка на переменную | нет | **обязан** присвоить до выхода |
| `in` | ссылка только для чтения | да | нет, менять запрещено компилятором |

#### `ref`: метод работает с переменной вызывающего

~~~csharp
int a = 1, b = 2;
Swap(ref a, ref b);
Console.WriteLine($"{a} {b}");   // 2 1

var account = new Account { Owner = "Анна" };
ReplaceOwner(ref account);
Console.WriteLine(account.Owner);   // Борис — ref позволил подменить сам объект

static void Swap(ref int x, ref int y) => (x, y) = (y, x);
static void ReplaceOwner(ref Account acc) => acc = new Account { Owner = "Борис" };

class Account { public string Owner { get; set; } = ""; }
~~~
~~~console
2 1
Борис
~~~

Сравни с примером `ReplaceClass` из [value vs reference](#p1-types/pass): без `ref` подмена объекта не была видна снаружи, с `ref` — видна.

Параметр с `ref` нужно помечать `ref` и **при вызове** — читатель сразу видит, что переменная может измениться.

#### `out`: несколько результатов и Try-паттерн

~~~csharp
if (int.TryParse("123", out int number))
    Console.WriteLine(number + 1);       // 124

if (TryWithdraw(balance: 500m, amount: 800m, out decimal newBalance, out string? error))
    Console.WriteLine($"Новый баланс: {newBalance}");
else
    Console.WriteLine(error);            // Недостаточно средств

_ = int.TryParse("x", out _);           // _ — discard: результат не нужен

static bool TryWithdraw(decimal balance, decimal amount, out decimal newBalance, out string? error)
{
    if (amount <= 0m) { newBalance = balance; error = "Сумма должна быть положительной"; return false; }
    if (amount > balance) { newBalance = balance; error = "Недостаточно средств"; return false; }
    newBalance = balance - amount;
    error = null;
    return true;
}
~~~
~~~console
124
Недостаточно средств
~~~

Компилятор **требует** присвоить все `out`-параметры на каждом пути выхода из метода — забыть невозможно. Объявление переменной прямо в вызове (`out int number`, `out var x`) — удобный стандарт; переменная остаётся доступной и после `if`.

Правило Try-паттерна: метод называется `TryXxx`, возвращает `bool` (получилось ли), результат кладёт в `out`; при неудаче `out`-значение — `default`. Он **не бросает исключение** на ожидаемую ошибку — для этого и придуман.

#### `in`: большая структура без копирования

~~~csharp
var a = new Vector3D(1, 2, 3);
var b = new Vector3D(4, 5, 6);
Console.WriteLine(Dot(in a, in b));   // 32
Console.WriteLine(Dot(a, b));         // тоже можно: in при вызове необязателен

static double Dot(in Vector3D a, in Vector3D b)
{
    // a = default;   // ❌ ошибка: in-параметр только для чтения
    return a.X * b.X + a.Y * b.Y + a.Z * b.Z;
}

readonly record struct Vector3D(double X, double Y, double Z);
~~~
~~~console
32
32
~~~

`in` имеет смысл для **больших `readonly struct`**, чтобы не копировать их при каждом вызове. Для `int`, `decimal` или классов он бесполезен (ссылка не меньше значения). Если структура **не** `readonly`, компилятор при вызове её методов делает «защитные» копии — и выигрыш пропадает. В Фазе 1 достаточно понимать, что это такое.

#### Ссылочные локальные переменные и возвращаемые ссылки

`ref` работает не только в параметрах. Можно заводить *ссылку на ячейку* и возвращать её из метода:

~~~csharp
int[] arr = { 1, 2, 3 };
ref int slot = ref arr[1];       // slot — псевдоним для arr[1], а не копия
slot = 20;
Console.WriteLine(string.Join(",", arr));

ref int found = ref Find(arr, 3);
found = 300;
Console.WriteLine(string.Join(",", arr));

static ref int Find(int[] a, int value)
{
    for (int i = 0; i < a.Length; i++)
        if (a[i] == value) return ref a[i];
    throw new InvalidOperationException("не найдено");
}
~~~
~~~console
1,20,3
1,20,300
~~~

Это инструмент для оптимизации и низкоуровневого кода; в бизнес-логике джуну он почти не встречается. Главное — не удивляться синтаксису.

### Шаг 4. Параметры по умолчанию и именованные аргументы

~~~csharp
OpenAccount("Анна");
OpenAccount("Борис", currency: "USD");             // именованный аргумент: пропускаем initialDeposit
OpenAccount(owner: "Вера", initialDeposit: 100m);

static void OpenAccount(string owner, decimal initialDeposit = 0m, string currency = "TJS")
    => Console.WriteLine($"{owner}: {initialDeposit} {currency}");
~~~
~~~console
Анна: 0 TJS
Борис: 0 USD
Вера: 100 TJS
~~~

Именованные аргументы повышают читаемость вызовов с «голыми» литералами: `CreateUser("Анна", isAdmin: true, sendWelcome: false)` понятнее, чем `CreateUser("Анна", true, false)`.

Выражения в аргументах вычисляются **в том порядке, в каком написаны в вызове**, а не в порядке параметров:

~~~csharp
static int F(string name) { Console.Write(name + " "); return 1; }
static int Add(int a, int b) => a + b;

Add(b: F("b"), a: F("a"));       // порядок записи b, a
Console.WriteLine();
~~~
~~~console
b a
~~~

:::warn Значение по умолчанию «вшивается» в вызывающий код
Компилятор подставляет значение по умолчанию **в место вызова**. Если библиотека поменяет `currency = "TJS"` на `"USD"`, уже скомпилированные программы продолжат передавать `"TJS"`, пока их не пересоберут. Поэтому значения по умолчанию должны быть константами, которые не меняются.
:::

Параметры по умолчанию должны идти **в конце** списка и быть константами времени компиляции (`0`, `null`, `"текст"`, `default`). Для изменяемых типов (`List<int> items = null`) принято использовать `null` и заполнять внутри метода.

### Шаг 5. `params` и кортежи

~~~csharp
Console.WriteLine(Sum(1, 2, 3));          // 6
Console.WriteLine(Sum());                 // 0

var (min, max) = MinMax(new[] { 5, -2, 9 });
Console.WriteLine($"{min}..{max}");       // -2..9

static int Sum(params int[] numbers)
{
    int s = 0;
    foreach (int n in numbers) s += n;
    return s;
}

static (int Min, int Max) MinMax(int[] values)
{
    if (values.Length == 0) throw new ArgumentException("Пустой массив", nameof(values));
    int min = values[0], max = values[0];
    foreach (int v in values)
    {
        if (v < min) min = v;
        if (v > max) max = v;
    }
    return (min, max);
}
~~~
~~~console
6
0
-2..9
~~~

Кортеж `(int Min, int Max)` — часто более читаемая альтернатива двум `out`-параметрам. `out` уместен в Try-паттерне, где метод возвращает `bool`.

`params` позволяет передавать произвольное количество аргументов. Он должен быть **последним** параметром, и в методе будет всего один `params`. Начиная с C# 13 `params` работает не только с массивами, но и со `Span`/коллекциями, что избавляет от выделения массива на каждый вызов:

~~~csharp
Console.WriteLine(Total(1, 2, 3, 4));

static int Total(params ReadOnlySpan<int> values)   // C# 13: без аллокации массива
{
    int s = 0;
    foreach (int v in values) s += v;
    return s;
}
~~~
~~~console
10
~~~

## Как это работает под капотом

- **Перегрузка выбирается при компиляции.** В IL записан вызов конкретного метода. (Не путай с *виртуальным* вызовом — выбор переопределения в наследовании делается во время выполнения; об этом в теме про полиморфизм.)
- **`ref`, `out`, `in` — это управляемые указатели.** В IL параметр имеет тип `int&` («ссылка на `int`»). `out` — то же самое плюс атрибут и правило компилятора «обязан присвоить». `in` — то же плюс атрибут «только чтение». Управляемый указатель нельзя сохранить в поле класса или в куче: он живёт только на стеке (поэтому `ref`-параметры нельзя использовать в `async`-методах и лямбдах).
- **Значения по умолчанию подставляются на месте вызова**, поэтому в IL вызов `OpenAccount("Анна")` уже содержит `0m` и `"TJS"`.
- **Вызов `params`** без `Span` превращается в создание массива на каждом вызове — это аллокация. Для горячих мест выбирай перегрузки без `params` или `params ReadOnlySpan<T>`.
- **Кортеж** `(int, int)` — это структура `ValueTuple<int, int>`; имена `Min` и `Max` — только подсказка компилятора и среды разработки.
- **Вызов метода** — это кадр на стеке: туда кладутся аргументы, адрес возврата, локальные переменные. JIT часто *встраивает* (inline) маленькие методы в место вызова, и накладных расходов на вызов не остаётся — поэтому не нужно объединять мелкие методы «для скорости».
- **Рекурсия** занимает по кадру на каждый уровень; глубина ограничена размером стека (порядка десятков тысяч кадров).

## Типичные ошибки и ловушки

:::danger `ref` «для скорости» на классах
Передача класса и так копирует только ссылку (8 байт). `ref` на классе нужен **только** когда метод должен подменить объект вызывающего. Иначе это лишняя сложность.
:::

:::danger Много `out`-параметров
Метод с тремя `out` — сигнал вернуть кортеж, `record` или результат-объект. Исключение — устоявшийся Try-паттерн.
:::

- **Метод делает слишком много.** «Проверь, сохрани, отправь письмо и залогируй» — это четыре метода.
- **Булевы флаги вместо отдельных методов.** `Process(order, true)` — что значит `true`? Разделяй или используй именованные аргументы/перечисления.
- **Метод меняет входные данные неявно.** Если метод правит переданный объект — это должно быть понятно из имени (`Normalize`, `Apply…`) или документации; иначе возвращай новый объект.
- **Возврат `null` вместо пустой коллекции.** Вызывающий код вынужден проверять; возвращай пустой массив/список.
- **Игнорирование результата Try-метода.** `int.TryParse(s, out var n);` без проверки `bool` — `n` будет `0` при ошибке.
- **Исключение там, где ожидаема ошибка.** Для «пользователь ввёл мусор» — `TryParse` и `bool`, не `try/catch`.
- **Изменение `static`-состояния из методов** — скрытые связи между вызовами, невозможность тестировать.
- **Значения по умолчанию, которые меняются между версиями библиотеки** (вшиты в вызывающий код).
- **Неоднозначные перегрузки** с `null` или `params`: компилятор откажется выбирать (CS0121).

## Вопросы с собеседований

:::spoiler Разница между `ref` и `out` — одной фразой
`ref` требует инициализированную переменную и даёт методу право (но не обязанность) её изменить. `out` не требует инициализации, но **обязывает** метод присвоить значение до возврата.
:::

:::spoiler Можно ли перегрузить метод только по возвращаемому типу?
Нет. Тип возвращаемого значения не входит в сигнатуру для перегрузки, компилятор не сможет выбрать метод по месту вызова.
:::

:::spoiler Можно ли перегрузить методы, которые отличаются только `ref` и `out`?
Нет. `M(ref int x)` и `M(out int x)` считаются одинаковыми для перегрузки. А вот `M(int x)` и `M(ref int x)` — можно.
:::

:::spoiler Что выведет `Console.WriteLine(Pricing.Fee(1000m))` и почему не `10`?
`10.00`. Масштаб `decimal` при умножении складывается: 0 + 2 знака. Значение то же самое, отличается только представление.
:::

:::spoiler Если параметр — класс, нужен ли `ref`, чтобы метод изменил объект? (ловушка)
Нет: метод получает копию ссылки на тот же объект и может менять его поля. `ref` нужен, чтобы **подменить** объект целиком (`p = new …`) так, чтобы вызывающий код увидел новую ссылку.
:::

:::spoiler Зачем нужен `in` и когда он не нужен?
`in` передаёт большую `readonly struct` по ссылке только для чтения и экономит копирование. Для маленьких типов (`int`, `decimal`) и классов он не нужен — копия не дороже ссылки.
:::

:::spoiler Что такое Try-паттерн и почему `TryParse` лучше `Parse` + `try/catch` для пользовательского ввода?
Метод возвращает `bool` и кладёт результат в `out`. Ошибка ввода — ожидаемая ситуация, а исключения дороги (микросекунды против наносекунд) и засоряют логику; поэтому для ожидаемых ошибок возвращают `false`.
:::

:::spoiler Когда вычисляются значения параметров по умолчанию?
На месте вызова, при компиляции вызывающего кода. Поэтому смена значения по умолчанию в библиотеке не затронет уже собранные программы без пересборки.
:::

:::spoiler Какой метод вызовется: `M(int)` или `M(long)` для аргумента `byte`?
`M(int)`: преобразование `byte → int` лучше, чем `byte → long`. Выбор делает компилятор, по статическому типу аргумента.
:::

## Что запомнить

- Сигнатура = имя + типы/модификаторы параметров; **возвращаемый тип в перегрузке не участвует**, `ref` и `out` взаимозаменяемы для перегрузки.
- По умолчанию — передача по значению (у класса копия ссылки). `ref` — переменная вызывающего; `out` — метод обязан присвоить; `in` — только чтение без копирования.
- Try-паттерн: `bool TryXxx(…, out T result)` — для ожидаемых ошибок вместо исключений.
- Перегрузка выбирается **при компиляции**; не смешивай перегрузки с параметрами по умолчанию.
- Значения по умолчанию вшиваются в вызывающий код — должны быть константами; параметры по умолчанию — в конце.
- Кортеж часто лучше пары `out`; `params` без `Span` выделяет массив при каждом вызове.
- Метод — одна задача, понятное имя-глагол, guard clauses в начале, ≤ 3–4 параметров.
- Рекурсии нужен базовый случай.

:::why
Строки — самый частый тип в backend-коде: логи, JSON, SQL, сообщения об ошибках. Непонимание неизменяемости даёт два класса проблем: баги («я вызвал `ToUpper()`, а строка не поменялась») и производительность (склейка в цикле за O(n²)). Плюс сравнение строк с учётом культуры — источник реальных production-багов.
:::

## Зачем это нужно

Если составить список всего, с чем реально работает бэкенд-разработчик, на первом месте окажутся строки: имена и e-mail пользователей, JSON-тела запросов, SQL-запросы, строки подключения, пути к файлам, сообщения в логах, ключи кэша. Поэтому три вещи про строки надо знать твёрдо:

1. **Строки неизменяемы.** Все методы, которые «меняют» строку, возвращают новую. Забытое присваивание результата — классический баг новичка.
2. **Склейка в цикле стоит дорого.** Код `result += x` в цикле на десятки тысяч итераций превращает быструю программу в медленную и нагружает GC.
3. **Сравнение строк зависит от правил.** С учётом регистра или без, по правилам культуры или побайтово — разные способы дают разные результаты, и ошибка проявляется только на чужом компьютере с другой локалью.

Эта тема напрямую связана с предыдущими: строка — reference type, поведение которого (копирование ссылки, `==`) нужно отличать от остальных; и она же — лучший учебный пример того, как неизменяемость даёт безопасность, а цена за неё — аллокации.

## Интуиция и аналогия

Строка в C# — это **высеченная надпись на камне**. Хочешь «изменить» слово? Нельзя поправить надпись — можно высечь новую табличку и повесить на неё указатель. Старая остаётся лежать, пока уборщик (GC) не заметит, что на неё никто не смотрит.

Выгоды очевидны: на каждую табличку может смотреть сколько угодно людей — никто её не испортит (потокобезопасность), одну и ту же табличку «Выход» можно повесить в нескольких местах (интернирование). Минус: если ты строишь длинный текст, добавляя по слову, и каждый раз высекаешь новую табличку целиком, то будешь высекать тысячи табличек.

`StringBuilder` — это **рабочий блокнот**: ты спокойно дописываешь в него слова, а табличку высекаешь один раз, когда текст готов.

Про культуру: слово «сравнить» может означать «одинаковы ли символы» (Ordinal) или «одинаково ли это звучит и пишется по правилам языка» (Culture). Для служебных строк (команды, ключи, пути) нужно первое; для текста, который читает человек, — второе.

## Основная теория по шагам

### Шаг 1. `string` — неизменяемый reference type

~~~csharp
string name = "тимур";
name.ToUpper();                 // ❌ результат выброшен: строка не меняется
Console.WriteLine(name);        // тимур

name = name.ToUpper();          // ✅ новая строка, переменная указывает на неё
Console.WriteLine(name);        // ТИМУР
~~~
~~~console
тимур
ТИМУР
~~~

Любая «модифицирующая» операция (`Replace`, `Trim`, `ToUpper`, `+`, `Substring`) **создаёт новую строку**, исходная остаётся нетронутой.

#### Зачем строки сделали неизменяемыми

- **Безопасность ключей.** Строка — ключ в `Dictionary`. Если бы её можно было изменить после вставки, хэш перестал бы совпадать и элемент «потерялся» бы.
- **Потокобезопасность.** Неизменяемый объект можно читать из любого количества потоков без блокировок.
- **Интернирование.** Одинаковые литералы можно хранить в одном экземпляре — только потому, что никто не может их изменить.
- **Безопасность.** Проверил путь к файлу или строку подключения — никто не подменит её содержимое после проверки.

#### Что такое строка изнутри

`string` — последовательность `char`; каждый `char` — одна 16-битная единица UTF-16. Для большинства символов (латиница, кириллица) «один символ — один `char`», но не для всего:

~~~csharp
string smile = "😀";
Console.WriteLine(smile.Length);                       // 2 — суррогатная пара в UTF-16
Console.WriteLine(smile.EnumerateRunes().Count());     // 1 — один «настоящий» символ Unicode
Console.WriteLine("кот".Length);                       // 3

char c = 'а';
Console.WriteLine((int)c);                             // 1072 — числовой код
Console.WriteLine((char)(c + 1));                      // б — арифметика с кодами
Console.WriteLine(char.IsLetter('я') + " " + char.IsDigit('7'));
~~~
~~~console
2
1
3
1072
б
True True
~~~

`Length` считает **единицы UTF-16**, а не то, что пользователь видит как символы (эмодзи, составные символы с диакритикой). Для обычного бизнес-текста это не проблема, но для эмодзи, иероглифов и «e + акцент» — потенциальный баг.

Быстро получить байты (например, для сети или файла) можно через кодировку: `Encoding.UTF8.GetBytes(s)`; обратно — `Encoding.UTF8.GetString(bytes)`. Файлы и HTTP почти всегда в UTF-8; по умолчанию в .NET используй именно её.

### Шаг 2. Сравнение строк и string pool

~~~csharp
string a = "hello";
string b = "hello";
string c = new string(new[] { 'h', 'e', 'l', 'l', 'o' });

Console.WriteLine(a == c);                                   // True  — == у string сравнивает СОДЕРЖИМОЕ
Console.WriteLine(object.ReferenceEquals(a, b));             // True  — литералы интернированы: один объект
Console.WriteLine(object.ReferenceEquals(a, c));             // False — c создана во время выполнения
Console.WriteLine(object.ReferenceEquals(a, string.Intern(c))); // True — Intern вернул экземпляр из пула
~~~
~~~console
True
True
False
True
~~~

- **String pool (пул интернирования)** — таблица, которую ведёт рантайм. Все строковые **литералы** из кода попадают туда автоматически, поэтому `a` и `b` — один объект.
- Строки, созданные во время выполнения (чтение файла, конкатенация, `new string(...)`), в пул **не** попадают автоматически.
- `string.Intern(s)` возвращает экземпляр из пула (добавляя строку, если её там не было).
- Для `string` оператор `==` **перегружен** и сравнивает содержимое, хотя это reference type. Поэтому в обычном коде интернирование тебя почти не касается.

:::deep Граница
Ручной `string.Intern` в прикладном коде почти никогда не нужен: интернированные строки живут очень долго (фактически до конца процесса). Как устроена таблица интернирования и куда ушли строки в разных версиях рантайма — кроличья нора.
:::

#### Сравнение с учётом регистра и культуры

~~~csharp
string cmd = "EXIT";

bool bad = cmd.ToLower() == "exit";                                    // ❌ лишняя строка и зависимость от культуры
bool good = string.Equals(cmd, "exit", StringComparison.OrdinalIgnoreCase); // ✅
bool good2 = cmd.Equals("exit", StringComparison.OrdinalIgnoreCase);       // ✅
Console.WriteLine($"{bad} {good} {good2}");

// Для идентификаторов, команд, ключей, путей — Ordinal / OrdinalIgnoreCase.
// Для сортировки текста, который видит пользователь, — CurrentCulture.
~~~
~~~console
True True True
~~~

Варианты `StringComparison`:

| Значение | Что делает | Когда использовать |
|---|---|---|
| `Ordinal` | побайтово (по кодам символов), с учётом регистра | технические строки: ключи, команды, пути, идентификаторы |
| `OrdinalIgnoreCase` | побайтово, без учёта регистра | то же, но регистр не важен |
| `CurrentCulture` / `CurrentCultureIgnoreCase` | по правилам текущей локали | сортировка и сравнение текста для людей |
| `InvariantCulture*` | по правилам «нейтральной» культуры | хранимые/передаваемые данные, зависящие от языковых правил (редко) |

:::warn Турецкая «i»
В турецкой культуре `"i".ToUpper()` — это `"İ"` (с точкой), а не `"I"`. Код `if (cmd.ToUpper() == "EXIT")` на компьютере с турецкой локалью сломается. Это реальный класс багов, поэтому для технических строк всегда используй `StringComparison.Ordinal*`.
:::

Обрати внимание: многие методы строк по умолчанию **зависят от культуры** — `IndexOf(string)`, `StartsWith(string)`, `EndsWith(string)`, `CompareTo`, `ToUpper()`/`ToLower()`. В современном коде для технических данных передавай `StringComparison.Ordinal` явно (перегрузки с `char` — порядковые сами по себе). Статические анализаторы (правила CA1307, CA1309) подсказывают такие места.

Сортировка тоже зависит от выбранного сравнения:

~~~csharp
var words = new[] { "b", "A", "a", "B" };
Console.WriteLine(string.Join(",", words.OrderBy(w => w, StringComparer.Ordinal)));
Console.WriteLine(string.Join(",", words.OrderBy(w => w, StringComparer.OrdinalIgnoreCase)));
~~~
~~~console
A,B,a,b
A,a,b,B
~~~

`Ordinal`: заглавные буквы стоят раньше строчных (коды `A` < `a`). Для списка, который видит пользователь, нужна культурная сортировка (`StringComparer.CurrentCulture`).

### Шаг 3. Склейка в цикле и `StringBuilder`

~~~csharp @nocheck
using System.Text;   // StringBuilder живёт здесь; в implicit usings консольного шаблона его нет

// ❌ O(n²): на каждой итерации создаётся новая строка и копируется всё накопленное
string report = "";
for (int i = 0; i < 10_000; i++)
    report += $"Операция {i}\n";

// ✅ O(n): StringBuilder пишет в изменяемый буфер, строка создаётся один раз в конце
var sb = new StringBuilder();
for (int i = 0; i < 10_000; i++)
    sb.Append("Операция ").Append(i).AppendLine();
string report2 = sb.ToString();
~~~

Почему первый вариант медленный: на итерации k копируется вся строка длиной ~k строк. Сумма 1 + 2 + … + n ≈ n²/2 копирований символов. Плюс тысячи мусорных строк для GC. Измерим не время (оно «шумит»), а **объём выделенной памяти**:

~~~csharp
using System.Text;

const int N = 5000;

long before = GC.GetAllocatedBytesForCurrentThread();
string report = "";
for (int i = 0; i < N; i++) report += "Операция " + i + "\n";
long concatBytes = GC.GetAllocatedBytesForCurrentThread() - before;

before = GC.GetAllocatedBytesForCurrentThread();
var sb = new StringBuilder();
for (int i = 0; i < N; i++) sb.Append("Операция ").Append(i).Append('\n');
string report2 = sb.ToString();
long sbBytes = GC.GetAllocatedBytesForCurrentThread() - before;

Console.WriteLine(report == report2);
Console.WriteLine($"склейка выделила больше в 100+ раз: {concatBytes > 100 * sbBytes}");
~~~
~~~console
True
склейка выделила больше в 100+ раз: True
~~~

:::key Когда `StringBuilder` не нужен
`var s = a + b + c + d;` компилятор превращает в **один** вызов `string.Concat` — это эффективно. `StringBuilder` нужен, когда склейка идёт **в цикле** или количество частей заранее неизвестно. Для 2–5 фиксированных кусков используй интерполяцию.
:::

Два других хороших инструмента: `string.Join(", ", items)` — склеивает коллекцию, предварительно посчитав итоговую длину, и `string.Concat`. Если примерно знаешь итоговый размер, `new StringBuilder(capacity)` избавит от лишних расширений буфера.

~~~csharp
using System.Text;

var sb = new StringBuilder(capacity: 1000);
Console.WriteLine($"{sb.Length} {sb.Capacity}");     // пока пусто, но буфер зарезервирован
sb.Append("Привет, ").Append("мир").AppendLine("!");
sb.Insert(0, ">> ");                                 // вставка в начало — дороже дописывания в конец
sb.Replace("мир", "C#");
Console.Write(sb.ToString());
Console.WriteLine(sb.Length);
~~~
~~~console
0 1000
>> Привет, C#!
15
~~~

~~~csharp Выписка по счёту — типичное применение
using System.Text;

var ops = new List<(DateTime At, string Kind, decimal Amount)>
{
    (new DateTime(2026, 10, 1), "Пополнение", 1500m),
    (new DateTime(2026, 10, 3), "Снятие", -200m),
    (new DateTime(2026, 10, 7), "Перевод", -350.5m),
};

var sb = new StringBuilder();
sb.AppendLine($"{"Дата",-10}  {"Операция",-14} {"Сумма",10}");
sb.AppendLine(new string('-', 37));
decimal total = 0m;
foreach (var op in ops)
{
    sb.AppendLine($"{op.At:yyyy-MM-dd}  {op.Kind,-14} {op.Amount,10:N2}");
    total += op.Amount;
}
sb.AppendLine(new string('-', 37));
sb.AppendLine($"{"Итого",-26} {total,10:N2}");
Console.Write(sb.ToString());
~~~
~~~console
Дата        Операция            Сумма
-------------------------------------
2026-10-01  Пополнение       1,500.00
2026-10-03  Снятие            -200.00
2026-10-07  Перевод           -350.50
-------------------------------------
Итого                          949.50
~~~

`{op.Kind,-14}` — выравнивание влево по ширине 14, `{op.Amount,10:N2}` — вправо по ширине 10 с двумя знаками после запятой. Формат `N2` использует разделители текущей культуры (в русской локали будет `1 500,00`).

### Шаг 4. Полезные операции

~~~csharp
string line = "  ACC-001 ; Анна Иванова ; 1500.00  ";

string[] parts = line.Split(';', StringSplitOptions.TrimEntries);
Console.WriteLine(string.Join("|", parts));        // ACC-001|Анна Иванова|1500.00

bool empty = string.IsNullOrWhiteSpace("   ");     // True
string joined = string.Join(", ", parts);          // ACC-001, Анна Иванова, 1500.00
string first3 = parts[0][..3];                     // ACC — диапазон (range)
bool isAcc = parts[0].StartsWith("ACC", StringComparison.Ordinal);
Console.WriteLine($"{empty} | {joined} | {first3} | {isAcc}");

string path = @"C:\bank\data.txt";                 // verbatim: \ не экранирует
string json = """
    { "owner": "Анна", "balance": 1500.00 }
    """;                                           // raw string literal (C# 11): кавычки без экранирования
Console.WriteLine(path);
Console.WriteLine(json);
~~~

True | ACC-001, Анна Иванова, 1500.00 | ACC | True
C:\bank\data.txt

Короткий справочник методов, которые нужны каждый день:

| Нужно | Метод |
|---|---|
| Проверить на пустоту | `string.IsNullOrEmpty(s)`, `string.IsNullOrWhiteSpace(s)` |
| Обрезать пробелы | `Trim()`, `TrimStart()`, `TrimEnd()` |
| Разбить / склеить | `Split(...)`, `string.Join(sep, items)` |
| Найти | `Contains`, `IndexOf`, `StartsWith`, `EndsWith` (+ `StringComparison`) |
| Заменить | `Replace(old, new)` |
| Вырезать часть | `Substring(start, len)`, диапазон `s[1..4]` |
| Дополнить | `PadLeft(width, ch)`, `PadRight(...)` |
| Регистр | `ToUpperInvariant()`, `ToLowerInvariant()` (для технических строк) |
| Собрать | интерполяция `$"…"`, `string.Format`, `StringBuilder` |

**`null` и пустая строка — разные вещи.** `null` — «строки нет», `""` — «строка есть, но пустая». Конкатенация с `null` не падает: `null` трактуется как пустая строка. Вызов метода на `null` — `NullReferenceException`.

~~~csharp
string? maybe = null;
Console.WriteLine("[" + maybe + "]");                    // [] — null при склейке превращается в ""
Console.WriteLine(string.IsNullOrEmpty(maybe));          // True
Console.WriteLine(maybe?.Length ?? -1);                  // -1 — безопасный доступ
Console.WriteLine(string.Equals(maybe, null));           // True — null-безопасное сравнение
~~~
~~~console
[]
True
-1
True
~~~

**Срезы без копирования.** `Substring` создаёт новую строку (копирует символы). Если нужно только *прочитать* часть строки, `AsSpan()` даёт «окно» на ту же память без аллокации:

~~~csharp
string text = new string('x', 1000);

long before = GC.GetAllocatedBytesForCurrentThread();
string sub = text.Substring(0, 500);
long copyBytes = GC.GetAllocatedBytesForCurrentThread() - before;

before = GC.GetAllocatedBytesForCurrentThread();
ReadOnlySpan<char> window = text.AsSpan(0, 500);
long spanBytes = GC.GetAllocatedBytesForCurrentThread() - before;

Console.WriteLine($"Substring выделил память: {copyBytes > 1000}");
Console.WriteLine($"AsSpan выделил память: {spanBytes > 0}, длина окна {window.Length}");
~~~
~~~console
Substring выделил память: True
AsSpan выделил память: False, длина окна 500
~~~

`Span<T>` — тема следующих лет, но знать, что такой способ существует, полезно: парсеры и сериализаторы широко используют его, чтобы не создавать лишних строк.

## Как это работает под капотом

- **Устройство объекта `string`.** Это объект в куче с полями «длина» и последовательностью `char` прямо внутри объекта (не отдельный массив). Размер ≈ 22 байта служебных данных + 2 байта на символ. Пустая строка `""` тоже объект (общий экземпляр `string.Empty`).
- **Литералы.** Текст литерала хранится в метаданных сборки; инструкция IL `ldstr` при первом выполнении загружает его в пул интернирования и возвращает ссылку. Поэтому одинаковые литералы — один объект.
- **Константы времени компиляции.** `"hel" + "lo"` и `const string` склеиваются компилятором заранее — на этапе выполнения конкатенации нет.
- **Склейка `a + b + c`** превращается в один вызов `string.Concat(a, b, c)`: считается итоговая длина, выделяется ровно одна строка, символы копируются. Именно поэтому `+` вне цикла нормален.
- **Интерполяция** (`$"…{x}…"`) компилируется (с C# 10) в использование `DefaultInterpolatedStringHandler`: он пишет в буфер и в конце создаёт ровно одну итоговую строку; значения форматируются без боксинга.
- **`StringBuilder`** хранит текст как цепочку блоков `char[]`; `Append` дописывает в последний блок, при переполнении добавляет новый — поэтому амортизированно O(1), а `ToString()` собирает всё за O(n). Операции «в середину» (`Insert`, `Remove`) и индексатор по огромному билдеру — дороже.
- **Хэш-код строки** (`GetHashCode()`) в .NET Core+ намеренно **рандомизирован для каждого запуска процесса**. Нельзя сохранять его в базу или файл и сравнивать между запусками.
- **Сравнение `Ordinal`** — это сравнение массивов 16-битных значений, очень быстрое и векторизованное. **Культурные** сравнения идут через библиотеку локализации ОС (ICU/NLS) и заметно дороже.

Больше о стоимости аллокаций и работе с памятью — в справочнике: [аллокации](#/ref/g/rt-allocations), [стоимость операций](#/ref/g/pf-op-costs).

## Типичные ошибки и ловушки

:::danger Вызов метода без присваивания результата
`s.Trim();`, `s.Replace("a", "b");` без `s = ...` — частый баг новичков. Анализатор IDE подсвечивает такие вызовы предупреждением, не игнорируй их.
:::

:::danger `+=` в цикле на тысячи итераций
Для выписок, отчётов, CSV — `StringBuilder` или `string.Join`.
:::

:::danger `ToLower()`/`ToUpper()` для сравнения
Создаёт лишние строки и зависит от культуры. Используй `StringComparison.OrdinalIgnoreCase`.
:::

- **Культурно-зависимые методы по умолчанию.** `s.StartsWith("x")`, `s.IndexOf("x")` используют текущую культуру: могут быть медленнее и менять результат на другом компьютере. Для технических строк — `StringComparison.Ordinal`.
- **Числа и даты в строках без `InvariantCulture`.** `decimal.Parse("1.5")` на русской локали упадёт или вернёт другое значение. В файлах и API используй `CultureInfo.InvariantCulture`.
- **Хранение хэша строки.** `GetHashCode()` меняется между запусками.
- **Склеивание SQL строками.** `"... WHERE name = '" + input + "'"` — прямой путь к SQL-инъекции. Только параметры (Фаза 3).
- **Пароли и секреты в строках.** Строки неизменяемы и живут в памяти, пока их не соберёт GC; не логируй и не выводи их.
- **`Length` как «число символов».** Для эмодзи и составных символов это число единиц UTF-16.
- **Сравнение `==` с `null` для проверки «пусто».** Пустая и `null` — разные случаи; используй `IsNullOrEmpty`/`IsNullOrWhiteSpace`.
- **Изменяемость через `Span` и `unsafe`.** Технически возможна, но ломает гарантии (интернированные строки изменятся «для всех») — не делай так.

## Вопросы с собеседований

:::spoiler Почему `string` — reference type, но `==` сравнивает содержимое?
Для `string` оператор `==` перегружен: он сравнивает символы. Без перегрузки `==` сравнивал бы ссылки, как у обычных классов.
:::

:::spoiler Что такое string pool и какие строки туда попадают автоматически?
Таблица интернированных строк, которую ведёт рантайм: одинаковые значения хранятся в одном экземпляре. Автоматически туда попадают строковые литералы из кода (и константные выражения вроде `"hel" + "lo"`, которые компилятор склеивает заранее). Строки, созданные во время выполнения, попадают туда только через `string.Intern`.
:::

:::spoiler Почему склейка в цикле — O(n²), а `StringBuilder` — O(n)?
Каждая `+=` создаёт новую строку и копирует в неё всё накопленное: суммарно 1 + 2 + … + n копирований. `StringBuilder` дописывает в буфер и расширяет его с запасом (амортизированно O(1) на добавление), а итоговая строка создаётся один раз.
:::

:::spoiler Почему неизменяемость строк важна для Dictionary?
Хэш-код ключа вычисляется при вставке. Если бы ключ можно было изменить, его хэш изменился бы, и словарь искал бы элемент не в той «корзине» — элемент стал бы недостижимым.
:::

:::spoiler Строка — значимый или ссылочный тип? Почему тогда её «копирование» не создаёт общих проблем? (ловушка)
Ссылочный. Присваивание копирует ссылку, но так как строка неизменяема, «изменение» через одну переменную создаёт новую строку и не затрагивает другие переменные.
:::

:::spoiler Чем `string.Empty` отличается от `""` и от `null`?
`""` и `string.Empty` — пустая строка (один и тот же экземпляр), это валидный объект. `null` — отсутствие объекта; вызов метода на нём — `NullReferenceException`.
:::

:::spoiler Как правильно сравнивать строки без учёта регистра и почему не `ToLower()`?
`string.Equals(a, b, StringComparison.OrdinalIgnoreCase)`. `ToLower()` создаёт новую строку (аллокация) и зависит от культуры (турецкая «i»).
:::

:::spoiler Когда `StringBuilder` хуже простой конкатенации?
Для небольшого фиксированного числа частей: `a + b + c` превращается в один `Concat` и быстрее, чем создание билдера. `StringBuilder` выигрывает на циклах и неизвестном числе фрагментов.
:::

:::spoiler Что выведет `"😀".Length` и почему?
`2`: эмодзи кодируется в UTF-16 двумя единицами (суррогатная пара); `Length` считает `char`, а не символы Юникода.
:::

## Что запомнить

- `string` неизменяем: `Trim`, `Replace`, `ToUpper` возвращают **новую** строку — результат нужно присваивать.
- `==` у `string` сравнивает содержимое; литералы интернированы (один объект), строки из рантайма — нет; `string.Intern` — редкий инструмент.
- Технические строки сравнивай через `StringComparison.Ordinal*`; `ToLower() ==` — антипаттерн; помни про турецкую «i».
- Склейка в цикле — O(n²) и мусор; используй `StringBuilder`/`string.Join`. `a + b + c` вне цикла — один `Concat`, это нормально.
- `Length` — число единиц UTF-16, не «видимых символов».
- Числа и даты в файлах и API — с `InvariantCulture`.
- Никогда не склеивай SQL из пользовательского ввода; хэш строки не хранят между запусками.
