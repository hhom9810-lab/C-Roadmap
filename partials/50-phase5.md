:::why
async/await есть в каждой строке современного backend-кода, а тесты и CI отличают «проект студента» от «проекта, который можно поддерживать». На собеседовании почти гарантированы вопросы про `async void`, deadlock на `.Result` и «как ты тестируешь свой код».
:::

## Границы фазы {#borders}

:::deep Что НЕ входит в эту фазу
Устройство пула потоков и ExecutionContext, `ValueTask` в деталях, lock-free алгоритмы, модель памяти .NET, мутационное тестирование, «коллекционирование» всех паттернов GoF — **не сейчас**. Цель — уверенный прикладной уровень: правильный async, осмысленные тесты, паттерны по месту.
:::

## Практика фазы

- Покрыть тестами существующий проект Фазы 4 (не новый)
- CI: GitHub Actions гоняет тесты на каждый push и pull request

## Проект фазы

Доработка проекта Фазы 4 **или** новый сервис с асинхронной обработкой (фоновые задачи: обработка файлов, отправка уведомлений через очередь). Ключевое требование — **осмысленное тестовое покрытие ключевой бизнес-логики**, а не 100% → [техзадание](#p5-project).

## Критерий готовности {#criteria}

:::criteria Критерий готовности к фазе 6
- [ ] Можешь объяснить разницу `async Task` и `async void`, и почему второе — почти всегда ошибка
- [ ] Написано минимум 40–50 осмысленных unit-тестов суммарно по проектам, плюс несколько интеграционных
- [ ] CI настроен и зелёный
- [ ] Использован хотя бы один паттерн проектирования с объяснением, какую проблему он решил в твоём коде
:::
