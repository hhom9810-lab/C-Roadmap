:::why
`List<T>` — самая используемая коллекция в .NET. Понимание того, что внутри это обычный массив, сразу объясняет, какие операции дешёвые, а какие дорогие. Вопрос «какая сложность у `List.Add`?» с ответом «амортизированная O(1)» — классика собеседований.
:::

## Зачем это нужно

В реальном коде списки встречаются буквально в каждой строчке: заказы пользователя, строки файла, результаты запроса к базе, элементы корзины. Выбор между массивом, `List<T>` и чем-то иным определяет и читаемость, и скорость. Но главное — это **первая коллекция, внутренности которой нужно знать**, потому что на ней строится всё остальное: `Dictionary`, `HashSet`, `Queue` и `Stack` внутри устроены так же (массив + учёт заполненности + рост).

Что даёт понимание «внутри — массив»:

- ты сразу видишь, почему `list[i]` мгновенный, а `Insert(0, x)` в цикле на 100 000 элементов «подвисает»;
- ты понимаешь, зачем у `List<T>` есть `Capacity` и когда стоит указать начальную ёмкость;
- ты знаешь, почему нельзя менять список в `foreach` и как это делать правильно;
- ты можешь ответить на вопросы собеседования: сложность `Add`/`Insert`/`Remove`/`Contains`, амортизированная сложность, отличие массива от списка.

Кроме того, в реальных проектах часто выбирают «не ту» коллекцию просто по привычке: список ради поиска по ключу (`O(n)` вместо `O(1)`), список ради очереди (`RemoveAt(0)`). Эта тема даёт критерии выбора.

## Интуиция и аналогия

**Массив — вагон с фиксированным числом пронумерованных мест.** Пассажира по номеру места находят мгновенно: идёшь по вагону и сразу попадаешь на нужное место. Но если вагон заполнен, добавить место нельзя — нужно пересадить всех в вагон побольше.

**`List<T>` — оператор, который сам заказывает вагон побольше.** Заполнился вагон на 4 места — он заказывает вагон на 8, переносит всех туда (пересадка дорогая, но редкая) и продолжает сажать. Поскольку каждый новый вагон вдвое больше, пересадки случаются всё реже. Поэтому в среднем посадка одного пассажира стоит «почти ничего» — это и есть *амортизированная O(1)*.

А вот посадить человека на **первое место** при полном вагоне — значит сдвинуть всех на одно место вперёд. Каждый раз. Поэтому вставка в начало — дорогая, а в конец — дешёвая.

## Основная теория по шагам

### Шаг 1. Массив: основа всего

~~~csharp
int[] numbers = new int[5];          // 5 ячеек подряд в памяти, все равны 0
numbers[2] = 42;                     // O(1): адрес = начало + индекс × размер элемента
Console.WriteLine(numbers.Length);   // 5 — размер фиксирован навсегда

int[] more = { 1, 2, 3 };
try { more[3] = 4; }                 // массив не растёт
catch (IndexOutOfRangeException) { Console.WriteLine("IndexOutOfRangeException"); }
Console.WriteLine(string.Join(",", numbers));
~~~
~~~console
5
IndexOutOfRangeException
0,0,42,0,0
~~~

Массив — непрерывный блок памяти фиксированного размера. Доступ по индексу мгновенный, потому что адрес элемента вычисляется одной формулой. Но вставить элемент в середину или увеличить размер нельзя: можно только создать **новый** массив и скопировать данные.

Полезное про массивы:

- **Массив — reference type**, даже `int[]`: переменная хранит ссылку, `b = a` не копирует элементы (см. [тему про value/reference](#p1-types)).
- Значения по умолчанию: числа — `0`, `bool` — `false`, ссылки — `null`.
- Индексы с нуля; с C# 8 есть «индекс с конца» и диапазоны: `arr[^1]` — последний, `arr[1..3]` — элементы с 1-го по 2-й (диапазон создаёт **копию** для массива).
- Многомерные: прямоугольный `int[,]` (одна матрица) и «рваный» `int[][]` (массив массивов, строки разной длины).
- Вспомогательные методы: `Array.Sort`, `Array.IndexOf`, `Array.Copy`, `Array.Resize` (на самом деле создаёт новый массив), `Array.Reverse`, `Array.Fill`.

~~~csharp
int[,] grid = new int[2, 3];                 // прямоугольная матрица 2×3
grid[1, 2] = 7;
Console.WriteLine($"{grid.GetLength(0)}x{grid.GetLength(1)}, всего {grid.Length}");

int[][] jagged = new int[3][];               // «рваный» массив: строки разной длины
for (int i = 0; i < jagged.Length; i++) jagged[i] = new int[i + 1];
Console.WriteLine(string.Join(",", jagged.Select(r => r.Length)));

int[] arr = { 10, 20, 30, 40, 50 };
Console.WriteLine(arr[^1]);                  // 50 — последний
Console.WriteLine(string.Join(",", arr[1..4]));   // 20,30,40 — копия среза

int[] old = arr;
Array.Resize(ref arr, 8);                    // создан НОВЫЙ массив, старый остался
Console.WriteLine($"{arr.Length}, тот же массив: {ReferenceEquals(old, arr)}");
~~~
~~~console
2x3, всего 6
1,2,3
50
20,30,40
8, тот же массив: False
~~~

### Шаг 2. Как устроен `List<T>`

`List<T>` — обёртка над массивом, которая сама создаёт массив побольше, когда старый заполнился.

~~~csharp
var list = new List<int>();
Console.WriteLine(list.Capacity);    // 0 — массива ещё нет

for (int i = 1; i <= 9; i++)
{
    list.Add(i);
    Console.WriteLine($"Count = {list.Count}, Capacity = {list.Capacity}");
}
~~~
~~~console
0
Count = 1, Capacity = 4
Count = 2, Capacity = 4
Count = 3, Capacity = 4
Count = 4, Capacity = 4
Count = 5, Capacity = 8
Count = 6, Capacity = 8
Count = 7, Capacity = 8
Count = 8, Capacity = 8
Count = 9, Capacity = 16
~~~

- `Count` — сколько элементов реально лежит в списке.
- `Capacity` — размер внутреннего массива.
- Когда `Count == Capacity` и ты вызываешь `Add`, список выделяет новый массив **в 2 раза больше** (первое выделение — 4 ячейки) и копирует туда всё старое.

#### Почему `Add` — «амортизированная O(1)»

Большинство вызовов `Add` просто кладут элемент в свободную ячейку — O(1). Изредка происходит расширение — O(n), копируются все элементы. Но расширения случаются всё реже (на 4, 8, 16, 32… элементах). Если сложить работу за n добавлений, получится примерно 2n копирований, то есть **в среднем O(1) на одно добавление**. Это и называется амортизированной сложностью.

Посчитаем расширения руками для миллиона добавлений:

~~~csharp
var list = new List<int>();
int growths = 0, copied = 0;
for (int i = 0; i < 1_000_000; i++)
{
    int before = list.Capacity;
    list.Add(i);
    if (list.Capacity != before) { growths++; copied += before; }   // before элементов пришлось копировать
}
Console.WriteLine($"расширений: {growths}, скопировано элементов: {copied:N0} (это меньше 2 × 1 000 000: {copied < 2_000_000})");

var presized = new List<int>(1_000_000);        // если размер известен заранее — ни одного расширения
int before2 = presized.Capacity;
for (int i = 0; i < 1_000_000; i++) presized.Add(i);
Console.WriteLine($"ёмкость не менялась: {presized.Capacity == before2}");
~~~
~~~console
расширений: 19, скопировано элементов: 1,048,572 (это меньше 2 × 1 000 000: True)
ёмкость не менялась: True
~~~

:::tip Если размер известен заранее
`new List<Book>(capacity: 10_000)` сразу выделит нужный массив, и ни одного копирования при заполнении не будет. Для больших загрузок это заметная экономия. Методы `EnsureCapacity(n)` и `TrimExcess()` помогают подстроить ёмкость позже.
:::

### Шаг 3. Что умеет `List<T>`

Основные операции:

| Нужно | Метод |
|---|---|
| Добавить | `Add(x)`, `AddRange(items)`, `Insert(i, x)` |
| Удалить | `Remove(x)`, `RemoveAt(i)`, `RemoveAll(pred)`, `Clear()` |
| Найти | `Contains(x)`, `IndexOf(x)`, `Find(pred)`, `FindAll(pred)`, `Exists(pred)` |
| Упорядочить | `Sort()`, `Sort(comparison)`, `Reverse()` |
| Бинарный поиск | `BinarySearch(x)` (только в отсортированном списке) |
| Копировать часть | `GetRange(i, n)`, `ToArray()`, `new List<T>(other)` |

~~~csharp
var people = new List<(string Name, int Age)> { ("Борис", 30), ("Анна", 25), ("Вера", 30), ("Глеб", 22) };

people.Sort((a, b) => a.Age.CompareTo(b.Age));                     // сортировка на месте по возрасту
Console.WriteLine(string.Join(", ", people.Select(p => p.Name)));

var sorted = people.OrderByDescending(p => p.Age).ThenBy(p => p.Name).ToList();   // LINQ — новый список, стабильно
Console.WriteLine(string.Join(", ", sorted.Select(p => p.Name)));

var nums = new List<int> { 1, 3, 5, 7, 9 };
Console.WriteLine(nums.BinarySearch(7));        // 3 — индекс найденного
int idx = nums.BinarySearch(4);                 // не найден → отрицательное число
Console.WriteLine(idx);                          // -3 = ~2: побитовое дополнение индекса, где элемент стоял бы
Console.WriteLine(~idx);                         // 2 — позиция вставки, сохраняющая порядок
~~~
~~~console
Глеб, Анна, Борис, Вера
Борис, Вера, Анна, Глеб
3
-3
2
~~~

Важные нюансы: `List<T>.Sort()` — **неустойчивая** сортировка (равные элементы могут поменяться местами), а LINQ `OrderBy` — устойчивая. `BinarySearch` на неотсортированном списке даёт мусор без ошибки.

#### Стоимость операций

| Операция | Сложность | Почему |
|---|---|---|
| `list[i]`, `list[i] = x` | O(1) | индекс в массиве |
| `Add(x)` | O(1) амортизированно | редкие расширения |
| `Insert(0, x)` | O(n) | все элементы сдвигаются вправо |
| `RemoveAt(list.Count - 1)` | O(1) | удаление с конца, сдвигать нечего |
| `RemoveAt(0)` | O(n) | все элементы сдвигаются влево |
| `Remove(x)` | O(n) | сначала поиск, потом сдвиг |
| `Contains(x)`, `IndexOf(x)` | O(n) | перебор подряд |
| `Sort()` | O(n log n) | интроспективная сортировка |
| `BinarySearch(x)` | O(log n) | только на **отсортированном** списке |

~~~text Insert(1, 99) в список [10, 20, 30, 40]
 до:    [10][20][30][40][  ]
 сдвиг:  10 [  ][20][30][40]   ← каждый элемент после индекса 1 переезжает
 после: [10][99][20][30][40]
~~~

Проверим, что разница — не теория. Вставка в начало 30 000 раз и добавление в конец 30 000 раз:

~~~csharp
using System.Diagnostics;

const int N = 30_000;
var sw = Stopwatch.StartNew();
var front = new List<int>();
for (int i = 0; i < N; i++) front.Insert(0, i);        // каждый раз сдвигает все элементы
long tFront = sw.ElapsedTicks;

sw.Restart();
var back = new List<int>();
for (int i = 0; i < N; i++) back.Add(i);
long tBack = sw.ElapsedTicks;

Console.WriteLine($"{front.Count} {back.Count}");
Console.WriteLine($"Insert(0, x) медленнее Add более чем в 20 раз: {tFront > 20 * tBack}");
~~~
~~~console
30000 30000
Insert(0, x) медленнее Add более чем в 20 раз: True
~~~

### Шаг 4. Изменение во время перебора

~~~csharp
var books = new List<string> { "A", "B", "C" };
try
{
    foreach (var b in books) if (b == "B") books.Remove(b);   // ❌ InvalidOperationException
}
catch (InvalidOperationException) { Console.WriteLine("нельзя менять список в foreach"); }

books = new List<string> { "A", "B", "C" };
books.RemoveAll(b => b == "B");                               // ✅ один проход, O(n)

for (int i = books.Count - 1; i >= 0; i--)                    // ✅ цикл с конца
    if (books[i] == "C") books.RemoveAt(i);
Console.WriteLine(string.Join(",", books));
~~~
~~~console
нельзя менять список в foreach
A
~~~

Внутри `List<T>` есть счётчик версий: любое изменение его увеличивает, а перечислитель `foreach` проверяет, не изменилась ли версия. Это защита от трудноуловимых багов. Идём с конца, чтобы сдвиг после удаления не пропускал соседние элементы.

### Шаг 5. Копии и вложенные списки

`new List<T>(other)` и `ToList()` создают **новый список**, но элементы — те же ссылки (поверхностная копия):

~~~csharp
var orig = new List<List<int>> { new() { 1, 2 }, new() { 3 } };
var copy = new List<List<int>>(orig);          // новый внешний список...
copy[0].Add(99);                               // ...но внутренние списки общие
Console.WriteLine(orig[0].Count);

var ints = new List<int> { 1, 2, 3 };
var intsCopy = ints.ToList();
intsCopy[0] = 100;                             // для значимых типов копируются сами значения
Console.WriteLine(ints[0]);
~~~
~~~console
3
1
~~~

Ловушка массивов: **ковариантность**. Массив строк можно присвоить переменной `object[]`, но запись в него неподходящего типа проверяется во время выполнения:

~~~csharp
object[] objects = new string[2];              // компилируется: массивы ковариантны
try { objects[0] = 42; }                       // а в рантайме — исключение
catch (ArrayTypeMismatchException) { Console.WriteLine("ArrayTypeMismatchException"); }
~~~
~~~console
ArrayTypeMismatchException
~~~

У `List<T>` такой проблемы нет (generics инвариантны, ошибка видна при компиляции).

### Шаг 6. Срезы без копирования

Диапазоны `arr[1..4]` создают копию. Если нужно «окно» в тот же массив без аллокации — `Span<T>`:

~~~csharp
int[] data = { 1, 2, 3, 4, 5 };
Span<int> window = data.AsSpan(1, 3);          // элементы 2,3,4 — НЕ копия
window[0] = 99;
Console.WriteLine(string.Join(",", data));
~~~
~~~console
1,99,3,4,5
~~~

`Span<T>` — тема продвинутого уровня (парсинг, буферы, высоконагруженный код); для списка есть `CollectionsMarshal.AsSpan(list)`. На этой фазе достаточно знать, что такой инструмент есть.

### Шаг 7. Массив, `List<T>` или что-то ещё

- **Массив** — размер известен и не меняется, нужна максимальная простота (буфер, матрица, результат `ToArray()`).
- **`List<T>`** — размер меняется, доступ по индексу, добавление в конец. Выбор по умолчанию.
- Частое **удаление из начала** (очередь) → [`Queue<T>`](#p2-collections); частые вставки и удаления в середине при известном узле → `LinkedList<T>` (но только если это действительно нужно).
- Частый поиск «есть ли элемент» → [`HashSet<T>`](#p2-dictionary).
- Поиск по ключу → [`Dictionary<TKey, TValue>`](#p2-dictionary).
- Отдавать наружу, не позволяя менять → `IReadOnlyList<T>` (см. [инкапсуляцию](#p1-encapsulation)).

:::deep Граница
`CollectionsMarshal.AsSpan`, `ArrayPool<T>`, устройство `Array.Sort` (introsort) в деталях — для performance-работы. Сейчас достаточно таблицы сложностей.
:::

## Как это работает под капотом

- **Поля `List<T>`.** По сути три: `T[] _items`, `int _size`, `int _version`. `Count` возвращает `_size`, `Capacity` — `_items.Length`. `Add` проверяет `_size < _items.Length`, при нехватке вызывает `Grow` (новая ёмкость — удвоенная, минимум 4), копирует старые данные через `Array.Copy` и записывает элемент; `_version++` защищает перечислитель.
- **Массив — объект в куче** с полями «длина» и данными подряд. Элементы `int[]` лежат прямо в нём, без упаковки; для ссылочных типов — массив ссылок. Доступ по индексу — проверка границ плюс одно смещение; JIT часто убирает проверку в простых циклах.
- **Сдвиг при `Insert`/`RemoveAt`** — это `Array.Copy` внутри одного массива: быстрая блочная копия памяти (`memmove`), поэтому небольшие списки сдвигаются быстро, но стоимость растёт линейно.
- **Большие массивы.** Объекты от ~85 000 байт попадают в кучу больших объектов (LOH), которая собирается редко и дороже. Список на 100 000 `int` (≈400 КБ) уже в LOH; при каждом удвоении выделяется новый большой массив — ещё один довод указывать `capacity` заранее.
- **Локальность кэша.** Элементы лежат подряд, процессор подгружает их пачками — перебор `List<T>` обычно **быстрее**, чем перебор «теоретически равных» структур с узлами (`LinkedList`) — см. [когда Big-O обманывает](#/ref/g/pf-bigo-lies).
- **`foreach` по `List<T>`** использует структуру-перечислитель (`List<T>.Enumerator`, `struct`), поэтому не создаёт мусор; при обходе через `IEnumerable<T>` она упаковывается.
- **Расширение — не «realloc».** .NET не умеет увеличивать массив на месте: всегда новая аллокация и копирование, а старый массив уходит в мусор.

Справочник: [List и массивы](#/ref/e/co-list), [сложность коллекций](#/ref/e/co-complexity), [стек и куча](#/ref/g/rt-stack-heap).

## Типичные ошибки и ловушки

- **`Insert(0, x)` / `RemoveAt(0)` в цикле.** O(n²) на ровном месте. Очередь — `Queue<T>`; нужно в обратном порядке — добавляй в конец и `Reverse()` один раз.
- **`Contains` внутри цикла.** `list.Contains(x)` в цикле по другому списку — O(n·m). Положи данные в `HashSet<T>`.
- **Изменение списка в `foreach`.** `InvalidOperationException`; используй `RemoveAll`, цикл с конца или новый список.
- **Список ради поиска по ключу.** `list.First(x => x.Id == id)` — O(n) на каждый поиск; для частых поисков — `Dictionary<int, T>`.
- **Игнорирование `Capacity` при массовой загрузке.** Миллион добавлений без указания ёмкости — десятки расширений и мусорные массивы в LOH.
- **Путаница `Count` и `Length`.** У массива — `Length`, у `List<T>` и остальных коллекций — `Count`; LINQ `Count()` — метод (может перебирать).
- **Возврат внутреннего списка наружу.** Вызывающий код может менять твоё состояние; отдавай `AsReadOnly()`/`IReadOnlyList<T>`.
- **Поверхностная копия.** `new List<T>(other)` не клонирует элементы-объекты.
- **`BinarySearch` без сортировки.** Результат бессмысленный, и ошибки нет.
- **Бесконечная «большая» коллекция.** Список, куда только добавляют (кэш, лог в памяти), без ограничения рано или поздно съедает память.
- **Забыть про `ToList()` у отложенных запросов.** `var x = items.Where(...)` — не список, а запрос, который выполнится при переборе (тема про LINQ).

## Вопросы с собеседований

:::spoiler Почему `list.Insert(0, x)` в цикле на 100 000 элементов работает медленно?
Каждая вставка в начало сдвигает все существующие элементы: O(n) на вставку, O(n²) на весь цикл. Если нужно часто добавлять в начало — `LinkedList<T>`, `Queue`/`Stack` или добавление в конец с последующим `Reverse()`.
:::

:::spoiler Чем `Count` отличается от `Capacity`?
`Count` — число элементов, `Capacity` — размер внутреннего массива. `Capacity >= Count` всегда.
:::

:::spoiler Что значит «амортизированная O(1)»?
Отдельная операция иногда стоит O(n), но суммарная стоимость n операций — O(n), то есть в среднем O(1) на операцию.
:::

:::spoiler Чем массив отличается от `List<T>`? (ловушка: «список просто удобнее»)
Массив имеет фиксированный размер и минимальные накладные расходы; `List<T>` — обёртка над массивом с автоматическим ростом (Count/Capacity), методами `Add/Insert/Remove` и счётчиком версий. Они оба дают O(1) доступ по индексу; но у `List<T>` вставка/удаление могут стоить O(n), а `Add` — амортизированная O(1).
:::

:::spoiler Во сколько раз растёт `List<T>` при заполнении и почему именно так?
В 2 раза (первое выделение — 4 элемента). Геометрический рост даёт амортизированную O(1): суммарное копирование за n добавлений — порядка 2n. Рост на константу (например, +10) дал бы O(n²).
:::

:::spoiler Почему `RemoveAt(list.Count - 1)` быстрый, а `RemoveAt(0)` медленный?
Удаление последнего не требует сдвига; удаление первого сдвигает все оставшиеся элементы на одну позицию влево.
:::

:::spoiler Как безопасно удалить из списка элементы во время обхода?
`RemoveAll(predicate)`, либо цикл `for` с конца, либо построить новый список через `Where(...).ToList()`. В `foreach` менять коллекцию нельзя (InvalidOperationException из-за версии).
:::

:::spoiler Устойчива ли `List<T>.Sort()`? А `OrderBy`?
`List<T>.Sort()` — нет (introsort), `OrderBy` в LINQ — да. Если важен порядок равных элементов — `OrderBy().ThenBy()`.
:::

:::spoiler Можно ли присвоить `string[]` переменной `object[]`? Что дальше?
Да (ковариантность массивов), но запись элемента неподходящего типа в рантайме даст `ArrayTypeMismatchException`. У `List<string>` присвоить `List<object>` нельзя вообще.
:::

## Что запомнить

- Массив — фиксированный непрерывный блок: индекс O(1), размер менять нельзя (только создать новый).
- `List<T>` = массив + `Count` + рост ×2: `Add` — амортизированная O(1), `Insert`/`RemoveAt` не в конце — O(n), `Contains`/`Remove` — O(n).
- Знаешь размер — укажи `capacity`; не менять список в `foreach` (`RemoveAll`, цикл с конца).
- `Sort` не устойчива, `OrderBy` устойчива; `BinarySearch` — только на отсортированном.
- Копия списка — поверхностная; наружу отдавай `IReadOnlyList<T>`.
- Для частого поиска — `HashSet`/`Dictionary`, для очереди — `Queue`, не `List.RemoveAt(0)`.
- Данные подряд в памяти → перебор списка быстрый (кэш процессора).

:::why
Это **первый пункт критерия** фазы: объяснить, почему `Dictionary` в среднем O(1), а в худшем — нет. Хэш-таблицы стоят за кэшами, индексами баз данных, дедупликацией и половиной алгоритмических задач («используй словарь, чтобы найти пару за O(n)»).
:::

## Зачем это нужно

Представь библиотеку на 100 000 читателей. Нужно по номеру билета найти карточку читателя. В `List<Reader>` придётся перебирать — в худшем случае 100 000 сравнений на каждый поиск. В `Dictionary<string, Reader>` — одно-два сравнения. Разница не «в разы», а **на порядки**, и она растёт вместе с данными.

Словарь и множество — рабочие лошадки практически любого бэкенда:

- **кэш**: «по ключу запроса отдай готовый ответ»;
- **индекс**: «по Id найти объект», вместо повторных `First(x => x.Id == id)`;
- **дедупликация**: «были ли мы здесь раньше?» (`HashSet`);
- **группировка и подсчёт**: частоты слов, сумма по категориям;
- **алгоритмические задачи**: Two Sum, анаграммы, «первый неповторяющийся символ».

Плюс отдельная причина знать устройство: свой класс в роли ключа **ломается тихо**, если неправильно написан `GetHashCode`/`Equals`. Ошибка не падает с исключением — просто элемент «не находится». Эта тема учит не попадать в такие ловушки и объяснять, почему `Dictionary` быстрый.

## Интуиция и аналогия

**Гардероб с номерками.** Приходишь в театр, сдаёшь куртку, получаешь номерок, и гардеробщик вешает её на крючок с этим номером. Чтобы забрать, не нужно перебирать все куртки — идёшь прямо к своему крючку.

Хэш-таблица — гардероб, где номерок вычисляется **из самого ключа** (формулой, хэш-функцией). Не нужно хранить «карту», куда что положили: по ключу формула каждый раз даёт один и тот же номер.

Коллизия — когда формула двум разным людям дала один и тот же номер крючка. Тогда на одном крючке висят две куртки, и гардеробщик смотрит, какая из них твоя (`Equals`). Если коллизий мало, это быстро. Если формула плохая и **всем** даёт крючок №1, гардероб превращается в одну огромную кучу — поиск вернулся к перебору.

Изменяемый ключ — это если после сдачи куртки у тебя поменялся номерок. Куртка висит на старом крючке, а ты приходишь к новому — гардеробщик разводит руками.

## Основная теория по шагам

### Шаг 1. Идея хэш-таблицы

Задача: по ключу (номеру читательского билета) мгновенно найти значение (читателя), не перебирая всех.

1. Из ключа вычисляем **хэш-код** — целое число (`key.GetHashCode()`).
2. Превращаем хэш в номер **корзины** (bucket): примерно `bucket = |hash| % количество_корзин`.
3. Кладём пару «ключ–значение» в эту корзину.
4. При поиске повторяем шаги 1–2 и смотрим только в одну корзину.

~~~text Вставка ключей в таблицу из 7 корзин
 ключ "R-102" → hash 918273 → 918273 % 7 = 3
 ключ "R-517" → hash 554410 → 554410 % 7 = 0
 ключ "R-044" → hash 102340 → 102340 % 7 = 3   ← КОЛЛИЗИЯ: та же корзина

 корзина 0: [R-517]
 корзина 1:
 корзина 2:
 корзина 3: [R-102] → [R-044]       ← цепочка: при поиске сравниваем по Equals
 корзина 4:
 ...
~~~

Числа хэшей в схеме условные. Важно главное: поиск — это **вычисление хэша + просмотр одной корзины**, а не перебор всех элементов.

**Коллизия** — два разных ключа попали в одну корзину. Это нормально и неизбежно: возможных ключей бесконечно много, корзин конечное число. `Dictionary<TKey, TValue>` разбирается с коллизиями так: внутри корзины ключи образуют цепочку, а при поиске каждый ключ цепочки сравнивается через `Equals`.

### Шаг 2. Простое использование без исключений

~~~csharp
var stock = new Dictionary<string, int>(StringComparer.OrdinalIgnoreCase)
{
    ["978-5-17-090630-7"] = 3,
};

if (stock.TryGetValue("978-5-17-090630-7", out int count))
    Console.WriteLine($"найден: {count}");

try { int n = stock["нет-такого"]; }                       // индексатор бросает исключение
catch (KeyNotFoundException) { Console.WriteLine("KeyNotFoundException"); }

stock["978-5-389-07435-4"] = 1;                            // индексатор: добавить ИЛИ перезаписать
try { stock.Add("978-5-389-07435-4", 5); }                 // Add на существующий ключ — ошибка
catch (ArgumentException) { Console.WriteLine("ArgumentException"); }

bool added = stock.TryAdd("978-5-389-07435-4", 5);         // безопасный вариант
Console.WriteLine($"TryAdd: {added}, значение осталось {stock["978-5-389-07435-4"]}");

Console.WriteLine(stock.ContainsKey("978-5-17-090630-7".ToLower()));   // компаратор без учёта регистра
~~~
~~~console
найден: 3
KeyNotFoundException
ArgumentException
TryAdd: False, значение осталось 1
True
~~~

Коротко о методах:

- `dict[key]` — получить (исключение, если нет) или записать (добавит/перезапишет).
- `TryGetValue(key, out v)` — **один** поиск вместо двух (`ContainsKey` + индексатор). Предпочитай его.
- `Add` — только если ключа заведомо нет; `TryAdd` — безопасная версия.
- `GetValueOrDefault(key)` — значение или `default`; `Remove(key)` — удалить.
- Перебор `foreach (var (k, v) in dict)` отдаёт пары `KeyValuePair<TKey,TValue>`; свойства `Keys`/`Values` — коллекции без копирования.

`StringComparer.OrdinalIgnoreCase` в конструкторе делает ключи нечувствительными к регистру. Компаратор отвечает **и за хэш, и за сравнение**, поэтому нельзя «подменять» его потом.

### Шаг 3. Подсчёт частот и группировка

Самый частый приём со словарями — счётчик:

~~~csharp
var words = "мир труд май мир май мир".Split(' ');

var freq = new Dictionary<string, int>();
foreach (var w in words)
    freq[w] = freq.GetValueOrDefault(w) + 1;      // нет ключа → 0, прибавляем 1

foreach (var (word, n) in freq.OrderByDescending(p => p.Value).ThenBy(p => p.Key))
    Console.WriteLine($"{word}: {n}");

// группировка: ключ → список значений
var byLen = new Dictionary<int, List<string>>();
foreach (var w in words.Distinct())
{
    if (!byLen.TryGetValue(w.Length, out var list))
        byLen[w.Length] = list = new List<string>();
    list.Add(w);
}
Console.WriteLine(string.Join("; ", byLen.OrderBy(p => p.Key).Select(p => $"{p.Key} → {string.Join(",", p.Value)}")));
~~~
~~~console
мир: 3
май: 2
труд: 1
3 → мир,май; 4 → труд
~~~

Порядок перебора обычного `Dictionary` формально **не гарантирован** (на практике это порядок вставки, пока ничего не удаляли, но полагаться на него нельзя). Нужен порядок — сортируй явно, как выше, либо возьми `SortedDictionary<TKey,TValue>` (O(log n) на операцию) — подробнее [в теме про другие коллекции](#p2-collections).

Два более коротких способа решить те же задачи — LINQ `GroupBy`/`ToDictionary` и `CollectionsMarshal.GetValueRefOrAddDefault`; оба разберёшь позже.

### Шаг 4. Почему O(1) в среднем и O(n) в худшем

- **В среднем.** Хэш-функция раскидывает ключи равномерно, а таблица расширяется, когда элементов становится слишком много на корзину. Цепочки получаются короткими (1–2 элемента), поиск — O(1).
- **В худшем.** Если у всех ключей **одинаковый хэш**, все они в одной корзине, и поиск превращается в перебор цепочки — **O(n)**, а заполнение словаря на n элементов — O(n²).
- **Расширение.** Когда внутренние массивы заполнены, `Dictionary` создаёт таблицы примерно вдвое больше (размер — простое число) и перераскладывает все элементы. Как и у `List<T>`, это даёт амортизированную O(1) на вставку.

Проверим на практике, но без нестабильных замеров времени. Вместо секундомера **посчитаем вызовы `Equals`** — именно столько лишней работы делает словарь:

~~~csharp
const int N = 2000;

var good = new Dictionary<GoodKey, int>();
for (int i = 0; i < N; i++) good[new GoodKey(i)] = i;
GoodKey.Calls = 0;
for (int i = 0; i < N; i++) _ = good[new GoodKey(i)];

var bad = new Dictionary<BadKey, int>();
for (int i = 0; i < N; i++) bad[new BadKey(i)] = i;
BadKey.Calls = 0;
for (int i = 0; i < N; i++) _ = bad[new BadKey(i)];

Console.WriteLine($"хороший хэш: {GoodKey.Calls} вызовов Equals на {N} поисков");
Console.WriteLine($"плохой хэш : больше миллиона вызовов Equals — {BadKey.Calls > 1_000_000}");
Console.WriteLine($"плохой хэш : больше, чем у хорошего, в сотни раз — {BadKey.Calls > 100L * GoodKey.Calls}");

sealed class GoodKey(int id)
{
    public static long Calls;
    public int Id { get; } = id;
    public override bool Equals(object? obj) { Calls++; return obj is GoodKey o && o.Id == Id; }
    public override int GetHashCode() => Id;              // равномерно: разные Id → разные хэши
}

sealed class BadKey(int id)
{
    public static long Calls;
    public int Id { get; } = id;
    public override bool Equals(object? obj) { Calls++; return obj is BadKey o && o.Id == Id; }
    public override int GetHashCode() => 1;               // ❌ все ключи в одной корзине
}
~~~
~~~console
хороший хэш: 2000 вызовов Equals на 2000 поисков
плохой хэш : больше миллиона вызовов Equals — True
плохой хэш : больше, чем у хорошего, в сотни раз — True
~~~

На хорошем хэше каждый поиск стоит ровно один вызов `Equals` (нашли нужный ключ в корзине). На плохом поиск ключа с номером `k` проходит цепочку примерно до `k`-го элемента, итого около N²/2 вызовов — в тысячи раз больше. В реальном времени это превращается в секунды вместо миллисекунд.

### Шаг 5. Контракт `GetHashCode` + `Equals`

Если ты используешь свой класс как ключ словаря или элемент `HashSet`, обязательны **оба** метода, и они должны быть согласованы:

1. Если `a.Equals(b)`, то `a.GetHashCode() == b.GetHashCode()`. **Обязательно.**
2. Если хэши равны, объекты **не обязаны** быть равны (это коллизия).
3. Хэш объекта не должен меняться, пока объект лежит в словаре.
4. `GetHashCode` должен быть дешёвым и стабильным в рамках одного запуска программы (между запусками значения могут различаться — хэши строк в .NET рандомизируются, не сохраняй их в БД и файлы).

~~~csharp
var a = new Isbn("978-5-17-090630-7");
var b = new Isbn("978-5-17-090630-7");

var set = new HashSet<Isbn> { a };
Console.WriteLine(set.Contains(b));                       // True — Equals и GetHashCode согласованы
Console.WriteLine(a == b);                                // False — оператор == мы не переопределяли
Console.WriteLine(a.Equals(b));                           // True

var badSet = new HashSet<OnlyEquals> { new OnlyEquals("x") };
Console.WriteLine(badSet.Contains(new OnlyEquals("x")));  // False: Equals есть, GetHashCode — нет

var rec = new HashSet<IsbnRec> { new IsbnRec("978-5") };
Console.WriteLine(rec.Contains(new IsbnRec("978-5")));    // True — всё сгенерировал record

public sealed class Isbn : IEquatable<Isbn>
{
    public string Value { get; }
    public Isbn(string value) => Value = value.Replace("-", "");

    public bool Equals(Isbn? other) => other is not null && Value == other.Value;
    public override bool Equals(object? obj) => Equals(obj as Isbn);
    public override int GetHashCode() => Value.GetHashCode();
}

public sealed class OnlyEquals(string v)
{
    public string V { get; } = v;
    public override bool Equals(object? obj) => obj is OnlyEquals o && o.V == V;
    // GetHashCode не переопределён → хэш зависит от ссылки на объект
}

public record IsbnRec(string Value);
~~~
~~~console
True
False
True
False
True
~~~

:::danger Переопределил только `Equals`
Тогда два «равных» объекта дадут разные хэши (по умолчанию хэш зависит от ссылки), попадут в разные корзины, и `Contains`/`TryGetValue` вернут `false`. Компилятор выдаёт предупреждение CS0659 — не игнорируй его. Обратная ошибка (хэш есть, `Equals` по умолчанию) тоже беда: объекты с равными данными будут считаться разными.
:::

:::tip Проще всего — `record`
`record Isbn(string Value);` генерирует согласованные `Equals`, `GetHashCode` и `==` автоматически — по всем полям. Для нескольких полей вручную используй `HashCode.Combine(Field1, Field2)`. Для структур (`record struct`) то же самое работает без выделения памяти.
:::

`IEquatable<T>` нужен не для корректности, а для скорости и чистоты: `Dictionary` и `HashSet` вызывают типизированный `Equals(Isbn?)`, и для структур это избавляет от упаковки.

### Шаг 6. Изменяемый ключ — потерянный элемент

~~~csharp
var key = new MutableKey { Id = 1 };
var dict = new Dictionary<MutableKey, string> { [key] = "книга" };

key.Id = 2;                                   // хэш изменился, а элемент лежит в старой корзине
Console.WriteLine(dict.ContainsKey(key));     // False — элемент «потерян»
Console.WriteLine(dict.Count);                // 1 — но он там есть
Console.WriteLine(dict.Keys.Count(k => ReferenceEquals(k, key)));   // 1 — через перебор находится

key.Id = 1;                                   // вернули значение — снова находится
Console.WriteLine(dict.ContainsKey(key));

class MutableKey
{
    public int Id { get; set; }
    public override bool Equals(object? o) => o is MutableKey k && k.Id == Id;
    public override int GetHashCode() => Id;
}
~~~
~~~console
False
1
1
True
~~~

Ключи словаря должны быть **неизменяемыми**: строки, числа, `record`-ы с `init`-свойствами, `readonly struct`. Если приходится брать изменяемый объект — используй его неизменяемый идентификатор (`Id`) как ключ, а не сам объект.

### Шаг 7. `HashSet<T>` — словарь без значений

~~~csharp
var borrowed = new HashSet<string> { "B-1", "B-7", "B-9" };
var damaged  = new HashSet<string> { "B-7", "B-12" };

Console.WriteLine(borrowed.Contains("B-7"));     // O(1)
Console.WriteLine(borrowed.Add("B-1"));          // False — дубликаты не добавляются

var both = new HashSet<string>(borrowed);
both.IntersectWith(damaged);                      // пересечение
Console.WriteLine(string.Join(",", both));

borrowed.UnionWith(damaged);                      // объединение
Console.WriteLine(string.Join(",", borrowed.OrderBy(x => x)));

var onlyBorrowed = new HashSet<string>(borrowed);
onlyBorrowed.ExceptWith(damaged);                 // разность
Console.WriteLine(string.Join(",", onlyBorrowed.OrderBy(x => x)));
Console.WriteLine(new HashSet<int> { 1, 2 }.IsSubsetOf(new[] { 1, 2, 3 }));
~~~
~~~console
True
False
B-7
B-1,B-12,B-7,B-9
B-1,B-9
True
~~~

Классический приём: заменить `list.Contains(x)` внутри цикла (O(n·m)) на `HashSet` (O(n + m)). Подробнее — в [Big O на практике](#p2-bigo). Решение Two Sum — словарь «значение → индекс»:

~~~csharp
static int[] TwoSum(int[] nums, int target)
{
    var seen = new Dictionary<int, int>();           // значение → индекс
    for (int i = 0; i < nums.Length; i++)
    {
        if (seen.TryGetValue(target - nums[i], out int j)) return new[] { j, i };
        seen[nums[i]] = i;
    }
    return Array.Empty<int>();
}
Console.WriteLine(string.Join(",", TwoSum(new[] { 2, 7, 11, 15 }, 9)));

static bool HasDuplicate(IEnumerable<int> xs)
{
    var set = new HashSet<int>();
    foreach (var x in xs) if (!set.Add(x)) return true;   // Add вернул false → уже был
    return false;
}
Console.WriteLine(HasDuplicate(new[] { 1, 2, 3, 1 }));
~~~
~~~console
0,1
True
~~~

Один проход, O(n) времени и O(n) памяти — вместо двух вложенных циклов O(n²).

:::deep Граница
Открытая адресация против цепочек, рандомизация хэшей строк, `FrozenDictionary`, `ConcurrentDictionary`, `SortedDictionary` — интересно, но для Фазы 2 достаточно модели «хэш → корзина → цепочка → Equals».
:::

## Как это работает под капотом

- **Два массива.** В современном .NET `Dictionary<TKey,TValue>` хранит `int[] _buckets` и `Entry[] _entries`. Каждая `Entry` — структура `{ hashCode, next, key, value }`. В `_buckets[i]` лежит индекс первой записи цепочки, а `next` ведёт к следующей — цепочки организованы **индексами внутри массива**, а не отдельными объектами-узлами. Поэтому словарь компактнее и дружелюбнее к кэшу, чем «список объектов в каждой корзине».
- **Поиск.** `hash = comparer.GetHashCode(key)` → `bucket = hash % _buckets.Length` → по цепочке сравнить сначала сохранённый `hashCode` (дешёвое целое сравнение), и только при совпадении вызвать `Equals`. Поэтому на хорошем хэше `Equals` вызывается около одного раза.
- **Расширение.** Когда записи кончились, размер увеличивается примерно вдвое до ближайшего простого числа, а все записи перераскладываются по новым корзинам — это дорогая, но редкая операция. Знаешь число элементов — передай `capacity` в конструктор.
- **Удаление.** Освободившиеся записи образуют список свободных ячеек (`_freeList`) и переиспользуются; именно поэтому порядок перебора после `Remove` и новых `Add` может «перепутаться».
- **Строки.** Хэш строки по умолчанию **рандомизируется** при каждом запуске процесса (защита от атак, подбирающих коллизии). Значит, `"abc".GetHashCode()` различается между запусками — не сохраняй хэши на диск и не используй их как стабильный идентификатор.
- **Структуры как ключи.** Для `struct` без своего `GetHashCode` используется реализация по умолчанию, которая может оказаться медленной (рефлексия/первое поле); у `record struct` и кортежей `(int, int)` всё сгенерировано корректно.
- **`HashSet<T>`** внутри устроен так же, как словарь: массив корзин + массив записей, только без значения.

Справочник: [Dictionary и HashSet](#/ref/e/co-dictionary), [сложность коллекций](#/ref/e/co-complexity), [равенство и хэш-коды](#/ref/e/co-equality).

## Типичные ошибки и ловушки

- **Переопределили `Equals`, забыли `GetHashCode`** (и наоборот). Элементы «не находятся». Предупреждение CS0659 — не шум.
- **`GetHashCode() => 1`** «чтобы было проще». Словарь вырождается в список, всё O(n²).
- **Изменяемый ключ.** Менять поля, влияющие на хэш, после вставки нельзя.
- **`dict[key]` вместо `TryGetValue`.** `KeyNotFoundException` в рабочем коде; либо двойной поиск через `ContainsKey` + индексатор.
- **`Add` на существующий ключ.** `ArgumentException`; если важна перезапись — индексатор, если важно не трогать — `TryAdd`.
- **Опора на порядок перебора.** Он не гарантируется; нужна упорядоченность — `SortedDictionary` или явная сортировка.
- **Изменение словаря в `foreach`.** Добавление/удаление при обходе даёт `InvalidOperationException` (удаление через `Remove` во время перебора в современных версиях допустимо, но не рассчитывай на это — собери ключи в список и удаляй после).
- **Регистр ключей.** `"ABC"` и `"abc"` — разные ключи; для нечувствительности передай `StringComparer.OrdinalIgnoreCase`. Не используй `ToLower()` на каждом поиске — это лишние аллокации.
- **`null`-ключ.** `Dictionary` не допускает `null` как ключ (`ArgumentNullException`).
- **Словарь из многопоточного кода.** Параллельная запись без синхронизации ломает структуру; нужен `ConcurrentDictionary` или `lock`.
- **Использование дробных чисел как ключей.** `0.1 + 0.2` и `0.3` — разные `double`; ключ «не найдётся».
- **Забыли про `capacity`.** На больших загрузках лишние расширения — как у `List<T>`.

## Вопросы с собеседований

:::spoiler Почему `Dictionary` в среднем O(1), а в худшем O(n)? (вопрос из критерия)
По хэшу ключа вычисляется номер корзины, и поиск идёт только внутри неё. При хорошей хэш-функции и своевременном расширении таблицы цепочки короткие — O(1). Если много ключей имеют одинаковый хэш (коллизии), они попадают в одну корзину, и поиск перебирает всю цепочку, сравнивая через `Equals` — до O(n).
:::

:::spoiler Что такое коллизия и почему она не ошибка?
Два разных ключа с одинаковым номером корзины (или одинаковым хэшем). Хэшей конечное число, ключей — бесконечно, поэтому коллизии неизбежны. Таблица их обрабатывает: хранит цепочку и различает ключи через `Equals`.
:::

:::spoiler Зачем переопределять `GetHashCode` вместе с `Equals`?
Словарь сначала по хэшу выбирает корзину и только потом сравнивает `Equals`. Если равные объекты дают разные хэши, они окажутся в разных корзинах и не найдутся. Контракт: `a.Equals(b)` ⇒ равные хэши (обратное неверно).
:::

:::spoiler Что будет, если изменить поле объекта, который уже лежит ключом в словаре?
Если поле участвует в `GetHashCode`, хэш изменится, а элемент останется в старой корзине. Поиск пойдёт в новую корзину и не найдёт его — элемент «потерян», хотя `Count` его учитывает.
:::

:::spoiler Если у двух объектов одинаковые хэши, они равны? (ловушка)
Нет. Одинаковый хэш — лишь повод сравнить через `Equals`. Равенство объектов требует `Equals == true`; одинаковые хэши у разных объектов — коллизия. Обратное верно: равные объекты обязаны иметь одинаковые хэши.
:::

:::spoiler Чем `HashSet<T>` отличается от `List<T>` и когда его брать?
У `HashSet` нет индексов и порядка, зато `Contains`/`Add`/`Remove` — O(1) в среднем и гарантия уникальности. Берём для проверок «есть ли», дедупликации и операций над множествами. `List` — когда важен порядок/индекс.
:::

:::spoiler Как решить Two Sum за O(n)?
Идём по массиву, для каждого `x` проверяем в словаре `target - x`; если есть — ответ найден, иначе кладём `x → индекс`. Один проход, O(n) времени и O(n) памяти.
:::

:::spoiler Почему строка — хороший ключ, а изменяемый объект — плохой?
Строка неизменяема: её хэш не изменится, пока она лежит в словаре. У изменяемого объекта поле, входящее в хэш, можно поменять — и элемент потеряется.
:::

:::spoiler Что быстрее: `ContainsKey` + индексатор или `TryGetValue`? Почему?
`TryGetValue`: он делает один поиск, а первый вариант — два (хэш и обход цепочки считаются дважды).
:::

## Что запомнить

- Хэш → корзина → цепочка → `Equals`: поиск смотрит одну корзину, а не все элементы.
- O(1) в среднем при хорошем хэше; при одинаковых хэшах — O(n); расширение — амортизированно.
- `Equals` и `GetHashCode` переопределяются **парой**: равные объекты обязаны иметь равные хэши; обратное неверно.
- Ключи — неизменяемые (`string`, числа, `record`); изменяемый ключ «теряется».
- `TryGetValue` вместо `ContainsKey` + индексатор; индексатор — «добавить или перезаписать», `Add` — только новый.
- `HashSet<T>` — словарь без значений: уникальность, `Contains` за O(1), операции над множествами.
- Порядок перебора не гарантирован; хэши строк рандомизируются между запусками.
- `list.Contains` в цикле → замени на `HashSet`.

## Зачем это нужно

`List<T>` и `Dictionary` закрывают большую часть задач, но не все. Есть ситуации, где «просто список» — плохая модель:

- **очередь заявок** — обрабатываем в порядке поступления; `list.RemoveAt(0)` будет сдвигать весь список при каждой обработке;
- **история действий и «Отменить»** — нужен доступ к *последнему* действию; это стек;
- **обход графа или дерева** — в ширину нужна очередь, в глубину — стек;
- **«самый срочный» элемент** — планировщик задач, Dijkstra, топ-N; нужна очередь с приоритетом;
- **всегда отсортированные данные** — рейтинг, интервалы, словарь «год → книга»;
- **LRU-кэш** — связный список вместе со словарём.

Ещё одна причина: собеседование. «Как реализовать очередь через два стека?», «Проверь баланс скобок», «Чем `Queue` отличается от `List`?» — вопросы про именно эти структуры. Задачи на скобки, на «следующий больший элемент», на обход — это `Stack<T>` и `Queue<T>` почти всегда.

И наконец, имя коллекции — документация. Читая `Stack<Action>` или `Queue<Order>`, ты сразу понимаешь намерение автора.

## Интуиция и аналогия

- **Очередь (`Queue`)** — очередь в кассу. Пришёл последним — стоишь в конце, обслуживают с начала. FIFO: *first in, first out*.
- **Стек (`Stack`)** — стопка тарелок. Кладёшь сверху, берёшь тоже сверху. Чтобы достать нижнюю, нужно снять все верхние. LIFO: *last in, first out*. Кнопка «Назад» в браузере: последняя открытая страница закрывается первой.
- **Связный список (`LinkedList`)** — поезд из вагонов, сцепленных друг с другом. Вставить вагон в середину просто — расцепил в нужном месте и вставил. Но «найти пятый вагон» значит идти от головы и считать.
- **Очередь с приоритетом (`PriorityQueue`)** — приёмное отделение: тяжело больных принимают раньше, независимо от времени прибытия.
- **Отсортированный словарь (`SortedDictionary`)** — алфавитный указатель: добавляя запись, ты ставишь её на «своё» место, зато всегда можешь листать по порядку.

## Основная теория по шагам

### Шаг 1. `Queue<T>` — очередь (FIFO)

~~~csharp
var waiting = new Queue<string>();          // очередь на популярную книгу
waiting.Enqueue("Анна");
waiting.Enqueue("Борис");
waiting.Enqueue("Вера");

Console.WriteLine(waiting.Peek());          // посмотреть первого, не забирая
Console.WriteLine(waiting.Dequeue());       // забрать первого
Console.WriteLine(waiting.Count);

if (waiting.TryDequeue(out var next)) Console.WriteLine(next);

waiting.Clear();
Console.WriteLine(waiting.TryDequeue(out _));       // пусто → false, без исключения
try { waiting.Dequeue(); }                          // а так — исключение
catch (InvalidOperationException) { Console.WriteLine("InvalidOperationException"); }
~~~
~~~console
Анна
Анна
2
Борис
False
InvalidOperationException
~~~

Основные члены: `Enqueue` (в конец), `Dequeue` (с начала), `Peek` (посмотреть начало), `TryDequeue`/`TryPeek` (без исключений), `Count`, `Contains` (O(n)). Индексатора нет — это сознательно: очередь не для произвольного доступа.

Внутри — **кольцевой массив**: «голова» и «хвост» ходят по кругу, поэтому и `Enqueue`, и `Dequeue` — O(1) без сдвига элементов (в отличие от `list.RemoveAt(0)`).

Применения: обработка заказов, очередь задач для фонового воркера, обход графа в ширину (BFS), буфер между производителем и потребителем.

### Шаг 2. `Stack<T>` — стек (LIFO)

~~~csharp
var history = new Stack<string>();          // история действий для «Отменить»
history.Push("выдал книгу B-1");
history.Push("изменил email читателя");

Console.WriteLine(history.Peek());          // последнее, не убирая
Console.WriteLine(history.Pop());           // последнее действие забираем первым
Console.WriteLine(history.Count);

// перебор стека идёт от вершины к основанию
var s = new Stack<int>(new[] { 1, 2, 3 });  // конструктор из коллекции кладёт по порядку: 3 окажется сверху
Console.WriteLine(string.Join(",", s));
~~~
~~~console
изменил email читателя
изменил email читателя
1
3,2,1
~~~

Классическая задача — проверка скобок:

~~~csharp
Console.WriteLine(IsBalanced("{[()]}"));
Console.WriteLine(IsBalanced("([)]"));
Console.WriteLine(IsBalanced("(("));
Console.WriteLine(IsBalanced(""));

static bool IsBalanced(string s)
{
    var stack = new Stack<char>();
    foreach (char c in s)
    {
        if (c is '(' or '[' or '{') stack.Push(c);
        else if (c is ')' or ']' or '}')
        {
            if (stack.Count == 0) return false;      // закрывающая без открывающей
            char open = stack.Pop();
            if ((c == ')' && open != '(') || (c == ']' && open != '[') || (c == '}' && open != '{'))
                return false;                        // не та пара
        }
    }
    return stack.Count == 0;                         // не осталось незакрытых
}
~~~
~~~console
True
False
False
True
~~~

Три «проверки провала» в этой функции — лишняя закрывающая, не та пара, незакрытая открывающая — и есть содержание задачи Valid Parentheses. Ещё применения стека: отмена/повтор, разбор выражений (калькулятор), обход графа в глубину (DFS без рекурсии), хранение состояния «вызовов» (стек вызовов устроен так же).

### Шаг 3. Очередь из двух стеков (разминка с собеседования)

Классический вопрос: «Реализуй очередь с помощью двух стеков». Идея: один стек принимает `Enqueue`, второй отдаёт `Dequeue`; когда второй пуст, перекладываем в него всё из первого — порядок разворачивается.

~~~csharp
var q = new TwoStackQueue<int>();
q.Enqueue(1); q.Enqueue(2); q.Enqueue(3);
Console.WriteLine(q.Dequeue());     // 1
q.Enqueue(4);
Console.WriteLine(q.Dequeue());     // 2
Console.WriteLine(q.Dequeue());     // 3
Console.WriteLine(q.Dequeue());     // 4

class TwoStackQueue<T>
{
    private readonly Stack<T> _in = new(), _out = new();
    public void Enqueue(T x) => _in.Push(x);
    public T Dequeue()
    {
        if (_out.Count == 0)
            while (_in.Count > 0) _out.Push(_in.Pop());   // разворачиваем порядок
        return _out.Pop();                                // пусто → InvalidOperationException
    }
}
~~~
~~~console
1
2
3
4
~~~

Каждый элемент перекладывается максимум один раз, поэтому `Dequeue` — амортизированная O(1).

### Шаг 4. `LinkedList<T>` — двусвязный список

~~~csharp
var playlist = new LinkedList<string>();
var first = playlist.AddLast("Глава 1");
playlist.AddLast("Глава 3");
playlist.AddAfter(first, "Глава 2");        // O(1), если узел уже на руках

Console.WriteLine(string.Join(" | ", playlist));

var node = playlist.Find("Глава 2")!;       // поиск — O(n)
playlist.Remove(node);                       // удаление по узлу — O(1)
Console.WriteLine($"{playlist.First!.Value} … {playlist.Last!.Value}, всего {playlist.Count}");
Console.WriteLine(playlist.First.Next!.Value);
~~~
~~~console
Глава 1 | Глава 2 | Глава 3
Глава 1 … Глава 3, всего 2
Глава 3
~~~

~~~text
 null ← [Глава 1] ⇄ [Глава 2] ⇄ [Глава 3] → null
         каждый узел — отдельный объект в куче со ссылками Previous/Next
~~~

| | `List<T>` | `LinkedList<T>` |
|---|---|---|
| Доступ по индексу | O(1) | **нет** (только перебором, O(n)) |
| Вставка/удаление в начале | O(n) | O(1) |
| Вставка/удаление при известном узле | O(n) | O(1) |
| Память | один массив | объект на **каждый** элемент + 2 ссылки |
| Скорость перебора на практике | высокая (данные рядом) | ниже (узлы разбросаны по куче) |

:::warn На практике `LinkedList` нужен редко
Несмотря на красивые O(1), в реальном коде `List<T>` почти всегда быстрее: данные лежат подряд, и процессор отлично их кэширует. Для очереди и стека есть специализированные `Queue<T>` и `Stack<T>`. `LinkedList<T>` оправдан, когда ты действительно держишь ссылки на узлы и часто вставляешь/удаляешь в середине (например, LRU-кэш). Разбор — в [когда Big O обманывает](#/ref/g/pf-bigo-lies).
:::

Важная деталь про O(1): «вставка в середину за O(1)» — только при **уже найденном узле**. Найти узел по значению — O(n). Поэтому «связный список быстрее для вставок» — это полуправда.

### Шаг 5. Отсортированные коллекции

~~~csharp
// SortedDictionary: ключи всегда упорядочены; операции O(log n) (сбалансированное дерево)
var byYear = new SortedDictionary<int, string>
{
    [1869] = "Война и мир",
    [1866] = "Преступление и наказание",
    [1878] = "Анна Каренина",
};
foreach (var (year, title) in byYear) Console.WriteLine($"{year}: {title}");

// SortedSet<T>: уникальные элементы в порядке сортировки + быстрые запросы по диапазону
var scores = new SortedSet<int> { 50, 10, 30, 30, 90 };
Console.WriteLine(string.Join(",", scores));                       // дубликат 30 не добавился
Console.WriteLine($"{scores.Min} {scores.Max}");
Console.WriteLine(string.Join(",", scores.GetViewBetween(20, 60)));   // от 20 до 60 включительно

// SortedList<K,V>: два массива (ключи, значения) — экономит память, но вставка O(n)
var sl = new SortedList<string, int> { ["b"] = 2, ["a"] = 1 };
Console.WriteLine(sl.Keys[0] + sl.Values[0]);                      // индексный доступ к ключам
~~~
~~~console
1866: Преступление и наказание
1869: Война и мир
1878: Анна Каренина
10,30,50,90
10 90
30,50
a1
~~~

- `SortedDictionary` и `SortedSet` — деревья, O(log n) на всё; ключи должны быть сравнимыми (`IComparable<T>` или свой `IComparer<T>`).
- `SortedList` — два массива: меньше памяти и быстрый индексный доступ, но вставка O(n) в общем случае. Бери, когда данные заполняются один раз, а читаются часто.
- Если порядок нужен не всё время, а один раз, проще `Dictionary` + `OrderBy` в конце.

### Шаг 6. `PriorityQueue<TElement, TPriority>`

Появилась в .NET 6. Достаёт элемент с **наименьшим** приоритетом (минимальная куча).

~~~csharp
var requests = new PriorityQueue<string, int>();
requests.Enqueue("обычный читатель", 3);
requests.Enqueue("преподаватель", 1);
requests.Enqueue("студент-дипломник", 2);
while (requests.TryDequeue(out var who, out var priority))
    Console.WriteLine($"{priority}: {who}");

// нужен «наибольший первым» — инвертируем компаратор или знак приоритета
var biggestFirst = new PriorityQueue<string, int>(Comparer<int>.Create((a, b) => b.CompareTo(a)));
biggestFirst.Enqueue("мелкая", 1);
biggestFirst.Enqueue("крупная", 100);
Console.WriteLine(biggestFirst.Dequeue());
Console.WriteLine(requests.Count);
~~~
~~~console
1: преподаватель
2: студент-дипломник
3: обычный читатель
крупная
0
~~~

`Enqueue` и `Dequeue` — O(log n), `Peek` — O(1). Важные оговорки:

- очередь **не гарантирует порядок среди равных приоритетов** (не стабильна) — при необходимости добавь в приоритет второй компонент (счётчик поступления);
- нет быстрого «изменить приоритет» или «удалить произвольный элемент»; в алгоритмах это решают повторной вставкой и пропуском устаревших записей;
- применения: планировщик задач, алгоритм Дейкстры, топ-K элементов, слияние отсортированных потоков.

### Шаг 7. Сравнение скорости: `List.RemoveAt(0)` против `Queue.Dequeue()`

Опять без нестабильных таймеров — сравним то, что делает код: считаем, сколько элементов пришлось сдвинуть.

~~~csharp
using System.Diagnostics;

const int N = 50_000;
var list = Enumerable.Range(0, N).ToList();
var queue = new Queue<int>(list);

var sw = Stopwatch.StartNew();
while (list.Count > 0) list.RemoveAt(0);          // каждый раз сдвиг всех остальных
long listTicks = sw.ElapsedTicks;

sw.Restart();
while (queue.Count > 0) queue.Dequeue();           // только перемещение индекса головы
long queueTicks = sw.ElapsedTicks;

Console.WriteLine($"Queue быстрее List.RemoveAt(0) более чем в 10 раз: {listTicks > 10 * queueTicks}");
long shifts = (long)N * (N - 1) / 2;
Console.WriteLine($"сдвигов элементов у List: {shifts:N0}");
~~~
~~~console
Queue быстрее List.RemoveAt(0) более чем в 10 раз: True
сдвигов элементов у List: 1,249,975,000
~~~

### Шаг 8. Где `LinkedList` всё-таки нужен: мини-LRU-кэш

LRU-кэш хранит ограниченное число записей и при переполнении выбрасывает «давно не использованную». Нужны две операции за O(1): найти запись по ключу и переместить её в «свежий» конец. Словарь даёт поиск, связный список — перемещение узла без сдвигов.

~~~csharp
var cache = new LruCache<string, int>(capacity: 2);
cache.Put("a", 1);
cache.Put("b", 2);
Console.WriteLine(cache.TryGet("a", out var v) ? v : -1);   // 1, "a" стал самым свежим
cache.Put("c", 3);                                            // вытеснит "b" — он самый старый
Console.WriteLine(cache.TryGet("b", out _));                  // False
Console.WriteLine(cache.TryGet("c", out _));                  // True

class LruCache<K, V> where K : notnull
{
    private readonly int _capacity;
    private readonly Dictionary<K, LinkedListNode<(K Key, V Value)>> _map = new();
    private readonly LinkedList<(K Key, V Value)> _order = new();   // начало — самые свежие

    public LruCache(int capacity) => _capacity = capacity;

    public bool TryGet(K key, out V value)
    {
        if (_map.TryGetValue(key, out var node))
        {
            _order.Remove(node);            // O(1): узел уже на руках
            _order.AddFirst(node);          // O(1)
            value = node.Value.Value;
            return true;
        }
        value = default!;
        return false;
    }

    public void Put(K key, V value)
    {
        if (_map.TryGetValue(key, out var existing)) { _order.Remove(existing); _map.Remove(key); }
        else if (_map.Count == _capacity)
        {
            var oldest = _order.Last!;       // самый давний
            _order.RemoveLast();
            _map.Remove(oldest.Value.Key);
        }
        _map[key] = _order.AddFirst((key, value));
    }
}
~~~
~~~console
1
False
True
~~~

Это и есть та ситуация, ради которой `LinkedList<T>` существует: узлы нужны *снаружи* (в словаре), и их перемещение стоит O(1). Без словаря «найти узел» было бы O(n), и вся выгода пропала бы.

### Шаг 9. Шпаргалка выбора

| Нужно | Коллекция |
|---|---|
| Список с доступом по индексу, добавление в конец | `List<T>` |
| Поиск по ключу | `Dictionary<TKey, TValue>` |
| «Есть ли элемент?», уникальность, операции над множествами | `HashSet<T>` |
| Обработка в порядке поступления | `Queue<T>` |
| Последний пришёл — первый обработан, отмена, обход в глубину | `Stack<T>` |
| Ключи всегда отсортированы | `SortedDictionary<TKey, TValue>` / `SortedSet<T>` |
| Каждый раз брать самый приоритетный | `PriorityQueue<TElement, TPriority>` |
| Только читать и отдавать наружу | `IReadOnlyList<T>`, `IReadOnlyDictionary<TKey, TValue>` |
| Работа из нескольких потоков | `System.Collections.Concurrent` (Фаза 5) |

Правило выбора: сначала сформулируй *операции*, которые нужны («добавить в конец, брать с начала»), и только потом выбирай структуру. Не наоборот.

## Как это работает под капотом

- **`Queue<T>`** — массив `T[] _array` и три числа: `_head`, `_tail`, `_size`. `Enqueue` пишет в `_array[_tail]` и двигает `_tail` по модулю длины; `Dequeue` читает `_array[_head]`, обнуляет ячейку и двигает `_head`. Когда место кончается — рост вдвое и «распрямление» кольца при копировании, как у `List<T>`.
- **`Stack<T>`** — массив и счётчик `_size`: `Push` пишет в `_array[_size++]`, `Pop` — `_array[--_size]`. Это тот же `List<T>`, но с урезанным интерфейсом, чтобы нельзя было нарушить дисциплину LIFO.
- **`LinkedList<T>`** — каждый элемент в отдельном объекте `LinkedListNode<T>` с полями `Next`, `Prev`, `List`, `Value`. Плата — аллокация на каждый элемент (давление на GC) и разброс по памяти: переход к следующему узлу — это «прыжок по указателю», который часто промахивается мимо кэша.
- **`SortedDictionary` / `SortedSet`** — красно-чёрное дерево; ребалансировка при вставках держит высоту ~log₂ n.
- **`PriorityQueue`** — **4-арная куча** в массиве: у узла `i` дети `4i+1…4i+4`. Вставка «всплывает» вверх, извлечение «погружает» последний элемент вниз; обе операции — O(log n).
- **Стек вызовов** — тоже стек (LIFO) в памяти потока: каждый вызов метода кладёт на него кадр. Глубокая рекурсия → `StackOverflowException`; обход в глубину через явный `Stack<T>` этого избегает, потому что `Stack<T>` лежит в куче.
- **Перечисление**: у всех этих коллекций перечислитель — struct и защита версией, как у `List<T>`; изменять коллекцию во время `foreach` нельзя. Исключение — `PriorityQueue`: её `UnorderedItems` отдаёт элементы **без** порядка приоритета.

Справочник: [Queue и Stack](#/ref/e/co-queue-stack), [сложность коллекций](#/ref/e/co-complexity).

## Типичные ошибки и ловушки

- **`List.RemoveAt(0)` как очередь.** O(n) на каждое извлечение, O(n²) на всё. Используй `Queue<T>`.
- **`Dequeue`/`Pop`/`Peek` на пустой коллекции.** `InvalidOperationException`; проверяй `Count` или используй `TryDequeue`/`TryPop`/`TryPeek`.
- **Ожидание порядка от `PriorityQueue` среди равных.** Она не стабильна; добавляй счётчик в приоритет.
- **Путаница «максимум или минимум первым».** `PriorityQueue` отдаёт наименьший; для «наибольший первым» инвертируй компаратор.
- **`LinkedList` «потому что быстрее вставка».** Доступа по индексу нет, поиск O(n), память и скорость хуже; без явных узлов на руках выигрыша нет.
- **Перебор `Stack` и ожидание «порядка добавления».** Перечисление идёт от вершины к основанию, то есть в обратном порядке.
- **Рекурсия там, где хватит `Stack<T>`.** На глубоких структурах рекурсивный обход убивает процесс `StackOverflow`; итеративный — нет.
- **`SortedList` для частых вставок.** Вставка O(n); для динамичных данных — `SortedDictionary`.
- **Потокобезопасность.** `Queue<T>` и `Stack<T>` не потокобезопасны; для нескольких потоков — `ConcurrentQueue<T>`, `ConcurrentStack<T>`, `BlockingCollection<T>` или `Channel<T>`.
- **Забыть про `Contains`.** `queue.Contains(x)` и `stack.Contains(x)` — O(n); если нужны быстрые проверки, держи рядом `HashSet<T>`.

## Вопросы с собеседований

:::spoiler Почему `Queue<T>.Dequeue` — O(1), а `List<T>.RemoveAt(0)` — O(n)?
`Queue<T>` хранит индексы головы и хвоста в кольцевом массиве: при `Dequeue` сдвигается только индекс головы. `List<T>` обязан держать элементы с индекса 0, поэтому после удаления первого элемента сдвигает все остальные.
:::

:::spoiler Когда `LinkedList<T>` действительно лучше `List<T>`?
Когда часто вставляешь и удаляешь элементы в середине или начале, имея на руках ссылку на узел, и не нужен доступ по индексу. Пример — LRU-кэш (вместе со словарём «ключ → узел»).
:::

:::spoiler Реализуй очередь через два стека. Какая сложность `Dequeue`?
Входной стек принимает элементы, выходной отдаёт. Когда выходной пуст, перекладываем в него всё из входного (порядок разворачивается). Каждый элемент перекладывается не более одного раза → амортизированная O(1).
:::

:::spoiler Как проверить правильность расстановки скобок? (ловушка: «посчитать открывающие и закрывающие»)
Счётчик не поймает `([)]`. Нужен стек: открывающую кладём, закрывающую сверяем с вершиной (должна быть парной) и снимаем; в конце стек должен быть пустым.
:::

:::spoiler Чем `Stack<T>` отличается от `Queue<T>`? Где применяется каждый?
Стек — LIFO (отмена, DFS, разбор выражений), очередь — FIFO (обработка по порядку, BFS, задачи воркеру).
:::

:::spoiler Что делает `PriorityQueue` и какая у неё сложность?
Отдаёт элемент с наименьшим приоритетом; `Enqueue`/`Dequeue` — O(log n), `Peek` — O(1). Внутри — двоичная (в .NET — 4-арная) куча в массиве. Не стабильна для равных приоритетов.
:::

:::spoiler Чем `SortedDictionary` отличается от `Dictionary`?
`Dictionary` — хэш-таблица, O(1), порядок не гарантирован. `SortedDictionary` — дерево, O(log n), ключи всегда упорядочены, но требуют сравнимости.
:::

:::spoiler Как обойти дерево в ширину? А в глубину без рекурсии?
В ширину — `Queue<T>`: берём узел, кладём детей в конец. В глубину — `Stack<T>`: берём узел, кладём детей в стек; обход итеративный и не рискует переполнить стек вызовов.
:::

## Что запомнить

- `Queue<T>` — FIFO, кольцевой массив, `Enqueue`/`Dequeue` O(1); вместо `List.RemoveAt(0)`.
- `Stack<T>` — LIFO, `Push`/`Pop` O(1): отмена, скобки, DFS.
- `LinkedList<T>` — O(1) вставка при известном узле, но нет индекса и плохая локальность; нужен редко.
- `SortedDictionary`/`SortedSet` — дерево, O(log n), всегда по порядку; `SortedList` — массивы, вставка O(n).
- `PriorityQueue` — минимальная куча, O(log n); не стабильна; «наибольший первым» — через компаратор.
- Пустая коллекция + `Dequeue`/`Pop`/`Peek` = исключение; используй `Try…`.
- Выбирай структуру по операциям, а не по привычке; для нескольких потоков — `Concurrent`-варианты.

## Зачем это нужно

Код, который работает на 10 тестовых записях, на 10 миллионах боевых может не завершиться. Классическая история: разработчик пишет вложенный цикл «для простоты», на тестовой базе всё мгновенно, а в продакшене страница грузится минуту, потому что данных стало в тысячу раз больше, а работы — в миллион.

Big O — язык, на котором об этом говорят заранее:

- **при проектировании**: «этот шаг O(n²), а n может дойти до 100 тысяч — значит, нужен другой подход»;
- **на собеседовании**: после решения задачи всегда звучит «а какая сложность?»; ответ «O(n) по времени и O(n) по памяти, вот почему» — признак мышления Junior+;
- **при code review**: заметить `list.Contains` в цикле и предложить `HashSet`;
- **при выборе коллекций**: таблица сложностей из тем про [List](#p2-list), [Dictionary](#p2-dictionary) и [Queue/Stack](#p2-collections) — это применение Big O.

Важный нюанс: Big O — **инструмент рассуждения, а не измерения**. Он отвечает на вопрос «как будет расти?», а не «сколько миллисекунд?». Это различие мы разберём в ловушках.

## Интуиция и аналогия

Представь, что ты ищешь человека в списке гостей.

- **O(1)**: у тебя есть номер места — идёшь прямо к нему. Сколько бы гостей ни было, шагов столько же.
- **O(log n)**: телефонная книга — открываешь посередине, смотришь, левее или правее, отбрасываешь половину. Книга выросла вдвое — добавился один шаг.
- **O(n)**: список без порядка — читаешь строчку за строчкой. Гостей вдвое больше — вдвое дольше.
- **O(n log n)**: отсортировать всех гостей — каждый «раскладывается» на своё место за log n шагов.
- **O(n²)**: каждый гость должен поздороваться с каждым. Гостей вдвое больше — рукопожатий вчетверо больше.

Хорошее мысленное упражнение: «если данных станет в 10 раз больше, во сколько раз вырастет работа?». O(n) — в 10, O(n²) — в 100, O(log n) — почти не изменится. Это и есть «форма роста».

## Основная теория по шагам

### Шаг 1. Что измеряет Big O

Big O описывает, **как растёт время (или память) при росте входных данных**, без учёта констант. Нас интересует верхняя оценка роста для больших n.

| Класс | Название | n = 1 000 | n = 1 000 000 | Пример |
|---|---|---|---|---|
| O(1) | константа | 1 | 1 | `dict[key]`, `list[i]` |
| O(log n) | логарифм | ~10 | ~20 | бинарный поиск |
| O(n) | линейная | 1 000 | 1 000 000 | один проход по списку |
| O(n log n) | линейно-логарифмическая | ~10 000 | ~20 000 000 | хорошая сортировка |
| O(n²) | квадратичная | 1 000 000 | 10¹² | вложенные циклы по одним данным |
| O(2ⁿ) | экспонента | невозможно | невозможно | перебор всех подмножеств |

Посмотрим на рост своими глазами — посчитаем «шаги» вместо замера секундомером:

~~~csharp
foreach (int n in new[] { 1_000, 2_000, 4_000 })
{
    long linear = 0, quadratic = 0, logarithmic = 0;

    for (int i = 0; i < n; i++) linear++;                              // O(n)

    for (int i = 0; i < n; i++)
        for (int j = 0; j < n; j++) quadratic++;                       // O(n²)

    for (int k = n; k > 1; k /= 2) logarithmic++;                      // O(log n): делим пополам

    Console.WriteLine($"n={n,5}: O(log n)={logarithmic,2}  O(n)={linear,5}  O(n²)={quadratic,9:N0}");
}
~~~
~~~console
n= 1000: O(log n)= 9  O(n)= 1000  O(n²)=1,000,000
n= 2000: O(log n)=10  O(n)= 2000  O(n²)=4,000,000
n= 4000: O(log n)=11  O(n)= 4000  O(n²)=16,000,000
~~~

При удвоении n линейный счётчик удваивается, квадратичный растёт вчетверо, логарифмический прибавляет единицу. Это и есть «форма роста».

### Шаг 2. Как считать сложность своего кода

1. **Последовательные шаги складываются**, оставляем самый большой: O(n) + O(n log n) = O(n log n).
2. **Вложенные циклы перемножаются**: цикл по n внутри цикла по m — O(n·m).
3. **Учитывай стоимость вызываемых методов**: `list.Contains` внутри цикла — это скрытый вложенный цикл.
4. **Константы и младшие слагаемые отбрасываем**: два прохода по списку — всё ещё O(n); O(n² + n) — это O(n²).
5. **Разные входы — разные буквы**: книги (n) и читатели (m) — пиши O(n + m), а не O(n).
6. **Делим пополам на каждом шаге — это log n**: бинарный поиск, обход сбалансированного дерева.
7. **Рекурсия**: сложность = число вызовов × стоимость одного вызова. Наивный Фибоначчи — O(2ⁿ), с запоминанием — O(n).

Лучше всего считать **общее число выполнений самой «внутренней» строки**, а не количество слов `for`:

~~~csharp
// Два вложенных цикла — но сложность O(n), а не O(n²): указатель j не возвращается назад
static int CountPairsWithSum(int[] sorted, int target)
{
    int count = 0, steps = 0;
    int i = 0, j = sorted.Length - 1;
    while (i < j)
    {
        steps++;
        int sum = sorted[i] + sorted[j];
        if (sum == target) { count++; i++; j--; }
        else if (sum < target) i++;
        else j--;
    }
    Console.WriteLine($"шагов: {steps} при n = {sorted.Length}");
    return count;
}

Console.WriteLine(CountPairsWithSum(Enumerable.Range(1, 1000).ToArray(), 1001));
~~~
~~~console
шагов: 500 при n = 1000
500
~~~

Техника «двух указателей» делает один проход с двух концов: суммарно указатели проходят n позиций. Вложенность цикла не равна квадрату — считай общее число итераций.

### Шаг 3. Скрытый квадрат: задача и два решения

~~~csharp
// Задача: найти книги, которые есть в каталоге, но ни разу не выдавались.
List<string> catalog = LoadCatalog();      // n книг
List<string> loaned = LoadLoanedIsbns();   // m выдач

// ❌ O(n · m): Contains у List перебирает весь список на каждой итерации
long compares = 0;
var neverLoanedSlow = new List<string>();
foreach (var isbn in catalog)
{
    bool found = false;
    foreach (var l in loaned) { compares++; if (l == isbn) { found = true; break; } }
    if (!found) neverLoanedSlow.Add(isbn);
}

// ✅ O(n + m): построение HashSet — O(m), каждая проверка — O(1)
var loanedSet = new HashSet<string>(loaned);
var neverLoanedFast = new List<string>();
foreach (var isbn in catalog)
    if (!loanedSet.Contains(isbn)) neverLoanedFast.Add(isbn);

Console.WriteLine(neverLoanedSlow.Count == neverLoanedFast.Count);
Console.WriteLine($"каталог {catalog.Count}, выдано {loaned.Count}");
Console.WriteLine($"сравнений в медленном варианте: {compares:N0}");
Console.WriteLine($"операций в быстром: порядка {catalog.Count + loaned.Count:N0}");

static List<string> LoadCatalog() => Enumerable.Range(0, 20_000).Select(i => $"ISBN-{i}").ToList();
static List<string> LoadLoanedIsbns() => Enumerable.Range(0, 20_000).Where(i => i % 3 == 0).Select(i => $"ISBN-{i}").ToList();
~~~
~~~console
True
каталог 20000, выдано 6667
сравнений в медленном варианте: 111,118,889
операций в быстром: порядка 26,667
~~~

Медленный вариант делает больше ста миллионов сравнений, быстрый — десятки тысяч операций. Замерь `Stopwatch`-ом и увидишь разницу на порядки.

### Шаг 4. Обоснование вслух

~~~csharp
// Есть ли в массиве два числа с суммой target?
static bool HasPairWithSum(int[] nums, int target)
{
    var seen = new HashSet<int>();
    foreach (int x in nums)                    // n итераций
    {
        if (seen.Contains(target - x)) return true;   // O(1) в среднем
        seen.Add(x);                                 // O(1) амортизированно
    }
    return false;
}
Console.WriteLine(HasPairWithSum(new[] { 3, 9, 4, 7 }, 11));
Console.WriteLine(HasPairWithSum(new[] { 3, 9, 4, 7 }, 100));
~~~
~~~console
True
False
~~~

> «Один проход по массиву — n итераций. Внутри — операции `HashSet`, в среднем O(1). Итого O(n) по времени. По памяти — O(n) на множество. Решение в лоб двумя циклами — O(n²) по времени и O(1) по памяти. Мы обменяли память на время.»

Вот такая формулировка и нужна на собеседовании: **что повторяется, сколько раз, сколько стоит каждая итерация, сколько памяти**.

### Шаг 5. Лучший, средний и худший случаи; амортизация

Одна и та же операция может иметь разные оценки:

- **Худший случай** — самый неудачный вход. Для `Contains` в списке: элемент в конце или отсутствует → n сравнений.
- **Лучший случай** — самый удачный (элемент первый). Обычно неинтересен.
- **Средний случай** — на «типичных» данных. У `Dictionary` — O(1), хотя худший — O(n) (см. [Dictionary](#p2-dictionary)).
- **Амортизированная** сложность — стоимость, усреднённая по серии операций. `List.Add`: редкое расширение O(n), но в среднем O(1).

Когда спрашивают «какая сложность», обычно подразумевают **худший** случай и сразу оговаривают, если средний сильно отличается («в среднем O(1), в худшем O(n) при плохом хэше»).

### Шаг 6. Память тоже считается

- Создал новый список того же размера — O(n) дополнительной памяти.
- Рекурсия глубины n — O(n) памяти стека вызовов (и риск `StackOverflow`).
- Сортировка «на месте» (`list.Sort()`) — дополнительная память небольшая; `OrderBy(...).ToList()` создаёт новую коллекцию — O(n).
- Часто быстрее = больше памяти (кэш, хэш-таблица), медленнее = меньше. Этот компромисс «время ↔ память» стоит озвучивать.

### Шаг 7. Сложность LINQ-операторов

| Оператор | Сложность | Замечание |
|---|---|---|
| `Where`, `Select` | O(n) при переборе | отложенные, ничего не делают до перебора |
| `Any(pred)`, `First(pred)` | до O(n) | останавливаются на первом совпадении |
| `Count()` у `List`/массива | O(1) | у произвольной последовательности — O(n) |
| `OrderBy` | O(n log n) | буферизует всю последовательность |
| `GroupBy`, `ToDictionary`, `Distinct` | O(n) | внутри хэш-таблица |
| `Contains` у `List` | O(n) | у `HashSet` — O(1) |

~~~csharp
var data = Enumerable.Range(1, 100_000).ToList();
int calls = 0;

// Where — отложенный: пока нет перебора, предикат НЕ вызывается
var query = data.Where(x => { calls++; return x % 2 == 0; });
Console.WriteLine($"после Where: вызовов {calls}");

bool any = query.Any();              // остановился на первом подходящем
Console.WriteLine($"после Any: вызовов {calls}, результат {any}");

int count = query.Count();           // полный перебор
Console.WriteLine($"после Count: вызовов {calls - 2}, чётных {count}");
~~~
~~~console
после Where: вызовов 0
после Any: вызовов 2, результат True
после Count: вызовов 100000, чётных 50000
~~~

Отложенное выполнение — отдельная тема ([LINQ](#p2-linq)); важное следствие для Big O: **один и тот же запрос, перебранный дважды, делает работу дважды**.

## Как это работает под капотом

- **Что такое «шаг».** Big O считает не секунды, а *число элементарных операций* (сравнение, присваивание, чтение из массива). Какая из них реально «дорогая» на конкретном железе, он не учитывает.
- **Константы существуют.** Два алгоритма O(n) могут отличаться в 50 раз: один читает последовательно лежащий массив, другой прыгает по указателям. Процессор подгружает память кусками (кэш-линии по ~64 байта) — последовательный доступ эффективен, случайный — нет. Подробнее — [термины производительности](#/ref/g/pf-terms) и [когда Big O обманывает](#/ref/g/pf-bigo-lies).
- **Малые n.** При n ≈ 20–50 простой O(n²) (например, вставки) часто быстрее «умного» O(n log n): накладные расходы последнего (рекурсия, временные массивы) перевешивают. Поэтому реальные библиотечные сортировки гибридные: внутри `Array.Sort` для коротких кусков используется сортировка вставками.
- **Сортировка в .NET.** `Array.Sort`/`List.Sort` — *интроспективная* (быстрая сортировка + пирамидальная как страховка от худшего случая + вставки на мелких кусках): O(n log n) гарантированно, но неустойчивая. LINQ `OrderBy` — устойчивая, с буфером ключей.
- **Стоимость аллокаций.** Big O не видит, что внутри цикла создаются объекты: `s += x` в цикле над строкой — O(n²) по копированию символов; `StringBuilder` — O(n) (см. [строки](#p1-strings)).
- **Логарифм — по основанию 2.** В Big O основание не важно (отличается константой), но интуитивно log₂ 1 000 000 ≈ 20 — «20 раз пополам».
- **Big O — верхняя оценка.** Формально «O» значит «не хуже, чем». Строгая оценка — Θ (тета). На собеседованиях в обиходе под O понимают тесную оценку.

Справочник: [сложность коллекций](#/ref/e/co-complexity), [термины производительности](#/ref/g/pf-terms), [стоимость операций](#/ref/g/pf-op-costs).

## Типичные ошибки и ловушки

:::danger Не замечать стоимость вызова
`list.Contains`, `list.IndexOf`, `list.Remove`, `string.Contains`, `Count()` у `IEnumerable` — все O(n). Внутри цикла они превращают O(n) в O(n²).
:::

:::danger Оптимизировать без измерения
Big O говорит о росте. На 50 элементах O(n²) может быть быстрее «умного» решения. Сначала измерь на реальных объёмах, потом оптимизируй.
:::

- **Считать слова `for`, а не итерации.** Два вложенных цикла бывают O(n) (два указателя); один цикл с `Contains` внутри — O(n²).
- **Забыть про вторую переменную.** Два разных входа: O(n·m), а не O(n²).
- **Путать время и память.** Решение «в лоб» часто O(1) по памяти; ускорение через `HashSet` стоит O(n) памяти. Называй оба.
- **Игнорировать повторные перечисления LINQ.** `query.Count()` и потом `foreach (var x in query)` — двойная работа (и двойные побочные эффекты). Материализуй `ToList()`.
- **Конкатенация строк в цикле.** O(n²) по символам; нужен `StringBuilder`.
- **Считать «амортизированную O(1)» гарантией для каждой операции.** Отдельный `Add` может быть O(n); в системах реального времени это важно.
- **Ответить «O(n)» не объяснив.** Всегда проговаривай *что* повторяется и *сколько* стоит итерация.
- **Игнорировать константы там, где они определяют результат.** Миллион вызовов O(1) за 1 мкс — секунда; один O(n²) на 100 элементах — доли миллисекунды.
- **Преждевременная оптимизация.** Решение на `HashSet` на 10 элементах только усложняет код.

## Вопросы с собеседований

:::spoiler Какая сложность у сортировки списка и последующего бинарного поиска k элементов?
O(n log n) на сортировку + O(k log n) на поиски = O((n + k) log n).
:::

:::spoiler Почему `HashSet` вместо `List.Contains` в цикле даёт O(n + m)?
Построение множества из m элементов — O(m), затем n проверок по O(1) в среднем — O(n). Сумма — O(n + m) вместо O(n·m).
:::

:::spoiler Два вложенных цикла — это всегда O(n²)? (ловушка)
Нет. Если внутренний цикл идёт по другой коллекции — O(n·m). Если внутренний цикл в сумме проходит каждый элемент один раз (как в технике двух указателей), итог может быть O(n). Считай общее число итераций, а не количество слов `for`.
:::

:::spoiler Чем худший случай отличается от амортизированной сложности?
Худший случай — самая дорогая одиночная операция; амортизированная — средняя по длинной серии операций. `List.Add`: худший случай O(n) (расширение), амортизированно O(1).
:::

:::spoiler Какая сложность у `string +=` в цикле, и как исправить?
O(n²) по копируемым символам: каждый `+=` создаёт новую строку. Используй `StringBuilder` — O(n) в сумме.
:::

:::spoiler Правда ли, что O(n log n) всегда быстрее O(n²)?
Для больших n — да. Для малых n константы могут перевесить, поэтому библиотечные сортировки на коротких кусках переключаются на вставки. Big O говорит о росте, а не о скорости на конкретных данных.
:::

:::spoiler Какая сложность у обращения к `Dictionary` и когда она хуже?
В среднем O(1); в худшем O(n) при массовых коллизиях (плохой `GetHashCode`).
:::

:::spoiler Какая сложность по памяти у рекурсивного обхода дерева глубины h?
O(h) на стек вызовов; для вырожденного дерева h = n.
:::

## Что запомнить

- Big O — «как растёт», а не «сколько секунд»; константы отбрасываем, оценка — по худшему случаю, если не оговорено иное.
- Последовательное складывается, вложенное перемножается; считай *число итераций*, а не количество циклов.
- Скрытые O(n): `Contains`/`IndexOf`/`Remove` у списка, `Count()` у `IEnumerable`, `+=` у строки.
- `List.Add` — амортизированная O(1); `Dictionary`/`HashSet` — O(1) в среднем; сортировка — O(n log n); бинарный поиск — O(log n).
- Оценивай и время, и память; «быстрее» часто значит «больше памяти».
- Один LINQ-запрос, перебранный дважды, делает работу дважды.
- Сначала измерь, потом оптимизируй: на малых n константы важнее формы роста.
- Шаблон ответа: что повторяется / сколько раз / сколько стоит итерация / сколько памяти.
